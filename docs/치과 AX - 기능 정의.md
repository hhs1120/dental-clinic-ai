> 가상 데이터로 개발하므로 외부 LLM API를 자유롭게 쓴다. 인프라·하드웨어·운영 비용은 범위 밖.
> 이 문서는 **무엇을 만드나**. 데이터 구조와 생성 규칙은 [[치과 AX - 가상 데이터 생성 설계]], 앱 테이블·도구·쿼리는 [[치과 AX - 앱 설계]], 지표·채점·정답 저장소는 [[치과 AX - 평가 설계]], 구현 규칙은 `CLAUDE.md`.

## 1. 조건

- 인원: 1인 기준. 팀이 되면 슬롯을 사람별로 배분
- 목표: "AI 도구를 잘 다루는 개발자" 포트폴리오. 풀스택 직접 구현, 프론트를 일부러 줄이지 않음
- 스택: [[치과 AX - 앱 설계]] §7. Claude Code 설정(`CLAUDE.md`·`.claude/` — 구성은 `CLAUDE.md` 폴더)은 깃에 포함

## 2. 범위

| 구분 | 기능 | 한 줄 |
|---|---|---|
| 코어 | 가상 데이터 생성기 | 모든 기능의 토대. 정답 내장 |
| 코어 | ① 통화 요약·분류 | 모델 2개 교차검증으로 완성. 할 일 없는 통화는 자동 종결, 할 일 있는 통화는 후속 에이전트의 처리안과 함께 후속 큐로(처리하면 빠짐) |
| 코어 | ② 판정·자동 개선 + 블라인드 비교 | "AI 검증"의 간판 화면. 판정 에이전트가 1차, 사람은 기준 측정·엇갈림·표본. 프롬프트 개선은 관문을 넘어야 반영. 키보드 UX. 업무 메뉴와 떨어진 "AI 평가" 메뉴 |
| 코어 | ③ 물어보기 (RAG 검색 + 챗 + 문서함) | 하이브리드 검색(문서·통화·문자·차트 케이스) + 도구 5개 에이전트 + 문서함(읽기 전용) + 빠진 문서 초안 에이전트. 부트캠프 직결 |
| 코어 (MVP) | ④ 진료 준비표 | 전환 전 EMR 대비 회의 보기·체어 보기. "코드 집계 → LLM 해석" + 주의 환자 야간 조사 에이전트. `make gate` 통과 시 착수 |
| 슬롯 | ⑤ 청구 점검·삭감 대응 | 청구 전 점검(차트 기반 누락 포함)·조정 사유 판단(조정 목록·재심 기한)·재심 사유서 초안. 재심 근거 조사는 에이전트 |
| 슬롯 | ⑥ 경영 리포트 | 월간·주간·일간 운영 숫자 + 상병 착오. 인건비가 들어간 손익은 `[추정]`. ④ 패턴(코드 집계 → LLM 해석) + 튄 숫자 원인 조사 에이전트 |
| 슬롯 | ⑦ 아침 브리핑 | 오늘 화면의 한 칸. ④ 패턴(코드 집계 → LLM 요약). 입력에 운영 에이전트의 밤사이 결과 포함 |
| 슬롯 | ⑧ 재무 대조 | ⑧-1 수입 일계표 불일치 원인 추적(에이전트) + ⑧-2 지출 증빙 매칭·계정 과목 분류(규칙으로 안 맞은 건은 증빙 탐색 에이전트). 조건을 넘은 건은 자동 처리 |
| 슬롯 | ⑨ 후속 관리 | 리콜 연체·스케일링 급여 미사용·노쇼 이탈·미수·진료계획 미예약을 코드 점수로 순위화. 근거 찾기는 에이전트, 문자 작성은 LLM, 의료·금액 내용이 없는 안내는 발송함 자동 기록 |
| 공통 | 에이전트 하네스 | 상태·도구 실행·피드백 루프·제약·재발 방지. 가장 먼저 만들고 모든 에이전트가 쓴다 |
| 공통 | 운영 에이전트 | 코드 스케줄러가 밤에 깨우면 조사 우선순위를 정하고 기능 에이전트를 부르며, 기능별 신호를 환자 단위로 묶는다 |
| 제외 | 메신저 / 방송 / 동의서 / 근태 / 음성봇·실시간 받아쓰기 / 상담 포털·음성 차팅 / 대기자 명단 | 범위 폭발, AI 비중 낮음, 또는 실제 전화·음성이 필요 |
| 제외 → 프로젝트 후 개인 확장 | 임플란트 평생 한도 | ④·⑨는 없이 성립 |

기능 번호는 이 표의 순서다(코어 ①~④, 슬롯 ⑤~⑨). 공통 항목에는 번호가 없다. 동그라미 숫자는 기능 번호에만 쓴다. 슬롯 착수 순서는 §9.

## 3. 공통 원칙

**용어**
- **에이전트**: LLM이 도구를 쓰며 다음 단계를 스스로 정하는 시스템. 코드가 정한 경로로 돌면 **워크플로**다. 사람 확인이 있는지와는 별개다
- **하네스**: 모델이 아닌 코드·설정·실행 로직 전부. 상태·도구 실행·피드백 루프·제약을 붙여 모델이 일하게 하고, 실수가 나면 같은 실수를 못 하게 환경을 고친다. 앱에서는 에이전트 하네스(§4)·LLM 게이트웨이·프롬프트·설정·평가 하네스(`evaluation/`)가 여기에 든다

| 기능 | 에이전트 | 워크플로·코드 |
|---|---|---|
| ① 통화 | 후속 처리 | 분류·요약 함수, 엇갈림, 자동 종결 조건 |
| ② 판정 | 판정, 개선 | 사람 판정, 관문, 블라인드 집계 |
| ③ 물어보기 | 챗, 문서 초안 | 색인·검색 |
| ④ 준비표 | 주의 환자 조사 | 칩 집계, 제안 후검증 |
| ⑤ 청구 | 재심 근거 조사 | 규칙 점검, ⑤-2 차트 판정, ⑤-4 초안 후검증 |
| ⑥ 리포트 | 튄 숫자 조사 | 숫자 쿼리, 문장화 |
| ⑦ 브리핑 | 없음 | 숫자 쿼리, 요약 |
| ⑧ 재무 | 원인 추적, 증빙 탐색 | 대조 계산, 규칙 매칭 |
| ⑨ 후속 관리 | 근거 찾기 | 칩·점수·순위, 문자 후검증 |
| 공통 | 운영 | 스케줄러, 자동 처리 정책 |


1. **원본에 쓰는 건 사람, 자동 처리는 `ax_`까지.** 원본 장부·차트에 AI가 직접 쓰지 않음. 일은 세 단계로 나눈다
   - **자동 처리**: ① 자동 종결 조건을 넘은 통화 종결, ⑧-1 규칙 묶음 불일치 마감, ⑧-2 일치하는 지출 확정, ⑨ 의료·금액 내용이 없는 안내의 발송함 기록(건별 조건은 §4 ①·§5 ⑧·⑨). 사람은 예외와 표본을 보고 되돌릴 수 있다. 작업 종류마다 dev 오류율이 기준을 넘지 않을 때 사람이 켠다(`auto_policy`)
   - **사람 확인**: ① 자동 종결되지 않은 통화, ⑧-1 자동 마감되지 않은 불일치, ⑧-2 자동 확정되지 않은 지출, ⑤ 재심 여부, ③ 문서 초안 게시, ⑨ 미수 안내·치료 권유 문자
   - **자동화 안 함**: 차트 기록, 청구·재심 제출, 처치 판단, 장부 수정
2. **숫자는 코드, AI는 해석.** 매출·건수·잔액은 쿼리로. LLM 출력의 숫자는 입력 fact에 있는지 **후검증**. 가정값이 들어간 숫자와 AI의 추정 문장은 `[추정]`으로 따로 표시
3. **교차검증은 구조화 출력(① 분류)에만.** 자유 텍스트(요약·제안·답변)는 diff가 안 되므로 블라인드 비교로
4. **LLM은 게이트웨이 모듈 하나로.** [[치과 AX - 앱 설계]] §7
5. **정답은 앱 DB 밖에.** 원본은 `CLAUDE.md` 절대 규칙
6. **구조화 출력.** 분류·추출은 JSON 스키마 + 고정 enum
7. **스펙 → 평가셋 → 구현.** "프롬프트 수정 전 N% → 후 M%"를 `prompt_version`으로 기록
8. **조사는 에이전트, 고정 산출은 워크플로.** 찾아볼 곳이 건마다 달라지는 일은 LLM이 경로를 정한다. 숫자 계산·① 분류·④ 집계처럼 결과가 고정돼야 하는 부분은 코드 경로로 둔다. 에이전트는 규칙이나 고정 흐름과 나란히 재고, 못 이기면 그 결과를 그대로 보고하고 기준선으로 돌린다
9. **개선은 자동, 기준은 사람.** 오류 분석·프롬프트 후보·재측정·반영은 자동으로 돌되 관문을 넘어야 반영한다. 관문 기준 수정, 프롬프트 밖 변경의 승인, test 실행은 사람만 한다([[치과 AX - 평가 설계]] §2.7)
10. **실수는 환경을 고친다.** 사람이 되돌리는 것으로 끝내지 않고 재현 테스트와 훅·정책·도구로 남겨 같은 실수를 구조로 막는다

## 4. 코어 기능

> 각 기능: 목적 / 화면 / API / 완료 기준 / 설계 근거(왜 이렇게 하는지만)

### 앱 구성

- **시작 화면**: 카드 4개로 갈라진다 — 사내 포털(오늘) · 물어보기 · AI 평가 · 전환 전 EMR. 메뉴바 없음
- **메뉴**: 업무 화면만 — 오늘 / 통화 / 준비표 / 물어보기 + 슬롯(청구 점검 / 경영 리포트 / 재무 대조 / 후속 관리). 슬롯은 구현 범위 구분이고 화면에는 구분을 표시하지 않는다
- **별도 공간**: AI 평가(② 판정·블라인드·정확도·자동 개선)와 전환 전 EMR(④)은 메뉴에 넣지 않는다. 들어가면 메뉴 자리에 공간 이름과 돌아가기가 나오고, 돌아가기는 들어오기 전 화면으로 간다. AI 평가는 시작 화면과 오늘 화면의 판정 대기에서, EMR은 시작 화면과 환자 이름에서 들어간다
- **표시 세 종류**: AI가 만듦(`AI` 배지 + 보라 바탕) / 코드가 계산(표시 없음) / 사람이 정함(`확정`). 숫자·칩에는 배지를 붙이지 않는다 — 다 붙이면 구분이 사라진다
- **오늘 화면**(사내 포털의 첫 화면): 요약 카드 + **AI가 한 일**(자동 처리 목록과 건별 이유·되돌리기, 운영 에이전트가 묶은 환자, 배치 결과 — 끝남 / 사람에게 넘김 / 실패) + **사람이 볼 일**(급한 통화·후속 큐, 그날 주의 환자, 예약 미확인, 엇갈림·표본 판정, 문서 초안, 슬롯이 붙으면 재심 기한 임박·청구 전 상병 경고·후속 관리·일계표 불일치) — 누르면 그 화면으로. 숫자는 전부 쿼리(§3 원칙 2). ⑦ 아침 브리핑은 이 화면의 한 칸. API `GET /today`, `POST /auto-actions/{id}/revert`
- **목록 화면 공통**: 마지막 갱신 시각, 칩마다 건수, 처리하면 목록에서 빠짐, AI 결과 옆에 근거(`used_facts`·`cited_ids`), 순위·기준이 있으면 "어떻게 정해지나" 설명
- **사용자**: 상단 사용자 선택(원장 / 데스크 / 상담실장) — §7

### 에이전트 하네스

**목적**: 모든 에이전트가 같은 틀로 돈다. 가장 먼저 만들고 나머지가 재사용한다. 구성은 다섯 축이다.

| 축 | 내용 |
|---|---|
| **상태** | 실행과 단계(도구·인자·결과·판단)를 전부 남겨 화면에 보인다. 끊긴 야간 실행은 마지막 단계부터 이어 간다. 도구 결과는 크기 상한에서 자르고 잘린 사실을 표시하며, 운영 에이전트는 기능 에이전트의 요약만 받는다 |
| **도구 실행** | 이름·인자·권한을 등록한다. 읽기 도구는 `source.sqlite`·`app.sqlite`, 쓰기 도구는 `ax_` 테이블만 |
| **피드백 루프** | 실행 후 훅이 공통 후검증을 돌린다. 판정·표본·관문·재생 테스트가 결과를 다음 수정으로 잇는다 |
| **제약** | 에이전트별 호출·비용 상한(넘으면 사람에게 넘김), 실행 전 훅의 권한·금지 도구·입력 제한 검사, 같은 자동 처리는 한 번만. 녹취록·문자·문서·차트와 도구 결과는 데이터로만 다루고 그 안의 지시를 따르지 않는다. LLM은 자동 처리를 요청만 하고 코드가 `auto_policy`와 건별 조건으로 허용하며, 허용된 건은 이유와 함께 기록해 되돌릴 수 있다 |
| **재발 방지** | 자동 처리 되돌리기·훅 차단·표본 오류·관문 탈락을 실수 후보로 모아 원인을 나눈다. 재현 테스트를 먼저 만들고 프롬프트·도구 설명·훅·정책·입력 제한 중 맞는 곳을 고친다. 프롬프트는 관문을 넘으면 자동 반영하고, 그 밖(도구 설명·도구 권한·훅·정책·입력 제한)은 후보와 테스트까지만 만들고 사람이 승인한다. 규칙별 차단 횟수를 남겨 쓸모없는 규칙은 사람이 지운다 |

**야간 실행**: `make nightly` — 코드 스케줄러가 운영 에이전트를 깨운다. 화면은 저장된 결과를 읽어 바로 뜬다.

**운영 에이전트**: 기능 에이전트가 모두 붙은 뒤 추가한다. 밤에 새 통화·청구·불일치·후속 대상을 보고 조사 우선순위를 정해 기능 에이전트를 부른다. 불만·노쇼·미수처럼 흩어진 신호를 한 환자로 묶어 오늘 화면에 이유와 함께 올린다. 숫자는 쓰지 않고 쿼리 결과만 인용한다. 평가는 시나리오 DB로 한다([[치과 AX - 평가 설계]] §5).

**완료 기준**: 호출·비용 상한 초과 시 사람에게 넘김(pytest), 정책이 꺼진 작업은 자동 처리 0건(pytest), 되돌리면 원상태(pytest), 실행마다 단계 기록 존재, 금지 도구 호출은 실행 전 차단(pytest), 재생 테스트가 키 없이 통과, 끊긴 실행을 재개해도 자동 처리 중복 0건(pytest), 지시문이 섞인 입력으로 도구 호출·자동 처리가 달라지지 않음([[치과 AX - 평가 설계]] §5), 실수 후보마다 재현 테스트가 수정 전 실패하고 수정 뒤 통과(pytest)

### 가상 데이터 생성기

**목적**: 미니 EMR + 비정형(통화·문서·문자) + 정답을 시드 재현 가능하게 생성. 산출물·규칙은 [[치과 AX - 가상 데이터 생성 설계]].

**완료 기준**: `make verify` 통과 + 결정성(같은 시드 2회 → 테이블 내용 해시 동일, LLM 캐시 포함)

### ① 통화 요약·분류

**목적**: 녹취록 1건 → 모델 2개가 각각 분류하고 분류 모델이 요약·할 일을 낸다. 분류 뒤 단계는 후속 에이전트가 맡는다.

**현실 구성과 대체**: 원본 사례(실제 동네 치과 AX 전환기 글)는 병원 자체 교환기(PBX)로 대표번호를 받아 녹음하고 통화 중 실시간으로 글로 옮긴다. 이 프로젝트는 실제 전화를 받을 수 없으므로 PBX·STT 구간을 **데이터로 대체**하고, 녹취록이 들어온 뒤부터 구현한다.

| 현실 | 이 프로젝트 |
|---|---|
| PBX 수신·녹음, 수신/발신 구분 | 가상 통화 녹취록(`ax_calls`, 생성 7단계) + `direction` |
| 통화 중 실시간 STT | 녹취록 텍스트 입력(붙여넣기 폼). 옵션: 샘플 녹음 → Whisper |
| AI 음성 1차 응대·모바일 앱 | 범위 밖 |
| 끊으면 요약·할 일 | ① 그대로 |
| "지난번에 뭐 물어봤지" 검색 | ③ 사례 버킷 |

분류기 입력이 녹취록과 방향뿐인 것(앱 설계 §1 — 정답 힌트 차단)은 PBX가 넘겨주는 정보(녹음 → 녹취록, 방향)와도 맞는다.

**화면**: 통화 목록 / **후속 큐**(할 일 있음인 통화 — 급함 먼저, 후속 에이전트의 처리안과 조사 과정이 함께 보이고, 직원이 "처리함"을 누르면 빠지고 처리한 사람·시각이 남음) / 상세(녹취록 · 요약·분류·할 일 · 엇갈림 배지) / 붙여넣기 폼(수신·발신, 기본 수신). 옵션: 샘플 녹음 → Whisper로 글로 옮김 → 붙여넣기 폼

**API**
- `GET /calls`, `GET /calls/{call_uid}`
- `POST /calls/paste` → 분류 1행, 색인(판정 큐는 운영 구간 규칙 — 앱 설계 §6)
- `POST /calls/{call_uid}/classify`(재시도) / `POST /jobs/classify-batch`(`in_eval_pool` 일괄, `ax_jobs`)
- `GET /calls/followups` / `POST /calls/{call_uid}/followup-done`
- `POST /agents/call-followup/run`(야간 실행, 재시도)
- `POST /calls/transcribe-sample/{n}`(옵션)

**완료 기준**
- E2E: 붙여넣기 → `ax_call_classifications` 1행 `ok`
- 판정 풀(`in_eval_pool`) 전체 행 `ok` (`active_prompt_version` 기준. 블라인드 풀은 판정 풀의 부분집합이라 별도 분류 없음)
- 후속 큐(pytest): `ok` 분류 중 할 일 있음인 통화만 나오고, 처리하면 빠짐
- 엇갈림(pytest): 9항목 중 하나라도 다르면 엇갈림 행, 목적·급함·응급이 다르면 `is_core`
- 자동 종결(pytest): 두 모델 모두 할 일 없음이고 응급·불만·급함이 아니며 엇갈림이 없을 때만 종결되고, 나머지는 큐에 남음
- 후속 처리안: 처리 정답(`truth_call_actions`) 정확도를 규칙 기준선과 나란히
- 분류 스키마 enum은 [[치과 AX - 가상 데이터 생성 설계]] §4.1, 채점은 [[치과 AX - 평가 설계]] §2

**설계 근거**: 자동 종결은 사람이 안 보는 오류를 만들므로 일치 오류율을 재는 교차검증을 코어로 둔다. 분류기 입력 제한은 [[치과 AX - 앱 설계]] §1 — 도구로 EMR을 보면 통화 뒤 기록이 정답을 드러내므로([[치과 AX - 평가 설계]] §1 원칙 7) 분류는 함수로 두고, 에이전트는 분류 다음 단계부터 들어간다. 복수 주제 통화는 주 목적 1 + 불리언 플래그(생성 제약은 가상 데이터 생성 설계 §4.1, 채점은 평가 설계 §2.2). 후속 큐와 자동 종결은 분류를 믿고 움직이므로 분류가 틀리면 할 일이 빠진다 — ② 판정으로 분류를 재는 이유.

**교차검증**: 모델 A(분류기)와 모델 B(판정 에이전트, ②)가 각각 분류하고, 9항목 중 하나라도 다르면 엇갈림 배지 → 운영 구간 판정 큐에서 핵심 엇갈림 먼저. 엇갈림 테이블은 [[치과 AX - 앱 설계]] §1, 효용 지표는 [[치과 AX - 평가 설계]] §2.5

**후속 에이전트**: 할 일 있는 통화의 환자 이력·예약·미수·관련 문서를 조회해 처리안(enum + 근거)을 낸다. 입력은 분류 결과와 그 통화이고, 처리안 실행은 사람 몫이다.

### ② 판정·자동 개선 + 블라인드 비교

**목적**: 판정 에이전트가 1차로 판정하고, 사람은 기준을 측정하고 엇갈림·표본을 본다. 그 결과로 프롬프트를 자동 개선하고 요약을 블라인드로 비교한다.

**화면**
- **판정 구간**: 판정 풀(측정 구간)은 사람이 전수 판정하고, 그 밖의 통화(운영 구간)는 판정 에이전트가 판정해 사람은 엇갈림·표본만 본다(규칙은 [[치과 AX - 평가 설계]] §2.3)
- **판정 에이전트**: 모델 A와 다른 모델. 입력은 녹취록과 방향뿐이고 모델 A 결과를 보지 않는다. 도구는 판정 기준·매뉴얼 문서 검색만이고 EMR·환자 도구는 쓰지 않는다([[치과 AX - 평가 설계]] §1 원칙 7)
- **판정**: 한 건씩, 녹취록 기본 노출
  - 입력: 항목마다 선택지 버튼을 모두 펼치고 숫자 키로 고름 — 목적 2자리·나머지 1자리 → 자동 다음 항목 → Enter 저장·다음 건. 위에 진행 현황 한 줄(오늘·누적 판정 수), 아래에 단축키 안내
  - 메모 칸(선택 — 애매한 이유, 기준이 필요한 경우): 단축키로 들어가고 Enter로 저장
  - 저장 뒤에만 모델 라벨을 보여 준다(저장 전에 보이면 앵커링).
- **블라인드 탭**: 두 프롬프트 버전 요약을 버전 가리고 — 기본 같은 모델 v1 vs vN, 최종 vN vs vN-final → `1 / 2 / 비슷 / 둘 다 틀림`
- **정확도 표**: 항목별 모델 vs 사람 일치율·판정 에이전트 vs 사람 일치율·블라인드 승률·좌우 선택 비율. 프롬프트 버전을 나란히 놓아 개선 추이를 보인다. 모수는 **dev 판정만** — [[치과 AX - 평가 설계]] §2.2. test 수치는 `eval.py --split test`에서만. 교차검증 효용은 화면 없이 `eval.py`만
- **자동 개선**: 개선 실행 이력(오류 유형·바뀐 규칙·관문 결과·반영 여부), 재발 방지 후보(원인·재현 테스트·승인 상태)·규칙별 차단 횟수. 읽기 전용이며 기준 수정과 버전 되돌리기(`make set`)는 화면에 두지 않는다

**API**
- `GET /judge/next` / `POST /judgments` / `POST /calls/{call_uid}/skip`
- `GET /blind/next` / `POST /blind-votes`
- `GET /metrics/accuracy?prompt_version=` / `GET /metrics/blind`
- `GET /improve/runs` / `GET /failure-cases` / `make improve TASK=…`(재료 → 후보 → 관문 → 반영, `evaluation/` 쪽 실행)
- `make export-human` / `import-human`(보존 키는 [[치과 AX - 앱 설계]] §7)

**완료 기준**
- Playwright(`make fixture` DB 또는 실데이터 복사본에서 — 진짜 판정 DB를 오염시키지 않게): 키 시퀀스 10회 → `ax_judgments` +10, 블라인드 5회 → `ax_blind_votes` +5
- 정확도 뷰 2개 SQL이 행 ≥ 9(pytest)
- 판정 에이전트 입력 검사(pytest): 도구 목록에 EMR·환자 도구가 없고 모델 A 결과가 입력에 없음
- 자동 개선(pytest): 관문 조건을 하나라도 못 넘으면 활성 버전이 바뀌지 않음, test 분할을 읽으면 실패

**자동 개선** — 재료의 오류 유형 → 개선 에이전트가 프롬프트 후보 작성 → 관문 재측정 → 반영 → 버전별 추이. `make improve`는 `evaluation/`에서 돌고 재료·관문·반영 조건은 [[치과 AX - 평가 설계]] §2.7. 프롬프트 v1 → vN 변화가 §8 결과표의 근거이며, README에 "오류 유형 → 수정 내용 → 수치 변화"를 한 표로. 골드(`truth_call_labels`)의 통화·라벨은 프롬프트에 넣지 않는다(few-shot 규칙은 [[치과 AX - 평가 설계]] §7)

**설계 근거**: 녹취록 기본 노출(모델 요약을 읽고 판정하면 정답지가 모델에 앵커링). 판정 풀·판정·블라인드 절차와 정확도 3종은 [[치과 AX - 평가 설계]] §2.

### ③ 물어보기 (RAG 검색 + 챗 + 문서함)

**목적**: 매뉴얼·공지·청구 기준·통화·문자·차트 기록을 하이브리드 검색, 도구 5개 단일 턴 에이전트가 "확인된 사실만" 답함. 하네스 위에 만든다.

**검색 대상** (현장 인터뷰에서 나온 질문 기준)

| 대상 | 예시 질문 | 버킷 |
|---|---|---|
| 업무 절차(직원 매뉴얼) | 틀니 수리 접수 절차, 구형 임플란트 부품 주문 | 문서 |
| 청구 기준·보험 안내 | 치석제거 다음 달로 넘어가면 치주치료가 왜 깎여? (청구 기준 질문은 ③ 질문 밖, ⑤ 평가셋) | 문서 |
| 원내 공지(최신성) | 바뀐 기준이 뭐였지 | 문서 |
| 통화·문자 사례 | 그 환자 지난번에 뭘 물어봤지 | 사례 |
| **차트 케이스** | 치석제거 뒤 치주치료로 이어진 환자는 간격·상병을 어떻게 적었지, 사랑니가 완전 매복이라 골삭제한 환자 | 사례 |
| 환자 사실 | 지난 스케일링이 언제였지, 이 환자 남은 치료가 뭐지 | 도구 `query_patient` |

차트 케이스는 "차트 검색이 환자 이름으로만 돼서 이름을 모르면 못 찾는다"는 인터뷰 고충에 대한 답 — 케이스 내용으로 찾고 결과에 차트 번호를 띄운다. 차트 기록 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §4.3.

**화면**: 메뉴 하나에 탭 `질문하기 | 기록 검색` — 입력한 내용은 탭을 바꿔도 유지, 챗 답변의 "근거 더 보기"는 같은 질문으로 기록 검색을, 검색 결과의 "이걸로 질문하기"는 챗을 연다. **질문하기**(질문 1 → 진행 이벤트 SSE → 답변 + 출처. 멀티턴 없음. 근거가 없으면 `refuse` → 고정 문구 "문서함에 없음") / **기록 검색**(`매뉴얼 결과` / `실제 사례 결과` 분리 + AI 요약 + 출처, 필터: 출처 종류·기간·환자번호) / **문서함**(매뉴얼·공지·FAQ·청구 기준 목록 — 공지는 최신 버전만·시행일 표시, 본문 보기, 읽기 전용). 챗이 문서에서 근거를 못 찾아 거절한 질문은 문서 초안 에이전트가 기존 문서·통화·문자에서 재료를 찾아 초안을 만들고, 오늘 화면의 "사람이 볼 일"에 올린다. 게시는 사람

**API**
- `GET /search?q=&source_types=&date_from=&date_to=&chart_no=` → `{manual_results, case_results}`
- `POST /chat`(SSE 진행 + 최종 답변) → `ax_search_logs`
- `GET /documents` / `GET /documents/{id}`. 문서 초안 입력은 `ax_search_logs`, 오늘 화면은 `GET /today`
- 도구 5개(시그니처는 앱 설계 §3): `search_docs`, `query_patient`, `query_schedule`, `query_claims`, `refuse`
- `make index` / `eval.py --split dev [--retrieval-only]` · `--split test --section …`([[치과 AX - 평가 설계]] §7)

**완료 기준**
- `eval.py --split dev` exit 0 + 리포트
- 데이터형 도구 선택 ≥ 1/2(dev), `--retrieval-only` Hit@5 ≥ 1/2(dev 문서 검색형 — 문항 수는 `verify.QA_TYPE_COUNTS`)
- 질문 구성(유형·수·dev/test)·채점 규칙·지표는 [[치과 AX - 평가 설계]] §3 — `make verify`가 문항 구성을 검사

**설계 근거**: 문서 청크가 통화·문자 청크보다 훨씬 적어 단일 RRF에서 묻힘 → **문서 버킷·사례 버킷 따로 검색** 후 리랭커. 모든 청크에 출처 prefix 의무(환자명 없이는 사례형 검색 불가). 차트 서술은 비식별이고 prefix는 차트 번호까지만이다(형식은 [[치과 AX - 앱 설계]] §3). 리랭커·임베딩 선택은 앱 설계 §7.

### ④ 진료 준비표 (MVP — `make gate` 통과 시 착수)

**목적**: 환자마다 EMR 여러 화면(기본정보·예약·진료기록·수납·청구·가족·주의사항)을 뒤지는 걸 코드가 조인해 한 행으로 모으고, LLM이 그날 할 일(관련 주의사항 처리 + 권할 진료)을 한두 줄로 묶는다. 주의 칩이 켜진 환자는 야간에 에이전트가 지난 통화·차트를 더 조회해 제안에 근거를 보탠다. 도구 결과도 후검증의 입력 사실로 본다. 체어 보기는 저장된 결과만 읽는다. 둘 다 없으면 "그대로 진행". 아침 회의에서 오늘 전체를, 진료 중에는 체어 옆에서 지금 환자 한 명을 본다.

**화면 (MVP)**
- **전환 전 EMR**(④ 착수와 함께, 개선 전, 읽기 전용): 상용 전자차트의 일반적인 구조를 가상 프로그램으로 보인다 — 데스크(환자 정보·당일 수납·히스토리·접수 목록·예약표), 예약(담당자별 예약표), 전자차트(상단 Alert·진료 기록·치식·처치 입력·환자정보 패널). 주의사항은 전자차트, 미수는 데스크, 남은 치료는 차트 옆 패널에 있어 한 환자를 챙기려면 화면을 옮겨 다니는 현재 모습을 보이고, 개발자 독자가 가상 데이터를 둘러보는 화면을 겸한다. 실제 제품의 이름·로고·색·화면 이미지는 쓰지 않는다. README에 화면 이동 수 vs 준비표 1행
- **준비표 공통**: 날짜 탭(최근 7일 + 오늘, 날짜마다 인원수) + 기준 시각 + 칩 7개 + 행 펼침(fact + 예정 시술 + 제안 + 근거) + "다시 만들기"
  - 칩: **예약 · 보험 잔여**(스케일링 미사용 성인) **· 미수 잔액 · 가족 리콜 지남 · 주의**(그날 예정 시술과 관련된 주의사항 — 코드가 `master` 표로 정확히 표시) **· 남은 치료계획**(열린 계획 항목 중 그날 예정 시술이 아닌 것) **· 예약 미확인**(그날 예약 중 `emr_appointments.confirmed`가 아닌 것 — 코드 표시만, 제안 사실이 아니므로 LLM 입력과 과잉 제안률에서 뺀다)
- **회의 보기**: 오늘 전체 — 시간 × 체어 예약표, 몰리는 시간대, 할 일 있는 환자 위주, 위생 / 진료 필터, 인쇄
- **체어 보기**: 체어별 오늘 순서 + 지금 환자 한 장 — 주의사항을 가장 크게, 예정 시술, 제안. 시간이 되면 다음 환자로 — "지금"은 TODAY 날짜 + 실제 시계의 시:분
- **제외**: 칩 여러 개를 조합하는 필터, "다음 진료일", "다른 치과 추정"(⑨ 후속 관리 몫)

**API**
- `GET /prep?date=` / `POST /jobs/prep-regenerate?date=`(`facts_hash` 같으면 LLM 생략). 두 보기 모두 `GET /prep?date=`(행에 체어 번호 포함)
- 집계는 순수 함수 `prep_facts(date)`. 출력 `{action: suggest|none, text, used_facts}` — `text`는 그날 할 일 요약(주의사항 처리 + 권할 진료), 둘 다 없으면 `none` = "그대로 진행"(후검증 실패의 `null`과 다름)
- 전환 전 EMR API는 [[치과 AX - 앱 설계]] §9

**완료 기준**
- 집계 회귀 테스트·제안 후검증(`suggestion_valid`) — 규칙은 [[치과 AX - 평가 설계]] §4. 후검증 실패 시 null + 재시도
- 주의사항 반영률·과잉 언급률·과잉 제안률(칩이 꺼진 행 — 항상 켜지는 예약 칩 제외 — 인데 `suggest`) — 전부 코드 채점, 정의는 [[치과 AX - 평가 설계]] §4. `none`의 후검증 처리는 ④ 착수 때(§9)

**설계 근거**: 주의사항 → 행동은 표로 정해져 있어 칩은 코드가 정확히 띄우고, LLM은 여러 사실(주의사항 여럿 + 예정 시술 + 미수·리콜)을 그날 행동으로 묶는 일만 한다(§3 원칙 2). 반영률은 그 요약이 관련 주의사항을 빠뜨리지 않는지 보는 안전망. 제안은 사람이 채점하지 않는다 — 버전 비교·개선에 쓰이지 않는 절대값 하나만 남아 §8(조건 간 차이가 주 지표)과 맞지 않는다. `none`을 허용 — 매 행 제안을 강제하면 근거 약한 제안을 지어낸다. 출력을 `{action, text, used_facts}`로 강제 — 자유 문장에서 (키, 값) 역파싱은 불가능하므로 모델이 쓴 사실을 스스로 명시. 예정 시술은 `emr_appointments.planned_procedure_code`, 남은 치료계획은 치료계획 테이블([[치과 AX - 가상 데이터 생성 설계]] §2.3). "다음 예약 없음" 칩은 두지 않는다 — 예약이 없는 환자는 ⑨ 후속 관리가 맡는다.

## 5. 슬롯 기능

- **⑤ 심평원 청구 점검·삭감 대응**(짧게 "청구 점검·삭감 대응", 건강보험 심평원 청구, 코드명 `claim_review`): 심사결과는 청구 프로그램(전자차트)이 전자로 받아 장부에 반영돼 있다 — 장부와 심사결과가 어긋나는 일은 다루지 않고, 그 뒤에 남는 일(조정 사유 해석·재심 판단)과 청구 전 점검을 돕는다. 하위 기능 3개 — ⑤-2는 독립, 조정 건은 ⑤-3 → ⑤-4. 지표는 [[치과 AX - 평가 설계]] §5, 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §2.4·§4.2·§4.3
  - **⑤-2 청구 전 점검**(규칙 + AI): 전월분(`pending`) 청구를 진료 기록·청구 기준과 대조해 누락·삭감 위험을 근거와 함께 표시(표시만 — 청구 수정·제출은 사람, §3 원칙 1)
    - **급여 조건**(규칙): 나이·횟수 등은 시술 표에 있어 규칙(SQL)이 점검한다 — 나이처럼 정형으로 판정되는 요건은 규칙 몫
    - **임상 요건**(AI): 청구 기준 문서와 **차트 서술**을 읽어 임상 요건 근거(치석제거 뒤 치주치료 연결·치주 소견·같은 부위 재시행 사유 등)가 차트에 있는지 보고 근거를 단다 — 서술을 읽어야 하는 요건이 AI 몫
    - **상병 확인 경고**(규칙): 시술 × 차트 상병이 `master` 허용 조합 밖이면 경고하고, 지난 조정에서 같은 조합이 상병 착오로 깎였으면 "지난달 이 조합으로 n건, ₩x 못 받음"을 붙인다 — 상병 착오는 재청구가 안 되니 미리 막는 게 유일한 방법
    - **차트 기반 누락**(AI): 차트 서술에 시행했다고 적힌 처치인데 진료 기록·청구에 없는 것을 근거 문장과 함께 표시 — 서술을 읽어야만 보여서 규칙으로는 찾을 수 없다
    - 완료 기준: "서술 있는 줄 전부" 기준선과 나란히 AI의 정밀도·재현율·근거 정확도 — 임상 요건형·차트 기반 누락 모두. 나이·횟수·단순 누락·코드 착오는 규칙 fixture 테스트(가상 데이터에 심은 오류는 상병 착오·임상 요건형·차트 기반 누락뿐 — [[치과 AX - 가상 데이터 생성 설계]] §2.4)
  - **⑤-3 조정 사유 검색 + 다툴 만한지**(RAG — ③ 검색 구조 재활용)
    - **조정 목록**(코드): 확정 월 조정 건(일부·전액)을 통보일·재심 기한(통보일 + `master.APPEAL_DAYS`, 남은 날 표시 — 기한 임박은 오늘 화면으로)과 함께 보인다
    - **검색·판단**: 조정 건(사유 범주 코드·일반사유 서술)으로, 또는 코드 없이 비고·질문으로 재심 근거 조사 에이전트가 청구 기준 검색·그 진료의 차트 조회·비슷한 지난 조정 비교를 반복해 재심할 만한지와 근거(기준 절 + 그 진료의 차트 서술)를 제시, 최종 판단은 사람. 답은 정당 / 다툴 만함 / 보완 후 재청구(정의는 [[치과 AX - 가상 데이터 생성 설계]] §2.4)
    - **보완 후 재청구**: 청구 때 빠뜨린 것(내역설명·증빙)을 채워 다시 내는 길이라, 채울 항목과 근거 차트 문장을 함께 보여 준다
    - **상병 착오**(코드 표시로 따로 강조): "재청구 불가 · 상병 착오" 배지 + 못 받은 금액 + 차트 상병 ↔ 시술 + "다음 청구 때 상병 확인" — 같은 조합은 ⑤-2 상병 확인 경고로 이어진다
    - 완료 기준: 상세 사유 → 기준 절 찾기 테스트, 코드 없이 묻는 청구 기준 질문의 Hit@5·MRR, 판단 정확도(3분류)를 규칙 기준선과 나란히
  - **⑤-4 재심 사유서 초안**(LLM): ⑤-3에서 다툴 만함으로 본 건만 → 조정 건 + 청구 기준 절 + 그 진료의 차트 기록으로 초안, 사람이 검토·수정·제출 결정(§3 원칙 1). **추측 목록**: 초안의 모든 문장은 기준 절·차트 문장 인용이거나 추측 목록(`assumptions[]`)에 올라야 한다 — 둘 다 아닌 문장이 있으면 후검증 실패. 화면은 초안 + 추측 칸 + "검토 확인" 체크 뒤에만 "제출 결정". 완료 기준: 초안이 인용한 기준 절·차트 문장이 실제로 있는지 후검증(③ 인용 확인·④ 후검증 재사용) + 인용도 추측 표시도 없는 문장 비율
- **⑥ 경영 리포트**: ④ 패턴 복제. 월간·주간·일간을 고른다
  - **공통 숫자**(쿼리): 매출(`emr_treatments` 진료비), 수금(환자 수납 + 공단 지급), 노쇼율, 신환
  - **월간 전용**(쿼리): 재료비·기공비(⑧-2 확정 계정 — 사람 확정 + 자동 확정, ⑧ 전에는 거래처 표), 인건비 제외 손익(수금 − 통장 출금·병원 카드 사용), 상병 착오 건수·못 받은 금액과 금액이 가장 큰 시술 × 상병 조합(입력자별 집계는 하지 않음). 재료비·손익을 월간에만 두는 이유는 월말 이체가 많아서다
  - **`[추정]`**: 인건비는 실제 급여가 아니라 역할별 직원 수(`emr_staff`) × 앱 설정 가정값이다. 대표 원장 보수는 넣지 않는다. 추정 손익·손익분기 매출(고정비 ÷ (1 − 재료비·기공비 비율))은 항상 `[추정]`으로 표시하고, "대표 원장 보수·세금 전"을 함께 적는다. 값이 가정값에 달려 있어 성과 지표로 쓰지 않는다(§8 결과표에 넣지 않음)
  - **AI**: 숫자를 문장으로 풀고, 추정 문장은 `[추정]`을 단다
  - **튄 숫자 조사**(에이전트): 숫자는 쿼리가 낸다. 이전 기간과 차이가 큰 항목을 코드가 고르면 에이전트가 예약·청구·지출 쿼리 도구로 원인을 찾고, 문장과 근거 쿼리를 함께 남긴다. 추측은 `[추정]`
  - 완료 기준: 본문 숫자 전부 `metrics`에 존재(④ 후검증 재사용), 가정값이 들어간 숫자에 `[추정]` 누락 0, 시나리오 DB의 원인 정확도([[치과 AX - 평가 설계]] §5)
- **⑦ 아침 브리핑**: 오늘 화면의 한 칸. 그날 예약 수·신환·몰리는 시간대·주의 환자 수·예약 미확인 수 같은 숫자는 쿼리, LLM은 운영 에이전트의 밤사이 결과와 함께 몇 문장으로 묶기만 한다. 추정 문장은 `[추정]`을 단다. 완료 기준: 본문 숫자 전부 입력에 존재(④ 후검증 재사용)
- **⑧ 재무 대조**: 데이터는 `fin_` 테이블, 장부 실수는 `emr_payments`에 생성 단계에서 심는다([[치과 AX - 가상 데이터 생성 설계]] §2.4·§2.7). 정답은 truth.sqlite에만. 원인·계정 과목은 고정 enum(§3 원칙 6 — 에이전트 출력·사람 확정·정답이 공유)
  - **⑧-1 수입 일계표 대조**(에이전트): 현장의 일계표 확인을 옮긴 기능. 장부(`emr_payments`) ↔ 카드 승인·정산 입금·통장 입금 대조는 코드(§3 원칙 2). 에이전트는 불일치마다 가설 → 조회(그날 내원, 미수 잔액, 다음 날 장부, 구강용품 가격표, 가족) → 비교를 반복해 원인을 고르고 그 과정을 보인다(③ 챗은 질문 하나에 짧은 도구 루프로 답만 — 조사 과정이 화면의 주인공인 것이 ⑧-1의 차이). 원인은 통장·카드 쪽과 장부 쪽(목록과 묶음은 [[치과 AX - 평가 설계]] §5), 근거가 부족하면 `unknown`
    - **화면**: 날짜별 일계표(결제수단별 장부 합계 vs 금융 합계) + 불일치 행 배지 → 펼침 = 조사 과정(도구 호출 순서·조회 조건·비교 결과) + 원인 후보·근거 + 사람 확정(`맞음 / 아님`, 아님이면 원인 선택 — `ax_` 테이블, 사람 라벨이라 앱 DB). 규칙 묶음이고 장부 수정이 필요 없으며 규칙과 에이전트의 원인이 같으면 자동 마감(§3 원칙 1). 장부 수정은 사람
    - **완료 기준**: 원인 정확도(top-1)를 규칙 기준선과 나란히, "규칙으로 되는 원인 / 애매한 원인" 두 묶음으로. 탐지 재현율은 코드 대조라 테스트. 조사 단계 수 상한(③처럼 호출 상한). 사람 확정은 지표가 아니라 화면 흐름과 프롬프트 개정 재료. 자동 마감 오류율. 지표 세부는 [[치과 AX - 평가 설계]]
  - **⑧-2 지출 증빙·계정 분류**(AI): 통장 출금·병원 카드 사용을 증빙(거래명세서·세금계산서·주문 메일·영수증·고지서)과 맞추고(1:1, 거래처 월말 이체는 1:N 합계), 계정 과목을 확신도와 함께 추천한다. 못 찾으면 "증빙 없음". 급여·공단 입금은 대상이 아니다
    - **화면**: 미매칭 목록(계좌·카드별 건수·금액) + 행마다 찾은 증빙·금액 차이·추천 계정 과목 → 사람 확정(`ax_`). 규칙으로 안 맞은 건은 증빙 탐색 에이전트가 후보를 찾는다. 금액·증빙이 일치하고 계정 과목이 거래처 기본값과 같으면 자동 확정(§3 원칙 1). 확정한 거래처는 다음부터 기본값
    - **완료 기준**: 매칭 정확도·계정 과목 정확도를 규칙 기준선(금액·날짜만으로 맞추기)과 나란히, 자동 확정 오류율(평가 달 밖 정답을 추가 검증에 씀)
- **⑨ 후속 관리**: 예약 없이 놓친 환자를 칩별 목록 + 코드 점수 순위로 보인다
  - **칩**: 리콜 연체 · 올해 스케일링 급여 미사용 · 노쇼 뒤 재예약 없음 · 미수 잔액 · 진료계획 미예약 · 다른 치과 추정(타 기관 이력·연락 무응답)
  - **순위**: 코드 점수(마지막 방문, 최근 연락, 다른 치과 흔적 감점 등 — 규칙과 값은 앱 설정, [[치과 AX - 앱 설계]] §8). 화면에 "순위는 어떻게 정해지나요?" 설명. 예약이 잡히면 자동으로 빠짐. 필터: 1순위만 · 연락함 숨기기
  - **근거 찾기**(에이전트): 상위 환자의 통화·문자·차트에서 이탈 근거를 찾아 다른 치과 추정 칩에 근거를 붙인다. 순위는 코드 점수가 정한다
  - **문자**(LLM): 큰 계획은 "가장 급한 것 하나부터". 숫자는 ④ 후검증 재사용. 리콜·재예약처럼 의료·금액 내용이 없는 안내는 `ax_outbox`에 자동 기록하고(실제 발송 없음), 미수 안내와 치료 권유는 사람이 보낸다
  - **완료 기준**: 칩별 목록·점수 회귀 테스트(코드), 다른 치과 추정의 정밀도·재현율(정답은 흔적 있는 이탈·병행 — [[치과 AX - 평가 설계]] §5 ⑨), 문자 후검증 통과율

## 7. 운영 결정

- 인증 없음. 상단 사용자 선택(원장 / 데스크 / 상담실장)으로 `judged_by`와 처리한 사람(후속 큐 처리, ⑧ 확정, 자동 처리 되돌리기)을 남긴다. 에이전트가 한 일은 실행 id로 남겨 사람과 구분한다
- 토큰 스트리밍 없음. ③ 챗은 진행 이벤트 SSE, 배치(①·④)와 야간 실행은 `ax_jobs` + 폴링
- `make save-demo` / `reset-demo`(서버 중지 → 파일 교체 → 재시작)
- 설정 변경은 CLI `make set KEY=… VALUE=…`(허용 키: `judge_upto`·`active_prompt_version`·`active_models`·`blind_versions`·`daily_usd_limit`·`labor_cost_assumed`·`auto_policy`·`prompt_versions` — 기준일은 바꾸지 않음). 화면 없음
- 배포: 로컬 `docker compose` + 녹화 영상. 공개 필요 시 볼륨 있는 단일 서버
- LLM 실패는 `failed` 기록 + 재시도 버튼
- **모델 사용** (비용의 원본은 여기 — 모델은 [[치과 AX - 앱 설계]] §7·`config/llm.yaml`): 튜닝 중 경량 모델, 데모 직전 1회만 상위 모델 — 비용 때문이고, 상위 모델은 튜닝 대상이 아니라 최종 구성(= test 1회 구성, [[치과 AX - 평가 설계]] §1 원칙 2)이다. 튜닝 중 상위 모델로 dev 약 30건만 돌려 출력 형식·실패율만 점검할 수 있다(별도 버전, 집계에서 제외)
- **비용**: 생성기 1회 약 $35(Batch — 녹취록 약 $20·차트 서술 약 $12·문서 약 $1. 프롬프트를 고쳐 다시 채우면 그 작업만큼 더), 런타임 3주 $40~100(추정, §9에서 실측). 하드리밋 런타임 $15/일, 생성기 $40/일(즉시 호출에만 — `config/llm.yaml` `daily_usd_limit`이 같은 값 — 앱의 `ax_settings.daily_usd_limit`은 그날만 올리는 값). 생성기 배치(`make llm-fill-api`)는 하루 상한 밖 — 건수가 정해져 있어 사람이 건수(`make data`가 알려 줌)를 보고 제출한다
