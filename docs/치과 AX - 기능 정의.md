> 가상 데이터로 개발하므로 외부 LLM API를 자유롭게 쓴다. 인프라·하드웨어·운영 비용은 범위 밖.
> 이 문서는 **무엇을 만드나**. 데이터 구조와 생성 규칙은 [[치과 AX - 가상 데이터 생성 설계]], 앱 테이블·도구·쿼리는 [[치과 AX - 앱 설계]], 지표·채점·정답 저장소는 [[치과 AX - 평가 설계]], 구현 규칙은 `CLAUDE.md`.

## 1. 조건

- 기간: 준비(문서·데이터셋 생성·평가셋·환경) → 개발 3~4주
- 인원: 1인 기준. 팀이 되면 슬롯을 사람별로 배분
- 목표: "AI 도구를 잘 다루는 개발자" 포트폴리오. 풀스택 직접 구현, 프론트를 일부러 줄이지 않음
- 스택: [[치과 AX - 앱 설계]] §7. Claude Code 설정(`CLAUDE.md`·서브에이전트·스킬)은 깃에 포함

## 2. 범위

| 구분 | 기능 | 한 줄 |
|---|---|---|
| 코어 | 가상 데이터 생성기 | 모든 기능의 토대. 정답 내장 |
| 코어 | ① 통화 요약·분류 | 모델 1개로 완성. 파이프라인의 뼈대. 모델 2개 교차검증은 확장(나중) |
| 코어 | ② 사람 판정 + 블라인드 비교 | "AI 검증"의 간판 화면. 키보드 UX |
| 코어 | ③ RAG 검색 + 챗 | 하이브리드 검색(문서·통화·문자·차트 케이스) + 도구 5개 에이전트. 부트캠프 직결 |
| 코어 (MVP) | ④ 진료 준비표 | 가상 EMR 뷰어(개선 전) 대비 한 화면. "코드 집계 → LLM 해석". `make gate` 통과 시 착수 |
| 슬롯 | ⑤ 청구 점검·삭감 대응 | 전자 심사결과 대조·청구 전 점검·조정 사유 검색·재심 사유서 초안. 기능은 코어와 독립 → 팀원용(근거 데이터인 차트 기록은 데이터 고정 전 생성 — §9) |
| 슬롯 | ⑥ 리포트 + ⑦ 브리핑 | ④ 패턴 복제 |
| 슬롯 | ⑧ 재무 대조 에이전트 | 일계표 불일치 원인 추적 + 조사 과정 표시. 도구 루프 과제. 데이터 미설계 |
| 제외 | 메신저 / 방송 / 동의서 / 근태 | 범위 폭발 또는 AI 비중 낮음 |
| 제외 → 프로젝트 후 개인 확장 | 연쇄 치료계획·리콜 큐·임플란트 평생 한도·다회차 시술 회차 추적 | ④ MVP는 없이 성립. 생성기의 치료 코스는 연속 내원일 뿐 회차 추적 없음 |

기능 번호는 이 표의 순서다(코어 ①~④, 슬롯 ⑤~⑧). 동그라미 숫자는 기능 번호에만 쓴다.

## 3. 공통 원칙

1. **AI는 읽고 제안만, 쓰는 건 사람.** 원본 장부·차트에 AI가 직접 쓰지 않음
2. **숫자는 코드, AI는 해석.** 매출·건수·잔액은 쿼리로. LLM 출력의 숫자는 입력 fact에 있는지 **후검증**
3. **교차검증(① 확장)은 구조화 출력(① 분류)에만.** 자유 텍스트(요약·제안·답변)는 diff가 안 되므로 블라인드 비교로
4. **LLM은 게이트웨이 모듈 하나로.** [[치과 AX - 앱 설계]] §7
5. **정답은 앱 DB 밖에.** 원본은 `CLAUDE.md` 절대 규칙
6. **구조화 출력.** 분류·추출은 JSON 스키마 + 고정 enum
7. **스펙 → 평가셋 → 구현.** "프롬프트 수정 전 N% → 후 M%"를 `prompt_version`으로 기록

## 4. 코어 기능

> 각 기능: 목적 / 화면 / API / 완료 기준 / 설계 근거(왜 이렇게 하는지만)

### 가상 데이터 생성기

**목적**: 미니 EMR + 비정형(통화·문서·문자) + 정답을 시드 재현 가능하게 생성. 산출물·규칙은 [[치과 AX - 가상 데이터 생성 설계]].

**완료 기준**: `make verify` 통과 + 결정성(같은 시드 2회 → 테이블 내용 해시 동일, LLM 캐시 포함)

### ① 통화 요약·분류

**목적**: 전사 1건 → 모델이 요약 + 분류 JSON + 할 일. 모델 1개로 시작하고, 두 번째 모델과 불일치 표시는 아래 확장.

**현실 구성과 대체**: 원본 사례(실제 동네 치과 AX 전환기 글)는 병원 자체 교환기(PBX)로 대표번호를 받아 녹음하고 통화 중 실시간 전사한다. 이 프로젝트는 실제 전화를 받을 수 없으므로 PBX·STT 구간을 **데이터로 대체**하고, 전사가 들어온 뒤부터 구현한다.

| 현실 | 이 프로젝트 |
|---|---|
| PBX 수신·녹음, 수신/발신 구분 | 가상 통화 전사(`ax_calls`, 생성 7단계) + `direction` |
| 통화 중 실시간 STT | 전사 텍스트 입력(붙여넣기 폼). 옵션: 샘플 녹음 → Whisper |
| AI 음성 1차 응대·모바일 앱 | 범위 밖 |
| 끊으면 요약·할 일 | ① 그대로 |
| "지난번에 뭐 물어봤지" 검색 | ③ 사례 버킷 |

분류기 입력이 전사와 방향뿐인 것(앱 설계 §1 — 정답 힌트 차단)은 PBX가 넘겨주는 정보(녹음 → 전사, 방향)와도 맞는다.

**화면**: 통화 목록 / 상세(전사 · 요약·분류·할 일) / 붙여넣기 폼(수신·발신, 기본 수신). 옵션: 샘플 녹음 → Whisper 전사 → 붙여넣기 폼

**API**
- `GET /calls`, `GET /calls/{id}`
- `POST /calls/paste` → 분류 1행, 색인, 판정 큐 `pending`
- `POST /calls/{id}/classify`(재시도) / `POST /jobs/classify-batch`(`in_eval_pool` 일괄, `ax_jobs`)
- `POST /calls/transcribe-sample/{n}`(옵션)

**완료 기준**
- E2E: 붙여넣기 → `ax_call_classifications` 1행 `ok`
- 판정 풀(`in_eval_pool`) 전체 행 `ok` (`active_prompt_version` 기준. 블라인드 풀은 판정 풀의 부분집합이라 별도 분류 없음)
- 분류 스키마 enum은 [[치과 AX - 가상 데이터 생성 설계]] §4.1, 채점은 [[치과 AX - 평가 설계]] §2

**설계 근거**: 모델 2개·엇갈림 배지는 효용(일치 오류율·무작위 검토 대비 포착 향상)을 재기 전까지는 가설이라, 구조를 두 배로 짓기 전에 모델 1개로 코어를 완성한다. 분류기 입력 제한은 [[치과 AX - 앱 설계]] §1. 복수 주제 통화는 주 목적 1 + 불리언 플래그(생성 제약은 가상 데이터 생성 설계 §4.1, 채점은 평가 설계 §2.2).

**확장 — 모델 2개 교차검증** (`make gate` 이후, 시간이 남으면): 모델 B를 붙여 A·B가 각각 분류하고, 9항목 중 하나라도 다르면 엇갈림 배지 → 판정 큐에서 핵심 엇갈림 먼저. 붙이는 방법: `active_models`에 B 추가 + 판정 풀 재분류(분류 테이블이 처음부터 모델별 행이라 스키마 변경 없음, 비용 경량 ~$0.3). 붙일 때 엇갈림 테이블(`(call_id, prompt_version)` 1행, `is_core` = 목적·급함·응급 불일치)과 판정 큐 순서(핵심 엇갈림 먼저)를 앱 설계에 추가. 효용 지표는 [[치과 AX - 평가 설계]] §2.5

### ② 사람 판정 + 블라인드 비교

**목적**: 사람이 분류를 판정해 정답지를 만들고, 요약을 블라인드로 비교.

**화면**: **판정**(전사 기본 노출, 항목별 키 입력 — 목적 2자리·나머지 1자리 → 자동 다음 항목 → Enter 저장·다음 건. 저장 뒤에만 모델 라벨을 보여 주고, 틀린 항목에 오류 유형 태그(선택, **`make gate` 이후** — 개선 루프 1회는 태그 없이 dev 덤프로 가능) — 개선 루프의 재료. 저장 전에 보이면 앵커링. 태그도 `export-human` 보존 대상) / **블라인드 탭**(두 프롬프트 버전 요약을 버전 가리고 — 기본 같은 모델 v1 vs v2, 최종 v2 vs v3-final → `1 / 2 / 비슷 / 둘 다 틀림`) / **정확도 표**(항목별 모델 vs 사람 일치율·블라인드 승률·좌우 선택 비율. 프롬프트 버전을 나란히 놓아 개선 추이를 보인다. 모수는 **dev 판정만** — [[치과 AX - 평가 설계]] §2.2. test 수치는 `eval.py --split test`에서만. 교차검증 효용은 화면 없이 `eval.py`만)

**API**
- `GET /judge/next` / `POST /judgments` / `POST /calls/{id}/skip`
- `GET /blind/next` / `POST /blind-votes`
- `GET /metrics/accuracy?prompt_version=` / `GET /metrics/blind`
- `make export-human` / `import-human`(보존 키는 [[치과 AX - 앱 설계]] §7)

**완료 기준**
- Playwright(`make fixture` DB 또는 실데이터 복사본에서 — 진짜 판정 DB를 오염시키지 않게): 키 시퀀스 10회 → `ax_judgments` +10, 블라인드 5회 → `ax_blind_votes` +5
- 정확도 뷰 2개 SQL이 행 ≥ 9(pytest)

**개선 루프** — 사람 판정 → 오류 유형 → 사람이 프롬프트 개정 → 재측정 → 버전별 추이. 이 프로젝트가 보여 주려는 방향(사람 평가로 AI 성능을 올린다)이고, 같은 틀을 ④ 사람 채점에도 쓴다(§4 ④). **1회는 필수** (`make gate` 조건 아님 — §8 결과표 "프롬프트 v1 → v2"의 근거): dev 판정에서 모델이 틀린 건을 모아 오류 유형을 나눔(판정 화면의 태그) → 유형별로 프롬프트 v2 수정(규칙 추가·few-shot) → 판정 풀 재분류 → 모델을 고정한 v1·v2 교집합 비교([[치과 AX - 평가 설계]] §2.2). few-shot 예시는 dev 판정에서만 고르고(라벨은 사람 판정, 골드 `truth_call_labels`는 프롬프트에 넣지 않음), 예시 통화는 집계에서 뺀다(규칙은 [[치과 AX - 평가 설계]] §7). README에 "오류 유형 → 수정 내용 → 수치 변화"를 한 표로. 사람 판정은 평가용 정답지이면서 개선 재료다 — 이 루프로 프롬프트가 바뀌고, 운영 중에는 사람의 판정(확장 시 엇갈림 건 우선)이 쌓여 다음 프롬프트 개정의 재료가 된다(자동 반영 없음). 판정은 `export-human`으로 보존돼 미세조정 재료가 되지만 미세조정은 범위 밖

**설계 근거**: 전사 기본 노출(모델 요약을 읽고 판정하면 정답지가 모델에 앵커링). 판정 풀·판정·블라인드 절차와 정확도 3종은 [[치과 AX - 평가 설계]] §2.

### ③ RAG 검색 + 챗

**목적**: 매뉴얼·공지·청구 기준·통화·문자·차트 기록을 하이브리드 검색, 도구 5개 단일 턴 에이전트가 "확인된 사실만" 답함.

**검색 대상** (현장 인터뷰 — 치위생사 1명, 질문지는 Obsidian `치과 AX - 현장 인터뷰 질문지` — 에서 나온 질문 기준)

| 대상 | 예시 질문 | 버킷 |
|---|---|---|
| 업무 절차(직원 매뉴얼) | 틀니 수리 접수 절차, 구형 임플란트 부품 주문 | 문서 |
| 청구 기준·보험 안내 | 치석제거 다음 달로 넘어가면 치주치료가 왜 깎여? (청구 기준 질문은 ③ 질문 밖, ⑤ 평가셋) | 문서 |
| 원내 공지(최신성) | 바뀐 기준이 뭐였지 | 문서 |
| 통화·문자 사례 | 그 환자 지난번에 뭘 물어봤지 | 사례 |
| **차트 케이스** | 치석제거 뒤 치주치료로 이어진 환자는 간격·상병을 어떻게 적었지, 구형 스크류 임플란트 환자 | 사례 |
| 환자 사실 | 지난 스케일링이 언제였지 | 도구 `query_patient` |

차트 케이스는 "차트 검색이 환자 이름으로만 돼서 이름을 모르면 못 찾는다"는 인터뷰 고충에 대한 답 — 케이스 내용으로 찾고 결과에 차트 번호를 띄운다. 차트 기록 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §4.3.

**화면**: **검색**(`매뉴얼 결과` / `실제 사례 결과` 분리 + AI 요약 + 출처) / **챗**(질문 1 → 진행 이벤트 SSE → 답변 + 출처. 멀티턴 없음. 근거가 없으면 `refuse` → 고정 문구 "문서함에 없음")

**API**
- `GET /search?q=&source_types=&date_from=&date_to=` → `{manual_results, case_results}`
- `POST /chat`(SSE 진행 + 최종 답변) → `ax_search_logs`
- 도구 5개(시그니처는 앱 설계 §3): `search_docs`, `query_patient`, `query_schedule`, `query_claims`, `refuse`
- `make index` / `eval.py --split dev|test [--retrieval-only]`

**완료 기준**
- `eval.py --split dev` exit 0 + 리포트
- 데이터형 도구 선택 ≥ 3/6(dev), `--retrieval-only` Hit@5 ≥ 10/20(dev)
- 70문항 / 6유형(차트형 10 포함), dev 35 / test 35. 질문 구성·채점 규칙·지표는 [[치과 AX - 평가 설계]] §3

**설계 근거**: 문서 청크가 통화·문자 청크보다 훨씬 적어 단일 RRF에서 묻힘 → **문서 버킷·사례 버킷 따로 검색** 후 리랭커. 모든 청크에 출처 prefix 의무(환자명 없이는 사례형 검색 불가). 차트 서술은 비식별(본문에 환자 이름 없음)이고 prefix는 `[차트 C-xxxxx | 날짜 | 시술]`처럼 차트 번호까지만 — 케이스 내용으로 찾고 차트 번호로 환자에 닿는다. 리랭커·임베딩 선택은 앱 설계 §7.

### ④ 진료 준비표 (MVP — `make gate` 통과 시 착수)

**목적**: 환자마다 EMR 여러 화면(기본정보·예약·진료기록·수납·청구·가족·주의사항)을 뒤지는 걸 코드가 조인해 한 행으로 모으고, LLM이 그날 할 일(관련 주의사항 처리 + 권할 진료)을 한두 줄로 묶는다. 둘 다 없으면 "그대로 진행".

**화면 (MVP)**: **가상 EMR 뷰어**(④ 착수와 함께, 개선 전, 읽기 전용 — 위 탭 6개. 한 환자를 보려면 탭을 옮겨 다녀야 하는 현재 모습을 그대로 보이고, 개발자 독자가 가상 데이터를 둘러보는 화면을 겸한다. README에 탭 이동 수 vs 준비표 1행) / **준비표**: 날짜 탭(최근 7일 + 오늘) + 칩 5개(**예약 · 보험 잔여(스케일링 미사용 성인) · 미수 잔액 · 가족 리콜 지남 · 주의**(그날 예정 시술과 관련된 주의사항 — 코드가 `master` 표로 정확히 표시)) + 환자 행 펼침(fact + 예정 시술 + 제안) + "다시 만들기". 제외: 복합 필터, "다음 진료일", "다른 치과 추정"

**API**
- `GET /prep?date=` / `POST /jobs/prep-regenerate?date=`(`facts_hash` 같으면 LLM 생략) / `POST /prep/{id}/rating`(`useful/ok/wrong`, `rated_by`)
- 집계는 순수 함수 `prep_facts(date)`. 출력 `{action: suggest|none, text, used_facts}` — `text`는 그날 할 일 요약(주의사항 처리 + 권할 진료), 둘 다 없으면 `none` = "그대로 진행"(후검증 실패의 `null`과 다름)
- 가상 EMR 뷰어 API는 앱 설계 반영 때(§9)

**완료 기준**
- 집계 회귀 테스트·제안 후검증(`suggestion_valid`)·사람 채점 — 규칙은 [[치과 AX - 평가 설계]] §4. 후검증 실패 시 null + 재시도
- **주의사항 반영률**: 주의 칩이 켜진 행 중 요약의 `used_facts`에 그 주의사항이 들어간 비율(규칙 채점, 사람 불필요) + 관련 없는 주의사항을 끌어온 과잉 언급률 — 정의는 [[치과 AX - 평가 설계]] §4
- 칩이 꺼진 행(항상 켜지는 예약 칩 제외)의 과잉 제안률(`suggest`인데 사람 채점 `wrong`) — 정의·`none`의 후검증 처리는 평가 설계 반영 때(§9)

**개선 루프**(선택 — ④ 완료 후 시간이 남으면. ② 개선 루프와 같은 틀): 표본 30행 밖에서 채점한 `wrong` 행을 모아 오류 유형을 나눔 → 제안 프롬프트 v2 → 같은 날짜 재생성 → 채점 비교. §8 결과의 채점 표본 30행은 튜닝에 쓰지 않는다(①의 dev/test와 같은 이유)

**설계 근거**: 주의사항 → 행동은 표로 정해져 있어 칩은 코드가 정확히 띄우고, LLM은 여러 사실(주의사항 여럿 + 예정 시술 + 미수·리콜)을 그날 행동으로 묶는 일만 한다(§3 원칙 2). 반영률은 그 요약이 관련 주의사항을 빠뜨리지 않는지 보는 안전망. `none`을 허용 — 매 행 제안을 강제하면 근거 약한 제안을 지어낸다. 출력을 `{action, text, used_facts}`로 강제 — 자유 문장에서 (키, 값) 역파싱은 불가능하므로 모델이 쓴 사실을 스스로 명시. 예정 시술은 `emr_appointments.planned_procedure_code`. 가족 리콜은 가족 구성원 `MAX(내원)+recall_cycle < sheet_date` 계산식. 치료계획·"다음 예약 없음" 칩은 프로젝트 후.

## 5. 슬롯 기능

- **⑤ 심평원 청구 점검·삭감 대응**(짧게 "청구 점검·삭감 대응", 건강보험 심평원 청구, 코드명 `claim_review` = 코드 주석의 "심사결과 슬롯"): 전자 심사결과를 받은 뒤 남는 일(조정 사유 해석·재심 판단·청구 누락)을 돕는다. 하위 기능 4개 — ⑤-2는 독립, 제출 월 조정은 ⑤-1 → ⑤-3 → ⑤-4(확정 월 조정은 장부에 이미 있어 ⑤-3부터). 지표는 [[치과 AX - 평가 설계]] §5, 데이터는 [[치과 AX - 가상 데이터 생성 설계]] 슬롯 메모
  - **⑤-1 전자 심사결과 대조 + 재심 기한**(코드, AI 없음): 전자 심사결과 레코드를 장부(`emr_claims`)와 대조 키로 맞춰 조정·불능·결과 누락(청구했는데 결과에 없음)·장부에 없는 줄을 모으고 재심 기한을 표시. 완료 기준: 심사결과 레코드에 심은 불일치(결과 누락·장부에 없는 줄·대조 키 어긋남 — 같은 줄인데 치아 번호·수가코드가 다르게 들어옴)의 대조 정확도(`truth_claims` 대비) + 재심 기한 테스트. 현장 인터뷰에서는 어긋남이 드물다고 했으나 대조 로직을 지표로 보이기 위해 심는다
  - **⑤-2 청구 전 점검**(규칙 + AI): 전월분(`pending`) 청구를 진료 기록·청구 기준과 대조해 누락·삭감 위험을 근거와 함께 표시(표시만 — §3). 급여 조건(나이·횟수 등)은 시술 표에 있어 규칙(SQL)이 점검하고, AI는 청구 기준 문서와 **차트 서술**을 읽어 임상 요건 근거(치석제거 뒤 치주치료 연결·치주 소견·같은 부위 재시행 사유 등)가 차트에 있는지 보고 근거를 단다 — 나이처럼 정형으로 판정되는 요건은 규칙 몫, 서술을 읽어야 하는 요건이 AI 몫. 가상 데이터에 심은 오류는 상병 착오·임상 요건형뿐이라 나이·횟수 규칙은 fixture 테스트([[치과 AX - 가상 데이터 생성 설계]] §2.4). **상병 확인 경고**(규칙): 시술 × 차트 상병이 `master` 허용 조합 밖이면 경고하고, 지난 조정에서 같은 조합이 상병 착오로 깎였으면 "지난달 이 조합으로 n건, ₩x 못 받음"을 붙인다 — 상병 착오는 재청구가 안 되니 미리 막는 게 유일한 방법. 완료 기준: "서술 있는 줄 전부" 기준선과 나란히 AI의 정밀도·재현율·근거 정확도(나이·횟수·단순 누락·코드 착오는 규칙 테스트)
  - **⑤-3 조정 사유 검색 + 다툴 만한지**(RAG — ③ 검색 구조 재활용): 조정 건(사유 범주 코드·일반사유 서술)으로, 또는 코드 없이 비고·질문으로 관련 청구 기준을 찾아 재심할 만한지와 근거(기준 절 + 그 진료의 차트 서술)를 제시, 최종 판단은 사람. 다툴 만함 = 차트에 요건 근거 있음(단 타 기관 이력으로 연 1회를 넘겨 깎인 스케일링은 차트가 정상이어도 정당). 답은 정당 / 다툴 만함 / 보완 후 재청구(정의는 [[치과 AX - 가상 데이터 생성 설계]] §2.4). 보완 후 재청구는 청구 때 빠뜨린 것(내역설명·증빙)을 채워 다시 내는 길이라, 채울 항목과 근거 차트 문장을 함께 보여 준다. 상병 착오는 재청구가 안 되므로 정당(현장 확인 2026-10-23). 상병 착오 건은 따로 강조(코드 표시): "재청구 불가 · 상병 착오" 배지 + 못 받은 금액 + 차트 상병 ↔ 시술 + "다음 청구 때 상병 확인" — 같은 조합은 ⑤-2 상병 확인 경고로 이어진다. 완료 기준: 상세 사유 → 기준 절 찾기 테스트, 코드 없이 묻는 청구 기준 질문의 Hit@5·MRR, 판단 정확도(3분류)
  - **⑤-4 재심 사유서 초안**(LLM): ⑤-3에서 다툴 만함으로 본 건만(보완 후 재청구는 재심이 아니라 보완해 다시 내는 길 — 현장 확인) → 조정 건 + 청구 기준 절 + 그 진료의 차트 기록으로 초안, 사람이 검토·수정·제출 결정(§3 원칙 1). 완료 기준: 초안이 인용한 기준 절·차트 문장이 실제로 있는지 후검증(③ 인용 확인·④ 후검증 재사용) + 사람 채점 표본
- **⑥ 경영 리포트 + ⑦ 아침 브리핑**: ④ 패턴 복제. 지난달 상병 착오 건수·못 받은 금액과 많이 틀린 시술 × 상병 조합 한 줄(숫자는 쿼리, 입력자별 집계는 하지 않음). 완료 기준: 본문 숫자 전부 `metrics`에 존재(④ 후검증 재사용)
- **⑧ 재무 대조 에이전트**: 현장의 일계표 확인(카드 전표·현금 입금 ↔ 프로그램 수납)을 옮긴 기능. 가상 통장·카드 거래 ↔ 장부(`emr_payments`) 대조는 코드(§3 원칙 2), 에이전트는 불일치 건마다 가설 → 조회 → 비교를 반복해 원인을 추적하고 그 과정을 보인다(③ 챗은 질문 하나에 짧은 도구 루프로 답만 — 조사 과정이 화면의 주인공인 것이 ⑧의 차이). 대조 단위: 카드는 승인 ↔ 장부 카드 수납, 입금은 승인 − 기준 수수료, 현금·이체는 통장 입금 ↔ 장부. 데이터는 슬롯 착수 시 설계 — 기존 `emr_*`는 수정하지 않는 추가 테이블, 불일치는 통장·카드 쪽에만 심음([[치과 AX - 가상 데이터 생성 설계]] §0), 심은 불일치의 원인 정답은 truth.sqlite에만. 원인은 고정 enum(§3 원칙 6 — 에이전트 출력·사람 확정·정답이 공유). 후보(통장·카드 쪽에 나타나는 모습): 장부에 없는 거래(수납 입력 누락) / 한 수납이 승인 여러 건(분할결제) / 입금이 승인 − 기준 수수료와 다름(수수료 차이). 확정은 슬롯 착수 시
  - **화면**: 날짜별 일계표(장부 합계 vs 통장·카드 합계) + 불일치 행 배지 → 행 펼침 = 조사 과정(도구 호출 순서·조회 조건·비교 결과) + 원인 후보·근거 + 사람 확정(`맞음 / 아님`, 아님이면 원인 enum 선택 — `ax_` 테이블, `ax_judgments`처럼 사람 라벨이라 앱 DB에 둔다). AI는 원인을 제안만, 장부 수정은 사람(§3 원칙 1)
  - **완료 기준**: 헤드라인은 원인 정확도(심은 불일치 전체 모수, 에이전트 원인 top-1 = 정답 enum). 탐지 재현율은 코드 대조라 테스트(심은 불일치 전부 탐지). 조사 단계 수는 상한(③처럼 호출 상한)을 두고 적을수록 좋음. 지표 세부는 평가 설계 반영 때(§9). 평가는 심은 정답(골드)만으로 하고, 사람 확정은 화면 흐름과 다음 프롬프트 개정의 재료(지표 아님)

## 7. 운영 결정

- 인증 없음. 상단 작업자 셀렉트(원장/데스크/상담실장)로 `judged_by`
- 토큰 스트리밍 없음. ③ 챗은 진행 이벤트 SSE, 배치(①·④)는 `ax_jobs` + 폴링
- `make save-demo` / `reset-demo`(서버 중지 → 파일 교체 → 재시작)
- 설정 변경은 CLI `make set KEY=… VALUE=…`(허용 키: `judge_upto`·`active_prompt_version`·`active_models`·`blind_versions`·`daily_usd_limit` — 기준일은 바꾸지 않음). 화면 없음

## 8. 최종 산출물

끝났을 때 보여 주는 것. 자동 지표는 조건별 test 1회 실행 결과(`truth_eval_runs` — [[치과 AX - 평가 설계]] §1 원칙 2), 사람 지표는 test 판정분(④ 사람 채점은 표본 30행 전체). 절대값보다 조건 간 차이가 주 지표(같은 §1 원칙 3).

**README 결과표**

| 기능 | 비교 | 지표 |
|---|---|---|
| ① 분류 | 프롬프트 v1 → v2 | 목적 Strict(헤드라인)·항목별 모델 vs 사람 일치율 |
| ① 분류 | v2 → v3-final (같은 프롬프트, 경량 → 상위 모델) | 목적 Strict(헤드라인)·항목별 모델 vs 사람 일치율 |
| ① 요약 | 프롬프트 v1 vs v2 (같은 모델) | 블라인드 승률 |
| ① 요약 | v2 vs v3-final (경량 → 상위 모델) | 블라인드 승률 |
| ③ 검색 | 리랭커 off → on | Hit@5·MRR·최신성(`--retrieval-only`) |
| ③ 챗 | 최종 조건 | 인용 정확도·도구 선택 정확도·환각 억제율 |
| ④ 준비표 | — | 제안 후검증 통과율, 주의사항 반영률·과잉 언급률, 사람 채점(칩 켜진 행 / 안 켜진 행), 과잉 제안률 |
| ④ 준비표 (선택) | 제안 프롬프트 v1 → v2 (개선 루프) | 사람 채점(표본 30행) |

- **증명하는 것**: AI가 쓴 분류·근거·숫자를 코드(후검증·인용 확인)와 사람 판정으로 검증하고, 조건 간 차이로 개선을 보여 준다
