> 가상 데이터로 개발하므로 외부 LLM API를 자유롭게 쓴다. 인프라·하드웨어·운영 비용은 범위 밖.
> 이 문서는 **무엇을 만드나**. 데이터 구조와 생성 규칙은 [[치과 AX - 가상 데이터 생성 설계]], 앱 테이블·도구·쿼리는 [[치과 AX - 앱 설계]], 지표·채점·정답 저장소는 [[치과 AX - 평가 설계]], 구현 규칙은 `CLAUDE.md`.

## 1. 조건

- 기간: 준비(문서·데이터셋 생성·평가셋·환경) → 개발 3~4주
- 인원: 1인 기준. 팀이 되면 슬롯을 사람별로 배분
- 목표: "AI 도구를 잘 다루는 개발자" 포트폴리오. 풀스택 직접 구현, 프론트를 일부러 줄이지 않음
- 스택: [[치과 AX - 앱 설계]] §7. Claude Code 설정(`CLAUDE.md`·`.claude/` — 구성은 `CLAUDE.md` 폴더)은 깃에 포함

## 2. 범위

| 구분 | 기능 | 한 줄 |
|---|---|---|
| 코어 | 가상 데이터 생성기 | 모든 기능의 토대. 정답 내장 |
| 코어 | ① 통화 요약·분류 | 모델 1개로 완성. 할 일 있는 통화는 후속 큐로(처리하면 빠짐). 모델 2개 교차검증은 확장(나중) |
| 코어 | ② 사람 판정 + 블라인드 비교 | "AI 검증"의 간판 화면. 키보드 UX. 업무 메뉴와 떨어진 "AI 평가" 메뉴 |
| 코어 | ③ 물어보기 (RAG 검색 + 챗 + 문서함) | 하이브리드 검색(문서·통화·문자·차트 케이스) + 도구 5개 에이전트 + 문서함(읽기 전용). 부트캠프 직결 |
| 코어 (MVP) | ④ 진료 준비표 | 가상 EMR 뷰어(개선 전) 대비 회의 보기·체어 보기. "코드 집계 → LLM 해석". `make gate` 통과 시 착수 |
| 슬롯 | ⑤ 청구 점검·삭감 대응 | 청구 전 점검(차트 기반 누락 포함)·조정 사유 판단(조정 목록·재심 기한)·재심 사유서 초안 |
| 슬롯 | ⑥ 경영 리포트 | ④ 패턴 복제 |
| 슬롯 | ⑦ 아침 브리핑 | 오늘 화면의 한 칸. ④ 패턴(코드 집계 → LLM 요약) |
| 슬롯 | ⑧ 재무 대조 | ⑧-1 수입 일계표 불일치 원인 추적(에이전트) + ⑧-2 지출 증빙 매칭·계정 과목 분류 |
| 슬롯 | ⑨ 후속 관리 | 리콜 연체·스케일링 급여 미사용·노쇼 이탈·미수·진료계획 미예약을 코드 점수로 순위화. 문자 초안은 선택 |
| 제외 | 메신저 / 방송 / 동의서 / 근태 / 음성봇·실시간 받아쓰기 / 상담 포털·음성 차팅 / 대기자 명단 | 범위 폭발, AI 비중 낮음, 또는 실제 전화·음성이 필요 |
| 제외 → 프로젝트 후 개인 확장 | 임플란트 평생 한도 | ④·⑨는 없이 성립 |

기능 번호는 이 표의 순서다(코어 ①~④, 슬롯 ⑤~⑨). 동그라미 숫자는 기능 번호에만 쓴다. 슬롯 착수 순서는 §9.

## 3. 공통 원칙

1. **AI는 읽고 제안만, 쓰는 건 사람.** 원본 장부·차트에 AI가 직접 쓰지 않음
2. **숫자는 코드, AI는 해석.** 매출·건수·잔액은 쿼리로. LLM 출력의 숫자는 입력 fact에 있는지 **후검증**
3. **교차검증(① 확장)은 구조화 출력(① 분류)에만.** 자유 텍스트(요약·제안·답변)는 diff가 안 되므로 블라인드 비교로
4. **LLM은 게이트웨이 모듈 하나로.** [[치과 AX - 앱 설계]] §7
5. **정답은 앱 DB 밖에.** 원본은 `CLAUDE.md` 절대 규칙
6. **구조화 출력.** 분류·추출은 JSON 스키마 + 고정 enum
7. **스펙 → 평가셋 → 구현.** "프롬프트 수정 전 N% → 후 M%"를 `prompt_version`으로 기록

## 4. 코어 기능

> 각 기능: 목적 / 화면 / API / 완료 기준 / 설계 근거(왜 이렇게 하는지만)

### 앱 구성

- **메뉴**: 오늘 / 통화 / 준비표 / 물어보기 / AI 평가 / EMR. 업무 메뉴(오늘·통화·준비표·물어보기)와 AI 평가(② 판정·블라인드·정확도)를 나눈다. EMR은 AX 전 병원 프로그램 모습을 보이는 별도 창(④)
- **오늘 화면**(첫 화면): 요약 카드 + **AI가 한 일**(분류·준비표 생성·색인 같은 배치 결과 — 끝남 / 사람에게 넘김 / 실패) + **사람이 볼 일**(급한 통화·후속 큐, 그날 주의 환자, 판정 대기, 문서에서 근거를 못 찾은 질문. 슬롯이 붙으면 재심 기한 임박·후속 관리·일계표 불일치) — 누르면 그 화면으로. 숫자는 전부 쿼리(§3 원칙 2). ⑦ 아침 브리핑은 이 화면의 한 칸. API `GET /today`
- **목록 화면 공통**: 마지막 갱신 시각, 칩마다 건수, 처리하면 목록에서 빠짐, AI 결과 옆에 근거(`used_facts`·`cited_ids`), 순위·기준이 있으면 "어떻게 정해지나" 설명
- **사용자**: 상단 사용자 선택(원장 / 데스크 / 상담실장) — §7

### 가상 데이터 생성기

**목적**: 미니 EMR + 비정형(통화·문서·문자) + 정답을 시드 재현 가능하게 생성. 산출물·규칙은 [[치과 AX - 가상 데이터 생성 설계]].

**완료 기준**: `make verify` 통과 + 결정성(같은 시드 2회 → 테이블 내용 해시 동일, LLM 캐시 포함)

### ① 통화 요약·분류

**목적**: 전사 1건 → 모델이 요약 + 분류 JSON + 할 일. 모델 1개로 시작하고, 두 번째 모델과 불일치 표시는 아래 확장.

**현실 구성과 대체**: 원본 사례(실제 동네 치과 AX 전환기 글)는 병원 자체 교환기(PBX)로 대표번호를 받아 녹음하고 통화 중 실시간 전사한다. 이 프로젝트는 실제 전화를 받을 수 없으므로 PBX·STT 구간을 **데이터로 대체**하고, 전사가 들어온 뒤부터 구현한다.

| 현실 | 이 프로젝트 |
|---|---|
| PBX 수신·녹음, 수신/발신 구분 | 가상 통화 전사(`ax_calls`, 생성 7단계) + `direction` |
| 통화 중 실시간 STT | 전사 텍스트 입력(붙여넣기 폼). 옵션: 샘플 녹음 → Whisper |
| AI 음성 1차 응대·모바일 앱 | 범위 밖 |
| 끊으면 요약·할 일 | ① 그대로 |
| "지난번에 뭐 물어봤지" 검색 | ③ 사례 버킷 |

분류기 입력이 전사와 방향뿐인 것(앱 설계 §1 — 정답 힌트 차단)은 PBX가 넘겨주는 정보(녹음 → 전사, 방향)와도 맞는다.

**화면**: 통화 목록 / **후속 큐**(모델 분류에서 할 일 있음인 통화 — 급함 먼저, 직원이 "처리함"을 누르면 빠지고 처리한 사람·시각이 남음) / 상세(전사 · 요약·분류·할 일) / 붙여넣기 폼(수신·발신, 기본 수신). 옵션: 샘플 녹음 → Whisper 전사 → 붙여넣기 폼

**API**
- `GET /calls`, `GET /calls/{call_uid}`
- `POST /calls/paste` → 분류 1행, 색인, 판정 큐 `pending`
- `POST /calls/{call_uid}/classify`(재시도) / `POST /jobs/classify-batch`(`in_eval_pool` 일괄, `ax_jobs`)
- `GET /calls/followups` / `POST /calls/{call_uid}/followup-done`
- `POST /calls/transcribe-sample/{n}`(옵션)

**완료 기준**
- E2E: 붙여넣기 → `ax_call_classifications` 1행 `ok`
- 판정 풀(`in_eval_pool`) 전체 행 `ok` (`active_prompt_version` 기준. 블라인드 풀은 판정 풀의 부분집합이라 별도 분류 없음)
- 후속 큐(pytest): `ok` 분류 중 할 일 있음인 통화만 나오고, 처리하면 빠짐
- 분류 스키마 enum은 [[치과 AX - 가상 데이터 생성 설계]] §4.1, 채점은 [[치과 AX - 평가 설계]] §2

**설계 근거**: 모델 2개·엇갈림 배지는 효용(일치 오류율·무작위 검토 대비 포착 향상)을 재기 전까지는 가설이라, 구조를 두 배로 짓기 전에 모델 1개로 코어를 완성한다. 분류기 입력 제한은 [[치과 AX - 앱 설계]] §1. 복수 주제 통화는 주 목적 1 + 불리언 플래그(생성 제약은 가상 데이터 생성 설계 §4.1, 채점은 평가 설계 §2.2). 후속 큐는 모델 분류를 그대로 믿고 움직이므로, 분류가 틀리면 할 일이 큐에서 빠진다 — ② 판정으로 분류를 재는 이유.

**확장 — 모델 2개 교차검증** (`make gate` 이후, 시간이 남으면): 모델 B를 붙여 A·B가 각각 분류하고, 9항목 중 하나라도 다르면 엇갈림 배지 → 판정 큐에서 핵심 엇갈림 먼저. 붙이는 방법: `active_models`에 B 추가 + 판정 풀 재분류(분류 테이블이 처음부터 모델별 행이라 스키마 변경 없음). 붙일 때 엇갈림 테이블(`(call_uid, prompt_version)` 1행, `is_core` = 목적·급함·응급 불일치)과 판정 큐 순서(핵심 엇갈림 먼저)를 앱 설계에 추가. 효용 지표는 [[치과 AX - 평가 설계]] §2.5

### ② 사람 판정 + 블라인드 비교

**목적**: 사람이 분류를 판정해 정답지를 만들고, 요약을 블라인드로 비교.

**화면**: **판정**(한 건씩. 전사 기본 노출. 항목마다 선택지 버튼을 모두 펼치고 숫자 키로 고름 — 목적 2자리·나머지 1자리 → 자동 다음 항목 → Enter 저장·다음 건. 위에 진행 현황 한 줄(오늘·누적 판정 수), 아래에 단축키 안내. 메모 칸(선택 — 애매한 이유, 기준이 필요한 경우. 단축키로 들어가고 Enter로 저장). 저장 뒤에만 모델 라벨을 보여 주고, 틀린 항목에 오류 유형 태그(선택, **`make gate` 이후** — 개선 루프 1회는 태그 없이 dev 덤프로 가능) — 개선 루프의 재료. 저장 전에 보이면 앵커링. 태그도 `export-human` 보존 대상) / **블라인드 탭**(두 프롬프트 버전 요약을 버전 가리고 — 기본 같은 모델 v1 vs v2, 최종 v2 vs v3-final → `1 / 2 / 비슷 / 둘 다 틀림`) / **정확도 표**(항목별 모델 vs 사람 일치율·블라인드 승률·좌우 선택 비율. 프롬프트 버전을 나란히 놓아 개선 추이를 보인다. 모수는 **dev 판정만** — [[치과 AX - 평가 설계]] §2.2. test 수치는 `eval.py --split test`에서만. 교차검증 효용은 화면 없이 `eval.py`만)

**API**
- `GET /judge/next` / `POST /judgments` / `POST /calls/{call_uid}/skip`
- `GET /blind/next` / `POST /blind-votes`
- `GET /metrics/accuracy?prompt_version=` / `GET /metrics/blind`
- `make export-human` / `import-human`(보존 키는 [[치과 AX - 앱 설계]] §7)

**완료 기준**
- Playwright(`make fixture` DB 또는 실데이터 복사본에서 — 진짜 판정 DB를 오염시키지 않게): 키 시퀀스 10회 → `ax_judgments` +10, 블라인드 5회 → `ax_blind_votes` +5
- 정확도 뷰 2개 SQL이 행 ≥ 9(pytest)

**개선 루프** — 사람 판정 → 오류 유형 → 사람이 프롬프트 개정 → 재측정 → 버전별 추이. 이 프로젝트가 보여 주려는 방향(사람 평가로 AI 성능을 올린다). **1회는 필수** (`make gate` 조건 아님 — §8 결과표 "프롬프트 v1 → v2"의 근거): dev 판정에서 모델이 틀린 건을 모아 오류 유형을 나눔(판정 화면의 태그, 메모 처리는 [[치과 AX - 평가 설계]] §2.3) → 유형별로 프롬프트 v2 수정(규칙 추가·few-shot) → 판정 풀 재분류 → 모델을 고정한 v1·v2 교집합 비교([[치과 AX - 평가 설계]] §2.2). 골드(`truth_call_labels`)는 프롬프트에 넣지 않는다(few-shot 규칙은 [[치과 AX - 평가 설계]] §7). README에 "오류 유형 → 수정 내용 → 수치 변화"를 한 표로. 사람 판정은 평가용 정답지이면서 개선 재료다 — 이 루프로 프롬프트가 바뀌고, 운영 중에는 사람의 판정(확장 시 엇갈림 건 우선)이 쌓여 다음 프롬프트 개정의 재료가 된다(자동 반영 없음). 판정은 `export-human`으로 보존돼 미세조정 재료가 되지만 미세조정은 범위 밖

**설계 근거**: 전사 기본 노출(모델 요약을 읽고 판정하면 정답지가 모델에 앵커링). 판정 풀·판정·블라인드 절차와 정확도 3종은 [[치과 AX - 평가 설계]] §2.

### ③ 물어보기 (RAG 검색 + 챗 + 문서함)

**목적**: 매뉴얼·공지·청구 기준·통화·문자·차트 기록을 하이브리드 검색, 도구 5개 단일 턴 에이전트가 "확인된 사실만" 답함.

**검색 대상** (현장 인터뷰에서 나온 질문 기준)

| 대상 | 예시 질문 | 버킷 |
|---|---|---|
| 업무 절차(직원 매뉴얼) | 틀니 수리 접수 절차, 구형 임플란트 부품 주문 | 문서 |
| 청구 기준·보험 안내 | 치석제거 다음 달로 넘어가면 치주치료가 왜 깎여? (청구 기준 질문은 ③ 질문 밖, ⑤ 평가셋) | 문서 |
| 원내 공지(최신성) | 바뀐 기준이 뭐였지 | 문서 |
| 통화·문자 사례 | 그 환자 지난번에 뭘 물어봤지 | 사례 |
| **차트 케이스** | 치석제거 뒤 치주치료로 이어진 환자는 간격·상병을 어떻게 적었지, 사랑니가 완전 매복이라 골삭제한 환자 | 사례 |
| 환자 사실 | 지난 스케일링이 언제였지, 이 환자 남은 치료가 뭐지 | 도구 `query_patient` |

차트 케이스는 "차트 검색이 환자 이름으로만 돼서 이름을 모르면 못 찾는다"는 인터뷰 고충에 대한 답 — 케이스 내용으로 찾고 결과에 차트 번호를 띄운다. 차트 기록 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §4.3.

**화면**: 메뉴 하나에 탭 `질문하기 | 기록 검색` — 입력한 내용은 탭을 바꿔도 유지, 챗 답변의 "근거 더 보기"는 같은 질문으로 기록 검색을, 검색 결과의 "이걸로 질문하기"는 챗을 연다. **질문하기**(질문 1 → 진행 이벤트 SSE → 답변 + 출처. 멀티턴 없음. 근거가 없으면 `refuse` → 고정 문구 "문서함에 없음") / **기록 검색**(`매뉴얼 결과` / `실제 사례 결과` 분리 + AI 요약 + 출처, 필터: 출처 종류·기간·환자번호) / **문서함**(매뉴얼·공지·FAQ·청구 기준 목록 — 공지는 최신 버전만·시행일 표시, 본문 보기, 읽기 전용). 챗이 문서에서 근거를 못 찾아 거절한 질문은 오늘 화면의 "사람이 볼 일"로 모인다

**API**
- `GET /search?q=&source_types=&date_from=&date_to=&chart_no=` → `{manual_results, case_results}`
- `POST /chat`(SSE 진행 + 최종 답변) → `ax_search_logs`
- `GET /documents` / `GET /documents/{id}`. 답 못 한 질문은 `GET /today`가 `ax_search_logs`에서 모음
- 도구 5개(시그니처는 앱 설계 §3): `search_docs`, `query_patient`, `query_schedule`, `query_claims`, `refuse`
- `make index` / `eval.py --split dev [--retrieval-only]` · `--split test --section …`([[치과 AX - 평가 설계]] §7)

**완료 기준**
- `eval.py --split dev` exit 0 + 리포트
- 데이터형 도구 선택 ≥ 1/2(dev), `--retrieval-only` Hit@5 ≥ 1/2(dev 문서 검색형 — 문항 수는 `verify.QA_TYPE_COUNTS`)
- 질문 구성(유형·수·dev/test)·채점 규칙·지표는 [[치과 AX - 평가 설계]] §3 — `make verify`가 문항 구성을 검사

**설계 근거**: 문서 청크가 통화·문자 청크보다 훨씬 적어 단일 RRF에서 묻힘 → **문서 버킷·사례 버킷 따로 검색** 후 리랭커. 모든 청크에 출처 prefix 의무(환자명 없이는 사례형 검색 불가). 차트 서술은 비식별(본문에 환자 이름 없음)이고 prefix는 `[차트 C-xxxxx | 날짜 | 시술]`처럼 차트 번호까지만 — 케이스 내용으로 찾고 차트 번호로 환자에 닿는다. 리랭커·임베딩 선택은 앱 설계 §7.

### ④ 진료 준비표 (MVP — `make gate` 통과 시 착수)

**목적**: 환자마다 EMR 여러 화면(기본정보·예약·진료기록·수납·청구·가족·주의사항)을 뒤지는 걸 코드가 조인해 한 행으로 모으고, LLM이 그날 할 일(관련 주의사항 처리 + 권할 진료)을 한두 줄로 묶는다. 둘 다 없으면 "그대로 진행". 아침 회의에서 오늘 전체를, 진료 중에는 체어 옆에서 지금 환자 한 명을 본다.

**화면 (MVP)**: **가상 EMR 뷰어**(④ 착수와 함께, 개선 전, 읽기 전용 — 위 탭에 치료계획·차트 기록·문자를 더한 메뉴. 한 환자를 보려면 메뉴를 옮겨 다녀야 하는 현재 모습을 그대로 보이고, 개발자 독자가 가상 데이터를 둘러보는 화면을 겸한다. README에 탭 이동 수 vs 준비표 1행) / **준비표 공통**: 날짜 탭(최근 7일 + 오늘, 날짜마다 인원수) + 기준 시각 + 칩 6개(**예약 · 보험 잔여(스케일링 미사용 성인) · 미수 잔액 · 가족 리콜 지남 · 주의**(그날 예정 시술과 관련된 주의사항 — 코드가 `master` 표로 정확히 표시) **· 남은 치료계획**(열린 계획 항목 중 그날 예정 시술이 아닌 것)) + 행 펼침(fact + 예정 시술 + 제안 + 근거) + "다시 만들기" / **회의 보기**(오늘 전체 — 시간 × 체어 예약표, 몰리는 시간대, 할 일 있는 환자 위주, 위생 / 진료 필터, 인쇄) / **체어 보기**(체어별 오늘 순서 + 지금 환자 한 장 — 주의사항을 가장 크게, 예정 시술, 제안. 시간이 되면 다음 환자로 — "지금"은 TODAY 날짜 + 실제 시계의 시:분). 제외: 칩 여러 개를 조합하는 필터, "다음 진료일", "다른 치과 추정"(⑨ 후속 관리 몫)

**API**
- `GET /prep?date=` / `POST /jobs/prep-regenerate?date=`(`facts_hash` 같으면 LLM 생략). 두 보기 모두 `GET /prep?date=`(행에 체어 번호 포함)
- 집계는 순수 함수 `prep_facts(date)`. 출력 `{action: suggest|none, text, used_facts}` — `text`는 그날 할 일 요약(주의사항 처리 + 권할 진료), 둘 다 없으면 `none` = "그대로 진행"(후검증 실패의 `null`과 다름)
- 가상 EMR 뷰어 API는 앱 설계 반영 때(§9)

**완료 기준**
- 집계 회귀 테스트·제안 후검증(`suggestion_valid`) — 규칙은 [[치과 AX - 평가 설계]] §4. 후검증 실패 시 null + 재시도
- 주의사항 반영률·과잉 언급률·과잉 제안률(칩이 꺼진 행 — 항상 켜지는 예약 칩 제외 — 인데 `suggest`) — 전부 코드 채점, 정의는 [[치과 AX - 평가 설계]] §4. `none`의 후검증 처리는 ④ 착수 때(§9)

**설계 근거**: 주의사항 → 행동은 표로 정해져 있어 칩은 코드가 정확히 띄우고, LLM은 여러 사실(주의사항 여럿 + 예정 시술 + 미수·리콜)을 그날 행동으로 묶는 일만 한다(§3 원칙 2). 반영률은 그 요약이 관련 주의사항을 빠뜨리지 않는지 보는 안전망. 제안은 사람이 채점하지 않는다 — 버전 비교·개선에 쓰이지 않는 절대값 하나만 남아 §8(조건 간 차이가 주 지표)과 맞지 않는다. `none`을 허용 — 매 행 제안을 강제하면 근거 약한 제안을 지어낸다. 출력을 `{action, text, used_facts}`로 강제 — 자유 문장에서 (키, 값) 역파싱은 불가능하므로 모델이 쓴 사실을 스스로 명시. 예정 시술은 `emr_appointments.planned_procedure_code`, 남은 치료계획은 치료계획 테이블([[치과 AX - 가상 데이터 생성 설계]] §2.3). "다음 예약 없음" 칩은 두지 않는다 — 예약이 없는 환자는 ⑨ 후속 관리가 맡는다.

## 5. 슬롯 기능

- **⑤ 심평원 청구 점검·삭감 대응**(짧게 "청구 점검·삭감 대응", 건강보험 심평원 청구, 코드명 `claim_review`): 심사결과는 청구 프로그램(전자차트)이 전자로 받아 장부에 반영돼 있다 — 장부와 심사결과가 어긋나는 일은 다루지 않고, 그 뒤에 남는 일(조정 사유 해석·재심 판단)과 청구 전 점검을 돕는다. 하위 기능 3개 — ⑤-2는 독립, 조정 건은 ⑤-3 → ⑤-4. 지표는 [[치과 AX - 평가 설계]] §5, 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §2.4·§4.2·§4.3
  - **⑤-2 청구 전 점검**(규칙 + AI): 전월분(`pending`) 청구를 진료 기록·청구 기준과 대조해 누락·삭감 위험을 근거와 함께 표시(표시만 — §3). 급여 조건(나이·횟수 등)은 시술 표에 있어 규칙(SQL)이 점검하고, AI는 청구 기준 문서와 **차트 서술**을 읽어 임상 요건 근거(치석제거 뒤 치주치료 연결·치주 소견·같은 부위 재시행 사유 등)가 차트에 있는지 보고 근거를 단다 — 나이처럼 정형으로 판정되는 요건은 규칙 몫, 서술을 읽어야 하는 요건이 AI 몫. 가상 데이터에 심은 오류는 상병 착오·임상 요건형·차트 기반 누락뿐이라 나이·횟수 규칙은 fixture 테스트([[치과 AX - 가상 데이터 생성 설계]] §2.4). **상병 확인 경고**(규칙): 시술 × 차트 상병이 `master` 허용 조합 밖이면 경고하고, 지난 조정에서 같은 조합이 상병 착오로 깎였으면 "지난달 이 조합으로 n건, ₩x 못 받음"을 붙인다 — 상병 착오는 재청구가 안 되니 미리 막는 게 유일한 방법. **차트 기반 누락**(AI): 차트 서술에 시행했다고 적힌 처치인데 진료 기록·청구에 없는 것을 근거 문장과 함께 표시 — 서술을 읽어야만 보여서 규칙으로는 찾을 수 없다. 완료 기준: "서술 있는 줄 전부" 기준선과 나란히 AI의 정밀도·재현율·근거 정확도 — 임상 요건형·차트 기반 누락 모두(나이·횟수·단순 누락·코드 착오는 규칙 테스트)
  - **⑤-3 조정 사유 검색 + 다툴 만한지**(RAG — ③ 검색 구조 재활용): **조정 목록**(코드) — 확정 월 조정 건(일부·전액)을 통보일·재심 기한(통보일 + `master.APPEAL_DAYS`, 남은 날 표시 — 기한 임박은 오늘 화면으로)과 함께 보인다. 조정 건(사유 범주 코드·일반사유 서술)으로, 또는 코드 없이 비고·질문으로 관련 청구 기준을 찾아 재심할 만한지와 근거(기준 절 + 그 진료의 차트 서술)를 제시, 최종 판단은 사람. 답은 정당 / 다툴 만함 / 보완 후 재청구(정의는 [[치과 AX - 가상 데이터 생성 설계]] §2.4). 보완 후 재청구는 청구 때 빠뜨린 것(내역설명·증빙)을 채워 다시 내는 길이라, 채울 항목과 근거 차트 문장을 함께 보여 준다. 상병 착오 건은 따로 강조(코드 표시): "재청구 불가 · 상병 착오" 배지 + 못 받은 금액 + 차트 상병 ↔ 시술 + "다음 청구 때 상병 확인" — 같은 조합은 ⑤-2 상병 확인 경고로 이어진다. 완료 기준: 상세 사유 → 기준 절 찾기 테스트, 코드 없이 묻는 청구 기준 질문의 Hit@5·MRR, 판단 정확도(3분류)
  - **⑤-4 재심 사유서 초안**(LLM): ⑤-3에서 다툴 만함으로 본 건만 → 조정 건 + 청구 기준 절 + 그 진료의 차트 기록으로 초안, 사람이 검토·수정·제출 결정(§3 원칙 1). **추측 목록**: 초안의 모든 문장은 기준 절·차트 문장 인용이거나 추측 목록(`assumptions[]`)에 올라야 한다 — 둘 다 아닌 문장이 있으면 후검증 실패. 화면은 초안 + 추측 칸 + "검토 확인" 체크 뒤에만 "제출 결정". 완료 기준: 초안이 인용한 기준 절·차트 문장이 실제로 있는지 후검증(③ 인용 확인·④ 후검증 재사용) + 인용도 추측 표시도 없는 문장 비율
- **⑥ 경영 리포트**: ④ 패턴 복제. 지난달 상병 착오 건수·못 받은 금액과 많이 틀린 시술 × 상병 조합 한 줄(숫자는 쿼리, 입력자별 집계는 하지 않음). 완료 기준: 본문 숫자 전부 `metrics`에 존재(④ 후검증 재사용)
- **⑦ 아침 브리핑**: 오늘 화면의 한 칸. 그날 예약 수·신환·몰리는 시간대·주의 환자 수 같은 숫자는 쿼리, LLM은 몇 문장으로 묶기만 한다. 완료 기준: 본문 숫자 전부 입력에 존재(④ 후검증 재사용)
- **⑧ 재무 대조**: 데이터는 `fin_` 테이블, 장부 실수는 `emr_payments`에 생성 단계에서 심는다([[치과 AX - 가상 데이터 생성 설계]] §2.4·§2.7). 정답은 truth.sqlite에만. 원인·계정 과목은 고정 enum(§3 원칙 6 — 에이전트 출력·사람 확정·정답이 공유)
  - **⑧-1 수입 일계표 대조**(에이전트): 현장의 일계표 확인을 옮긴 기능. 장부(`emr_payments`) ↔ 카드 승인·정산 입금·통장 입금 대조는 코드(§3 원칙 2). 에이전트는 불일치마다 가설 → 조회(그날 내원, 미수 잔액, 다음 날 장부, 구강용품 가격표, 가족) → 비교를 반복해 원인을 고르고 그 과정을 보인다(③ 챗은 질문 하나에 짧은 도구 루프로 답만 — 조사 과정이 화면의 주인공인 것이 ⑧-1의 차이). 원인은 통장·카드 쪽과 장부 쪽(목록과 묶음은 [[치과 AX - 평가 설계]] §5), 근거가 부족하면 `unknown`
    - **화면**: 날짜별 일계표(결제수단별 장부 합계 vs 금융 합계) + 불일치 행 배지 → 펼침 = 조사 과정(도구 호출 순서·조회 조건·비교 결과) + 원인 후보·근거 + 사람 확정(`맞음 / 아님`, 아님이면 원인 선택 — `ax_` 테이블, 사람 라벨이라 앱 DB). 장부 수정은 사람(§3 원칙 1)
    - **완료 기준**: 원인 정확도(top-1)를 규칙 기준선과 나란히, "규칙으로 되는 원인 / 애매한 원인" 두 묶음으로. 탐지 재현율은 코드 대조라 테스트. 조사 단계 수 상한(③처럼 호출 상한). 사람 확정은 지표가 아니라 화면 흐름과 프롬프트 개정 재료. 지표 세부는 [[치과 AX - 평가 설계]]
  - **⑧-2 지출 증빙·계정 분류**(AI): 통장 출금·병원 카드 사용을 증빙(거래명세서·세금계산서·주문 메일·영수증·고지서)과 맞추고(1:1, 거래처 월말 이체는 1:N 합계), 계정 과목을 확신도와 함께 추천한다. 못 찾으면 "증빙 없음". 급여·공단 입금은 대상이 아니다
    - **화면**: 미매칭 목록(계좌·카드별 건수·금액) + 행마다 찾은 증빙·금액 차이·추천 계정 과목 → 사람 확정(`ax_`). 확정한 거래처는 다음부터 기본값
    - **완료 기준**: 매칭 정확도·계정 과목 정확도를 규칙 기준선(금액·날짜만으로 맞추기)과 나란히
- **⑨ 후속 관리**: 예약 없이 놓친 환자를 칩별 목록 + 코드 점수 순위로 보인다
  - **칩**: 리콜 연체 · 올해 스케일링 급여 미사용 · 노쇼 뒤 재예약 없음 · 미수 잔액 · 진료계획 미예약 · 다른 치과 추정(타 기관 이력·연락 무응답)
  - **순위**: 코드 점수(마지막 방문, 최근 연락, 다른 치과 흔적 감점 등 — 규칙과 값은 앱 설정, [[치과 AX - 앱 설계]] §8). 화면에 "순위는 어떻게 정해지나요?" 설명. 예약이 잡히면 자동으로 빠짐. 필터: 1순위만 · 연락함 숨기기
  - **문자 초안**(LLM, 선택): 큰 계획은 "가장 급한 것 하나부터". 숫자는 ④ 후검증 재사용
  - **완료 기준**: 칩별 목록·점수 회귀 테스트(코드), 다른 치과 추정의 정밀도·재현율(정답은 이탈·병행 — [[치과 AX - 평가 설계]] §5 ⑨), 문자 초안을 넣으면 후검증 통과율

## 7. 운영 결정

- 인증 없음. 상단 사용자 선택(원장 / 데스크 / 상담실장)으로 `judged_by`와 처리한 사람(후속 큐 처리, ⑧ 확정)을 남긴다
- 토큰 스트리밍 없음. ③ 챗은 진행 이벤트 SSE, 배치(①·④)는 `ax_jobs` + 폴링
- `make save-demo` / `reset-demo`(서버 중지 → 파일 교체 → 재시작)
- 설정 변경은 CLI `make set KEY=… VALUE=…`(허용 키: `judge_upto`·`active_prompt_version`·`active_models`·`blind_versions`·`daily_usd_limit` — 기준일은 바꾸지 않음). 화면 없음
- 배포: 로컬 `docker compose` + 녹화 영상. 공개 필요 시 볼륨 있는 단일 서버
- LLM 실패는 `failed` 기록 + 재시도 버튼
- **비용** (비용의 원본은 여기): 튜닝 중 경량 모델, 데모 직전 1회만 상위 모델(모델은 [[치과 AX - 앱 설계]] §7·`config/llm.yaml` — 비용, 그리고 상위 모델은 튜닝 대상이 아니라 최종 구성 = test 1회 구성 — [[치과 AX - 평가 설계]] §1 원칙 2). 튜닝 중 상위 모델로 dev 약 30건만 돌려 출력 형식·실패율만 점검할 수 있다(별도 버전, 집계에서 제외). 생성기 1회 $30~60(전사·문서·차트 서술 — 모델은 [[치과 AX - 앱 설계]] §7), 런타임 3주 $40~100(추정 — 첫 실행 때 재추정). 하드리밋 런타임 $15/일, 생성기 $40/일(`config/llm.yaml` `daily_usd_limit`이 같은 값 — 앱의 `ax_settings.daily_usd_limit`은 그날만 올리는 값)

## 8. 최종 산출물

끝났을 때 보여 주는 것. 자동 지표는 조건별 test 1회 실행 결과(`reports/eval_runs.jsonl` — [[치과 AX - 평가 설계]] §1 원칙 2), 사람 지표는 test 판정분. 절대값보다 조건 간 차이가 주 지표(같은 §1 원칙 3).

| 기능 | 비교 | 지표 |
|---|---|---|
| ① 분류 | 프롬프트 v1 → v2 | 목적 Strict(헤드라인)·항목별 모델 vs 사람 일치율 |
| ① 분류 | v2 → v3-final (같은 프롬프트, 경량 → 상위 모델) | 목적 Strict(헤드라인)·항목별 모델 vs 사람 일치율 |
| ① 요약 | 프롬프트 v1 vs v2 (같은 모델) | 블라인드 승률 |
| ① 요약 | v2 vs v3-final (경량 → 상위 모델) | 블라인드 승률 |
| ③ 검색 | 리랭커 off → on | Hit@5·MRR·최신성(`--retrieval-only`) |
| ③ 챗 | 최종 조건 | 인용 정확도·도구 선택 정확도·환각 억제율 |
