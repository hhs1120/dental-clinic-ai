> 가상 데이터로 개발하므로 외부 LLM API를 자유롭게 쓴다. 인프라·하드웨어·운영 비용은 범위 밖.
> 이 문서는 **무엇을 만드나**. 데이터 구조와 생성 규칙은 [[치과 AX - 가상 데이터 생성 설계]], 앱 테이블·도구·쿼리는 [[치과 AX - 앱 설계]], 지표·채점·정답 저장소는 [[치과 AX - 평가 설계]], 구현 규칙은 `CLAUDE.md`.

## 1. 조건

- 인원: 1인 기준. 팀이 되면 슬롯을 사람별로 배분
- 목표: "AI 도구를 잘 다루는 개발자" 포트폴리오. 풀스택 직접 구현, 프론트를 일부러 줄이지 않음
- 스택: [[치과 AX - 앱 설계]] §7. Claude Code 설정(`CLAUDE.md`·`.claude/` — 구성은 `CLAUDE.md` 폴더)은 깃에 포함

## 2. 범위

| 구분 | 기능 | 한 줄 |
|---|---|---|
| 코어 | 가상 데이터 생성기 | 모든 기능의 토대. 정답 내장 |
| 코어 | ① 통화 요약·분류 | 모델 2개 교차검증으로 완성. 할 일 없는 통화는 자동 종결, 할 일 있는 통화는 후속 에이전트의 처리안과 함께 통화 화면 "오늘 할 일"로(끝내면 빠짐) |
| 코어 | ② 판정·자동 개선 + 블라인드 비교 | "AI 검증"의 간판 화면. 판정기가 1차, 사람은 엇갈림·표본과 골드 점검 표본. 프롬프트 개선은 관문을 넘어야 반영. 키보드 UX. 업무 메뉴와 떨어진 "AI 평가" 공간 |
| 코어 | ③ 물어보기 (RAG 검색 + 챗 + 문서함) | 하이브리드 검색(문서·통화·문자·차트 케이스) + 도구 6개 에이전트 + 문서함(읽기 전용) + 빠진 문서 초안 에이전트. 부트캠프 직결 |
| 코어 (MVP) | ④ 진료 준비표 | 전환 전 EMR 대비 준비표·체어 보기. "코드 집계 → LLM 해석". 주의 환자 야간 조사 에이전트는 운영 에이전트 때(§9) |
| 슬롯 | ⑤ 청구 점검·삭감 대응 | 청구 전 점검(차트 기반 누락 포함)·조정 사유 판단(조정 목록·재심 기한)·재심 사유서 초안. 판단은 사유 유형 규칙 제안 + 요건 사유는 ⑤-2 AI, 근거는 ⑤-3 검색·차트 문장 고르기 |
| 슬롯 | ⑥ 경영 리포트 | 월간·주간·일간 운영 숫자 + 상병 착오. 인건비가 들어간 손익은 `[추정]`. ④ 패턴(코드 집계 → LLM 해석) + 튄 숫자 원인 조사 에이전트 |
| 슬롯 | ⑦ 아침 브리핑 | 오늘 화면의 한 칸. ④ 패턴(코드 집계 → LLM 요약). 입력에 운영 에이전트의 밤사이 결과 포함 |
| 슬롯 | ⑧ 재무 대조 | ⑧-1 수입 일계표 불일치 원인 추적(에이전트) + ⑧-2 지출 증빙 매칭·계정 과목 분류(증빙 탐색 에이전트가 규칙이 못 푼 건을 찾고 푼 건을 검산). 조건을 넘은 건은 자동 처리 |
| 슬롯 | ⑨ 미예약 환자 | 다시 올 이유(리콜 연체·스케일링 급여 미사용·노쇼 이탈·미수·진료계획 미예약·다른 치과 추정)가 있는데 예약이 없는 환자를 코드 점수로 순위화. 근거 찾기는 에이전트, 문자 작성은 LLM, 의료·금액 내용이 없는 안내는 발송함 자동 기록(AI 부분은 2단계 — §5 ⑨) |
| 공통 | 에이전트 하네스 | 상태·도구 실행·피드백 루프·제약·재발 방지. 모든 에이전트가 쓴다 |
| 공통 | 운영 에이전트 | 코드 스케줄러가 밤에 깨우면 조사 우선순위를 정하고 기능 에이전트를 부르며, 기능별 신호를 환자 단위로 묶는다 |
| 제외 | 메신저 / 방송 / 동의서 / 근태 / 음성봇·실시간 받아쓰기 / 상담 포털·음성 차팅 / 대기자 명단 | 범위 폭발, AI 비중 낮음, 또는 실제 전화·음성이 필요 |
| 제외 → 프로젝트 후 개인 확장 | 임플란트 평생 한도 | ④·⑨는 없이 성립 |

기능 번호는 이 표의 순서다(코어 ①~④, 슬롯 ⑤~⑨). 공통 항목에는 번호가 없다. 동그라미 숫자는 기능 번호에만 쓴다. 슬롯 착수 순서는 §9.

## 3. 공통 원칙

**용어**
- **에이전트**: LLM이 도구를 쓰며 다음 단계를 스스로 정하는 시스템. 코드가 정한 경로로 돌면 **워크플로**다. 사람 확인이 있는지와는 별개다
- **하네스**: 모델이 아닌 코드·설정·실행 로직 전부. 상태·도구 실행·피드백 루프·제약을 붙여 모델이 일하게 하고, 실수가 나면 같은 실수를 못 하게 환경을 고친다. 앱에서는 에이전트 하네스(§4)·LLM 게이트웨이·프롬프트·설정·평가 하네스(`evaluation/`)가 여기에 든다

| 기능 | 에이전트 | 워크플로·코드 |
|---|---|---|
| ① 통화 | 후속 처리 | 분류·요약 함수, 엇갈림, 자동 종결 조건 |
| ② 판정 | 개선 | 판정기(모델 B, 도구 없음)·쌍 비교 판정기·골드 점검 중재, 사람 판정, 관문, 블라인드 집계 |
| ③ 물어보기 | 챗, 문서 초안 | 색인·검색 |
| ④ 준비표 | 주의 환자 조사(운영 에이전트 때, §9) | 칩 집계, 제안 후검증 |
| ⑤ 청구 | 없음 | 규칙 점검·사유 유형 판단 제안, ⑤-2 차트 판정, ⑤-3 근거 문장 고르기, ⑤-4 초안 후검증 |
| ⑥ 리포트 | 튄 숫자 조사 | 숫자 쿼리, 문장화 |
| ⑦ 브리핑 | 없음 | 숫자 쿼리, 요약 |
| ⑧ 재무 | 원인 추적, 증빙 탐색 | 대조 계산, 규칙 매칭 |
| ⑨ 미예약 환자 | 근거 찾기 | 칩·점수·순위, 문자 후검증 |
| 공통 | 운영 | 스케줄러, 자동 처리 정책 |


1. **원본에 쓰는 건 사람, 자동 처리는 `ax_`까지.** 원본 장부·차트에 AI가 직접 쓰지 않음. 일은 세 단계로 나눈다
   - **자동 처리**: ① 자동 종결 조건을 넘은 통화 종결, ⑧-1 규칙 묶음 불일치 마감, ⑧-2 일치하는 지출 확정, ⑨ 의료·금액 내용이 없는 안내의 발송함 기록(2단계, 건별 조건은 §4 ①·§5 ⑧·⑨). 사람은 예외와 표본을 보고 되돌릴 수 있다. 작업 종류마다 dev 오류율이 기준 이하이고 입력 신뢰 경계 위반이 0건일 때 사람이 켠다(`auto_policy`)
   - **사람 확인**: ① 자동 종결되지 않은 통화, ⑧-1 자동 마감되지 않은 불일치, ⑧-2 자동 확정되지 않은 지출, ⑤ 재심 여부, ③ 문서 초안 게시, ⑨ 미수 안내·치료 권유 문자(2단계)
   - **자동화 안 함**: 차트 기록, 청구·재심 제출, 처치 판단, 장부 수정
2. **숫자는 코드, AI는 해석.** 매출·건수·잔액은 쿼리로. LLM 출력의 숫자는 입력 fact에 있는지 **후검증**. 가정값이 들어간 숫자와 AI의 추정 문장은 `[추정]`으로 따로 표시
3. **교차검증은 구조화 출력(① 분류)에만.** 자유 텍스트(요약·제안·답변)는 diff가 안 되므로 블라인드 비교로
4. **LLM은 게이트웨이 모듈 하나로.** [[치과 AX - 앱 설계]] §7
5. **정답은 앱 DB 밖에.** 원본은 `CLAUDE.md` 절대 규칙
6. **구조화 출력.** 분류·추출은 JSON 스키마 + 고정 enum
7. **스펙 → 평가셋 → 구현.** "프롬프트 수정 전 N% → 후 M%"를 `prompt_version`으로 기록
8. **조사는 에이전트, 고정 산출은 워크플로.** 찾아볼 곳이 건마다 달라지는 일은 LLM이 경로를 정한다. 숫자 계산·① 분류·④ 집계처럼 결과가 고정돼야 하는 부분은 코드 경로로 둔다. 에이전트는 규칙이나 고정 흐름과 나란히 재고, 못 이기면 그 결과를 그대로 보고하고 기준선으로 돌린다
9. **개선은 자동, 기준은 사람.** 오류 분석·프롬프트 후보·재측정은 자동으로 돌고, 관문을 넘은 후보는 대기 버전이 된다. 전환은 사람이 재분류를 실행해 끝날 때 일어난다. 관문 기준 수정, 프롬프트 밖 변경의 승인, test 실행은 사람만 한다([[치과 AX - 평가 설계]] §2.7)
10. **실수는 환경을 고친다.** 사람이 되돌리는 것으로 끝내지 않고 재현 테스트와 훅·정책·도구로 남겨 같은 실수를 구조로 막는다

## 4. 코어 기능

> 각 기능: 목적 / 화면 / API / 완료 기준 / 설계 근거(왜 이렇게 하는지만)

### 앱 구성

- **시작 화면**: 카드 4개로 갈라진다 — 사내 포털(오늘) · 물어보기 · AI 평가 · 전환 전 EMR. 메뉴바 없음
- **일별 예약표**(읽기 전용, AI 없음): 사내 포털에서 지난 예약과 앞으로의 예약을 날짜별로 본다. 기본은 오늘이다. 가로는 진료 담당자(원장·위생사·상담실장), 세로는 시간이고 카드에 시각·환자·시술·소요 시간을 보인다. 카드 높이는 소요 시간만큼이고, 같은 담당자의 겹치는 예약(원장의 동시 진료)은 나란히 놓는다. "내원 확인 전" 배지는 기준일 예약에만 붙인다(앞날 예약은 확인 문자 전이다). 신환은 "신환" 배지. 취소·노쇼는 기본으로 숨기고 체크하면 보인다. 빈 시간은 빈칸으로만 보이고 추천하지 않는다. 앞 예약이 이어지는 칸은 빈칸과 구분한다. 진료 종류 예약의 `상담` 시술(응급 내원의 원장 진찰)은 `진찰`로 보인다 — 상담실장 상담과 헷갈리지 않게. 예약을 누르면 옆 패널(환자 요약 카드)이 나온다 — 이 예약(시각·시술·담당자·치료계획 몇 번째와 남은 항목·상태(완료·취소·노쇼만 — 예정은 표시하지 않음)·신환, 예약 확인은 직전 진료일 리마인드 기준 — 답이 없으면 "예약 확인 문자 무응답", 리마인드가 없으면 "내원 확인 전 · 문자 발송 시각이 지난 뒤 잡힌 예약"), 어떻게 잡혔나(전화·데스크, 잡은 시각, 잡은 통화·응급 여부), 이 환자의 일정(마지막 내원·앞으로의 예약·최근 1년 노쇼·취소), 연락(전화·보호자), 주의사항·미수 배지, "전자차트 열기"(그 환자의 전환 전 EMR 전자차트). 환자 사실은 고른 날짜가 아니라 기준일 기준이다. 같은 환자의 통화 시각이 예약을 잡은 시각과 같으면 그 통화로 잇고, ① 분류가 있으면 그 통화의 응급 여부를 AI 표시와 함께 보인다(판정 풀 통화는 연결만 하고 분류는 보이지 않는다 — ①과 같은 규칙). ① 전에는 "분류 전". 예약을 잡고 바꾸는 일은 EMR 몫이다. API는 [[치과 AX - 앱 설계]] §9
- **메뉴**: 업무 화면만, 이 순서로 — 오늘 / 예약 / 준비표 / 통화 + 슬롯(미예약 환자 / 청구 점검 / 재무 대조 / 경영 리포트). 슬롯은 구현 범위 구분이고 화면에는 구분을 표시하지 않는다. 물어보기(③)는 메뉴에 넣지 않고 아래 물어보기 창으로 닿는다
- **물어보기 창**: 업무 화면과 AI 평가 오른쪽 아래에 떠 있는 둥근 "물어보기" 버튼 — 물어보기 화면(`/ask`)과 전환 전 EMR에는 없다. 화면 아래에 버튼 높이만큼 여백을 둬 마지막 줄·더보기를 가리지 않는다. 누르면 오른쪽에 질문 창(좁은 화면에서는 전체)이 열리고 왼쪽 화면은 어둡게 하지 않고 그대로 쓴다. 창 안은 ③ 질문하기와 같다(단일 턴). X·Esc(창 안에서)로 닫고, 메뉴를 옮겨도 열린 채 남는다. 닫거나 물어보기 화면에 다녀와도 쓰던 질문·답·입력은 남고, 창에서 친 키는 화면 단축키(AI 평가의 숫자·Enter)로 가지 않는다. 인쇄에는 버튼·창이 나오지 않는다. 창은 화면과 옆 패널(통화 상세 등) 위에 놓이고, 확인 창(대화 상자)만 창 위에 뜬다 — 확인 창을 닫으면 창은 그대로다. 창 위의 "전체 화면으로"는 물어보기 화면 질문하기 탭으로 가서 마지막 질문·답·출처를 모델을 다시 부르지 않고 저장된 기록으로 보인다(`/ask?tab=chat&log=<id>` — 답을 기다리는 동안은 꺼지고, 마지막 질문이 실패했으면 빈 질문하기 탭을 연다). 창 안 출처 카드의 문서는 창이 아니라 물어보기 화면 문서함에서 연다
- **별도 공간**: AI 평가(② 판정·블라인드·정확도·자동 개선)와 전환 전 EMR(④)은 메뉴에 넣지 않는다. 들어가면 메뉴 자리에 공간 이름과 돌아가기가 나오고, 돌아가기는 들어오기 전 화면으로 간다. AI 평가는 시작 화면과 오늘 화면의 판정 대기에서, EMR은 시작 화면·일별 예약표 패널·환자 이름에서 들어간다
- **표시 세 종류**: AI가 만듦(`AI` 배지 + 보라 바탕) / 코드가 계산(표시 없음) / 사람이 정함(`확정`). 숫자·칩에는 배지를 붙이지 않는다 — 다 붙이면 구분이 사라진다
- **오늘 화면**(사내 포털의 첫 화면): 요약 카드(오늘 예약·신환·주의 환자·오늘 할 일) → **사람이 볼 일**(급한 것부터 — 급한 통화 전부, 확인할 통화, 내원 확인 전(환자가 오겠다고 답하지 않은 오늘 예약 — 확인 전화), 주의 환자, 남은 통화 할 일, 엇갈림·표본 판정 대기, 근거 없는 질문, 미예약 환자 화면 링크, 재심 신청 기한 임박, 청구 전 상병 경고, 청구 전 요건 근거 못 찾음(AI), 일계표 불일치, 지출 증빙 확인. 운영 에이전트가 붙으면 묶은 환자. 0건인 줄은 숨기고 모두 0이면 "오늘 남은 일이 없습니다". 예외: 미예약 환자 줄은 숫자 없는 고정 링크라 늘 보인다 — 숫자를 두면 오늘 화면이 미예약 목록 전체를 계산해야 한다) → **AI가 한 일**(한 줄 요약 + 펼치기) — 누르면 그 화면으로. 숫자는 전부 쿼리(§3 원칙 2)이고 그 숫자가 가리키는 화면과 같은 함수로 센다(`backend/today.py`). 준비표와 겹치는 것은 숫자와 이동만 둔다. 이 화면에서는 일을 처리하지 않는다(예외: 자동 처리 다시 열기). 역할별 보기 없이 모두 같은 화면. ⑦ 아침 브리핑은 이 화면의 한 칸. API `GET /today`, `POST /auto-actions/{id}/revert`
  - **확인할 통화**: 판정 풀 밖 통화 중 사람이 일이 남았다고 표시했는데(자동 종결을 다시 열었거나 사람 판정이 할 일·응급·불만·급함을 켬) 통화 화면 오늘 할 일에 뜨지 않는 통화 — AI 할 일 목록이 비었거나 오늘 할 일 창(`backend/calls.py` `TODAY_WINDOW_DAYS`) 밖. 날짜 제한 없음. 활성 분류가 실패한 통화는 여기 대신 AI가 한 일의 분류 실패로 센다. 문구는 `AI: 종결, 사람: 다시 열림` / `AI: 할 일 없음, 사람 판정: 응급·불만` / `AI: 할 일 있음(지난 통화), 사람 판정: 급함` 꼴(항목 이름은 `GET /labels`, 순서 응급 → 급함 → 불만 → 할 일 있음, 둘 다 해당하면 사람 판정 쪽 한 줄). 통화 상세의 **확인함**(`POST /calls/{call_uid}/check`)을 누를 때까지 남고, 확인 뒤 사람 판정이나 다시 열기가 새로 생기면 다시 뜬다
  - **근거 없는 질문**: 물어보기에서 문서 근거를 못 찾아 거절된 질문(챗·검색 요약, 평가 실행 제외, 비공개 정보라 거절한 챗은 뺌) 중 최근 `backend/today.py` `REFUSED_DAYS`일(실제 시계) — 확인함 없이 지나면 빠진다. 누르면 질문하기 입력칸에 질문만 채운다(실행하지 않음, `/ask?tab=chat&draft=`). 문서 초안 에이전트가 생기면 초안을 붙인다
  - **AI가 한 일**: 요약 `자동 처리 N건 · 오늘 준비표 N행 · 실패 n`(자동 종결 정책이 꺼져 있으면 "자동 종결 꺼짐"). 자동 처리는 통화 화면과 같은 유효 조건(① 완료 기준 "자동 종결") — 요약 숫자는 지금 닫혀 있는 통화 전부, 펼친 목록은 최근 닫힌 순 `backend/today.py` `AUTO_RECENT`건과 통화 기록 전체 보기, 건마다 이유·시각·**다시 열기**(다시 연 통화는 확인할 통화로 간다). 결과 줄은 결과 표에서 센다 — 오늘 준비표 행·제안·후검증 실패, 통화 분류 실패(분류 행 없이 남은 새 통화 포함), 처리안 실패(실패 0이면 끝남, 아니면 사람에게 넘김). 끝난 시각과 "실패" 꼬리표는 `make nightly`의 `ax_jobs` 때
- **목록 화면 공통**: 마지막 갱신 시각, 칩마다 건수, 처리하면 목록에서 빠짐, AI 결과 옆에 근거(`used_facts`·`cited_ids`), 순위·기준이 있으면 "어떻게 정해지나" 설명
- **담당 파트**: 상단 파트 선택(원장 / 데스크 / 상담실장) — §7. 고른 파트에 따라 화면이 바뀌지 않는다

### 에이전트 하네스

**목적**: 모든 에이전트가 같은 틀로 돈다. 구성은 다섯 축이다.

| 축 | 내용 |
|---|---|
| **상태** | 실행과 단계(도구·인자·결과·판단)를 전부 남겨 화면에 보인다. 끊긴 야간 실행은 마지막 단계부터 이어 간다. 도구 결과는 크기 상한에서 자르고 잘린 사실을 표시하며, 운영 에이전트는 기능 에이전트의 요약만 받는다 |
| **도구 실행** | 이름·인자·권한을 등록한다. 읽기 도구는 `source.sqlite`·`app.sqlite`, 쓰기 도구는 `ax_` 테이블만 |
| **피드백 루프** | 실행 후 훅이 공통 후검증을 돌린다. 판정·표본·관문·재생 테스트가 결과를 다음 수정으로 잇는다 |
| **제약** | 에이전트별 호출·비용 상한(넘으면 사람에게 넘김), 실행 전 훅의 권한·금지 도구·입력 제한 검사, 같은 자동 처리는 한 번만. 녹취록·문자·문서·차트와 도구 결과는 데이터로만 다루고 그 안의 지시를 따르지 않는다. LLM은 자동 처리를 요청만 하고 코드가 `auto_policy`와 건별 조건으로 허용하며, 허용된 건은 이유와 함께 기록해 되돌릴 수 있다 |
| **재발 방지** | 자동 처리 되돌리기·훅 차단·표본 오류·관문 탈락을 실수 후보로 모아 원인을 나눈다. 재현 테스트를 먼저 만들고 프롬프트·도구 설명·훅·정책·입력 제한 중 맞는 곳을 고친다(입력 출처와 승인 규칙은 [[치과 AX - 평가 설계]] §2.7). 규칙별 차단 횟수를 남겨 쓸모없는 규칙은 사람이 지운다 |

**개선 에이전트**(착수는 §9): 같은 하네스 코드를 쓰되 `evaluation/`에서 돌고 골드를 보므로 실행 기록은 앱 DB가 아니라 `evaluation/runs/`(커밋 안 함)에 남긴다. 앱으로 넘기는 범위는 [[치과 AX - 평가 설계]] §2.7

**야간 실행**: `make nightly` — 코드 스케줄러가 운영 에이전트를 깨운다. 화면은 저장된 결과를 읽어 바로 뜬다.

**운영 에이전트**: 기능 에이전트가 모두 붙은 뒤 추가한다. 밤에 새 통화·청구·불일치·후속 대상을 보고 조사 우선순위를 정해 기능 에이전트를 부른다. 불만·노쇼·미수처럼 흩어진 신호를 한 환자로 묶어 오늘 화면에 이유와 함께 올린다. 숫자는 쓰지 않고 쿼리 결과만 인용한다. 평가는 시나리오 DB로 한다([[치과 AX - 평가 설계]] §5).

**완료 기준**: 호출·비용 상한 초과 시 사람에게 넘김(pytest), 정책이 꺼진 작업은 자동 처리 0건(pytest), 되돌리면 원상태(pytest), 실행마다 단계 기록 존재, 금지 도구 호출은 실행 전 차단(pytest), 재생 테스트가 키 없이 통과, 끊긴 실행을 재개해도 자동 처리 중복 0건(pytest), 지시문이 섞인 입력으로 도구 호출·자동 처리가 달라지지 않음([[치과 AX - 평가 설계]] §5), 앱 테이블에 골드 값이 없음(검사 먼저), 실수 후보마다 재현 테스트가 수정 전 실패하고 수정 뒤 통과(pytest)

### 가상 데이터 생성기

**목적**: 미니 EMR + 비정형(통화·문서·문자) + 정답을 시드 재현 가능하게 생성. 산출물·규칙은 [[치과 AX - 가상 데이터 생성 설계]].

**완료 기준**: `make verify` 통과 + 결정성(같은 시드 2회 → 테이블 내용 해시 동일, LLM 캐시 포함)

### ① 통화 요약·분류

**목적**: 녹취록 1건 → 모델 2개가 각각 분류하고 분류 모델이 요약·할 일을 낸다. 분류 뒤 단계는 후속 에이전트가 맡는다.

**현실 구성과 대체**: 원본 사례(실제 동네 치과 AX 전환기 글)는 병원 자체 교환기(PBX)로 대표번호를 받아 녹음하고 통화 중 실시간으로 글로 옮긴다. 이 프로젝트는 실제 전화를 받을 수 없으므로 PBX·STT 구간을 **데이터로 대체**하고, 녹취록이 들어온 뒤부터 구현한다.

| 현실 | 이 프로젝트 |
|---|---|
| PBX 수신·녹음, 수신/발신 구분 | 가상 통화 녹취록(`ax_calls`, 생성 7단계) + `direction` |
| 통화 중 실시간 STT | 녹취록 텍스트 입력(새 통화 추가) |
| AI 음성 1차 응대·모바일 앱 | 범위 밖 |
| 끊으면 요약·할 일 | ① 그대로 |
| "지난번에 뭐 물어봤지" 검색 | ③ 사례 버킷 |

분류기 입력이 녹취록과 방향뿐인 것(앱 설계 §1 — 정답 힌트 차단)은 PBX가 넘겨주는 정보(녹음 → 녹취록, 방향)와도 맞는다.

**화면**: 탭 **오늘 할 일** / **통화 기록**, 버튼 **＋ 새 통화 추가**, 통화 상세. 화면 말·배치는 [[치과 AX - 앱 설계]] §9
- **오늘 할 일**: 기준일 전 며칠 안(`backend/calls.py` `TODAY_WINDOW_DAYS`) 통화와 새로 추가한 통화의 할 일 — 왼쪽 **할 일**(병원 안에서), 오른쪽 **연락할 사람**(전화·문자). 칸마다 통화 하나에 카드 하나, 카드 안에 그 통화의 할 일 여러 줄. 할 일 종류·상대·먼저 끝낼 일은 분류기 요약이 낸다. 응급·급함 통화 먼저, 그다음 최근 통화. 항목을 체크하면 끝낸 파트·시각이 남고 칸 아래 "끝낸 일"로 가며 되돌릴 수 있다. 할 일 있는 통화 카드에는 후속 에이전트 처리안 한 줄(종류 딱지 + 요지, 실패면 "처리안 실패")이 붙고, 상세 "처리안" 절에 근거 목록과 "과정 보기"(조회 도구)가 있다. 자동 종결된 통화는 오르지 않는다(조건은 아래 완료 기준 "자동 종결")
- **통화 기록**: 날짜별 카드(이름·시각·방향·목적·응급·급함·AI 엇갈림·할 일 남음·요약), 필터(걸려 온 전화·건 전화·응급·할 일 남음·AI 엇갈림)·검색(이름·번호·차트번호). 자동 종결된 통화에는 "자동 종결" 딱지
- **새 통화 추가**: 방향(걸려 온 전화가 기본)·전화번호(선택)·통화 내용 → 분류·판정·엇갈림 → 그 통화 상세. 번호가 EMR 환자와 맞으면 연결하되 화면 표시에만 쓴다(분류기 입력은 녹취록·방향뿐). 시각은 기준일 날짜 + 추가한 시각
- **상세**: 패널(기본) ↔ 넓게 보기. 처리안 → 할 일 → 요약 → AI 두 개가 다르게 본 곳 → 분류 9항목(판정기와 다른 값은 같은 칸에) → 환자 정보 → 녹취록. 넓게 보기는 왼쪽에 할 일·요약·엇갈림과 분류|환자 정보(반반), 오른쪽에 녹취록. 섹션은 펼친 채 시작하고 제목으로 접는다. 분류가 없거나 실패하면 다시 분류. 자동 종결된 통화는 맨 위에 이유·시각과 다시 열기. 확인할 통화(오늘 화면)면 맨 위에 그 문구와 확인함
- 판정 풀 통화는 통화 화면·자동 처리·야간 신호에서 빼고 AI 평가에서만 다룬다(test 통화를 업무 화면에서 보지 않게 — [[치과 AX - 평가 설계]] §1 원칙 2)

**API**
- `GET /calls/today` · `GET /calls?filter=&q=&before=` · `GET /calls/{call_uid}` · `GET /labels`(라벨 우리말 이름)
- `POST /calls`(새 통화 추가) → 분류·판정 1행씩·엇갈림, 판정 큐는 운영 구간 규칙(앱 설계 §6). 색인은 §9 "새 통화 색인"
- `POST /calls/{call_uid}/todos/{item}/done`(끝냄·되돌림)
- `POST /calls/{call_uid}/classify`(재시도). 일괄 분류·판정은 `make classify`·`make judge`(작업 API `POST /jobs/classify-batch`·`judge-batch`는 §9 — 대상은 판정 풀 포함 전체 녹취록과 새로 추가한 통화, 대기 버전 전환은 [[치과 AX - 앱 설계]] §7.2)
- `POST /auto-actions/{id}/revert`(자동 종결 다시 열기 — 자동 처리 되돌리기, [[치과 AX - 앱 설계]] §3b). `POST /calls/{call_uid}/check`(확인할 통화 확인함). 다시 계산은 `make autoclose`, 스위치는 `make auto-policy KIND=call_autoclose ON=1|0`
- 처리안은 새 통화·다시 분류 흐름 끝에서, 일괄은 `make followups`(오늘 할 일에 오른 통화 중 처리안 없는 것). 야간 실행(`POST /agents/call-followup/run`)은 `make nightly` 착수 때

**완료 기준**
- 새 통화 추가(pytest): 분류·판정 1행씩 `ok`·엇갈림 계산, 빈 내용·잘못된 방향은 거부, 실패하면 통화는 남고 다시 분류
- 판정 풀(`in_eval_pool`) 전체 행 `ok` (사람이 실행한 재분류 뒤 `active_prompt_version` 기준. 블라인드 풀은 판정 풀의 부분집합이라 별도 분류 없음)
- 오늘(pytest): 위 범위·판정 풀 밖 통화의 할 일만 종류별 칸에, 체크하면 끝낸 일로·되돌리면 복귀
- 엇갈림(pytest): 9항목 중 하나라도 다르면(급함은 urgent 여부만) 엇갈림 행, 목적·급함·응급이 다르면 `is_core`
- 자동 종결(pytest): `auto_policy`가 켜져 있고 두 모델 모두 할 일 없음이며 응급·불만·급함·엇갈림(라벨·요약 호출의 폴백, 할 일 목록 엇갈림 `todo_mismatch` 포함)이 없고 사람 판정이 할 일·응급·불만·급함을 켜지 않았을 때만 종결. 되돌리거나 사람 판정이 그 넷 중 하나를 켜면 딱지가 빠지고 다시 닫히지 않는다. 정책을 끄거나 활성 버전이 바뀌면 그 종결은 종결로 보지 않는다
- 후속 처리안: 처리 정답 정확도를 규칙 기준선과 나란히, dev에서 기준선 이상([[치과 AX - 평가 설계]] §5)
- 분류 스키마 enum은 [[치과 AX - 가상 데이터 생성 설계]] §4.1, 채점은 [[치과 AX - 평가 설계]] §2

**설계 근거**: 자동 종결은 사람이 안 보는 오류를 만들므로 일치 오류율을 재는 교차검증을 코어로 둔다. 분류기 입력 제한은 [[치과 AX - 앱 설계]] §1 — 도구로 EMR을 보면 통화 뒤 기록이 정답을 드러내므로([[치과 AX - 평가 설계]] §1 원칙 7) 분류는 함수로 두고, 에이전트는 분류 다음 단계부터 들어간다. 복수 주제 통화는 주 목적 1 + 불리언 플래그(생성 제약은 가상 데이터 생성 설계 §4.1, 채점은 평가 설계 §2.2). "오늘 할 일"의 할 일과 자동 종결은 분류를 믿고 움직이므로 분류가 틀리면 할 일이 빠진다 — ② 판정으로 분류를 재는 이유.

**교차검증**: 모델 A(분류기)와 모델 B(판정기, ②)가 각각 분류하고, 엇갈리면(규칙은 [[치과 AX - 평가 설계]] §2.5·[[치과 AX - 앱 설계]] §1) 엇갈림 배지 → 운영 구간 판정 큐에서 핵심 엇갈림 먼저. 효용 지표는 [[치과 AX - 평가 설계]] §2.5

**후속 에이전트**: "오늘 할 일"에 오른 통화 중 할 일 있는 통화만 환자 이력·예약·관련 문서를 조회해 처리안(처리 종류 하나 — `shared/followup.py` `ACTIONS` — + 한 줄 요지 + 근거)을 낸다. 입력은 분류 결과와 그 통화(차트 번호는 통화 화면과 같은 발신번호 매칭 값)이고, 근거의 숫자가 조회 결과·녹취록에 없으면 한 번 다시 돌리고 또 없으면 실패로 남긴다. 처리안 실행은 사람 몫이다.

### ② 판정·자동 개선 + 블라인드 비교

**목적**: 판정기가 1차로 판정하고, 사람은 엇갈림·표본을 본다. 판정기는 골드로 재고, 골드는 중재 판정기와 사람 표본으로 점검한다([[치과 AX - 평가 설계]] §2.3). 그 결과로 프롬프트를 자동 개선하고 요약을 블라인드로 비교한다.

**화면**
- **판정 구간**: 판정기는 모든 통화를 판정한다. 사람은 판정 풀 밖 통화(운영 구간)의 엇갈림·표본만 본다. 골드 점검은 앱 밖(`evaluation/`)에서 한다(규칙은 [[치과 AX - 평가 설계]] §2.3)
- **판정기**(모델 B): 모델 A와 다른 모델. 입력은 녹취록·방향이고, 판정 기준은 프롬프트 `prompts/judge/`에 들어 있다. 모델 A 결과를 보지 않고 도구도 없다 — 한 통화를 읽고 답하는 일이라 조사 경로가 필요 없고, 검색을 주면 다른 통화에서 정답 힌트를 얻을 수 있어 일부러 에이전트로 만들지 않는다([[치과 AX - 평가 설계]] §1 원칙 7)
- **판정**: 한 건씩, 왼쪽 9항목 고르기·오른쪽 녹취록(요약은 보이지 않음)
  - 입력: 항목마다 선택지 버튼을 모두 펼치고 숫자 키로 고름 — 목적 2자리·나머지 1자리 → 자동 다음 항목 → Enter 저장·다음 건. 위에 진행 현황 한 줄(오늘·누적 판정 수), 아래에 단축키 안내
  - 메모 칸(선택 — 애매한 이유, 기준이 필요한 경우): 단축키로 들어가고 Enter로 저장
  - 모델 라벨은 저장 뒤에만 보여 준다(저장 전에 보이면 앵커링).
- **블라인드 탭**: 왼쪽에 두 요약(할 일 포함)을 버전 가리고, 오른쪽에 녹취록(둘 다 틀렸는지는 원래 통화로만 판단된다) — `1 / 2 / 비슷 / 둘 다 틀림`. 대상과 투표의 쓰임은 [[치과 AX - 평가 설계]] §2.4
- **정확도 표**: 항목별 모델 vs 판정기 일치율·블라인드 승률(LLM 쌍 비교)·좌우 선택 비율. 프롬프트 버전을 나란히 놓아 개선 추이를 보인다. 모수는 **dev 판정 풀만** — [[치과 AX - 평가 설계]] §2.2. 앱 DB에 골드가 없어 골드 지표(모델·판정기 vs 골드, 골드 점검)와 test 수치는 `eval.py`에서만. 교차검증 효용은 화면 없이 `eval.py`만
- **자동 개선**(개선 에이전트 착수 때): 개선 실행 이력(오류 유형·바뀐 규칙·관문 결과·반영 여부), 재발 방지 후보(원인·재현 테스트·승인 상태)·규칙별 차단 횟수. 읽기 전용이며 기준 수정과 버전 되돌리기(`make set`)는 화면에 두지 않는다

**API**
- `GET /judge/next` / `POST /judgments` / `POST /calls/{call_uid}/skip`
- `GET /blind/next` / `POST /blind-votes`(사람) / `make blind-judge`(LLM 쌍 비교, [[치과 AX - 평가 설계]] §2.4 — 작업 API `POST /jobs/blind-judge-batch`는 §9)
- `GET /metrics/accuracy`(판정기 일치율·블라인드 승률·사람이 보는 몫)
- `make prompt-gate A=<기준> B=<후보> ITEM=<목표 항목>`(관문, [[치과 AX - 평가 설계]] §2.7) · 개선 에이전트 착수 때: `GET /improve/runs` / `GET /failure-cases` / `make improve TASK=…`(재료 → 후보 → 관문 → 대기 버전, `evaluation/` 쪽 실행)
- `make export-human` / `import-human`(착수 전, 보존 키는 [[치과 AX - 앱 설계]] §7.3)

**완료 기준**
- Playwright(`make e2e` — 실데이터 복사본에서, 진짜 판정 DB를 오염시키지 않게): 키 시퀀스 10회 → `ax_judgments` +10, 블라인드 5회 → `ax_blind_votes` +5
- 정확도 뷰([[치과 AX - 앱 설계]] §1 "(정확도 뷰)")가 정의한 모수·행을 낸다(pytest)
- 판정기 입력 검사(pytest): 입력이 녹취록·방향뿐이고 도구가 없음. 쌍 비교 판정기는 녹취록과 두 요약뿐이고, 좌우 바꾼 두 판정이 다르면 `tie`
- 골드 점검(pytest): 대상에 test 판정 풀 통화가 없고, 중재 판정기 입력에서 어느 라벨이 골드인지 드러나지 않음
- 프롬프트 관문(pytest): 조건(목표 항목 오름·응급·불만 새 놓침·오탐·회귀) 중 하나라도 못 넘으면 불합격, 자동 처리 정책이 켜졌거나 시도 상한이면 부르기 전에 멈춤, 모수에 dev·test 행이 있으면 멈춤, 출력·기록에 통화 id 없음
- 자동 개선(pytest, 개선 에이전트 착수 때): 관문 조건을 하나라도 못 넘으면 대기 버전이 생기지 않음, 재분류가 전부 `ok`로 끝나기 전에는 활성 버전이 바뀌지 않음, test 분할을 읽으면 실패

**프롬프트 관문** — 후보(사람이 쓰거나 개선 에이전트가 쓰거나)를 검증 구간에서 기준과 여러 번 돌려 다수결로 짝 비교하고 합격한 것만 쓴다. 흔들림만으로 합격·하락하지 않게 하는 장치([[치과 AX - 평가 설계]] §2.7). 프롬프트 v1 → vN 변화가 §8 결과표의 근거이며, README에 "오류 유형 → 수정 내용 → 수치 변화"를 한 표로. 골드(`truth_call_labels`)의 통화·라벨은 프롬프트에 넣지 않는다(few-shot 규칙은 [[치과 AX - 평가 설계]] §7)

**자동 개선**(개선 에이전트 착수 때) — 재료의 오류 유형 → 개선 에이전트가 프롬프트 후보 작성 → 관문 재측정(탈락하면 그 기록을 다음 후보에 넘김) → 대기 버전 → 사람이 재분류 실행 → 전환 → 버전별 추이. 재료·관문·전환은 [[치과 AX - 평가 설계]] §2.7.

**설계 근거**: 녹취록 기본 노출(모델 요약을 읽고 판정하면 판정이 모델에 앵커링). 판정기를 골드로 재는 것은 골드가 녹취록 전체에 있어서다. 판정 풀·판정·블라인드 절차와 정확도 분리 보고는 [[치과 AX - 평가 설계]] §2.

### ③ 물어보기 (RAG 검색 + 챗 + 문서함)

**목적**: 매뉴얼·공지·청구 기준·통화·문자·차트 기록을 하이브리드 검색, 도구 6개 단일 턴 에이전트가 "확인된 사실만" 답함. 하네스 위에 만든다.

**검색 대상** (현장 인터뷰에서 나온 질문 기준)

| 대상 | 예시 질문 | 버킷 |
|---|---|---|
| 업무 절차(직원 매뉴얼) | 틀니 수리 접수 절차, 구형 임플란트 부품 주문 | 문서 |
| 청구 기준·보험 안내 | 치석제거 다음 달로 넘어가면 치주치료가 왜 깎여? (청구 기준 질문은 ③ 질문 밖, ⑤ 평가셋) | 문서 |
| 원내 공지(최신성) | 바뀐 기준이 뭐였지 | 문서 |
| 통화·문자 사례 | 그 환자 지난번에 뭘 물어봤지 | 사례 |
| **차트 케이스** | 치석제거 뒤 치주치료로 이어진 환자는 간격·상병을 어떻게 적었지, 사랑니가 완전 매복이라 골삭제한 환자 | 사례 |
| 환자 사실 | 지난 스케일링이 언제였지, 이 환자 남은 치료가 뭐지 | 도구 `query_patient` |

차트 케이스는 "차트 검색이 환자 이름으로만 돼서 이름을 모르면 못 찾는다"는 인터뷰 고충에 대한 답 — 케이스 내용으로 찾고 결과에 차트 번호를 띄운다. 차트 기록 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §4.3.

**화면**: 물어보기 화면(`/ask` — 메뉴에 없음, 위 앱 구성 "물어보기 창") 하나에 탭 `질문하기 | 기록 검색 | 문서함` — 입력한 내용은 탭을 바꿔도 유지, 챗 답변의 "근거 더 보기"는 같은 질문으로 기록 검색을, 검색 결과의 "이걸로 질문하기"는 챗을 연다. **질문하기**(질문 1 → 진행 이벤트 SSE → 답변 + 출처. 멀티턴 없음. 근거가 없으면 `refuse` → 고정 문구 "문서함에 없음") / **기록 검색**(`매뉴얼 결과` / `실제 사례 결과` 분리 + AI 요약 + 출처, 필터: 출처 종류·기간·환자번호) / **문서함**(`ax_documents.type`별 목록 — 공지는 최신 버전만·시행일 표시, 본문 보기, 읽기 전용). 챗이 문서에서 근거를 못 찾아 거절한 질문은 문서 초안 에이전트가 기존 문서·통화·문자에서 재료를 찾아 초안을 만들고, 오늘 화면의 "사람이 볼 일"에 올린다. 게시는 사람이 문서함의 초안 목록에서 한다. 게시된 초안은 문서함과 색인에 합쳐진다

**API**
- `GET /search?q=&source_types=&date_from=&date_to=&chart_no=` → `{manual_results, case_results}` (카드 칸은 `backend/search_cards.py`)
- `POST /chat`(SSE 진행 + 최종 답변, 답에 저장 번호 `log_id`) → `ax_search_logs`
- `GET /chat/{log_id}`(저장된 질문 1개를 `answer`와 같은 모양으로 — 모델을 다시 부르지 않음, 평가 실행·검색 요약·실행 중은 404)
- `POST /search/summary`(기록 검색 AI 요약 — `GET /search`와 같은 인자, `{status, text, sources}`) → `ax_search_logs`
- `GET /documents` / `GET /documents/{id}`. `GET /doc-drafts` / `POST /doc-drafts/{id}/publish`. 문서 초안 입력은 `ax_search_logs`, 오늘 화면은 `GET /today`
- 도구 6개(시그니처는 앱 설계 §3): `search_docs`, `query_patient`, `query_schedule`, `query_claims`, `query_charts`(기간·간격 조건 차트), `refuse`
- `make index`(인자는 앱 설계 §3) / `eval.py --split dev [--retrieval-only]` · `--split test --section …`([[치과 AX - 평가 설계]] §7)

**완료 기준**
- `eval.py --split dev` exit 0 + 리포트
- 데이터형 도구 선택·문서 검색형 Hit@5가 dev에서 하한 이상(`evaluation/metrics.py` `CORE_TOOL_MIN`·`CORE_HIT5_MIN`, 문항 수는 `verify.QA_TYPE_COUNTS`)
- 인용 확인(pytest): 검색 결과 밖 청크를 인용하면 한 번 다시 답하고, 또 어긋나면 고정 문구로 끝나고 상태는 `cite_failed`([[치과 AX - 앱 설계]] §3)
- 보고(관문 조건 아님): 챗 vs 단순 RAG 기준선, 차트형 인용 정확도·공지형 현재 값·답 내용([[치과 AX - 평가 설계]] §3.3)
- 질문 구성(유형·수·dev/test)·채점 규칙·지표는 [[치과 AX - 평가 설계]] §3 — `make verify`가 문항 구성을 검사

**설계 근거**: 문서 청크가 통화·문자 청크보다 훨씬 적어 단일 RRF에서 묻힘 → **문서 버킷·사례 버킷 따로 검색** 후 리랭커. 모든 청크에 출처 prefix 의무(환자명 없이는 사례형 검색 불가). 차트 서술은 비식별이고 prefix는 차트 번호까지만이다(형식은 [[치과 AX - 앱 설계]] §3). 리랭커·임베딩 선택은 앱 설계 §7.

### ④ 진료 준비표 (MVP)

**목적**: 환자마다 EMR 여러 화면(기본정보·예약·진료기록·수납·청구·가족·주의사항)을 뒤지는 걸 코드가 조인해 한 행으로 모으고, LLM이 그날 할 일(관련 주의사항 처리 + 권할 진료)을 한두 줄로 묶는다. 둘 다 없으면 "그대로 진행". 체어 보기는 저장된 결과만 읽는다. 아침 회의에서 오늘 전체를, 진료 중에는 체어 옆에서 지금 환자 한 명을 본다. 주의 환자 야간 조사 에이전트는 운영 에이전트 때(§9)

**화면 (MVP)**
- **전환 전 EMR**(개선 전, 읽기 전용): 상용 전자차트의 일반적인 구조를 가상 프로그램으로 보인다 — 데스크(환자 정보·당일 수납·히스토리·접수 목록·예약표), 예약(담당자별 예약표), 전자차트(진료 기록·치식·처치 입력·진료 메모(최근 진료 내용)·옆 패널 탭). 주의사항은 따로 띄우지 않고 전자차트 옆 패널 메모 탭에만 있고, 미수는 데스크, 남은 치료는 차트 옆 패널에 있어 한 환자를 챙기려면 화면을 옮겨 다니는 현재 모습을 보이고, 개발자 독자가 가상 데이터를 둘러보는 화면을 겸한다. 실제 제품의 이름·로고·색·화면 이미지는 쓰지 않는다. 옆의 설명 카드가 치과 일을 모르는 사람에게 왜 옮겨 다니는지 보인다 — 흩어짐 지도(미수 › 데스크 당일 수납, 주의사항 › 전자차트 옆 패널 메모, 남은 치료 › 차트 옆 계획, 예약 확인 문자 응답 › 데스크 히스토리 문자) → 따라 보기(기준 환자로 네 단계를 EMR이 직접 넘어가며 강조, 없는 정보도 그 화면까지 가서 "없음", 그동안 EMR 창은 잠김) → 하루 규모(환자 한 명 화면 이동 수 × 기준일 예약 수). 시작 화면에서 오면 카드를 펼치고, 예약표에서 오면 한 줄로 접고 그 환자의 전자차트를 연다
- **공통**: 날짜 탭(최근 7일 + 오늘, 날짜마다 인원수) + 오른쪽에 AI 제안 기준 시각·사실이 바뀐 환자 수 + "AI 제안 갱신하기 (N명)"(N = 갱신하면 다시 부르는 행 — 조건은 [[치과 AX - 앱 설계]] §4 `ax_prep_sheets`, 없으면 꺼짐), 보기 전환 준비표 | 체어 보기
  - 제안 칸(두 보기 공통): 사실이 바뀐 행은 "제안 만든 뒤 바뀜: 바뀐 항목 전 → 후", 갱신 뒤 새로 만든 행은 "방금 갱신" + 이전 제안(화면을 다시 열면 사라짐)
  - 칩: **예약 · 보험 잔여**(스케일링 미사용 성인) **· 미수 잔액 · 가족 리콜 지남 · 주의**(그날 예정 시술과 관련된 주의사항 — 코드가 `master` 표로 정확히 표시) **· 남은 치료계획**(열린 계획 항목 중 그날 예정 시술이 아닌 것) **· 내원 확인 전**(그날 예약 중 `emr_appointments.confirmed`가 아닌 것, 일별 예약표 배지처럼 기준일만. 코드 표시만, 제안 사실이 아니므로 LLM 입력과 과잉 제안률에서 뺀다. 펼친 사실의 "내원 확인"은 예약표 패널과 같은 기준(환자가 온다고 답함 / 문자에 답 없음 / 문자 발송 시각이 지난 뒤 잡힌 예약)이고, 지난 날은 비운다)
  - 칩은 아직 챙길 일이 남았을 때만 켠다 — 보험 잔여는 그날 예정 시술이 스케일링이면 끄고, 가족 리콜은 그날 이후 위생 예약이 잡힌 가족을 뺀다
  - 사실은 그날 개원 전 기준이다 — 지난 날짜도 그날 아침에 보였을 값(치료계획 끝남·대체됨, 마지막 내원, 미수, 가족 리콜)으로 다시 센다
- **준비표**: 칩 7개 필터(칩별 인원수) + 종류(진료·위생·상담) + 할 일 있는 환자만 + 몰리는 시간대(시작 시각 기준) + 인쇄. 행: 시각·체어 / 환자(신환 딱지) / 예정 시술 / 칩 / 제안, 지난 날짜는 결과. 펼치면 사실 + 제안 + 근거 + 후검증. 아침 회의는 이 화면을 띄우거나 인쇄해 한다 — 시간 × 담당자 격자는 예약 화면(`/schedule`)이 맡는다
- **체어 보기**: 체어별 오늘 순서 + 지금 환자 한 장 — 주의사항을 가장 크게, 예정 시술, 제안. 시간이 되면 다음 환자로 — "지금"은 TODAY 날짜 + 실제 시계의 시:분
- **제외**: 칩 여러 개를 조합하는 필터, "다음 진료일", "다른 치과 추정"(⑨ 미예약 환자 몫), 따로 된 회의 보기(체어 전체 격자 — 필요하면 예약 화면에 체어별 전환으로)

**API**
- `GET /prep?date=`(날짜 탭 밖은 400) / `POST /jobs/prep-regenerate?date=` / `GET /jobs/{id}`. 두 보기 모두 `GET /prep?date=`(행에 체어 번호 포함). 만들기는 `make prep`(과금). 다시 부르지 않는 조건은 [[치과 AX - 앱 설계]] §4 `ax_prep_sheets`, 같은 날짜 작업은 §6 `ax_jobs`
- 집계는 `backend/prep.py` `prep_facts(conn, day, today)`, master 값(주의사항 관련 시술·행동, 보험 잔여 기준)은 `source.ax_master_values`로 읽는다. 출력 `{action: suggest|none, text, used_facts}` — `text`는 그날 할 일 요약(주의사항 처리 + 권할 진료), 둘 다 없으면 `none` = "그대로 진행"(후검증 실패의 `null`과 다름)
- 전환 전 EMR API는 [[치과 AX - 앱 설계]] §9

**완료 기준**
- 집계 회귀 테스트·제안 후검증(`suggestion_valid`) — 규칙은 [[치과 AX - 평가 설계]] §4. 후검증 실패 시 null + 재시도
- 주의사항 반영률·과잉 언급률·과잉 제안률(칩이 꺼진 행 — 항상 켜지는 예약 칩 제외 — 인데 `suggest`) — 전부 코드 채점(`eval.py --split dev`, `evaluation/prep.py`), 정의는 [[치과 AX - 평가 설계]] §4

**설계 근거**: 주의사항 → 행동은 표로 정해져 있어 칩은 코드가 정확히 띄우고, LLM은 여러 사실(주의사항 여럿 + 예정 시술 + 미수·리콜)을 그날 행동으로 묶는 일만 한다(§3 원칙 2). 반영률은 그 요약이 관련 주의사항을 빠뜨리지 않는지 보는 안전망. 제안은 사람이 채점하지 않는다 — 버전 비교·개선에 쓰이지 않는 절대값 하나만 남아 §8(조건 간 차이가 주 지표)과 맞지 않는다. `none`을 허용 — 매 행 제안을 강제하면 근거 약한 제안을 지어낸다. 출력을 `{action, text, used_facts}`로 강제 — 자유 문장에서 (키, 값) 역파싱은 불가능하므로 모델이 쓴 사실을 스스로 명시. 예정 시술은 `emr_appointments.planned_procedure_code`, 남은 치료계획은 치료계획 테이블([[치과 AX - 가상 데이터 생성 설계]] §2.3). "다음 예약 없음" 칩은 두지 않는다 — 예약이 없는 환자는 ⑨ 미예약 환자가 맡는다.

## 5. 슬롯 기능

- **⑤ 심평원 청구 점검·삭감 대응**(짧게 "청구 점검·삭감 대응", 건강보험 심평원 청구, 코드명 `claim_review`): 심사결과는 청구 프로그램(전자차트)이 전자로 받아 장부에 반영돼 있다 — 장부와 심사결과가 어긋나는 일은 다루지 않고, 그 뒤에 남는 일(조정 사유 해석·재심 판단)과 청구 전 점검을 돕는다. 하위 기능 3개 — ⑤-2는 청구 전 줄과 요건 사유 조정 건, 조정 건은 ⑤-3 → ⑤-4. 지표는 [[치과 AX - 평가 설계]] §5, 데이터는 [[치과 AX - 가상 데이터 생성 설계]] §2.4·§4.2·§4.3
  - **단계**: 1 코드(조정 목록·재심 기한·규칙 판단 제안·판단 기록, 청구 전 상병 확인 경고 — 과금 없음) → 2 ⑤-2 AI 점검 → 3 ⑤-3 근거 찾기 → 4 ⑤-4 재심 사유서. 앞 단계가 없는 칸·칩은 화면에 두지 않는다(빈 자리·시스템 말 없음). 화면은 메뉴 "청구 점검" 한 화면, 탭 `삭감 대응 | 청구 전 점검`
  - **⑤-2 청구 전 점검**(규칙 + AI): 전월분(`pending`) 청구를 진료 기록·청구 기준과 대조해 누락·삭감 위험을 근거와 함께 표시(표시만 — 청구 수정·제출은 사람, §3 원칙 1)
    - **급여 조건**(규칙): 나이·횟수 등은 시술 표에 있어 규칙(SQL)이 점검한다 — 나이처럼 정형으로 판정되는 요건은 규칙 몫
    - **임상 요건**(AI): 청구 기준 문서와 **차트 서술**을 읽어 임상 요건 근거(치석제거 뒤 치주치료 연결·치주 소견·같은 부위 재시행 사유 등)가 차트에 있는지 보고 근거를 단다 — 서술을 읽어야 하는 요건이 AI 몫. 대상은 요건이 있는 시술(`ax_master_values` `requirement_notes`)의 청구 줄, 입력은 시술·치아·상병·나이·차트 서술과 그 시술의 기준 절뿐(청구 상태·조정 결과·사유는 넣지 않는다). 판단은 근거 있음 / 근거 없음 / 판단 불가와 인용 — 인용이 차트·기준 원문에 글자 그대로(공백 뺀 `MIN_QUOTE`자 이상) 있어야 통과, 실패면 한 번 더 뒤 판단 없음. 차트 서술이 없는 줄은 부르지 않는다. 같은 입력·프롬프트 버전·모델로 통과한 줄은 다시 부르지 않는다(`backend/claim_check.py`)
    - **화면**: 청구 전 점검 탭에 점검 결과가 있을 때만 칩 "임상 요건·차트 기반 누락(AI)"과 딱지 "차트에 요건 근거 못 찾음(AI)" + 인용·"차트에 있는데 청구에 없음(AI)" + 처치·치아·인용, "AI 점검 갱신하기 (청구 전 n줄 · 삭감 대응 m건)" 버튼(한 번에 두 탭이 갱신, 0인 쪽은 뺌)과 "AI 점검: 시각 기준". 요건 사유 조정 건 할 일 칸은 "AI가 차트에서 근거 찾음 → 재심 신청" / "AI가 차트에서 근거 못 찾음 → 삭감 수용", 펼친 곳에 인용. 오늘 화면 "청구 전 차트에 요건 근거 못 찾음 n건(AI)"(처치 누락만 있는 줄은 세지 않는다)
    - **상병 확인 경고**(규칙): 시술 × 차트 상병이 `master` 허용 조합 밖이면 경고하고, 지난 조정에서 같은 조합이 상병 착오로 깎였으면 "지난 조정에서 이 조합 n건, x원 못 받음"을 붙인다 — 상병 착오는 재청구가 안 되니 미리 막는 게 유일한 방법
    - **차트 기반 누락**(AI): 차트 서술에 그날 시행했다고 적힌 처치인데 진료 기록·청구에 없는 것을 근거 문장과 함께 표시 — 서술을 읽어야만 보여서 규칙으로는 찾을 수 없다. 청구 줄마다 요건 대상과 무관하게 짧게 묻고(요건 점검과 따로), 급여 여부(비급여·나이·청구된 것)는 코드가 거른다
    - 완료 기준: AI 지표를 기준선과 나란히 — 임상 요건형은 "서술 있는 줄 전부"·키워드 규칙 대비 정밀도·재현율·근거 정확도, 차트 기반 누락은 키워드 규칙 대비 합성 사례 정밀도·재현율과 실데이터 "n건 중 m건"(채점은 [[치과 AX - 평가 설계]] §5 ⑤-2). 나이·횟수·단순 누락·코드 착오는 규칙 fixture 테스트(가상 데이터에 심은 오류는 상병 착오·임상 요건형·차트 기반 누락뿐 — [[치과 AX - 가상 데이터 생성 설계]] §2.4)
  - **⑤-3 조정 목록·판단·근거 찾기**(근거 검색은 ③ 검색 구조 재활용)
    - **조정 목록**(코드): 확정 월 조정 건(일부·전액) 중 재심 신청 기한(통보일 + `master.APPEAL_DAYS`, 기한 당일까지 남음)이 남은 건을 5칸 — 재심 신청 기한(남은 날, `backend/claims.py` `SOON_DAYS`일 이내 위험·`WATCH_DAYS`일 이내 주의 꼬리표(상병 착오 제외), 지났으면 기한 지남 딱지, 상병 착오는 재청구 불가 딱지) · 환자·시술(진료일·치아) · 못 받은 돈 · 왜 깎였나(상세 사유 문구) · 할 일. 칩 6개: 전체(기한 남음) · 상병 착오 · 신청 기한 임박(`SOON_DAYS`일 이내, 상병 착오 제외 — 오늘 화면 "재심 신청 기한 임박"과 같은 함수) · 전액 불능 · 일부 조정 · 기한 지남(판단 없이 사유·금액·남긴 판단만). 칩마다 건수·못 받은 돈 합계. 통보일·청구·지급 금액은 행을 펼친 곳에. 정렬은 기한 가까운 순(기본, 기한 지남 칩은 최근에 지난 순)과 못 받은 돈 큰 순, 지금 정렬을 표 위에 적는다
    - **판단**: 사유 유형(`master.ADJUST_REASONS` `type`) 규칙이 제안한다 — 상병 착오·외부 이력 → 정당, 서류(내역설명·증빙·기재 누락) → 보완 후 재청구. **요건 사유는 코드로 정해지지 않아**(차트에 요건 근거가 있으면 다툴 만함, 없으면 정당) ⑤-2 AI가 조정 건에도 돌아 제안한다(AI 결과가 없거나 판단 불가면 "차트 확인 후 결정"). 최종은 사람이 세 버튼(화면 이름 삭감 수용 = 정당 / 재심 신청 = 다툴 만함 / 보완 후 재청구, 정의는 [[치과 AX - 가상 데이터 생성 설계]] §2.4) 중 하나로 기록(누가 = 파트, 다시 누르면 덮어씀). 판단 전 행의 할 일 칸은 "판단 필요"와 규칙 추천. 재심 근거 조사 에이전트는 두지 않는다.
    - **근거 찾기**: 조정 건을 펼치면 ① 칸에 그 사유의 청구 기준 절 카드(`문서 › 절`, 전문 — 모든 사유), 서류 사유 건은 ② 칸에 "차트에서 옮겨 적을 문장(AI)"(그 절이 요구하는 차트 문장 0~3개, 인용 실재 후검증, 없으면 "차트에 옮겨 적을 문장 없음" — 요건 사유 건은 ⑤-2 근거를 그대로). 화면 맨 위 두 탭 공통 검색칸 "청구 기준 찾기"로 코드 없이 물어 절 5개를 원문 그대로 보인다(③ 검색 엔진을 청구 기준 문서의 절로 좁힘, AI 답 문장 없음)
    - **보완 후 재청구**: 청구 때 빠뜨린 것(내역설명·증빙)을 채워 다시 내는 길이라, 채울 항목과 차트 문장(위 근거 찾기)을 함께 보여 준다
    - **상병 착오**(코드 표시로 따로 강조): 기한 칸의 재청구 불가 딱지 + 못 받은 금액 + 차트 상병 ↔ 시술 + "다음 청구 때 상병 확인" — 같은 조합은 ⑤-2 상병 확인 경고로 이어진다
    - 완료 기준: 상세 사유 → 기준 절 찾기·사유 유형 판단 제안은 테스트, 코드 없이 묻는 청구 기준 질문의 절 단위 Hit@5·MRR, 서류 사유 차트 문장 인용 실재율. 요건 사유 조정 건 판단은 ⑤-2 채점에서 "모두 정당"·"모두 다툴 만함" 기준선과 나란히
  - **⑤-4 재심 사유서 초안**(LLM): 사람이 재심 신청(다툴 만함)으로 기록한 건만(`ax_claim_judgments`) → 조정 사유 + 청구 기준 절 + 그 진료의 차트 기록으로 초안(펼친 곳 ③, 누를 때 호출·저장), 사람이 검토·제출 결정(§3 원칙 1). **추측 목록**: 초안의 모든 문장은 조정 내역·기준 절·차트 인용(인용 구절이 원문과 그 문장에 있음)이거나 추측 목록(`assumptions[]`) 번호에 묶인다 — 한 칸 한 문장, 어긋나면 후검증 실패(한 번 다시, 또 실패면 "초안을 만들지 못했습니다"). 화면은 사유서 본문(복사될 글 그대로 한 문단, [복사]는 여기) + 문장별 근거(확인용, 문장마다 꼬리표) + "AI가 추측한 부분" + "검토했고 정확함" 체크 뒤에만 [복사]·[제출 결정](기록만 — AI는 제출하지 않는다). 화면에서 문장을 고치지 않는다 — 실제 제출은 심평원 포털·청구 프로그램에서 하고 고치기도 거기서. [다시 쓰기]는 검토 확인을 풀고, 제출 결정 뒤에는 다시 쓰기와 그 건의 판단을 잠근다. 완료 기준: 정답 다툴 만함 dev 건의 후검증 통과율 + 첫 답의 근거 없는 문장 비율
- **⑥ 경영 리포트**: ④ 패턴 복제. 월간·주간·일간을 고른다
  - **공통 숫자**(쿼리): 매출(`emr_treatments` 진료비), 수금(환자 수납 + 공단 지급), 노쇼율, 신환
  - **월간 전용**(쿼리): 재료비·기공비(⑧-2 확정 계정 — 사람 확정 + 자동 확정, ⑧ 전에는 거래처 표), 인건비 제외 손익(수금 − 통장 출금·병원 카드 사용), 상병 착오 건수·못 받은 금액과 금액이 가장 큰 시술 × 상병 조합(입력자별 집계는 하지 않음). 재료비·손익을 월간에만 두는 이유는 월말 이체가 많아서다
  - **`[추정]`**: 인건비는 실제 급여가 아니라 역할별 직원 수(`emr_staff`) × 앱 설정 가정값이다. 대표 원장 보수는 넣지 않는다. 추정 손익·손익분기 매출(고정비 ÷ (1 − 재료비·기공비 비율))은 항상 `[추정]`으로 표시하고, "대표 원장 보수·세금 전"을 함께 적는다. 값이 가정값에 달려 있어 성과 지표로 쓰지 않는다(§8 결과표에 넣지 않음)
  - **AI**: 숫자를 문장으로 풀고, 추정 문장은 `[추정]`을 단다
  - **튄 숫자 조사**(에이전트): 숫자는 쿼리가 낸다. 이전 기간과 차이가 큰 항목을 코드가 고르면 에이전트가 예약·청구·지출 쿼리 도구로 원인을 찾고, 문장과 근거 쿼리를 함께 남긴다. 추측은 `[추정]`
  - 완료 기준: 본문 숫자 전부 `metrics`에 존재(④ 후검증 재사용), 가정값이 들어간 숫자에 `[추정]` 누락 0, 시나리오 DB의 원인 정확도([[치과 AX - 평가 설계]] §5)
- **⑦ 아침 브리핑**: 오늘 화면의 한 칸. 그날 예약 수·신환·몰리는 시간대·주의 환자 수·내원 확인 전 수 같은 숫자는 쿼리, LLM은 운영 에이전트의 밤사이 결과와 함께 몇 문장으로 묶기만 한다. 추정 문장은 `[추정]`을 단다. 완료 기준: 본문 숫자 전부 입력에 존재(④ 후검증 재사용)
- **⑧ 재무 대조**: 데이터는 `fin_` 테이블, 장부 실수는 `emr_payments`에 생성 단계에서 심는다([[치과 AX - 가상 데이터 생성 설계]] §2.4·§2.7). 정답은 truth.sqlite에만. 원인·계정 과목은 고정 enum(§3 원칙 6 — 에이전트 출력·사람 확정·정답이 공유)
  - **단계**: 1 ⑧-1 코드(일계표·불일치 건 탐지·규칙 원인·사람 확정 — 과금 없음) → 2 ⑧-2 코드(규칙 매칭·거래처 기본 계정 과목·사람 확정) → 3 ⑧-1 조사 에이전트 → 4 ⑧-2 AI. 앞 단계가 없는 칸·탭은 화면에 두지 않는다. 화면은 메뉴 "재무 대조" 한 화면, 탭 `일계표 | 지출 증빙`
  - **⑧-1 수입 일계표 대조**(에이전트): 현장의 일계표 확인을 옮긴 기능. 장부(`emr_payments`) ↔ 카드 승인·정산 입금·통장 입금 대조는 코드(§3 원칙 2) — 하루 합계가 아니라 행 단위로 짝짓고 남은 행을 묶은 "불일치 건"이 단위다(취소 후 재승인처럼 하루 합계가 맞는 불일치도 잡게, `backend/recon_match.py`). 건마다 규칙 원인(규칙 기준선, `backend/recon.py` `rule_cause`)을 1단계부터 "규칙 추정"으로 보인다. 에이전트는 불일치마다 가설 → 조회(도구는 [[치과 AX - 앱 설계]] §3b ⑧-1 행) → 비교를 반복해 원인을 고르고 그 과정을 보인다(③ 챗은 질문 하나에 짧은 도구 루프로 답만 — 조사 과정이 화면의 주인공인 것이 ⑧-1의 차이). 원인은 통장·카드 쪽과 장부 쪽(목록과 묶음은 [[치과 AX - 평가 설계]] §5), 근거가 부족하면 `unknown`
    - **화면**: 날짜별 일계표(결제수단별 장부 합계 vs 금융 합계, 현금은 입금 기간 끝 날에 합산 입금) + 불일치 건이 있는 날 배지(합계 차이가 0이어도) → 펼침 = 건마다 관련 장부·금융 행 + 규칙 추정 + 조사 과정(도구 호출 순서·조회 조건·비교 결과 — 3단계, 직원이 `조사 시작`을 누르면 줄이 하나씩 생기고, 같은 에이전트를 일괄로도 돌려 평가·자동 마감에 쓴다) + 원인 후보·근거 + 사람 확정(`맞음 / 아님`, 아님이면 원인 선택 — `ax_` 테이블, 사람 라벨이라 앱 DB). 규칙 묶음이고 장부 수정이 필요 없으며 규칙과 에이전트의 원인이 같으면 자동 마감(§3 원칙 1). 장부 수정은 사람
    - **완료 기준**: 원인 정확도(top-1)를 규칙 기준선과 나란히, "규칙으로 되는 원인 / 애매한 원인" 두 묶음으로. 탐지 재현율은 코드 대조라 테스트. 조사 단계 수 상한(③처럼 호출 상한). 사람 확정은 지표가 아니라 화면 흐름이고, dev 달 확정만 재료 분할 뒤 프롬프트 개정에 쓴다. 자동 마감 오류율. 지표 세부는 [[치과 AX - 평가 설계]]
  - **⑧-2 지출 증빙·계정 분류**(AI): 통장 출금·병원 카드 사용을 증빙(거래명세서·세금계산서·주문 메일·영수증·고지서)과 맞추고(1:1, 거래처 월말 이체와 주문 두 건 한 번 결제는 1:N), 계정 과목을 확신도와 함께 추천한다. 못 찾으면 "증빙 없음". 급여·공단 입금은 대상이 아니다
    - **화면**: 달마다 출금 전부(칩으로 증빙 못 찾음·과목 확인 필요·규칙과 다름·미확정 거르기) + 행마다 찾은 증빙·금액 차이·계정 과목·AI 제안 → 사람 확정(`ax_`). 증빙 탐색 에이전트가 모든 출금을 규칙 답 없이 조사하고(규칙이 못 푼 줄은 찾기, 푼 줄은 검산) 코드가 규칙 답과 비교한다. 규칙과 AI의 증빙 집합·과목(거래처 표 기본 과목)이 같고 금액 차이가 0이며 품목으로 정하는 거래처가 아니고 같은 증빙을 다른 후보·확정이 갖지 않으면 자동 확정(§3 원칙 1, 조건은 `backend/expense_auto.py` `autoconfirm_reason`). 같은 증빙을 다른 출금의 살아 있는 확정이 가졌거나 기준일 이후 출금이면 확정을 막는다. 같은 출금처(적요·가맹점명 글자)를 사람이 확정하면 다음부터 그 과목이 기본값(품목으로 과목이 정해지는 거래처는 제외 — 확정 전까지 과목 확인 필요). 오늘 화면 "지출 증빙 확인 n건" = 기준일의 지난달 출금 중 증빙 못 찾음·과목 확인 필요·규칙과 다름이면서 확정·자동 확정 안 된 건(`backend/expense.py` `open_summary`, 월말 업무라 지난달만) → 지출 증빙 탭 그 달
    - **완료 기준**: 매칭 정확도·계정 과목 정확도를 규칙 기준선([[치과 AX - 평가 설계]] §5 ⑧-2)과 나란히, 자동 확정 오류율(평가 달 밖 정답을 추가 검증에 씀)
- **⑨ 미예약 환자**: 다시 올 이유가 있는데 다음 예약이 없는 환자를 칩과 코드 점수 순으로 보인다(`/missed`, `backend/missed.py`). 1단계(코드)만 만들고 2단계(AI)는 보류한다 — 아래 "2단계"
  - **목록 조건**: completed 내원이 있고, 기준일(포함) 이후에 그날 아침 잡혀 있던 예약이 없고, 연락 기록으로 빠지지 않았고, 칩이 하나 이상. 사실은 기준일 아침 기준(그날 전 사건만 — ④처럼 지난 날짜도 다시 셀 수 있다)
  - **칩**: 리콜 연체 · 올해 스케일링 급여 미사용 · 노쇼 뒤 재예약 없음 · 미수 잔액 · 진료계획 미예약 · 다른 치과 추정(외부 이력 사유로 거절·조정된 청구, 마지막 답장 뒤 답 없는 안내 문자 `NO_REPLY_RUN`번 연속, 노쇼 뒤 재예약 없음 중 하나). 리콜·스케일링·미수·진료계획 규칙은 ④ 준비표와 같다. 화면은 칩마다 인원수(칩 필터·숨기기 전)
  - **순위**: 점수 = "연락하면 결과(예약·수납)가 날 가능성". 가중 덧셈 + 마지막 방문 반감 + 미수(금액 비례, 상한 — 미수 하나로 맨 위를 차지하지 않게). 올림: 최근 방문·진료계획 미예약·올해 스케일링 급여 미사용·리콜 연체·미수. 내림: 노쇼 뒤 재예약 없음·문자 무응답·외부 이력 사유로 거절·조정된 청구·최근 연락했는데 결과 없음. 칩이 많다고 위가 아니다. 값은 원칙으로 정하고 과거 데이터로 맞추지 않는다(가상 데이터에는 연락 효과가 없어 맞추면 "연락 안 해도 올 사람"이 위로 간다 — [[치과 AX - AI 실험 기록]] §21). 값마다 이유를 `backend/missed.py` `REASONS`에 두고 화면 "순위는 어떻게 정해지나요?"가 지금 값과 같은 문구를 보인다. 기본값은 `WEIGHTS`, 바꾼 값만 `ax_settings.missed_weights`. 최근 연락은 앱 연락 기록만 읽는다(생성 데이터의 리콜·리마인드 문자는 거의 모든 환자가 받는 자동 문자라 넣으면 대부분이 내려간다)
  - **연락 기록**: 결과 `예약함`(빠짐) · `부재중·안 받음`(남음, 기간 동안 감점) · `나중에 다시`(남음, 기간 동안 감점) · `안 오겠다고 함`(기간 동안 빠짐) · `다른 치과 다님`(빠짐), 수단 전화·문자, 누가(파트)·언제(실제 시계). 환자마다 가장 최근 기록이 정한다. 가장 최근의 다른 결과 뒤 부재중이 연달아 쌓이면 문자 무응답과 같은 감점. 기간 값은 `WEIGHTS`
  - **화면**: 칩 필터 · 연락함 숨기기(최근 연락의 감점 기간이 남은 환자만 — 부재중·나중에 다시) · 순위 설명, 처음 10명, 더보기마다 10명씩(`backend/missed.py` `PAGE`). 순위 칸은 칩 필터 중에도 전체 순위. 목록에서 빠지는 결과(예약함·안 오겠다고 함·다른 치과 다님)는 남기기 전에 한 번 더 묻는다. "1순위" 꼬리표·필터는 두지 않는다(처음 10명이 그 역할). 오늘 화면 "사람이 볼 일"에는 숫자 없는 고정 링크(§4 오늘 화면)
  - **2단계(보류)**: 근거 찾기 에이전트(상위 환자의 통화·문자·차트에서 다른 치과 근거 — 보여 주기만 하고 점수에 넣지 않는다), 사람이 보내는 문자 초안(미수 안내·치료 권유, LLM — 큰 계획은 "가장 급한 것 하나부터", 숫자는 ④ 후검증 재사용), 의료·금액 내용이 없는 안내의 템플릿 자동 기록(`ax_outbox`, 실제 발송 없음). 보류 이유: 병행은 칩만으로 잡혀 에이전트가 생성 규칙을 다시 맞히는 정도다. 다시 열 때 정할 것: 에이전트 대상과 채점 모수(화면용 상위 몇 명 / 채점용 고정 표본), 병행·이탈을 따로 보고(병행은 칩만으로 다 잡혀 합치면 부풀려진다), 자동 안내를 연락 기록에 남길지
  - **완료 기준**: 1단계 — 칩·목록 조건·점수·연락 기록 회귀 테스트(코드, ④ 규칙과 대조, 쿼리 수가 환자 수와 무관). 2단계 — 다른 치과 추정의 정밀도·재현율(칩만 쓴 기준선과 나란히, 정답은 흔적 있는 이탈·병행 — [[치과 AX - 평가 설계]] §5 ⑨), 문자 후검증 통과율

## 6. 진행 조건

생성·평가셋 작성의 순서 제약은 [[치과 AX - 가상 데이터 생성 설계]] §0·§5.1, [[치과 AX - 평가 설계]] §3.1.

**앱 착수 조건**: 데이터 상태가 고정([[치과 AX - 가상 데이터 생성 설계]] §0)

**`make gate`** (종료 코드. 코어 ①~③ 합격 기준 — `make dev`를 끄고 돌린다)
1. ①·②·③ 완료 기준 전부(§4) — pytest 기준은 `make test`, UI 테스트(Playwright)는 `make e2e`(§4 ②, fixture는 §9), 수치는 `evaluation/gate.py`가 실데이터 DB(캐시된 실모델 분류)에서 판정 풀 `ok`를 보고 dev 평가를 새로 돌려 확인한다(과금 — 무료 검사를 다 넘은 뒤에만). dev 평가에 앱 경고(빈 색인·리랭커 실패)가 있으면 불합격
2. `next build` exit 0

`make ci`(착수 전 — CI가 돌릴 타깃: `make lint` + fixture + fake 게이트웨이 + pytest + verify + `next build` + Playwright. 그 전의 CI는 `CLAUDE.md` 깃 절)와는 다른 타겟.


## 7. 운영 결정

- 인증 없음. 상단 파트 선택(원장 / 데스크 / 상담실장)으로 `judged_by`와 처리한 파트(할 일 체크·새 통화 추가·확인할 통화 확인함, ⑧ 확정, 자동 처리 되돌리기)를 남긴다. 직원 이름은 남기지 않는다. 에이전트가 한 일은 실행 id로 남겨 사람과 구분한다
- 토큰 스트리밍 없음. ③ 챗은 진행 이벤트 SSE, 배치(①·④)와 야간 실행은 `ax_jobs` + 폴링
- `make save-demo` / `reset-demo`(착수 전, 서버 중지 → 파일 교체 → 재시작)
- 설정 변경은 CLI `make set KEY=… VALUE=…`(착수 전, 허용 키: `active_prompt_version`·`active_models`·`blind_versions`·`daily_usd_limit`·`labor_cost_assumed`·`auto_policy`(지금은 `make auto-policy`)·`prompt_versions` — 기준일은 바꾸지 않음). 화면 없음
- 배포: 로컬 `docker compose` + 녹화 영상. 공개 필요 시 볼륨 있는 단일 서버
- LLM 실패는 `failed` 기록 + 재시도 버튼
- **모델 사용** (비용의 원본은 여기 — 모델은 [[치과 AX - 앱 설계]] §7·`config/llm.yaml`): 튜닝 중 경량 모델, 데모 직전 1회만 상위 모델 — 비용 때문이고, 상위 모델은 튜닝 대상이 아니라 최종 구성(= test 1회 구성, [[치과 AX - 평가 설계]] §1 원칙 2)이다. 튜닝 중 상위 모델로 dev 약 30건만 돌려 출력 형식·실패율만 점검할 수 있다(별도 버전, 집계에서 제외)
- **비용**: 생성기 1회 약 $35(Batch — 녹취록 약 $20·차트 서술 약 $12·문서 약 $1. 프롬프트를 고쳐 다시 채우면 그 작업만큼 더), 런타임 3주 $40~100(추정, §9에서 실측). 하드리밋 런타임 $15/일, 생성기 $40/일(즉시 호출에만 — `config/llm.yaml` `daily_usd_limit`이 같은 값 — 앱의 `ax_settings.daily_usd_limit`은 그날만 올리는 값). 생성기 배치(`make llm-fill-api`)는 하루 상한 밖 — 건수가 정해져 있어 사람이 건수(`make data`가 알려 줌)를 보고 제출한다

| ① 분류 | 강한 기준선(규칙·글자 n-gram) → 분류기 | 항목별 모델 vs 골드 정확도(같은 통화) |
| ① 분류 | vN → vN-final (같은 프롬프트, 경량 → 상위 모델) | 목적 Strict(헤드라인)·항목별 모델 vs 골드 정확도 |
| ① 교차검증 | 엇갈림 vs 같은 양 무작위 검토 | 오류 포착 향상 배수·일치 오류율 |
| ① 자동 종결 | — | 자동 처리율·자동 처리 오류율 |
| ① 후속 처리 | 에이전트 vs 규칙 기준선 | 처리안 정확도 |
| ② 판정 | 판정기 vs 골드 | 항목별 일치율·운영 구간에서 사람이 보는 비율 |
| ② 골드 점검 | 중재 판정기 vs 사람(표본) | 항목별·중재 선택별 일치율·골드 오류 건수(사람 표본 기준) |
| ① 요약 | 프롬프트 v1 vs vN (같은 모델) | 블라인드 승률(LLM 쌍 비교) |
| ① 요약 | vN vs vN-final (경량 → 상위 모델) | 블라인드 승률(LLM 쌍 비교·사람 투표)·둘의 일치율 |
| ③ 검색 | 리랭커 off → on | Hit@5·MRR·최신성(`--retrieval-only`) |
| ③ 챗 | 단순 RAG 기준선 → 에이전트 | 인용 정확도·환각 억제율(도구 선택 정확도는 에이전트만) |
| ④ 준비표 | 템플릿 기준선 → LLM 제안(조사 에이전트를 만들면 조사 전 → 조사 후, §9) | 제안 후검증 통과율, 주의사항 반영률·과잉 언급률, 과잉 제안률 |
| ⑤ 청구 (슬롯) | AI vs 기준선("서술 있는 줄 전부"·키워드 규칙) | ⑤-2 정밀도·재현율(임상 요건형, 차트 기반 누락은 합성 사례 — 실데이터는 n건 중 m건), ⑤-2 요건 사유 조정 건 판단(vs 모두 정당·모두 다툴 만함), ⑤-3 절 단위 Hit@5·MRR·서류 사유 차트 문장 인용 실재율, ⑤-4 후검증 통과율·첫 답 근거 없는 문장 비율 |
| ⑥ 리포트 (슬롯) | 시나리오 DB | 튄 숫자 원인 정확도 |
| ⑧ 재무 (슬롯) | 에이전트 vs 규칙 기준선 | ⑧-1 원인 정확도(규칙으로 되는 / 애매한), ⑧-2 매칭·계정 과목 정확도, 자동 처리 오류율 |
| ⑨ 미예약 환자 (슬롯, 2단계) | 에이전트 vs 칩만 쓴 기준선 | 다른 치과 추정 정밀도·재현율 |
| 운영 에이전트 | 에이전트 vs 고정 순서 | 시나리오 DB의 환자 묶음 재현율·실행 비용 |
| 재발 방지 (공통) | — | 재발 방지 규칙 수·규칙별 차단 횟수·같은 유형 재발 건수 |

- **증명하는 것**: AI가 조사·처리·개선까지 맡되, 코드(후검증·정책·관문)와 사람 표본으로 검증하며, 실수를 재현 테스트와 훅으로 남겨 재발을 막고, 조건 간 차이로 개선을 보여 준다
