> **어떤 데이터를 어떻게 만드나.** 규칙·절차의 원본. 값은 코드가 원본이고 이름으로 가리킨다(CLAUDE.md). 아직 코드가 없는 값(§2.4 심사 결과 분포, §4.1 분포 등)은 구현 때 코드로 옮긴다. config 키는 `config` `unpaid_rate`처럼 접두어를 붙인다(`tests/test_doc_sync.py`가 검사).

## 0. 전제

| 항목 | 결정 |
|---|---|
| 규모 | large = `config/generator.yaml` 기본값(기간·환자·하루 상한·통화·문서 수) |
| 축소 규모 | `SCALE=small`은 끝(`config` `range.end`) 고정·시작일만 늦춘다(`config` `scale_presets`) → TODAY 기준 구간(확정월·제출월·전월·미래)이 모두 남음. **하루 밀도와 구환 수는 모든 규모에서 같다**(신환만 기간에 비례) — 환자 1인당 수요가 같아야 같은 파라미터로 두 규모가 모두 성립한다. 통화 전사·판정/블라인드 풀만 기간 비율로 축소, 문서 수(`config` `documents`)는 고정 |
| 평가 규모 | 사람 판정·RAG 질문 작성·`eval.py` 보고·`make gate`는 **large 하나에서만**. small은 개발·테스트용 |
| 기준일 | `TODAY`(config) 고정. 앱에서는 바꾸지 않는다(원본 [[치과 AX - 앱 설계]] §6) |
| 보험 | 건강보험 단일. 월 1회 일괄 청구. 실손은 환자 플래그 + 통화 소재만. 수가·심사는 흉내만(급여 청구액 = fee × 0.7, 소아 급여 특례 없음) |
| 테이블 접두어 | 현실의 소속 시스템 기준: `emr_*` 병원 원본(앱은 읽기 전용) / `ax_*` AX 시스템(앱이 읽고 씀) / `truth_*` 정답 별도 DB. `ax_calls`·`ax_documents`는 생성기가 채우지만 현실에선 AX 도입 후 쌓이므로 `ax_`. 슬롯 데이터도 같은 기준(통장·카드 거래 → `emr_`). **데이터를 고정(LLM 7·9·9b단계 실행)한 뒤에는 기존 `emr_*`를 수정하지 않고 새 테이블로** — 바뀌면 LLM 캐시·전사·사람 판정까지 연쇄 무효(LLM 캐시는 §5.1, 쓰기 보호는 [[치과 AX - 기능 정의]] §9). 슬롯의 기반 데이터는 고정 전에 정형 단계에 처음부터 넣을 수 있다(예: 슬롯 ⑤의 청구 오류 §2.4, 청구 기준 문서 §4.2, 차트 기록 §4.3) |

## 1. 병원 프로필

- 직원 구성·담당은 `master.STAFF`
- 영업시간·휴진(목·일·공휴일)·30분 슬롯은 `master.HOURS`·`SLOT_MIN`, 공휴일은 `config/holidays_2026.json`
- **생성 시 강제하는 운영 제약은 둘뿐**: (1) 예약은 진료일 영업시간 안의 슬롯(평일 점심 제외) (2) 하루 비취소 예약 ≤ 상한(`master.daily_cap` — `config` `visits_per_day`를 그날 슬롯 수에 비례해 내림, 토요일은 절반). 시각대별 상한·체어·원장/위생사 동시성은 모델링하지 않는다 — 기능은 날짜와 순서만 본다
- 비율 목표(노쇼·변경·신환 등)는 시뮬레이션 파라미터로 맞추고 강제하지 않는다 — 확인하는 경고·리포트는 §5.3

## 2. `emr_*`

컬럼·enum은 `shared/schema.sql`. 여기서는 **규칙이 붙은 것만** 적는다.

### 2.1 시술

값(코드·분류·급여·비용·소요·적용 연령·치아 단위)은 `master.PROCEDURES`. 코드에 없는 의미:
- 구강검진은 진찰·파노라마를 대체하는 가상 코드
- 임플란트 2차는 마스터에만 두고 **생성하지 않는다**(1차 선행 조건을 추적하지 않으려고)
- 미백은 가격 문의 통화 소재
- 시술의 `age_group`은 적용 대상(`age19plus` = 19세 이상, 노인 포함)이라 §2.2 연령 구간과 이름이 다르다
- `aliases`는 구어체 별칭 — 전사 fact 검증·검색 동의어(7단계에서 채움)

**치아 행**: 내원당 시술 1행(청구 1줄 — §2.4 청구 오류 줄은 예외). 치아 단위 시술은 `master.TOOTH_CHOICES`에서 1개를 뽑되 **코스(같은 수요의 연속 내원) 안에서는 같은 치아를 유지**(5b의 같은 부위 재시행 간격 요건이 성립하게), 아니면 `'00'`(센티널, NULL 아님).

### 2.2 환자

- **내원** = `completed` 예약. 노쇼·취소·아직 오지 않은 `scheduled`(TODAY 당일 포함)는 내원이 아니다. 마지막 내원일·가족 리콜은 이 기준
- **신환** = 창 안에서 처음 등록한 환자: `registered_at` = 첫 예약 `created_at`의 날짜(전화 예약 때 차트 생성) ≥ `range_start`. 화면·지표의 신환은 이 정의 하나뿐
- `chart_no` 형식 `C-00001`, 전화 `010-0000-xxxx`(가상 번호)
- **구환** = `range_start` 전 등록. 차트 번호는 등록순
- 파생(쿼리): 마지막 내원일, 가족 리콜 지남(가족 구성원 `MAX(내원) + recall_cycle < 기준일`)
- 연령 구간·비중은 `master.AGE_BANDS`. 비중은 추첨 없이 비중 × 인원을 반올림한 인원으로 맞춘다. 환자의 `master.FAMILY_SHARE`가 `master.FAMILY_SIZE`명 가족으로 묶이고, 소아는 100% 같은 가족 성인이 보호자. 소아 전화는 보호자 번호를 같이 쓴다(나머지는 환자마다 고유). 실손 `master.PRIVATE_INSURANCE_SHARE`, 이름은 전부 한국 이름, `recall_cycle_months`는 전원 `master.RECALL_CYCLE_MONTHS`. 노인 나이 상한 `master.MAX_AGE`
- **주의사항**(`emr_patient_alerts` — 예전 `emr_patients.note`는 없앴다): 환자당 0~3개, 행마다 주의사항 코드·기록일·출처(`intake` 등록 시 문진 / `visit` 진료 중 발견)·발견한 내원. 정의(문구·행동·관련 시술·대상 연령·성별·비율)는 `master` 목록(4b단계 구현 때 추가 — 항목은 [[치과 AX - 기능 정의]] §9). 4b단계가 자기 시드로 만든다: 문진분은 구환·신환 모두 기록일 = 등록일, 진료 중 발견분(마취가 잘 안 됨·구역반사·마취 후 실신)은 관련 시술을 받은 창 안 completed 내원 일부에 기록일 = 그 내원일(그날 차트에도 서술, §4.3). 장부에서 계산되는 사실(노쇼·미수·지난 스케일링)은 두지 않는다. 기록일 이후에만 보인다 — ④ 준비표·`query_patient`·통화 fact 모두 그 시점 기준

### 2.3 예약·진료

| 컬럼 | 의미 |
|---|---|
| `planned_procedure_code` | 예정 시술 — 준비표·전사가 읽음 |
| `rescheduled_from_id` | 변경으로 생긴 새 예약이면 원래 예약. **변경 쌍** = 원래(`cancelled`) + 새 예약(이후 상태는 일반 예약과 같음). 변경 쌍이 아닌 `cancelled`는 당일 취소뿐 — 취소 통화는 여기서 역산 |
| `booked_via` | 예약 경로 — `phone`(전화. 변경으로 생긴 새 예약 포함) / `desk`(내원 종료 때 데스크에서 잡은 코스 다음 회차). 예약 잡기 통화는 `phone`에서 역산 |
| `confirmed` | 직전 진료일 리마인드 응답 |
| `created_at`, `cancelled_at` | 예약을 잡은·취소한 시각 — 통화 시각·as-of의 근거 |

진료 기록(`emr_treatments`)은 completed 예약에 1행, 예정 시술 그대로. 불변식은 §5.3.

### 2.4 수납·청구

- **잔액** = Σ(`amount_due − amount_paid`). 창 안 completed 내원마다 `visit` 수납 행 1개(0원이어도). 미수는 `amount_due > 0`인 내원 중 `config` `unpaid_rate`에서 일부만 수납 → 그중 `config` `settle_next_visit`은 다음 내원 때 `settlement` 행(`amount_due = 0`)으로 정산, 나머지는 잔류. 발생률만 두면 잔액이 누적돼 준비표 미수 칩이 절반 넘게 켜진다. 결제 수단은 카드 80 / 현금 10 / 이체 10, 미수 내원의 부분 수납은 청구액의 U(0, 0.7), `settlement` 행은 정산한 다음 내원 예약에 붙인다(값은 5단계 구현 때 `master`로)
- **보험 잔여**(준비표 칩): 별도 테이블 없이 `emr_claims`의 그해 스케일링 급여 청구 유무로 계산 — 같은 사실을 두 곳에 두지 않는다. 청구 오류가 섞인 장부를 그대로 쓴다(데스크가 보는 화면과 같고, 청구 누락으로 칩이 잘못 켜지는 것은 ⑤-2가 잡을 현실 오류)
- **청구**: 급여 시술 completed마다 1줄(아래 청구 오류 줄은 예외). `claim_month` = 진료월, 월 일괄 청구만
  - `submitted_at`: 익월 1일(시각·휴진일은 따지지 않음), 전월분(`pending`)은 NULL
  - `status`: 전월 = `pending`(미제출) / 그 전 `SUBMITTED_MONTHS`개월 = `submitted`(결과는 장부에 없음) / 그 이전 = 확정(`paid·adjusted·denied`, 병원이 이미 아는 과거 결과)
- **청구 오류**(전 기간): 청구 기록은 한 벌, 상태만 `pending` → `submitted` → 결과. **5단계는 기준 오류만**(나이·횟수처럼 정형 조건으로 판정되는 것), 차트 서술을 읽어야 하는 임상 요건형 오류는 5b단계가 `truth_claim_errors`에 추가한다(진료·청구 행은 그대로, 차트에 요건 근거가 없거나 어긋남 — §4.3). 5단계가 심는 것은 **기준 오류**(급여 조건을 어긴 진료를 급여로 처리한 줄: 시술·치아는 기록대로이고, 실수는 청구 줄과 함께 그 진료 기록의 급여 금액·수납 청구액에도 들어간다 — 데스크가 급여 처리를 잘못한 것. 예: 19세 미만 스케일링·65세 미만 임플란트 1차를 급여로. 4단계를 바꾸지 않고 지금 생기는 진료에서 고른다. 조건은 `master` 값뿐이라 오류 목록 밖 줄은 모두 만족). 진료 기록과 단순 대조로 찾히는 누락·코드 착오는 심지 않는다(⑤-2에서 지표가 아니라 fixture 테스트 — [[치과 AX - 평가 설계]] §5). 종류·비율은 5단계 코드로, 정답은 `truth_claim_errors`에만(진료 1건당 최대 1개). 보낸 달의 오류는 그 오류에 맞는 사유로 조정·불능될 수 있다(아래 추첨). verify 필수 검사는 이 목록의 줄만 제외
- **대조 키** `(chart_no, service_date, procedure_code, tooth_no)` UNIQUE — 심사결과 대조용. 제출 월 결과 정답(`outcome`)은 `truth_claims`에만(앱 DB 쪽 전자 레코드는 슬롯 메모 ⑤-1)

**심사 결과 추첨**(확정 월 `emr_claims`, 정형 5단계. 제출 월 `truth_claims`는 슬롯 메모)
| 대상 | 분포(청구 줄 기준) |
|---|---|
| 확정 월 → `emr_claims.status` | paid 88 / adjusted 8 / denied 4 (`missing`·`extra`는 심사결과 대조 결과라 장부에 없음) |

- 금액: paid → `paid_amount = claim_amount` / adjusted → `claim_amount × U(0.5, 0.9)`, 10원 단위 내림 + `adjust_code` / denied → `paid_amount = 0` + `adjust_code`
- 사유 코드 10개는 `master.ADJUST_CODES`(5단계 구현 때 추가) — 코드마다 유형(요건 / 장부 밖)과 맞는 시술을 둔다. 조정의 판단 정답(⑤-3)은 따로 저장하지 않고 여기서 파생한다:
  - **정당**: `truth_claim_errors`에 있는 줄이 그 오류에 맞는 사유로 깎임
  - **다툴 만함**: 오류가 없는 줄이 요건 사유로 깎임(진료 기록이 청구 기준 §4.2의 요건을 충족 — 임상 요건형은 차트 기록 §4.3에 근거가 있음)
  - **보완 후 재청구**: 오류가 없는 줄이 장부 밖 사유(내역설명 누락·증빙 미제출 등)로 깎임
  - 세 유형의 비율·오류 → 조정 연결 확률과 위 분포의 관계는 5단계 구현 때

### 2.6 정형 생성 규칙 (2~5단계) — 정방향 시뮬레이션

> 하루씩 진행하며 예약을 잡고 그날의 예약을 처리한다. 사건이 시간 순서대로만 일어나므로 `created_at`·`registered_at`·코스 다음 회차·변경·노쇼 뒤 재예약이 저절로 정합된다. 강제하는 것은 §1의 운영 제약 둘과 §5.3 필수 검사뿐이고, 분포는 파라미터로 맞춘 뒤 경고로만 확인한다. 치료 코스는 연속 내원으로 있지만 회차 번호·순서는 기록하지 않는다(**회차 추적 없음**).

**(1) 환자와 수요** (2·3단계)
- **구환**: 창 이전 마지막 위생 내원일을 **시뮬레이션 시작 전 리콜 한 주기에 고르게** 시드(2단계) → 첫 리콜 기한 = 그날 + 리콜 주기(3단계, 첫날에 기한이 몰리지 않게 — 지터로 시작 전이 된 기한은 첫 `master.MAX_LEAD_DAYS`일에 나눠 받음). `config` `lapse_rate`만큼은 첫 리콜에 응하지 않는다(구환 첫 리콜만 — 신환과 이후 리콜은 응답. ④ 가족 리콜 지남 칩의 재료). **창 이전 내원 1행**: 그 마지막 위생 내원을 `emr_appointments`(completed) + `emr_treatments`(위생 시술 — 창 안 위생 내원과 같은 추첨)로 남긴다 — 창 안에 한 번도 오지 않은 구환도 마지막 내원(가족 리콜 칩·`query_patient`·통화 fact)이 비지 않게. 수납·청구·문자는 두지 않되, TODAY와 같은 해의 급여 스케일링이면 보험 잔여 칩(장부 기준)이 맞도록 청구 1줄을 둔다(`paid` 고정 — 청구 오류·심사 추첨 대상 아님). 진료 기록은 수가대로 금액을 두고, 차트는 템플릿 1행(§4.3), 진료 중 발견 주의사항의 대상은 아니다. 그해 급여 스케일링이면 그 해를 4단계 연 1회 이력(`scaling_years`)에 미리 넣는다(창 안 리콜이 다시 급여로 잡히지 않게). 3b단계 `pre_window`가 자기 시드로 2단계 날짜를 그 근처 진료일(등록일 뒤)로 맞추고 시술(성인·노인은 스케일링, 그 밖은 위생 가중표)·시각·전화 예약 시각을 뽑는다 — 2·3단계 결과를 바꾸지 않게 따로 둔다(리콜 기한과 4단계의 이후 리콜 계산은 2단계 날짜를 쓴다 — DB 내원일과 최대 7일 차이, 리콜 지터 ±30일 안이라 영향 없음). 행은 4단계가 먼저 넣는다(id 앞번호, 담당 위생사 순환). **창 안 집계·검사 범위**: 내원 구성·급여 진료 ↔ 청구 1줄 등 창 안 규칙은 `scheduled_at ≥ range_start`만 — 이 행은 그 밖. 등록일 < 그 내원일 < 창 시작(verify, 테스트 먼저)
- **리콜 주기** = `master.RECALL_CYCLE_MONTHS`개월 ± `master.RECALL_JITTER_DAYS`일
- **구환 수** = `config` `returning_patients`(규모와 무관하게 고정). 신환은 시뮬레이션이 목표 비율대로 만든 만큼이고, 환자 총수는 결과값이다
- **신환 후보 풀**: 이름·연령 등만 미리 만들어 두고 필요할 때 꺼내 등록
- **치료 수요**: 연령 구간별 월 발생률(`config` `treatment_demand_monthly`, 그날 나이 기준 포아송)로 '치료 필요'가 생기면 에피소드 하나((2))를 시작. **환자당 열린 수요는 동시에 1개**(진행 중인 에피소드·잡힌 예약이 있으면 새 수요는 그 뒤로) — 신환은 첫 내원 전에 다른 수요가 없다
- **리콜 시드**: completed 내원이 생기면 다음 리콜 기한 = 마지막 위생 내원(없으면 그 내원) + 리콜 주기

**(2) 에피소드**
| 유형 | 내원 | 다음 회차 간격 |
|---|---|---|
| H 정기 위생 | hygiene 1 | 리콜 주기 뒤 다시 리콜 |
| T1 단발 | treatment 또는 consult 1 | — |
| Tn 치료 코스 | treatment `master.COURSE_VISITS` | `master.COURSE_INTERVAL_DAYS` |

- 치료 수요의 유형 비중: `master.EPISODE_MIX`(연령 구간별)
- 코스 안의 시술은 내원마다 (4)에서 독립 추첨(교정 월 체크도 일반 시술 — 교정 과정을 따로 추적하지 않음)

**(3) 하루 진행** (4단계) — 스냅샷 시점은 **TODAY 개원 전**: `range_start`부터 TODAY 전날까지 돌고(워밍업 없음), TODAY에는 아무 일도 없다. **4단계는 예약·상태·시각만 정한다** — 진료 기록·수납·청구는 5단계가 자기 시드로 completed에서 파생하므로(스케줄에 영향 없음), `config` `unpaid_rate`를 바꿔도 예약은 그대로다
```
for d in 진료일(range_start … TODAY − 1):       # 휴진일은 예약 생성·처리 없음
  1. 그날 예약 처리 (영업시간 순)
     - 상태 추첨: completed / noshow / 당일 취소(cancelled_at = 예약 1~`master.SAMEDAY_CANCEL_LEAD_MIN`분 전)
     - completed → (진료·수납·청구는 5단계) 코스 다음 회차가 있으면 그 자리에서 데스크 예약(booked_via = desk, created_at = 내원 종료 시각, 희망 간격 (2) 뒤 첫 가능일)
     - noshow·당일 취소 → 그 수요는 남고, 재예약 지연(`config` `rebook_delay_days`) 뒤 다시 전화 예약 — 같은 시술(다시 뽑는 경우는 (4))
  2. 전화 예약(booked_via = phone): 그날 기한이 된 수요(리콜·치료 시작·재예약)와 신환
     - created_at = 그날 임의 시각(사건 시각 참고), 희망 리드 1~`master.MAX_LEAD_DAYS`일 뒤 첫 가능한 진료일, 시각은 그날 가능한 슬롯 중 균등 추첨
     - 가능 = §1 운영 제약 둘 + 같은 환자 같은 날 예약 없음 + 날짜 ≤ range_end
     - 신환: 그날 잡힌 기존 환자 예약 수에 비례해(비율 `master.NEW_PATIENT_SHARE`) 후보 풀에서 꺼냄. 예약이 잡혀야 등록(registered_at = 그날).
       첫 유형은 내원 구성 목표(VISIT_MIX)대로, 진료면 T1·Tn은 `master.EPISODE_MIX` 비율
     - 새 예약마다(전화·데스크 모두) reschedule_rate 확률로 "변경 예정" + 변경일(created_at 다음 날 ~ 예약 전날 중 진료일) 추첨
  3. 변경: 오늘이 변경일인 예약 → 원래 예약 cancelled(cancelled_at = 오늘 임의 시각), 새 예약은 원래 날짜 뒤 1~`master.RESCHEDULE_MAX_DAYS`일의
     첫 가능일(같은 유형·시술, booked_via = phone, created_at = 같은 시각, 다시 변경하지 않음)
  4. 리마인드: 오늘 전에 잡혀 있고 오늘 취소되지 않은 다음 진료일 예약에 발송(날짜 단위. 오늘 잡은 예약은 제외 — 문자·확인 통화가 `created_at` 뒤 같은 날에 들어갈 자리가 없을 수 있어서) → confirm_rate 확률로 confirmed

5단계(진료·수납·청구): completed마다 진료 기록 1행(창 이전 내원 포함 — 수가대로 급여·본인부담 금액), 수납·청구는 창 안만(예외: 창 이전 그해 급여 스케일링 청구 1줄, §2.6 (1)), visit 수납(paid_at = 내원 종료 시각), 미수 정산은 다음 completed
내원 종료 시각에 settlement 행, 급여 시술은 청구 1줄(§2.4)
```
- **사건 시각**: 전화 예약·변경·통화 시각은 그날 개원~평일 마감 사이 임의 분(점심·토요일 마감·같은 날 다른 예약과의 선후는 따지지 않음, 검사하지 않음). 기능이 쓰는 것은 날짜와 사건 순서뿐
- **시작 직후**: 워밍업 없이 `range_start`부터 돌아 모든 사건이 창 안에 있다. 처음 최대 리드(`master.MAX_LEAD_DAYS`)는 미리 잡힌 예약이 없어 덜 찬다 — large에선 2월 초(확정 청구 월)라 기능 영향 없고, 하루 채움 리포트에서 뺀다
- TODAY 이후에는 TODAY 전날까지 잡힌 예약만 남는다 — 미래 일정이 덜 찬 상태가 정상
- 하루 상한이 차면 수요는 뒤로 밀린다(희망 리드보다 늦어질 수 있음). 하루 채움 리포트(§5.3)로 확인
- 연령 기준일은 예약일(= 시술일)

**(4) 유형별 예정 시술 가중** (`planned_procedure_code`): `master.PLANNED_WEIGHTS`(유형 × 연령 구간, 예약일 기준). 성인·노인 hygiene은 가중이 아니라 규칙(`master.HYGIENE_SCALING_BANDS`) — 그해 급여 스케일링(`master.SCALING_MIN_AGE` 이상)을 이미 했으면(completed) 구강검진, 아니면 스케일링. 첫 후보일보다 늦은 날 잡혀(재예약 포함) 연령 구간·연도가 바뀌면 그날 기준으로 다시 뽑는다

- **스케일링**: `master.SCALING_MIN_AGE` 미만은 비급여(청구 없음). 성인은 그해 이미 썼으면 hygiene이 구강검진으로 바뀌므로 2회째가 생기지 않음
- **임플란트 1차(`conditional`)**: 시술일 기준 `master.CONDITIONAL_INSURED_MIN_AGE` 이상 급여(마스터의 본인부담률), 미만 비급여(본인부담 1.0, 청구 없음)

## 3. 생성기가 적재하는 `ax_*`

생성기는 `ax_calls`와 `ax_documents`만 적재한다(생성기와 앱 사이의 계약). 나머지 `ax_*`와 `make index`·`make fixture`는 [[치과 AX - 앱 설계]].

**`ax_calls`**
| 컬럼 | 의미 |
|---|---|
| `call_uid` | 불변 키 `c-0481` — 시드 셔플 순번. 캐시 키·human import 폴백. 목적을 담은 형식(`purpose:순번`)은 라벨 누출이라 금지 |
| `patient_id`, `caller_phone`, `caller_name` | **분류기 입력에 쓰지 않음**(분류기 입력 규칙은 앱 설계 §1) |
| `transcript` | 화자 구분된 **순수 대화만**(prefix 없음, 차트번호 발화 없음) |
| `in_eval_pool`·`eval_sort_order`, `in_blind_pool`·`blind_sort_order` | 생성기가 층화 추출해 마킹 — **카테고리 정보 없음**. 크기·순번·split 규칙은 [[치과 AX - 평가 설계]] §2.1 |

## 4. 비정형 생성

### 4.1 통화 전사

**절차**(건당)
1. 상대 → 목적 → 급함·플래그를 분포에서 추첨 = 골드 라벨
2. 환자/보호자면 EMR에서 환자를 뽑고 fact 추출: 최근 내원·시술, 잔액, 다음 예약, 가족, 주의사항(통화 시각 이전 기록분. 청구는 넣지 않음 — 장부 오류가 전사로 번지지 않게). **통화 시각 이후의 사실은 넣지 않음**(`created_at/performed_at/paid_at ≤ 통화 시각`, status 컬럼은 TODAY 스냅샷이라 읽지 않음). 프롬프트에는 통화 **날짜만** 넘기고 시각은 넘기지 않는다(사건 시각은 점심·토요일 마감 뒤에도 찍힘 — §2.6 사건 시각)
3. 노이즈 추첨 25%
4. **라벨 → 상황 → 대화** (단일 JSON 호출 `{scenario, transcript}`). 라벨 어휘("예약 변경", "불만")를 대화에 직접 쓰지 않게 지시
5. 전사 규칙: `환자:`/`직원:`, 2~4분 분량, fact 날짜는 절대 날짜(`11월 24일`), 시술은 표준명 또는 `aliases`
6. **건별 검증 루프**: (a) fact 날짜·시술 별칭 substring 존재 (b) 라벨 어휘 직접 등장 없음 (c) 금지 토픽 미매칭 → 실패 시 그 건만 재생성(최대 3회, 그래도 실패면 fact 단순화)
7. 금지 토픽: 생성 프롬프트에서 다루지 말라고 지시하고, 정규식(`config` `forbidden_topics`)은 검사로만 — 걸리면 그 건 재생성(6(c))
8. 저장: 전사 → `ax_calls`, 라벨·fact·노이즈 → `truth_call_labels`
9. 층화 추출 → 판정 풀·블라인드 풀 마킹(평가 설계 §2.1)

**예약류 통화는 예약에서 역산**: 통화가 원인, 예약이 결과(`created_at ≥ range_start`인 예약만 — 창 이전 내원 제외). `booked_via = phone` 예약(변경으로 생긴 새 예약은 변경 통화로 쓰이므로 제외) → 예약 잡기, 변경 쌍 → 예약 변경, 당일 취소 → 취소, confirmed(직전 진료일) → 확인. **확인 통화**: confirmed 예약에서 역산, 시각은 리마인드 날(직전 진료일) 임의 시각 — 그 예약의 리마인드 문자 `sent_at` 이후. 방향은 아래 방향 분포대로. 통화 시각 = 그 이벤트 시각. 연결은 `truth_call_labels.used_fact`에 `appointment_id`를 담는다.

**목적 분포**(%) — 현실보다 고르게 둔 **평가용 분포**. 현장 인터뷰에서는 예약 변경이 약 70%였는데, 그대로 따르면 다수 목적만 맞혀도 정확도가 높게 나와 분류 평가가 무의미하고 희귀 목적(불만·응급·모르겠음)이 평가할 만큼 나오지 않는다. 예약류는 예약 이벤트에서 역산하므로 실제 비율은 verify 경고(±2%p)로 본다
| 목적 | % | | 목적 | % |
|---|---|---|---|---|
| 예약 잡기 | 18 | | 가격·비용 문의 | 8 |
| 예약 변경 | 15 | | 수납·청구 문의 | 4 |
| 예약 확인 | 8 | | 서류·기록 요청 | 4 |
| 예약 취소 | 6 | | 응급·통증 | 5 |
| 리콜·안내 전화 | 8 | | 불만 | 3 |
| 치료 문의 | 10 | | 기타 | 3 |
| 보험 문의 | 6 | | 모르겠음·애매 | 2 |

**상대**: 환자 60 / 보호자 15 / 처음 연락 15 / 보험사 3 / 업체 4 / 기타 3

**enum 키**: 목적 `book / reschedule / confirm / cancel / recall / treatment_q / insurance_q / price_q / billing_q / document_req / emergency / complaint / other / unknown` · 상대 `patient / guardian / new_caller / insurer / vendor / other` · 급함 `urgent / normal / low`
**급함**: `emergency` → 전부 `urgent` / 노이즈 '급함 애매한 통증' → 50% `urgent` / 나머지 `normal` 85 · `low` 15
**플래그**: 주 목적이 함의하면 항상 true(`emergency`→emergency, `complaint`→complaint, `price_q`→price_inquiry, `book`→wants_appt) + 복수 주제 통화는 부 주제 플래그 1개. `appt_confirmed`는 `book`·`reschedule`의 70%. `has_todo`는 `confirm`·`recall` 30%, 나머지 80%
**노이즈**(25%): 주제 2개 섞임 10 / 말 끊김·되묻기 8 / 급함 애매한 통증 4 / 보호자가 정보 헷갈림 3
**방향**: outbound ~20%, **리콜에만 두지 않음** — 리콜·안내 8%p 전부 + 예약 확인 4%p + 수납 문의 3%p + 서류 요청 2%p + 치료 문의(경과 확인) 3%p. outbound의 절반은 복합 주제("리콜 안내 + 예약 희망")로 — 단일 구조면 흐름만으로 식별됨

**복수 주제 통화의 생성 제약**: `primary_purpose` 1개 + 부 주제는 불리언 플래그(가격·불만·응급·예약 희망)로 표현되는 조합만 생성. 플래그로 표현 불가한 조합(예: 예약 변경 + 서류 요청)은 만들지 않음. `accepted_purposes[]`에 주·부 모두 기록 → 채점은 평가 설계 §2.2

**`call_uid`는 6단계에서 전사 슬롯에 부여** — 7단계 LLM 캐시 키에 들어가므로 전사 전에 확정. 전사 슬롯은 6단계에서 `has_transcript=0` 빈 행으로 만들고(시각은 §2.6 사건 시각) 7단계가 채움

생성 분포는 현실대로(치우침 유지 — 리포트 쪽 처리는 [[치과 AX - 평가 설계]] §1 원칙 6).

### 4.2 RAG 문서

**순서**: 문서 생성 → ③ 질문을 사람이 **생성 후** 작성(평가 설계 §3.1) → 방해 문서에 정답 텍스트가 없는지 verify. 금지 토픽 지시·검사는 문서·통화·문자 전부.

**어휘 일치 방지**(생성 지시): 질문이 물을 핵심 어휘를 문단에 그대로 쓰지 않게 — "노쇼 3회"의 답 문단은 "예약 부도가 세 차례 누적되면"처럼 동의어·우회 표현.

| 종류 | 수 | 생성 |
|---|---|---|
| 직원 매뉴얼 | 12 | LLM, 정답 문단 심기 |
| FAQ | 10 | LLM |
| 보험 안내 | 6 | LLM + 마스터 값 주입 |
| 청구 기준 | 5 | LLM + 마스터 값 주입. 시술 분야별 문서(예방·치주·보존보철·외과임플란트·공통 — 고시처럼), 문서 안에서 조정 사유 코드(`master.ADJUST_CODES`) 하나 = 소제목 한 절. ⑤-3의 정답 = 그 사유의 절. 급여 조건은 `master` 값만 쓴다(생성기가 추적하지 않는 조건을 쓰면 오류 없는 줄이 위반처럼 보임). 임상 요건형 조건(§4.3)도 `master`에 두고 같은 값을 쓴다 |
| 원내 공지 | 12 | 템플릿 + LLM. 날짜·버전·수치가 바뀌는 구조(최신성 평가용) |
| 공지 옛 버전 | 12 | 공지마다 1개, 다른 수치·이전 날짜 |
| 치과 상식 | 10 | LLM |
| 유사 주제 무답 | 10 | LLM |
| 타 병원·일반 | 5 | LLM |

전부 마크다운. 청킹·색인은 [[치과 AX - 앱 설계]] §3.

### 4.3 차트 기록

③ 차트 케이스 검색과 ⑤-2·⑤-3의 근거. **사실 → 서술**: 코드(5b단계)가 근거 사실을 정하고 정답은 truth 쪽, LLM(9b단계)은 그 사실을 서술만 한다 — 통화 전사(§4.1)와 같은 틀이라 결정성·캐시·건별 검증을 재사용.

- **테이블**: `emr_chart_notes` — 진료(`emr_treatments`) 1건당 1행(`treatment_id`, `dx_code` 상병, `note` 본문. 실제로는 한 내원에 여러 시술이 한 기록에 묶이기도 하지만 청구 줄과 1:1로 맞추려고 단순화). 병원 원본이라 `emr_`, 기존 `emr_*`는 수정하지 않는 새 테이블. `dx_code`는 정상 EMR 값(오류 줄만의 신호가 되지 않게 추첨). **특이 여부는 앱 DB에 두지 않는다**(정답은 `truth_chart_notes` — [[치과 AX - 평가 설계]] §6). 서술인지 템플릿인지는 본문 모양으로 드러나므로 숨기지 않고, 디코이로 "서술 ≠ 특이"를 만든다
- **본문 칸**(웹 조사에서 국내 차트 실물 예시를 찾지 못함 — 기록 원칙·청구 요건으로 잡고 현장 확인으로 맞춤): C.C(환자 말 그대로) · 소견(치아 번호·치주낭 깊이·출혈·동요도·방사선) · 상병 · 시행(시술·부위, 분할이면 n/3악) · 내역설명(요건 근거) · 주의사항 처리 · 교육 · 다음 계획(다음 회차·간격).
- **5b단계가 정하는 사실**(그 내원 시점에 알 수 있는 것만 — 실제 다음 예약 날짜 같은 미래 사실은 넣지 않음): (1) 소견 수치 — 위생·잇몸치료 내원만, 치주낭 깊이(mm)·출혈·치석 정도·동요도 (2) 주의사항 연결 — 그날 시술과 관련된 주의사항(기록일 ≤ 내원일)을 어떻게 처리했는지("혈압 측정 후 진행", "보안경 사용"), 진료 중 발견이면 그 사실 (3) C.C — 시술별 증상 목록에서 추첨 (4) 분할·간격·상병·내역설명 — 임상 요건형 시술 줄 (5) 다음 계획 — 그 시점에 정해진 코스 남은 횟수·간격·다음 내원 목적. 건별 검증은 이 사실(수치 포함)이 본문에 그대로 있는지 본다 **문장형**으로 쓴다(현장 확인 — 칸 머리말·약어 없이 자연 문장). 현장에서 차팅 내용에 따라 청구 시 수가가 따라온다고 해, 차트와 청구는 같은 원천이다 — 그래서 오류는 차트·청구 불일치가 아니라 급여 기준 위반이 진료 기록과 청구에 함께 들어간 형태(§2.4)
- **템플릿**: 일반 진료는 템플릿 여러 개 + 소견 칸 추첨으로 모양을 다양하게(코드, 5b단계)
- **특이 케이스 = 오류 줄 + 임상 요건형 시술 줄**(진료 시점에 정해진 사실 — 제출 월 심사결과는 슬롯 착수 때 추첨하므로 조정 여부로 잡지 않는다. 어떤 줄이 나중에 조정돼도 "다툴 만함 = 차트에 요건 근거 있음"이 성립):
  - 임상 요건형 오류 줄: 5b가 임상 요건형 시술 줄 일부를 골라 `truth_claim_errors`에 추가하고, 차트에 요건 근거가 없거나 어긋나게 서술한다(5단계 청구 행은 그대로)
  - 창 이전 내원: 템플릿 1행만(LLM 서술·디코이·특이 케이스 대상 아님)
  - 오류 없는 임상 요건형 시술 줄: 전부 서술하고 차트에 요건 근거가 있다
  - 임상 요건 종류는 `master`(5b단계 구현 때 추가). 후보(공개 자료 조사 — repo 밖 Obsidian 노트 `치과 AX - 심평원 청구 조사`): 부분 치석제거 뒤 치주치료 연결(월 넘김), 같은 부위 재시행 간격, 내역설명. 나이처럼 정형으로 판정되는 요건은 서술 대상 아님
- **디코이**: 정답이 모양으로 새지 않게 평범한 진료 일부(특이 케이스의 1~2배 — `master.CHART_DECOY_RATIO`로 5b 구현 때 옮기고 문서에서 숫자 삭제, 시술 분포로 층화)도 LLM 서술. 그래도 "서술 있는 줄 전부"는 재현율 100%의 기준선이 되므로 ⑤-2 평가에 이 기준선을 함께 보고한다
- **서술 규칙**: 임상 사실만. 정답 어휘("청구 오류"·"삭감"·"조정") 금지(§4.1 라벨 어휘 금지와 같은 규칙). 환자 이름 없음(비식별), 차트 번호는 메타데이터만
- **건별 검증**: 근거 사실(치아 번호·수치·시술 별칭)이 본문에 그대로 있음, 금지 어휘 없음, 환자 이름 없음 → 실패 건만 재생성(§4.1 절차 6과 같은 방식)

- **단계별 독립 시드**: 각 단계는 `config` `seed`와 단계 이름으로 자기 난수 생성기를 만든다 — 단계를 추가·삭제해도 다른 단계의 결과가 바뀌지 않게(구현 방법은 `generator/seeding.py`). 5단계 안에서도 치아·수납·청구 오류·심사 추첨은 이름이 다른 난수로 나눈다 — 미수 파라미터를 튜닝해도 오류·심사 정답이 흔들리지 않게
- **정형 먼저, LLM 한 번**: 정형(1~6, 3b, 4b, 5b) 완성·verify(small·large 둘 다) 뒤에 LLM(7·9·9b)을 한 번 돌린다. 3b·4b·5b·9b는 기존 번호를 바꾸지 않으려고 붙인 번호(단계 이름이 시드를 정하므로 번호는 실행 순서 표시일 뿐). 정형 로직을 고치면 LLM 캐시가 전량 미스. **LLM은 large에서만** — small의 7·9·9b단계는 fake 게이트웨이(입력 해시 기반 결정적 가짜 전사·문서)를 써서 과금 없이 구조만 채운다(테스트 픽스처용)
- **LLM 캐시**: 생성물은 파일 캐시로 커밋, `make data REGEN_LLM=1`로만 재생성. 키 = `(call_uid, seed, prompt_template_hash, used_fact_hash, attempt)` — attempt가 없으면 검증 실패 후 재시도에 같은 실패작이 돌아옴

### 5.2 정답 출력 `ground_truth/`

DDL은 `ground_truth/schema.sql`(테이블은 그 단계를 구현할 때 추가 — `shared/`는 앱이 읽는 위치라 두지 않음). 테이블 정의와 채우는 쪽은 [[치과 AX - 평가 설계]] §6. `truth_gen_meta.scale`은 프리셋 이름, 또는 verify 테스트가 손으로 만든 DB(`tests/verify_db.py`)의 `fixture` — 앱의 `make fixture`(small 데이터로 만듦)와는 다르다.

### 5.3 `make verify`

불변식("항상 성립해야 하는 것")의 원본은 이 표다. §2의 절차는 이것을 지키도록 짠다. 구현 현황은 `generator/verify.py` docstring.

**필수**(실패 시 중단. `planned_procedure_code`·`tooth_no` 값 있음과 대조 키 유일은 스키마(NOT NULL·UNIQUE)가 보장해 검사하지 않음)
| 영역 | 검사 |
|---|---|
| 참조 | FK 전부 유효. 다형 참조(`ax_llm_calls.ref_*`, `ax_chunks.source_*`)는 타입별 조인 |
| TODAY 구간 | TODAY 당일은 `scheduled/cancelled`만; TODAY 이후는 예약만(treatments·payments·claims 없음); `started_at`·`sent_at`·`submitted_at`·`effective_date`·`created_at`·`cancelled_at`·`registered_at`·`birth_date` ≤ TODAY; `confirmed`는 직전 진료일 ≤ TODAY인 예약만; 청구 상태는 §2.4(전월 `pending`, 제출 월은 `submitted`·결과 없음). 생성 기간은 `truth_gen_meta`에서 읽음(없으면 실패) |
| 충돌 | 같은 환자 같은 날 중복 없음 (§1 운영 제약은 생성 코드가 보장 — 기능이 의존하지 않아 검사하지 않음) |
| 예약 | `created_at` < `scheduled_at`; 취소는 `created_at` ≤ `cancelled_at` < `scheduled_at`; `cancelled_at`은 cancelled에만(cancelled는 필수); `confirmed`는 리마인드 대상(직전 진료일 전에 잡혔고 그날까지 취소되지 않음 — §2.6 (3) 4)만; 취소는 변경 쌍의 원래 예약 또는 TODAY 이전 당일 취소뿐; 변경 쌍 = 원래 예약은 cancelled·새 `created_at` = 원래 `cancelled_at`; 예약류 통화 시각 == 대응 이벤트 시각(확인 통화는 리마인드 날, 리마인드 문자 `sent_at` 이후); 예약 이벤트 수 ≥ 그 목적 통화 수(6단계, LLM 전); 창 이전 내원(`scheduled_at` < 창 시작)은 환자당 completed 위생 1행·등록일 < 내원일 |

### 5.4 기술 선택

## 슬롯 메모 — 심평원 청구 점검·삭감 대응(⑤, 조건부)

전제: 심사결과는 전자문서(줄마다 수가코드·조정 사유코드·조정 금액)로 받아 청구 프로그램이 반영한다. 종이 판독·PDF 렌더링은 하지 않는다. 기반 데이터는 처음부터 들어간다(청구 오류 §2.4는 5단계, 청구 기준 문서 §4.2는 9단계 — §0). 이미 정한 것:
- ⑤-1 입력 = 전자 심사결과 레코드: 제출 월 outcome 추첨 → `truth_claims` → 앱 DB 새 `emr_` 테이블로 적재 — 줄마다 금액·조정 사유코드만, `outcome` 분류와 결과에 없는 줄은 없음(정답 분리). **대조 키 어긋남**도 일부 심는다(같은 줄인데 레코드의 치아 번호·수가코드가 장부와 다름 — 정답은 `truth_claims`, 비율은 착수 시). ⑤-1 완료 기준이 대조 정확도라서. 어긋남은 1건으로 센다 — `truth_claims`에 이를 담을 enum·컬럼은 ⑤ 착수 시 추가. 전월은 `pending`이라 결과 없음. 확정 월은 장부에 이미 반영된 결과
- ⑤-2 입력 = 전월분 `emr_claims`(`pending`)와 진료 기록(`treatment_id`로 연결). 정답 `truth_claim_errors`(§2.4, 앱 DB에는 표시 없음)
- ⑤-3 문서 = 청구 기준(§4.2 표 — ③ 말뭉치에 처음부터 포함, ③ 질문에는 넣지 않음). 사유 코드마다 한 절이라 코드 → 정답 절이 생성 규칙에서 바로 나온다. 조정의 판단 정답은 §2.4 사유 코드 규칙에서 파생(따로 저장하지 않음)

분포·`extra_in_claim_review` 생성 방법은 ⑤ 착수 시 정한다.
