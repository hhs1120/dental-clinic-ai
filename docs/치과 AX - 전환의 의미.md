> **왜 만드나.** 기능 정의가 "무엇을", 데이터·평가 설계가 "어떻게"라면, 이 문서는 "전환 전후로 치과 일이 어떻게 바뀌나". 구현 스펙이 아니라 배경이다.

## 1. 전환 전: 사람이 "읽고, 옮기고, 맞춰 보는" 일

진료 외 업무의 대부분은 판단이 아니라 **확인**이다. 문제는 그 확인을 전부 사람이 한다는 것.

- 전화를 받으며 예약을 바꾸고, 통화 내용은 직원의 기억과 메모에 의존
- 보험사 지급 내역을 장부와 한 줄씩 대조 — 반복적이고 실수하기 쉬운, 가장 기피되는 일
- 팩스 정리, 서류 찾기, "그거 예전에 어떻게 했더라?" 동료에게 물어보기
- 아침 회의 전, 환자마다 예약·보험 잔여·미수·가족 기록을 여러 화면에서 따로 확인
- 월말에 통장·카드 매출·치과 프로그램 숫자를 엑셀로 옮기며 "왜 안 맞지?"
- AI를 써 봐도 그 답이 맞는지 확인할 방법이 없음 → 믿고 쓰거나, 아예 안 씀

## 2. 기능별 전후

### ① 통화 요약·분류
- **전**: 통화가 끝나면 직원이 기억으로 메모·할 일을 정리. 누락되면 콜백을 놓침. "그 환자 지난번에 뭐 물어봤지?"는 사람 기억에 의존
- **후**: 전사 → 모델 2개가 각각 요약·분류·할 일 → 두 모델이 **엇갈린 통화만** 표시
- **사람**: 엇갈림 배지가 붙은 통화부터 확인
- **보여줄 것**: 모델 vs 사람 일치율, 엇갈림 비율

### ⑤ 사람 판정 + 블라인드 비교
- **전**: AI 분류가 맞는지 아무도 모름
- **후**: 키보드로 건당 1.5~2분 판정 → 정답지가 쌓임 → 모델·프롬프트를 숫자로 비교. 모델명을 가린 블라인드 비교로 선입견 제거
- **사람**: AI의 결과를 검사하는 채점자
- **보여줄 것**: 프롬프트 v1→v2 정확도 변화, 블라인드 승률

### ③ 사내 검색 + 챗
- **전**: 매뉴얼·공지·통화·문자가 흩어져 있어 동료에게 물어봄. 바뀐 공지와 옛 공지를 혼동
- **후**: 질문 하나로 매뉴얼과 실제 사례를 나눠 찾고 출처와 함께 답. "내일 미수 환자 몇 명?" 같은 질문은 DB 조회 도구로. 근거가 없으면 답하지 않음(`refuse`)
- **보여줄 것**: Hit@5, 최신 공지 정답률, 도구 선택 정확도, 환각 억제율

### ⑧ 진료 준비표
- **전**: 환자마다 여러 화면을 뒤져서 아침 회의 준비
- **후**: 코드가 한 화면으로 모아 칩(예약·보험 잔여·미수·가족 리콜)으로 표시, AI는 "오늘 권할 것" 한 줄. 문장 속 숫자는 입력 사실과 대조해 후검증
- **사람**: 아침 회의에서 보고 판단
- **보여줄 것**: 제안 후검증 통과율, 30명분 사람 채점

### ② 보험 지급 통보서(EOB) 판독·대조 — 효과가 가장 큰 영역
- **전**: 스캔·팩스로 온 통보서를 한 줄씩 장부와 대조
- **후**: AI가 읽고 → 코드가 장부와 대조 → 맞으면 확정, 다르면 "확인 필요"만 사람에게
- **보여줄 것**: 판독 재현율, 대조 정확도, 자동 확정률(= 사람이 안 봐도 되는 줄의 비율)

### ⑥ 리포트 + ⑦ 아침 브리핑
- **전**: 월말에 엑셀을 붙잡고 숫자 정리
- **후**: 숫자는 쿼리가 계산, AI는 해석만. 모델 3개의 진단을 합본해서, 셋이 같은 말을 하면 진짜 문제로 봄
- **보여줄 것**: 본문의 숫자가 전부 계산값에 존재하는지

### ⑪ 재무 대조 에이전트
- **전**: 통장·카드·치과 프로그램을 월말에 엑셀로 맞춤
- **후**: 에이전트가 도구로 내역을 모아 장부와 대조하고, 안 맞는 것만 표시
- **보여줄 것**: 일부러 심은 불일치를 찾아낸 비율

## 3. 쓰는 AI 기술

| 기능 | AI 기술 | 핵심 포인트 |
|---|---|---|
| ① 통화 요약·분류 | LLM 구조화 출력(JSON 스키마 + 고정 enum), 음성 인식(STT) | 모델 2개 **교차검증** — 엇갈린 것만 사람에게 |
| ⑤ 사람 판정 | Human-in-the-loop 라벨링, 블라인드 쌍 비교 | 사람이 만든 정답지로 모델·프롬프트를 **숫자로** 비교 |
| ③ 검색 + 챗 | 하이브리드 검색(키워드 BM25 + 벡터 임베딩) + 리랭커, **도구 호출 에이전트**(도구 5개) | 매뉴얼·사례를 따로 찾아 출처와 함께 답. 근거 없으면 거절 |
| ⑧ 진료 준비표 | LLM 해석 + **그라운딩 후검증** | AI가 쓴 사실을 스스로 명시하게 하고, 코드가 입력과 대조 |
| ② EOB 판독·대조 | 비전 언어 모델(VLM) 문서 판독 | 흐릿한 스캔본 판독 → 코드가 장부와 대조. OCR 베이스라인과 비교 |
| ⑥⑦ 리포트·브리핑 | 멀티 모델 앙상블, 음성 합성(TTS) | 모델 3개의 진단을 합본 — 의견이 갈리면 사람이 봄 |
| ⑪ 재무 대조 | 도구 루프 에이전트 | 내역을 모으고 대조하는 다단계 작업을 에이전트가 수행 |

**모든 기능을 받치는 것**
- **LLM 게이트웨이**: 모델을 이름으로 호출, 장애 시 폴백, 호출마다 토큰·비용·지연 기록, 일일 비용 상한. 모델 교체는 설정 한 줄
- **평가 하네스**: 정답지와 앱 DB를 분리하고, 튜닝용(dev)과 보고용(test)을 나눠 "프롬프트 v1 → v2", "리랭커 on/off"를 같은 조건에서 비교
- **합성 데이터**: 정답 라벨을 먼저 정하고 LLM이 그에 맞는 통화·문서를 생성 — 실제 환자 정보 없이 정답이 있는 데이터셋
- **AI 코딩 에이전트로 개발**: Claude Code에 설계 문서·작업 규칙(`CLAUDE.md`)을 주고 테스트 우선으로 구현

스택: Next.js + TypeScript / FastAPI / SQLite(FTS5) + Chroma. 구체적인 모델·임베딩·리랭커는 dev 평가셋으로 비교한 뒤 정한다.

## 4. 팀원이 맡을 수 있는 영역

코어(①⑤③⑧)와 독립적으로 시작할 수 있는 과제들이다. 가짜 데이터·LLM 게이트웨이·평가 하네스는 이미 공용으로 깔려 있어서, 맡은 기능의 로직과 화면에 집중하면 된다. 각자 **자기 지표**를 갖고 결과를 숫자로 보여줄 수 있다.

| 영역 | 해 보는 것 | 결과로 보여줄 지표 |
|---|---|---|
| ② EOB 판독·대조 | VLM으로 흐릿한 스캔 문서 읽기, 판독 결과와 장부를 코드로 대조, "확인 필요" 검토 화면 | 판독 재현율, 대조 정확도, 자동 확정률 (OCR 베이스라인 대비) |
| ⑥⑦ 리포트·브리핑 | 숫자는 쿼리·글은 LLM으로 나누는 리포트, 모델 3개 합본, 그래프·PDF·TTS — 프론트 비중이 큼 | 본문 숫자의 계산값 일치율 |
| ⑪ 재무 대조 에이전트 | 통장·카드 가짜 데이터 설계부터 도구 7개 에이전트까지 — 에이전트 루프를 처음부터 만들어 보는 과제 | 일부러 심은 불일치의 재현율 |

범위와 완료 기준은 [[치과 AX - 기능 정의]] §5에 있다.

## 5. 바뀌지 않는 것

- **판단은 사람이 한다.** AI는 읽고 정리하고 제안까지만. 장부·차트에 직접 쓰지 않음
- **숫자는 코드가 계산한다.** AI가 매출을 지어내면 끝이다
- **믿기 전에 잰다.** 사람 판정과 정답지로 AI를 채점한다 — 이 프로젝트의 중심
- 직원의 역할은 "전부 확인"에서 "확인 필요만 확인"으로 바뀐다. AI가 사람을 대체하기보다 사람이 싫어하던 일을 가져간다

## 6. 이 프로젝트의 한계

- **실제 병원 데이터가 아니다.** 가짜 데이터로 재현한다. 그래서 절대 수치보다 조건 간 차이(전/후, v1/v2, 리랭커 on/off)로 보여준다
- **업무 시간 절감은 재지 못한다.** 대신 "사람이 봐야 하는 양"이 얼마나 줄었는지(자동 확정률, 엇갈림 비율)로 보여준다
- **실제 병원은 환자 정보가 밖으로 나가면 안 된다.** 이 프로젝트는 가짜 데이터라 외부 API를 쓰지만, 실제로 적용하려면 로컬 모델로 바꿔야 한다. LLM 호출이 게이트웨이 하나를 거치므로 바꿀 곳은 한 군데다
- 메신저·원내 방송·동의서·근태는 범위 밖 ([[치과 AX - 기능 정의]] §2)
