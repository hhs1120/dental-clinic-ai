> **왜 만드나.** 기능 정의가 "무엇을", 가상 데이터 생성·앱·평가 설계가 "어떻게"라면, 이 문서는 "전환 전후로 치과 일이 어떻게 바뀌나". 구현 스펙이 아니라 배경이다.

## 1. 전환 전: 사람이 "읽고, 옮기고, 맞춰 보는" 일

진료 외 업무의 대부분은 판단이 아니라 **확인**이다. 문제는 그 확인을 전부 사람이 한다는 것.

- 전화를 받으며 예약을 바꾸고, 통화 내용은 직원의 기억과 메모에 의존
- 심사결과는 전산으로 들어오고 프로그램이 일부 오류는 잡아 주지만, 깎인 건(조정)마다 사유를 보고 기준을 찾아 다툴지 정하고 사유서를 쓰는 건 사람 몫
- 청구를 보내기 전에 빠뜨린 것·깎일 만한 것을 기억에 의존해 점검
- 팩스 정리, 서류 찾기, "그거 예전에 어떻게 했더라?" 동료에게 물어보기
- 아침 회의 전, 환자마다 예약·보험 잔여·미수·가족·주의사항 기록을 여러 화면에서 따로 확인
- 매일 마감 때 일계표(카드 전표·현금 입금)와 치과 프로그램 숫자를 맞추며 "왜 안 맞지?"
- AI를 써 봐도 그 답이 맞는지 확인할 방법이 없음 → 믿고 쓰거나, 아예 안 씀

## 2. 기능별 전후

### 오늘 화면
- **전**: 할 일이 메모·단톡방·기억에 흩어져 있음
- **후**: 첫 화면에 "AI가 한 일"과 "사람이 볼 일"(급한 통화, 주의 환자, 문서에 없는 질문 …)을 모으고, 누르면 그 화면으로 감. ⑦ 아침 브리핑이 이 화면의 한 칸

### ① 통화 요약·분류
- **전**: 통화가 끝나면 직원이 기억으로 메모·할 일을 정리. 누락되면 콜백을 놓침. "그 환자 지난번에 뭐 물어봤지?"는 사람 기억에 의존
- **후**: 전사(통화 녹음을 글로 옮긴 것) → 모델이 요약·분류·할 일. 할 일 있는 통화는 후속 큐에 쌓이고, 처리하면 빠짐. 확장: 모델 2개가 각각 분류해 **엇갈린 통화만** 표시
- **사람**: 분류를 판정(확장 시 엇갈림 배지가 붙은 통화부터)
- **보여줄 것**: 모델 vs 사람 일치율, 프롬프트 개선 전후 차이. 확장 시 엇갈림이 오류를 잡는 비율(오류 포착률)과 둘 다 같은 답으로 틀린 비율

### ② 사람 판정 + 블라인드 비교
- **전**: AI 분류가 맞는지 아무도 모름
- **후**: 키보드로 건당 약 1분 판정 → 정답지가 쌓임 → 모델·프롬프트를 숫자로 비교 → 틀린 건의 오류 유형으로 프롬프트를 고치고 다시 잰다(루프 1회). 모델명을 가린 블라인드 비교로 선입견 제거
- **사람**: AI의 결과를 검사하는 채점자
- **보여줄 것**: 프롬프트 v1→v2 정확도 변화, 블라인드 승률

### ③ 물어보기 (검색 + 챗 + 문서함)
- **전**: 매뉴얼·공지·통화·문자가 흩어져 있어 동료에게 물어봄. 바뀐 공지와 옛 공지를 혼동
- **후**: 질문 하나로 매뉴얼과 실제 사례를 나눠 찾고 출처와 함께 답. "내일 미수 환자 몇 명?" 같은 질문은 DB 조회 도구로. 근거가 없으면 답하지 않음(`refuse`)
- **보여줄 것**: Hit@5(찾은 결과 상위 5개 안에 정답이 있는 비율), 최신 공지 정답률, 도구 선택 정확도, 환각 억제율

### ④ 진료 준비표
- **전**: 환자마다 여러 화면을 뒤져서 아침 회의 준비
- **후**: 코드가 한 화면으로 모아 칩(예약·보험 잔여·미수·가족 리콜·주의·남은 치료계획)으로 표시, AI는 그날 할 일(주의사항 처리 + 권할 진료) 한두 줄. 문장 속 숫자는 입력 사실과 대조해 후검증
- **사람**: 아침 회의에서 오늘 전체를, 진료 중에는 체어 옆에서 지금 환자 한 명을 봄
- **보여줄 것**: 제안 후검증 통과율, 주의사항 반영률, 근거 없이 권한 비율(과잉 제안률)

### ⑤ 심평원 청구 점검·삭감 대응
- **전**: 심사결과는 전산으로 들어오지만, 깎인 건마다 사유코드를 보고 기준을 찾아 다툴지 판단하고 사유서를 씀. 청구 전 누락·위험은 사람이 기억으로 점검
- **후**: 깎인 건을 재심 기한과 함께 모아 보여 줌 → 청구 전에는 나이·횟수 같은 급여 조건과 상병·시술 조합은 규칙이, 차트를 읽어야 하는 요건(같은 부위를 다시 한 사유·치주 상태 등)과 차트에 적혔는데 청구에 빠진 처치는 AI가 근거와 함께 표시 → 깎인 건마다 AI가 관련 기준을 찾아 정당 / 다툴 만함 / 보완 후 재청구(빠진 내역설명·증빙을 채워 다시 냄)로 나누고, 다툴 만한 건은 재심 사유서 초안을 씀. 상병 착오는 재청구가 안 되므로 따로 강조하고, 같은 조합은 다음 청구 전에 경고
- **사람**: 재심할지 최종 판단, 사유서 검토, 보완 서류 준비
- **보여줄 것**: 점검 정밀도·재현율(일부러 심은 오류를 얼마나 정확히, 빠짐없이 찾나), 기준 검색 Hit@5·MRR(정답이 몇 번째로 나오나)·재심 판단 정확도, 사유서의 인용·추측 표시 검사

### ⑥ 리포트
- **전**: 월말에 엑셀을 붙잡고 숫자 정리
- **후**: 숫자는 쿼리가 계산, AI는 해석만
- **보여줄 것**: 본문의 숫자가 전부 계산값에 존재하는지

### ⑦ 아침 브리핑
- 오늘 화면의 한 칸. 숫자는 쿼리, AI는 몇 문장으로 묶기만 — ⑥과 같은 검사

### ⑧ 재무 대조
- **전**: 일계표가 안 맞으면 카드 전표·통장·프로그램을 오가며 원인을 찾음. 지출은 영수증·명세서를 모아 세무사에게 넘김
- **후**: ⑧-1 대조는 코드, 안 맞는 건마다 에이전트가 내원·미수·다음 날 장부를 조회해 원인을 추적하고 과정을 보임 — 사람이 확정 / ⑧-2 출금마다 증빙을 찾아 맞추고 계정 과목을 추천
- **보여줄 것**: 원인 정확도와 매칭·계정 과목 정확도를 규칙만 쓴 방식과 나란히(AI가 어디서 더 나은지)

### ⑨ 후속 관리
- **전**: 계획만 세우고 안 온 환자, 리콜이 지난 환자를 아무도 챙기지 않음
- **후**: 코드가 칩별 목록과 점수로 순위를 매기고, 예약이 잡히면 빠짐
- **보여줄 것**: 다른 치과로 간 환자 추정의 정밀도·재현율

## 3. 쓰는 AI 기술

| 기능 | AI 기술 | 핵심 포인트 |
|---|---|---|
| ① 통화 요약·분류 | LLM 구조화 출력(JSON 스키마 + 고정 enum), 음성 인식(STT) | 모델 1개로 완성, 모델 2개 **교차검증**(엇갈린 것만 사람에게)은 확장 |
| ② 사람 판정 | Human-in-the-loop 라벨링, 블라인드 쌍 비교 | 사람이 만든 정답지로 모델·프롬프트를 **숫자로** 비교 |
| ③ 검색 + 챗 | 하이브리드 검색(키워드 BM25(단어가 겹치는 정도로 찾기) + 벡터 임베딩(뜻이 비슷한 것 찾기)) + 리랭커, **도구 호출 에이전트**(도구 5개) | 매뉴얼·사례를 따로 찾아 출처와 함께 답. 근거 없으면 거절 |
| ④ 진료 준비표 | LLM 해석 + **그라운딩 후검증** | AI가 쓴 사실을 스스로 명시하게 하고, 코드가 입력과 대조 |
| ⑤ 청구 점검·삭감 대응 | 규칙 점검 + 검색(③과 같은 구조) | 청구 전 위험은 규칙과 AI가 기준을 찾아 표시, 깎인 건은 관련 기준을 찾아 근거 제시 |
| ⑥ 리포트 · ⑦ 브리핑(오늘 화면) | 숫자는 쿼리·글은 LLM | 본문 숫자 후검증 |
| ⑧ 재무 대조 | 도구 루프 에이전트(⑧-1) + 문서 매칭·분류(⑧-2) | 내역을 모으고 대조하는 다단계 작업을 에이전트가 수행, 증빙을 읽어 계정 과목 분류 |
| ⑨ 후속 관리 | 코드 점수 + 문자 초안(선택) | 순위는 코드, AI는 문자 초안만 |

**모든 기능을 받치는 것**
- **LLM 게이트웨이**: 모델을 이름으로 호출, 장애 시 폴백, 호출마다 토큰·비용·지연 기록, 일일 비용 상한. 모델 교체는 설정 한 줄
- **평가 하네스**: 정답지와 앱 DB를 분리하고, 튜닝용(dev)과 보고용(test)을 나눠 "프롬프트 v1 → v2", "리랭커 on/off"를 같은 조건에서 비교
- **합성 데이터**: 정답 라벨을 먼저 정하고 LLM이 그에 맞는 통화·문서를 생성 — 실제 환자 정보 없이 정답이 있는 데이터셋
- **AI 코딩 에이전트로 개발**: Claude Code에 설계 문서·작업 규칙(`CLAUDE.md`)을 주고 테스트 우선으로 구현

스택·모델은 [[치과 AX - 앱 설계]] §7.

## 4. 팀원이 맡을 수 있는 영역

코어(①②③④)와 독립적으로 시작할 수 있는 과제들이다. 가상 데이터·LLM 게이트웨이·평가 하네스는 이미 공용으로 깔려 있어서, 맡은 기능의 로직과 화면에 집중하면 된다. 각자 **자기 지표**를 갖고 결과를 숫자로 보여줄 수 있다.

| 영역 | 해 보는 것 | 결과로 보여줄 지표 |
|---|---|---|
| ⑤ 청구 점검·삭감 대응 | 청구 전 점검(규칙 + AI가 기준 적용·차트 기반 누락), 조정 사유 검색, 재심 사유서 초안 | 점검 정밀도·재현율, 검색 Hit@5·MRR·재심 판단 정확도 |
| ⑥ 리포트 | 숫자는 쿼리·글은 LLM으로 나누는 리포트, 그래프·PDF — 프론트 비중이 큼 | 본문 숫자의 계산값 일치율 |
| ⑧ 재무 대조 | 가상 데이터는 이미 있음 — 원인 추적 에이전트(에이전트 루프를 처음부터 만들어 보는 과제)와 증빙 매칭·계정 분류 | 원인 정확도, 매칭·계정 과목 정확도(규칙 기준선 대비) |
| ⑨ 후속 관리 | 칩별 목록·코드 점수·문자 초안 | 다른 치과 추정 정밀도·재현율 |

범위와 완료 기준은 [[치과 AX - 기능 정의]] §5에 있다.

## 5. 바뀌지 않는 것

- **판단은 사람이 한다.** AI는 읽고 정리하고 제안까지만. 장부·차트에 직접 쓰지 않음
- **숫자는 코드가 계산한다.** AI가 매출을 지어내면 끝이다
- **믿기 전에 잰다.** 사람 판정과 정답지로 AI를 채점한다 — 이 프로젝트의 중심
- 직원의 역할은 "전부 확인"에서 "확인 필요만 확인"으로 바뀐다. AI가 사람을 대체하기보다 사람이 싫어하던 일을 가져간다

## 6. 이 프로젝트의 한계

- **실제 병원 데이터가 아니다.** 가상 데이터로 재현한다. 그래서 절대 수치보다 조건 간 차이(전/후, v1/v2, 리랭커 on/off)로 보여준다
- **업무 시간 절감은 재지 못한다.** "사람이 봐야 하는 양"(엇갈린 통화 비율)은 모델 2개 교차검증 확장을 붙였을 때만 잰다
- **실제 병원은 환자 정보가 밖으로 나가면 안 된다.** 이 프로젝트는 가상 데이터라 외부 API를 쓰지만, 실제로 적용하려면 로컬 모델로 바꿔야 한다. LLM 호출이 게이트웨이 하나를 거치므로 바꿀 곳은 한 군데다
- 메신저·원내 방송·동의서·근태는 범위 밖 ([[치과 AX - 기능 정의]] §2)
