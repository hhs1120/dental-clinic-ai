# 통화·② 판정 화면 설계

기능 정의 §9 착수 순서의 첫 항목(통화·② 판정 화면)이다. 원본은 기능 정의 §4 ①·②, 앱 설계 §1·§6·§9. 화면의 레이아웃은 이 문서가 와이어프레임(`docs/wireframe/index-v2.html`)보다 우선한다 — 아래 "화면"에서 바꾼 곳이 사용자 결정이다. 시안은 브레인스토밍 때 띄운 목업(`.superpowers/brainstorm/` — 저장소에 넣지 않음)이고 이 문서가 그 내용을 글로 옮긴 것이다.

## 왜

① 분류기·판정기·엇갈림이 데이터로는 끝났지만(PR #20) 아직 눈에 보이는 곳이 없다. 이 브랜치에서 처음으로 데스크 직원이 쓰는 통화 화면과, 사람이 AI를 검사하는 판정 화면이 생긴다. 직원이 아침에 통화 화면을 열어 하는 일은 둘이다 — **오늘 연락해야 할 사람**과 **통화에서 나온 할 일** 확인(사용자). 화면 구성과 이름은 이 장면을 기준으로 다시 잡았다.

## 범위

**이번에 만든다**
- 통화 화면 `/calls`: "오늘" 탭, "통화 기록" 탭, "＋ 새 통화 추가", 통화 상세(패널 ↔ 넓게 보기)
- AI 평가 화면 `/eval`: 판정 탭, 블라인드 비교 탭, 정확도 표 탭
- LLM 쌍 비교(블라인드 승률): `prompts/blind_judge/v1.md`, 좌우 바꿔 두 번 판정, 일괄 실행 명령, 승률·좌우 선택 비율 집계(사용자)
- 분류기 v2: 요약 프롬프트를 고쳐 할 일을 종류(연락 / 안에서)로 나눠 낸다. 1,500건 전체를 다시 돌린다(약 $0.6)
- 위를 받치는 API·앱 테이블

**이번에 안 만든다**
- 자동 개선 탭 — 개선 에이전트 브랜치에서
- 녹음 파일 올리기 — 하지 않는다(사용자)
- 후속 에이전트 처리안·자동 종결·`--section auto`·정확도 뷰 정의 — 기능 정의 §9 "자동 종결 착수 시"
- 작업 API(`POST /jobs/classify-batch`·`judge-batch`) — 일괄 실행은 지금처럼 `make classify`·`make judge` 명령으로 — 내 판단
- 화면 테스트 fixture(`make fixture`) — 판정·블라인드 Playwright 완료 기준을 실데이터 복사본으로 돌린다(기능 정의 §4 ② 완료 기준이 허용) — 내 판단. Playwright는 아직 설정이 없어 이번에 붙인다(로컬 실행, CI에 넣을지는 계획 때)

## 화면 공통 원칙

- **하는 일·결과는 왼쪽, 근거 자료(녹취록)는 오른쪽**(사용자). 통화 상세 넓게 보기·블라인드 비교·판정 화면 모두
- 영어 코드(`inbound`, `has_todo`, enum 값)는 화면에 보이지 않게 우리말로. 방향은 "걸려 온 전화 / 건 전화"
- 이름은 하는 일로 짓는다 — "후속 큐"·"붙여넣기" 같은 시스템 말을 쓰지 않는다(사용자)
- 판정 풀 통화(`in_eval_pool`)는 통화 화면에 나오지 않는다(기능 정의 §4 ①, 평가 설계 §1 원칙 2)
- 색·모양은 `frontend/app/globals.css` 토큰과 `components/ui`(CLAUDE.md 코드 컨벤션)

## 통화 화면 `/calls`

탭 둘: **오늘** · **통화 기록**. 오른쪽 위에 버튼 **＋ 새 통화 추가**(사용자).

### 오늘

두 칸 보드(사용자):
- **왼쪽 "할 일"** — 병원 안에서 할 일(원장님께 여쭙기·전달, 일정·금액 확인, 서류 준비 등)
- **오른쪽 "연락할 사람"** — 환자·보호자·외부에 전화·문자로 연락하는 일. 응급·급함 통화의 항목이 맨 위
- 항목 한 줄 = 할 일 하나: 체크 칸 · (연락이면) 상대 이름 · 할 일 문장 · 통화 시각·한 줄 맥락. 왼쪽 일을 끝내야 할 수 있는 연락이면 "← 왼쪽 ○○ 끝나면" 표시
- 체크하면 끝난 것으로 남고(누가·언제 — 담당 파트, 실제 시계), 되돌릴 수 있다. 끝난 항목은 칸 아래 "끝낸 일"로 접어 둔다 — 내 판단
- 항목을 누르면 그 통화의 상세가 열린다
- **올라오는 통화**: 기준일(`shared/clinic.py` TODAY) 전 **7일** 안의 통화(사용자). 값은 설정 상수 하나(이름은 구현 때, 원본은 코드). 더 오래된 통화의 할 일은 이미 처리된 것으로 보고 "통화 기록"에서만 보인다. 대상 통화는 활성 분류 버전이 `ok`이고 판정 풀 밖인 생성 통화 + 새로 추가한 통화(새 통화는 날짜와 상관없이 올라온다 — 내 판단)
- 정렬: 응급·급함 통화 먼저, 그다음 통화 시각 최근 순 — 내 판단

### 통화 기록

날짜별 카드(사용자 — 표 대신). 하루씩 묶고("11월 30일 (일) · 14통") 통화마다 카드: 이름 · 시각 · 방향 · 무슨 통화(목적) · 표시(응급·급함·AI 엇갈림·할 일 n / 처리함) · 요약 한 줄. 필터 칩: 전체 · 걸려 온 전화 · 건 전화 · 응급 · 할 일 남음 · AI 엇갈림, 검색: 이름·번호·차트번호. 대상은 판정 풀 밖 생성 통화 + 새로 추가한 통화 전부(7일 제한 없음). 많으므로 페이지 나눔이나 날짜 범위 더 불러오기가 필요하다 — 방식은 구현에 맡김.

### 통화 상세 — 패널 ↔ 넓게 보기

같은 내용을 두 크기로(사용자):
- **패널(기본)**: 오른쪽 좁은 패널, 목록이 왼쪽에 그대로. 섹션 순서 — 머리(이름·차트번호·번호·시각·방향·통화 길이) → **할 일**(체크, 항목마다 "연락 / 안에서" 표시) → **요약**(+ 응급·급함·예약 잡힘 같은 표시) → **AI 두 개가 다르게 본 곳**(엇갈림 있을 때만) → **분류 9항목**(판정기와 다른 항목은 같은 줄에 "판정기: ○○" 빨간 글씨) → **녹취록** → **환자 정보**(EMR 환자 요약 + "EMR에서 보기"). 섹션은 **모두 펼친 채 시작**하고 제목을 누르면 접힌다. 패널 안에서 스크롤(사용자)
- **넓게 보기**: 패널 위 버튼으로 화면 전체. 왼쪽에 할 일·요약·분류·환자 정보, 오른쪽에 녹취록(말풍선). 두 칸 따로 스크롤. "패널로 돌아가기"로 복귀(사용자)
- 엇갈림·판정기 값은 활성 분류 버전 × 활성 판정기 버전(`ax_settings.prompt_versions.judge`) 쌍의 `ax_call_disagreements`·`ax_model_judgments`에서
- 환자 정보는 이미 있는 `GET /emr/patients/{chart_no}`의 `summary`. 차트 없는 상대(처음 연락·업체)는 "차트 없음"

### ＋ 새 통화 추가

창 하나: 방향 선택(**걸려 온 전화가 기본**, 건 전화일 때만 바꿈 — 사용자) · **전화번호 칸(선택)** · 통화 내용 칸 · "추가하기". 번호가 EMR 환자(`emr_patients` 전화번호)와 맞으면 그 환자로 연결(이름·차트번호), 없거나 안 맞으면 "차트 없음"(사용자 — 실제 교환기도 발신 번호를 넘긴다). 분류기 입력은 여전히 녹취록·방향뿐이다 — 번호·환자는 화면 표시에만 쓴다. 통화 시각은 **기준일 날짜 + 지금 시각**(사용자 — 실제 날짜는 생성 통화보다 앞서 날짜별 기록이 어색해진다), 통화 길이는 없음. 누르면 분류기(라벨·요약)와 판정기를 일반 호출로 부르고 엇갈림을 계산해 저장한 뒤 그 통화의 상세를 연다. 할 일은 "오늘"에 올라온다. 호출이 실패하면 통화는 남기고 상세에 실패와 "다시 분류" 버튼 — 내 판단. 앱이 만든 통화라 `ax_pasted_calls`(앱 설계 §1)에 `p-0001`부터.

## AI 평가 화면 `/eval`

탭 셋: **판정** · **블라인드 비교** · **정확도 표**(자동 개선 탭은 이번에 없음 — 사용자).

### 판정

기능 정의 §4 ② "판정"의 동작 그대로(숫자 키 입력·자동 다음 항목·Enter 저장·메모 칸·모델 라벨은 저장 뒤에만, 키 매핑은 앱 설계 §9). 바뀐 것은 배치 하나: **왼쪽에 9항목 고르는 칸, 오른쪽에 녹취록**(사용자 — 와이어프레임은 위 녹취록·아래 고르는 칸). 위에 진행 현황 한 줄, 아래 단축키 안내. 건너뛰기.

- 대상·순서: 앱 설계 §6 "판정 큐 다음 건" 그대로(판정 풀 밖 생성 통화 + 새로 추가한 통화 중 엇갈림 또는 표본, 활성 분류 `ok`; 건너뛴 건 뒤로 → 새 통화 → 핵심 엇갈림 → 나머지 엇갈림 → 표본)
- 표본 비율: 엇갈림 없는 통화 중 `call_uid` 해시로 5% — 내 판단. 값은 코드 상수(앱 설계 §6에 이름으로 적는다)
- `ax_judge_state`(pending / skipped / done)를 이번에 만든다. 엇갈림 계산이 끝나면 대상 통화를 pending으로 채운다
- 지금 데이터: 활성 쌍(v1 × v2)에서 판정 풀 밖 엇갈림 265건(핵심 41)

### 블라인드 비교

기능 정의 §4 ② "블라인드 탭"의 투표(1 / 2 / 비슷 / 둘 다 틀림, 버전은 고른 뒤에만, 좌우는 건마다 무작위)에 **녹취록을 같이 보인다**(사용자 — 원래 통화 없이는 둘 다 틀렸는지 판단할 수 없다). 배치: **왼쪽에 요약 두 개(각각 할 일 목록 포함)와 고르기 버튼, 오른쪽에 녹취록**(사용자). 비교하는 두 버전은 `ax_settings.blind_versions` — 이번에는 분류기 v1과 v2. 투표는 `ax_blind_votes`.
- **대상은 dev 블라인드 통화만**(사용자). test 블라인드 통화는 지금처럼 최종 비교(vN vs vN-final) 때만 사람이 본다
- 이 투표는 같은 쌍의 LLM 쌍 비교와 사람의 일치율을 내는 데 쓴다(평가 설계 §2.4 "LLM 쌍 비교를 믿을 근거") — 최종 비교는 다른 분류 행 쌍이라 `UNIQUE(left, right)`와 겹치지 않는다
- 평가 설계 §2.4·기능 정의 §4 ②·`shared/app_schema.sql` `ax_blind_votes` 주석의 "사람 투표는 최종 비교만"을 "사람 투표는 dev 블라인드에서 `blind_versions` 쌍, test 블라인드는 최종 비교 때만"으로 고친다

### 정확도 표

와이어프레임 `evalAcc` 구성: 항목별 분류기 vs 판정기 일치율을 분류 버전별로 나란히(막대), 모수는 dev 판정 풀만(앱 설계 §6). **블라인드 승률**(LLM 쌍 비교, v2 vs v1 — 나음·못함·비슷·둘 다 틀림)과 좌우 선택 비율. "사람이 보는 몫"(운영 구간 엇갈림·표본 비율).

### LLM 쌍 비교 (블라인드 승률)

규칙은 평가 설계 §2.4 그대로: 입력은 녹취록과 두 요약뿐(도구 없음), 좌우를 바꿔 두 번 판정해 같으면 그 선택·다르면 `tie`, 좌우 배치 `hash(transcript, seed) % 2`, 집계는 `(prompt_version, model_actual)` 쌍별, 위치 편향 지표 병기. 저장은 이미 있는 `ax_model_blind_votes`. 대상은 dev 블라인드 통화(앱 화면) — test 블라인드는 최종 비교 때만. 프롬프트 `prompts/blind_judge/v1.md`, 별칭은 `config/llm.yaml`에 새로, 모델은 **Haiku**(사용자). 요약을 쓴 모델과 같아 자기 글을 고르는 쪽으로 기울 수 있다 — 사람 투표와의 일치율(위 블라인드 비교)로 드러나고, 실험 기록·README 한계에 적는다. Anthropic이라 Batch로 돌릴 수 있다. 실행은 `make` 명령 하나(`POST /jobs/blind-judge-batch`는 작업 API와 함께 미룸). 블라인드 풀 dev 통화 × 2회라 호출 100회 안팎.

## 분류기 v2 — 할 일 종류

- `prompts/classify/v2/`: `labels.md`는 v1과 같은 본문, `summary.md`만 고친다. 버전 규칙은 앱 설계 §7.2(폴더 하나가 한 버전)
- 할 일 항목을 문장 대신 구조로: 종류(`contact` 연락 / `internal` 안에서) · 할 일 문장 · (연락이면) 상대 · (앞서 끝내야 할 안쪽 일이 있으면) 그 항목 번호. 지금 v1의 "원장님께 여쭤 확인 결과를 환자에게 회신함" 같은 섞인 문장은 안쪽 일 하나 + 연락 하나로 쪼갠다. 정확한 필드 이름·스키마는 구현 때 — `shared/call_labels.py`에 v2 스키마를 두고 v1 문자열 목록도 계속 읽을 수 있어야 한다(v1 행이 남는다)
- 실행: `make classify V=v2`(Haiku Batch) → `make disagreements A=v2 B=v2` → 활성 분류 버전을 v2로(`ax_settings.active_prompt_version`). 앱 설계 §7.2 "classify 전환"(전부 `ok`일 때만 전환) 규칙을 따른다
- 라벨도 다시 호출한다(v1 라벨을 복사하지 않음 — 버전 = 프롬프트 × 모델의 한 번 실행이고, 복사하면 호출 기록 칸이 거짓이 된다) — 내 판단. 같은 프롬프트라도 출력이 조금 흔들리므로 dev 채점(`eval.py` 분류 절)에서 목적 Strict·플래그 평균이 v1과 2%p 안이면 통과(Solar 맛보기 자리 바꿈 기준과 같은 폭). 엇갈림도 v2 × v2로 다시 계산한다. 실험 기록에 결과를 남긴다. 비용은 라벨 + 요약 Batch 약 $0.6
- 화면은 v2 할 일을 쓴다. v1만 있는 통화(새로 추가한 통화는 활성 버전으로 분류하므로 없음)를 만나면 할 일 전체를 "안에서"로 보인다 — 내 판단

## 앱 테이블 (이번에 만듦)

- `ax_pasted_calls` — 새로 추가한 통화(방향·녹취록·전화번호·연결된 환자·추가한 파트·시각). 통화 목록·분류·판정에서 생성 통화와 합쳐 보인다
- `ax_judge_state` — 앱 설계 §1
- 할 일 체크 기록 — 분류 행과 항목 번호 단위로 끝낸 파트·시각. 새 테이블(이름은 구현 때) — 내 판단: 앱 설계 §1의 `ax_call_followups`는 통화 단위 처리 + 후속 에이전트 처리안이라 그 브랜치에서 만든다
- `ax_settings`: `active_prompt_version`(v2), `blind_versions`([v1, v2])
- 기존 DB는 `init_schema`가 맞춘다

## 완료 기준

- 기능 정의 §4 ① 완료 기준 중: 새 통화 추가 E2E(→ 분류 1행 `ok`·판정 1행·엇갈림 계산), 엇갈림 pytest(이미 있음)
- "오늘" pytest: 7일 안의 판정 풀 밖 통화의 할 일만, 종류별 칸, 체크하면 끝낸 일로 이동·되돌리면 복귀, 판정 풀 통화 없음
- 기능 정의 §4 ② 완료 기준 중: Playwright 판정 키 시퀀스 10회 → `ax_judgments` +10, 블라인드 5회 → `ax_blind_votes` +5(실데이터 복사본)
- 분류기 v2: 1,500건 `ok`, 할 일 항목마다 종류가 있음, dev 목적 Strict·플래그 평균이 v1과 2%p 안
- `make lint`·`make test`·프론트 빌드 통과
