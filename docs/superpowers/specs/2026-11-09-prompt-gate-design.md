# ① 분류 프롬프트 관문 설계

원본: `docs/치과 AX - 평가 설계.md` §2.5(급함 비교)·§2.7(자동 개선과 재발 방지)·§3.3(McNemar), `docs/치과 AX - 기능 정의.md` §4 ②·§8·§9, 분할 `evaluation/splits.py` `silver_split`. 이 문서는 이번 브랜치에서 새로 정한 것만 적는다.

## 왜

① 분류 프롬프트를 바꿨을 때 "정말 나아졌는지"를 운과 구별해 판정하는 시험이 없다. 같은 v2를 검증 구간에 그대로 다시 돌리기만 해도 항목 오답 수가 출렁인다(아래 실측). 한 번씩 돌려 비교하면 운 좋은 결과를 개선으로, 운 나쁜 결과를 악화로 착각한다.

평가 설계 §2.7의 자동 개선(재료 오류 → 개선 에이전트가 후보 작성 → 관문 → 대기 버전)은 이번에 관문만 만든다. 이유: 검증 구간 v2 오답이 대부분 흔들림 안에 있다(목적 7~9, 상대 6~7, 예약 원함 6~7, 예약 확정 2~7, 응급·불만 놓침 0). 여지가 있는 건 할 일 있음(16~20)뿐이라 후보 작성 에이전트를 만들 값이 작다. 관문은 후보를 누가 썼든(사람·에이전트) 쓰고, ① 밖의 task로 넓힐 때도 같은 틀을 쓴다.

### 실측 — 같은 프롬프트의 흔들림(2026-11-09)

v2를 검증 구간 405건에 3번 다시 분류(Haiku 5.5, 일반 호출, 합계 약 $0.47)하고 저장된 v2와 4벌을 비교했다. Haiku 5.5는 sampling 값을 기본값 밖으로 바꾸면 400이라 temperature로 흔들림을 끌 수 없다.

| 항목 | 오답 수(저장·다시 1·2·3) | 두 실행 사이 바뀐 건수 평균 / 최대 |
|---|---|---|
| has_todo | 16 · 17 · 17 · 20 | 5.3 / 8 |
| primary_purpose | 7 · 9 · 8 · 7 | 4.0 / 6 |
| appt_confirmed | 7 · 2 · 4 · 4 | 3.2 / 5 |
| counterpart | 6 · 6 · 7 · 7 | 3.2 / 4 |
| wants_appt | 6 · 6 · 6 · 7 | 2.2 / 3 |
| emergency | 0 · 1 · 0 · 0 | 0.5 / 1 |
| urgency(urgent 여부)·complaint·price_inquiry | 변화 없음 | 0 |

확인(같은 v2를 이름만 바꿔 독립 3벌로 관문에 넣음): 불합격, 가장 큰 차이 할 일 있음 b 6 · c 2(p 0.29) — 흔들림만으로 합격·회귀 판정이 나지 않는다.

## 목표 · 비목표

- **목표**: `make prompt-gate A=<기준> B=<후보> ITEM=<목표 항목>` 한 번으로 합격/불합격과 떨어진 조건을 낸다. 같은 입력이면 같은 판정(저장된 실행을 다시 쓰므로)
- **비목표**: 후보 작성 에이전트, 재료 오류 묶기, 베끼기(겹침) 검사, 화면의 자동 개선 탭, 대기 버전 자동 설정, 재발 방지 경로(`ax_failure_cases`), ① 밖의 task — 모두 오답 여지가 큰 대상이 생길 때 자동 개선과 함께
- **실패로 볼 것**: 흔들림만으로 합격하는 것, 아무것도 안 바뀐 후보가 하락으로 불합격하는 것, 검증 통화 목록·건별 결과가 사람이나 후보 작성 쪽에 보이는 것, test 분할을 읽는 것

## 사람이 정한 것

- 관문만 만들고 후보 작성 에이전트는 미룬다
- 목표를 목적에 묶지 않고 넓힌다(목적은 이미 흔들림 수준)
- 급함은 urgent 여부만 비교(§2.5와 같은 이유 — 골드 normal/low는 녹취록과 무관한 추첨)
- 기준·후보를 각각 3번 돌려 다수결로 비교한다
- 값: 오름 p < 0.05 / 응급·불만 새로 놓침 0, 오탐 증가 +2까지 / 다른 항목은 유의한 하락 없음 + 다수결 오답 증가 3까지 / 같은 기준에 서로 다른 후보 2개까지(운으로 합격할 확률 약 5% — 5번이면 약 12%, 3번이면 약 7%)

## 동작

1. **모수**: `silver_split`의 `validation` 405건. 입력은 `truth_call_labels`에서 `split='silver'` 행만 읽어 만들고, 모수에 dev·test 통화가 하나라도 있으면 멈춘다. 재료 구간은 쓰지 않는다
2. **실행**: 버전마다 분류기 라벨 호출(`backend/classify.py` `label_request`, 별칭 `classify`)을 모수에 3번. 요약·할 일 문장 호출은 하지 않는다(관문이 채점하지 않음). 결과는 `evaluation/runs/prompt-gate/<버전>/run{1,2,3}.jsonl`(커밋 안 함 — 골드와 엮이는 건별 기록), LLM 호출 로그도 같은 폴더. 있으면 다시 쓰고, 빠진 통화만 부른다. 실행 파일에 프롬프트 파일(`labels.md`) 해시와 별칭의 첫 모델 이름을 적고, 둘 중 하나라도 지금과 다르면 그 버전의 실행을 버리고 새로 돈다. 라벨이 유효하지 않거나 폴백 모델이 답한 통화(평가 설계 §1 원칙 5)는 실패로 보고 다시 부른다 — 통화당 3번까지, 그래도 빈 통화가 있으면 판정하지 않고 멈춘다(기록 없음). 3벌 모두 모든 통화가 채워져야 판정한다
3. **다수결**: 통화·항목마다 3벌의 값 중 2벌 이상 같은 값. 목적·상대처럼 셋이 다 다르면 첫 실행 값(결정적이게)
4. **비교**(같은 통화 짝, 비가중): 항목마다 "기준 틀림·후보 맞음" b와 "기준 맞음·후보 틀림" c, `evaluation/metrics.py` `mcnemar_exact(b, c)`
5. **합격 조건** — 모두 넘어야 합격, 못 넘은 조건은 enum 이름으로 전부 기록
   - `target_up`: `ITEM`이 b > c이고 p < 기준값
   - `no_new_miss`: 골드 `emergency`·`complaint`가 1인데 기준 다수결은 맞히고 후보 다수결은 놓친 통화 0
   - `false_alarm_cap`: 같은 두 항목에서 후보 다수결 오탐 수 − 기준 다수결 오탐 수 ≤ 상한
   - `no_regression`: 목표 밖 항목마다 c > b이면서 p < 기준값인 항목이 없고, 다수결 오답 증가(c − b)가 상한 이하
   - `attempt_cap`: `reports/prompt_gate.jsonl`에서 기준 버전이 같고, 후보가 기준과 다르고, 관문 값(아래 상수)의 해시가 지금과 같은 행의 서로 다른 후보 버전 수가 상한 미만(이미 판정한 후보를 다시 돌리면 저장된 실행으로 같은 판정이 나오므로 세지 않는다). 넘으면 실행 전에 멈춘다(기록·비용 없음). 사람이 관문 값을 고치면 해시가 바뀌어 다시 0부터 센다(평가 설계 §2.7). 같은 버전끼리의 점검(`A=v2 B=v2`)은 세지 않는다
   - **자동 처리**: 앱 DB `ax_settings.auto_policy`(읽기 전용)에 켜진 정책이 하나라도 있으면 실행 전에 멈춘다 — 평가 설계 §1 원칙 9의 자동 처리 오류율·신뢰 경계 조건은 자동 개선과 함께 만들고, 그 전에는 켜진 정책의 근거를 관문 없이 바꾸지 않게 한다
6. **출력**: 터미널에 항목별 다수결 오답 수(기준·후보)·b·c·p와 조건별 통과 여부. 건별 목록·통화 id는 내지 않는다. 판정 1회 = `reports/prompt_gate.jsonl` 1행(커밋): 시각·기준·후보·목표 항목·관문 값과 그 해시·모델·항목별 집계(오답 수·b·c·p)·조건 결과·합격 여부·모수 n·비용
7. **합격 뒤**: 아무것도 바꾸지 않는다. 전환은 사람이 기존 절차(앱 설계 §7.2 — 재분류가 전부 `ok`로 끝날 때 활성 전환)로 한다

값은 `evaluation/metrics.py`에 이름으로 둔다: 반복 수 3, p 기준 0.05, 오탐 증가 상한 2, 회귀 상한 3, 시도 상한 2. 상한을 넘겨 다시 돌리려면 사람이 값을 고친다(평가 설계 §2.7 "관문 기준 수정은 사람만").

## 제약

- `evaluation/`에서만 돈다. `backend/`는 `evaluation/`·`ground_truth/`를 참조하지 않는다(기존 테스트)
- 앱 DB(`app.sqlite`)에 쓰지 않는다(`auto_policy` 읽기만). 기준 실행도 앱의 저장된 분류를 쓰지 않고 관문이 직접 돈다(같은 조건 3벌이어야 하므로)
- test 분할·test 판정을 읽지 않는다
- 비용: 새 버전 한 번(405 × 3) 약 $0.47, 기준은 저장된 실행을 다시 쓴다

## 정한 것(내 판단 — 검토 바람)

- **목표 항목을 부르는 쪽이 정한다**(`ITEM=`): 9항목 중 아무거나 오르면 합격이면 시도마다 9번 검정하는 셈이라 운으로 합격할 확률이 커진다. 후보를 쓰는 쪽은 무엇을 고치려 했는지 안다
- 명령 이름 `make prompt-gate` — `make gate`(코어 합격 기준)와 구분
- 오늘 측정한 v2 3벌(`evaluation/runs/variance-v2/`)은 형식만 맞춰 v2 기준 실행으로 옮긴다(다시 부르지 않음). 확인: `prompts/classify/v2/`는 2026-11-05 뒤 바뀌지 않았고, 1,215회 모두 `claude-haiku-5-5`·폴백 없음
- 폴백 답은 실패로 다시 부르고(통화당 3번), 무효화 키는 프롬프트 해시 + 첫 모델 이름
- 시도 상한은 관문 값 해시가 같은 행만 센다 — 값을 고치면 다시 0
- 자동 처리 정책이 켜져 있으면 관문을 돌리지 않는다(원칙 9 조건은 자동 개선 때)
- 실행 저장 단위는 통화 1줄 jsonl — 도중에 멈춰도 끝난 통화는 남는다
- 일반 호출을 스레드로(Batch는 결과가 늦고 비용 차이가 작다 — 405건 3번이 약 $0.47)

## 문서 반영

- 평가 설계 §2.7: 관문을 이 규칙(모수·다수결·조건·값 이름)으로 고치고, 후보 작성·재료·실패 기록·누출 차단·재발 방지 경로는 "자동 개선(미룸)"으로 묶어 남긴다. 기록 파일 이름을 `reports/prompt_gate.jsonl`로
- 기능 정의 §4 ②: 자동 개선 → "프롬프트 관문(자동 개선 에이전트는 오답 여지가 큰 대상이 생길 때)", §8 결과표 ① 행, §9 착수 순서와 "자동 개선 착수 시" 줄
- AI 실험 기록: 새 절 — 같은 프롬프트의 흔들림 실측(위 표)과 자동 개선을 미룬 근거
- CLAUDE.md 명령 목록에 `make prompt-gate`

## 테스트

- pytest(가짜 게이트웨이 — 대본으로 라벨을 정해 둠): 다수결(2:1, 셋 다 다름), b·c 계산, 조건별 합격/불합격(목표 오름 미달, 응급 새 놓침, 오탐 상한, 회귀 상한·유의 하락), 시도 상한에서 호출 없이 멈춤, 저장된 실행 재사용(게이트웨이를 부르지 않음)·빠진 통화만 부름·프롬프트 해시 바뀌면 다시 돎, 모수에 test 통화가 섞이면 멈춤, 출력·기록에 call_uid가 없음
- 실측: 같은 버전끼리(`A=v2 B=v2`) 돌려 불합격(`target_up` 미달)이고 `no_regression`·`no_new_miss`는 통과하는지 — 흔들림만으로 하락 판정이 나지 않는지 확인

## 만드는 쪽에 맡김

모듈 나누기(`evaluation/prompt_gate.py` 하나를 기본으로), 터미널 출력 모양, 스레드 수, jsonl 칸 이름.
