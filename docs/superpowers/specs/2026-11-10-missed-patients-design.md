# ⑨ 미예약 환자 — 설계

원본 규칙은 [[치과 AX - 기능 정의]] §5 ⑨(지금 이름 "후속 관리"), [[치과 AX - 앱 설계]] §3b·§4·§8, [[치과 AX - 평가 설계]] §5 ⑨, [[치과 AX - 가상 데이터 생성 설계]] §2.2(이탈·병행), 와이어프레임 `docs/wireframe/index-v2.html`의 `R.followup`. 이 문서는 그 위에서 정한 것을 적는다. 설계는 한 번에, 실행은 둘로 나눈다(사용자 결정) — **1단계**(코드만, 과금 없음)와 **2단계**(AI, 과금). **지금은 1단계만 하고 2단계는 보류한다**(사용자 결정 — 아래 "2단계를 보류한 이유"). 2단계 절(§8~§11)은 다시 열 때의 출발점으로 남긴다.

## 왜

동네 치과의 매출은 다니던 환자가 다시 오는 데서 나온다. 그런데 정기 검진 주기가 지났거나, 올해 보험 스케일링을 안 받았거나, 치료가 남았는데 다음 예약 없이 끊긴 환자는 EMR 어디에도 한 목록으로 모여 있지 않다. 직원이 손이 빌 때 "누구에게 먼저 연락할지"를 코드가 모으고 줄 세운다. 준비표가 "오늘 오는 환자"라면 이건 "와야 하는데 예약이 없는 환자"다.

## 이름 (사용자 결정)

화면·메뉴·문서 이름은 **미예약 환자**. "후속"은 통화 쪽(후속 에이전트·후속 큐·처리안)이 이미 쓰는 말이라 헷갈리고, "놓친 환자"는 처음부터 안 온 사람으로도 읽힌다. 기능 번호 ⑨는 그대로. 주소·코드 이름은 빌더 판단(예: `/missed`, 테이블 `ax_missed_contacts`) — 기존 `/followup` 자리(`frontend/lib/nav.ts`)를 바꾼다.

## 목표

**1단계**
- 미예약 환자 목록: 조건(아래 §1) + 칩 6개 + 점수 순 — 처음 10명, "더보기"마다 10명씩(사용자 결정)
- 연락 기록: 결과 5개 + 수단(전화·문자), 결과에 따라 목록에서 빠지거나 일정 기간 점수가 낮아짐
- 점수는 원칙으로 정하고 값마다 이유를 화면 설명과 문서에 적는다(사용자 결정 — §5)
- 과거 데이터 분석 한 번 → [[치과 AX - AI 실험 기록]] 한 절(값을 고르는 데 쓰지 않음, 유지하는 평가 코드 없음)
- 오늘 화면 "사람이 볼 일"에 줄 하나: `미예약 환자 · 상위 10명 → 미예약 환자 화면`

**2단계 (보류)**
- 자동 안내(템플릿) → 발송함 기록, 오늘 화면 "AI가 한 일"의 자동 처리로
- 사람이 보내는 문자 초안(LLM, 누를 때) + 후검증
- 다른 치과 근거 찾기 에이전트(보여 주기만)
- 채점: 다른 치과 추정 정밀도·재현율(칩만 쓴 기준선과 나란히), 문자 후검증 통과율, 자동 안내에 의료·금액 내용 없음

## 하지 않는 것

- 실제 문자 발송(발송함은 기록만 — 기능 정의 §5 ⑨)
- EMR 원본(`emr_*`)에 예약 쓰기 — 앱은 `emr_`을 쓰지 않는다(절대 규칙)
- 에이전트 판단을 점수에 넣기(사용자 결정 — 보여 주기만. 채점에서 기준선보다 낫다는 게 확인되면 다시 본다)
- 화면에서 에이전트를 눌러 돌리는 버튼(기다림·비용 대비 얻는 게 적음, **내 판단**)
- 역할별 보기, 와이어프레임의 "1순위만" 필터·"1순위" 꼬리표(처음 10명이 그 역할 — 사용자 결정)
- `make nightly` 자체(2단계 자동 안내·에이전트는 별도 `make` 명령으로 돌리고 나중에 야간 실행에 끼운다)

## 하면 실패인 것

- 이미 예약이 잡힌 환자, 직원이 "예약함"을 남긴 환자가 목록에 남는다
- 같은 환자를 여러 사람이 거듭 연락하게 만든다(연락 기록이 점수·숨기기에 안 닿음)
- 의료·금액 내용이 담긴 안내가 사람 확인 없이 발송함에 기록된다
- 사람이 보내는 문자에 사실에 없는 숫자·날짜가 들어간 채 "통과"로 보인다
- 점수 값마다 이유를 적지 않는다(화면 "순위는 어떻게 정해지나요?"·문서)
- backend가 `ground_truth/`·`generator/`·`evaluation/`을 import하거나, 정답(`truth_patient_churn`)이 앱 쪽으로 새어 든다

## 정한 것

### 1. 목록에 오르는 조건 (모두 맞아야)

1. **우리 환자**: `completed` 내원 기록이 있다
2. **다음 예약 없음**: 기준일 이후 `scheduled` 예약이 없다(EMR에 예약이 잡히면 자동으로 빠지는 정상 경로)
3. **앱 기록으로 빠지지 않음**: 직원 연락 결과가 "예약함"(기간 없이 — 고정 데이터라 EMR에 새 예약이 안 생기므로 이 기록이 2를 대신한다), "안 오겠다고 함"(일정 기간, 예 180일), "다른 치과 다님"이 아니다
4. **칩이 하나 이상** 켜져 있다

기준일 = 앱 기준일(`shared/clinic.py`). 사실은 기준일 아침 기준(④ 준비표 `prep_facts`처럼 그날 전 사건만 — 실험 기록 분석이 과거 날짜로 다시 셀 수 있게).

### 2. 칩 6개 (코드)

| 칩 | 켜는 조건 | 출처·재사용 |
|---|---|---|
| 리콜 연체 | 마지막 위생 내원 + `emr_patients.recall_cycle_months` < 기준일 | ④ 가족 리콜과 같은 기준(`backend/prep.py` `_family_recall`, `backend/query_tools.py`) |
| 올해 스케일링 급여 미사용 | 성인, 올해 급여 스케일링 없음 | ④ `_scaling_unused`(예정 시술 없음으로) |
| 노쇼 뒤 재예약 없음 | 마지막 예약이 `noshow`이고 그 뒤 예약 없음 | `emr_appointments` |
| 미수 잔액 | 잔액 > 0 | ④ 잔액 계산 |
| 진료계획 미예약 | 열린 계획 항목이 있음 | ④ `_open_plan` |
| 다른 치과 추정 | 신호 중 하나 이상: 연락 문자(리콜·리마인드 등 out) 무응답이 이어짐, 노쇼 뒤 재예약 없음, 외부 이력 사유로 거절·조정된 청구(병행 — 가상 데이터 생성 설계 §2.2, `master` 상세 사유의 `external`) | 외부 이력 사유 코드는 backend가 `generator/`를 못 읽으므로 생성기가 `source.ax_master_values`에 이름 하나를 더해 적재(④ 기준표 적재와 같은 방식, verify 먼저). 무응답의 정확한 기준(몇 번·며칠)은 빌더가 신호 분포를 보고 정한다 — 정답(`truth_patient_churn`)을 보고 맞추지 않는다(2단계 채점의 기준선이 되므로) |

화면은 칩마다 인원수(필터 적용 전 전체 수). 칩 이름은 위 표 그대로.

### 3. 점수 (사용자 결정 — "연락하면 결과(예약·수납)가 날 가능성")

- **올리는 신호**: 마지막 방문이 최근일수록(오래될수록 줄어듦), 진료계획 미예약, 올해 스케일링 급여 미사용, 리콜 연체, 미수 잔액(금액에 따라, **상한** — 미수 하나로 맨 위를 차지하지 않게)
- **내리는 신호**: 노쇼 뒤 재예약 없음, 문자 무응답, 다른 치과 흔적, 최근 연락했는데 결과 없음(부재중 일정 기간 예 7일·나중에 다시 예 14일)
- 와이어프레임처럼 "칩이 많을수록 위"가 아니다 — 칩이 많아도 오래 안 왔거나 다른 치과 흔적이 있으면 내려간다
- **값은 원칙으로 정하고 이유를 적는다**(사용자 결정, §5). 꼴은 가중 덧셈 + 최근성 감쇠 + 미수 상한. 기본값은 backend 코드 상수, 바꾼 값만 앱 설정 `ax_settings`(앱 설계 §8 "⑨ 점수 규칙과 값 — 앱 쪽 설정이 원본" — 평가 코드가 앱 DB에 쓰지 않게, **내 판단**)
- **최근 연락**은 앱 연락 기록만 읽는다(**내 판단**) — 생성 데이터의 리콜·리마인드 문자는 거의 모든 환자가 받는 자동 문자라 넣으면 대부분이 "최근 연락함"으로 내려간다. 문자 무응답은 다른 치과 신호에서 따로 쓴다
- 화면 "순위는 어떻게 정해지나요?"는 지금 설정값으로 규칙을 사람 말로 보인다(와이어프레임 `howOpen`)
- 다른 치과 근거 찾기 에이전트(2단계)의 판단은 점수에 넣지 않는다

### 4. 연락 기록 (사용자 결정)

- 결과 5개와 목록·점수에 주는 효과:

| 결과 | 목록 | 점수 |
|---|---|---|
| 예약함 | 바로 빠짐 | — |
| 부재중·안 받음 | 남음("연락함 숨기기"로 가림) | 일정 기간 낮춤, 여러 번 겹치면 무응답 신호 |
| 나중에 다시 | 남음(숨기기 대상) | 일정 기간 낮춤 |
| 안 오겠다고 함 | 일정 기간 빠짐 | — |
| 다른 치과 다님 | 빠짐 | 다른 치과 흔적으로 기록(채점에서 참고 — 정답 아님) |

- 수단: 전화 / 문자. 2단계 자동 안내도 같은 기록에 "문자 · AI 자동"으로 남아 "최근 연락"이 함께 읽는다
- 누가·언제(실제 시계, 다른 사람 기록과 같은 꼴 — 파트 이름 `frontend/lib/part.ts`)
- 기간 값(7·14·180일)은 **내 판단** — 원칙값으로 두고 이유를 적는다(과거 데이터에는 앱 연락 기록이 없어 데이터로 맞출 수 없다)
- 연락 기록 테이블은 앱 설계 §4의 `ax_followup_contacts` 자리 — 이름은 새 이름으로(빌더 판단). 앱 설계 §7.3 "버림"(재생성 때) 목록에 있다

### 5. 점수 값과 과거 데이터 (사용자 결정 — 원칙으로 정하고, 데이터는 실험 기록 한 절)

처음에는 과거 데이터로 값을 맞추기로 했다가 바꿨다. 가상 데이터에는 **연락의 효과가 없다** — 예약은 생성 규칙대로 수요 기한(리콜 기한, 노쇼 뒤 재예약 지연)이 되면 저절로 잡힌다. 그래서 과거 데이터로 맞출 수 있는 것은 "연락하면 올 사람"이 아니라 "연락 안 해도 어차피 올 사람"이고, 맞추면 목록의 목적과 반대로 간다. 예: 기준일 2026-07-01, 다음 예약 없는 환자의 30일 안 새 예약 — 리콜 기한 임박 25.9%, 기한 멂 5.3%, 위생 내원 없음 9.3%, 리콜 연체 4.6%(연체 환자는 첫 리콜 무응답·휴면·이탈 환자). 미수는 정산이 다음 내원에서만 일어나게 생성돼 효과를 따로 잴 수 없다.

- 값은 원칙("연락하면 결과가 날 가능성")으로 정하고, 값마다 이유를 화면 "순위는 어떻게 정해지나요?"와 기능 정의 §5 ⑨에 적는다
- 과거 데이터 분석은 **한 번** 해서 [[치과 AX - AI 실험 기록]]에 한 절로(문제 → 원인 → 시도 → 결과 숫자 → 한계 → 원칙으로 정함). 직원 화면에는 나오지 않는다. `evaluation/`에 유지하는 백테스트 코드는 두지 않는다
- 상위 10명·더보기 10명은 그대로

### 6. 화면

- 칩 필터(칩별 인원수) · "연락함 숨기기" · "순위는 어떻게 정해지나요?"
- 표: 순위 · 환자(이름은 EMR 열기, 차트번호·나이·전화) · 칩 · 마지막 내원(몇 개월 전) · 미수 · 연락(결과 5개를 고르는 버튼/메뉴, 이미 연락했으면 결과·시각)
- 처음 10명, "더보기"마다 10명. 칩 필터·숨기기를 적용한 뒤의 점수 순
- 2단계에서 더함: 다른 치과 추정 칩 옆 에이전트 판단·근거, "문자 초안" 버튼(미수·치료 권유)
- 시각 디자인은 와이어프레임 레이아웃 기준, 토큰·`components/ui/`만

### 7. 오늘 화면 줄 (1단계)

`backend/today.py`(오늘 화면 브랜치에서 생김)의 "사람이 볼 일"에 `미예약 환자 · 상위 10명 → 미예약 환자 화면` 한 줄. 같은 함수로 센다. 대상이 0이면 숨김(오늘 화면 규칙)

## 2단계를 보류한 이유 (사용자 결정)

2단계의 AI 부분이 이 데이터로는 약하다. 다른 치과 추정에서 병행 환자 25명은 외부 이력 거절 청구(E01)와 1:1로 생성돼 칩만으로 100% 잡히고, 이탈 환자 신호는 약하다(리콜 문자 답장률 정상 21%·이탈 7%·병행 16%) — 에이전트는 생성 규칙을 다시 맞히는 정도이고 결과는 보여 주기만 한다. 문자 초안은 ④ 준비표의 "사실 → LLM → 후검증" 틀과 같고, 자동 안내는 템플릿이라 AI가 아니다. AI 시간은 정답으로 채점할 수 있는 ⑤·⑧에 먼저 쓴다. 다시 열 때 정할 것: 에이전트 대상과 채점 모수(화면용 상위 30명 / 채점용 고정 표본으로 나눌지), 채점에서 병행·이탈을 따로 보고(병행은 칩만으로도 100%라 합치면 부풀려짐), 외부 이력 사유는 `adjust_code`가 다른 사유와 같은 'C'라 문구로 구분.

### 8. 2단계 — 자동 안내 (사용자 결정: 템플릿)

- 대상: 리콜 연체 또는 올해 스케일링 급여 미사용 칩이 켜진 환자 중 다른 치과 추정·최근 연락 없는 환자(빌더 판단으로 다듬음)
- 문구: 칩별 **고정 템플릿** 몇 개 중 하나(이름·병원 이름·전화 정도만, 의료·금액 내용 없음 — 구조로 보장). 템플릿은 코드 상수 또는 `prompts/`가 아닌 앱 설정(빌더 판단)
- 기록: `ax_outbox`(앱 설계 §3b) + 자동 처리 `ax_auto_actions`(작업 종류 하나, 키 = 작업 종류·환자·기간 — 같은 안내는 기간마다 한 번). 되돌릴 수 있고 되돌린 건은 다시 기록하지 않는다(§3b 규칙). 오늘 화면 "AI가 한 일"의 자동 처리 목록에 뜬다(버튼 문구는 작업 종류에 맞게 — 예: "기록 취소", 빌더 판단)
- `auto_policy`로 켜고 끄며 기본 꺼짐(앱 설계 §6)
- 언제: 별도 `make` 명령(이름은 빌더 판단). 과금 없음(템플릿)

### 9. 2단계 — 사람이 보내는 문자 (사용자 결정: 누를 때 LLM)

- 대상: 미수 안내, 치료 권유. 직원이 목록에서 "문자 초안"을 누르면 그 환자의 사실(칩 사실 — ④ `llm_facts`와 같은 평평한 키 꼴)로 "가장 급한 것 하나부터" 한두 문장
- 출력·후검증은 ④와 같은 틀: `{text, used_facts}`, used_facts 값 = 사실 값, 본문 숫자는 used_facts 안(④ `check_suggestion` 재사용). 실패면 한 번 다시, 또 실패면 초안 없음
- 사람이 읽고 고쳐서 "보냄"을 누르면 연락 기록에 "문자"로. 실제 발송 없음
- 프롬프트 `prompts/<task>/v1.md`, 별칭은 `config/llm.yaml`(빌더 판단 — ④와 같은 `chat` 별칭이 자연스러움)

### 10. 2단계 — 다른 치과 근거 찾기 에이전트 (사용자 결정: 보여 주기만)

- 대상: 점수 상위 30명 중 다른 치과 신호가 하나라도 있는 환자(**내 판단**) — 별도 `make` 명령
- 도구: 앱 설계 §4 표의 ⑨ 근거 도구(`query_patient`, `search_docs`) — 쓰기 도구 없음(자동 처리 요청 도구 `request_auto_action`은 이번 범위에서 쓰지 않음, **내 판단**)
- 출력: 판단(다님 / 아님 / 모르겠음) + 근거(통화·문자·차트 인용 — 인용 확인은 ③과 같은 방식)
- 화면: 다른 치과 추정 칩 옆에 판단과 근거. 점수·순위에 넣지 않음
- 하네스 제약(호출·비용 상한, 넘으면 사람에게 넘김)은 기존 하네스 규칙대로

### 11. 2단계 — 채점 (`make eval`, 평가 설계 §5 ⑨)

- 다른 치과 추정 정밀도·재현율: 정답 = `truth_patient_churn`의 병행 + 흔적 있는 이탈(이탈일 뒤 발송 문자 무응답·노쇼·취소), 흔적 없는 이탈은 모수에서 뺀다. **칩만 쓴 기준선**(코드 칩)과 **에이전트 판단**을 나란히
- 사람이 보내는 문자 후검증 통과율
- 자동 안내에 의료·금액 내용 없음(코드 검사 — 템플릿이라 구조상 통과하는지 확인)
- 판정 풀·dev/test 분할이 필요하면 평가 설계 §5 ⑨에 맞춘다(빌더 판단, 이미 정해진 분할 규칙이 있으면 따름)
