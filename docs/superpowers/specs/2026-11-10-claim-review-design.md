# ⑤ 청구 점검·삭감 대응 — 설계

원본 규칙은 [[치과 AX - 기능 정의]] §5 ⑤, [[치과 AX - 평가 설계]] §5 ⑤·§3.1, [[치과 AX - 가상 데이터 생성 설계]] §2.4·§4.2·§4.3, [[치과 AX - 앱 설계]](앱 테이블·화면), 와이어프레임 `docs/wireframe/index-v2.html`의 `R.claims`·`claimExpand`·`appealDraft`·`preClaim`. 이 문서는 그 위에서 정한 것을 적는다. 설계는 한 번에, 실행은 네 단계로 나눈다 — 단계마다 브랜치 하나, 다음 단계 계획은 앞 단계를 머지한 뒤 쓴다.

## 왜

심평원 심사 결과는 청구 프로그램이 받아 장부에 반영돼 있다. 그 뒤에 남는 일 — 깎인 청구를 다툴지, 언제까지인지, 다음 청구에서 같은 실수를 막을지 — 은 사람이 청구 기준 문서와 차트를 뒤져 판단한다. 이 기능은 규칙으로 정확히 할 수 있는 것(기한·상병 조합·판단 제안)은 규칙으로, 서술을 읽어야만 보이는 것(차트의 임상 근거·청구에서 빠진 처치)과 근거 찾기·사유서는 AI로 돕는다. 청구 수정·재심 제출 결정은 사람만(기능 정의 §3 원칙 1).

## 목표 (단계별)

**1단계 — 코드(과금 없음)**
- 메뉴 "청구 점검"(`/claims`) 한 화면, 탭 `삭감 대응 | 청구 전 점검`
- 삭감 대응: 조정 목록 + 재심 기한 + 규칙 판단 제안 + 사람 판단 기록
- 청구 전 점검: 상병 확인 경고(규칙)
- 오늘 화면 "사람이 볼 일"에 줄 둘
- 생성기가 `ax_master_values`에 재심 기한·허용 상병 조합을 적재

**2단계 — ⑤-2 AI 점검**: 임상 요건(2a)·차트 기반 누락(2b), 기준선 대비 채점

**3단계 — ⑤-3 근거 찾기**: 청구 기준 검색 + 그 진료의 차트 근거 문장, 청구 기준 질문 평가셋

**4단계 — ⑤-4 재심 사유서 초안**

## 하지 않는 것

- 장부와 심사 결과가 어긋나는 일(기능 정의 §5 ⑤ 전제)
- 청구 수정·재청구·재심 제출 자체(표시와 결정 기록만)
- **사유 코드만으로 정해지는 판단을 AI가 하기** — 상병 착오·외부 이력(정당), 서류 사유(보완 후 재청구)는 규칙이 제안한다. 다만 **요건 사유**는 코드로 정해지지 않는다 — 차트에 요건 근거가 있으면 다툴 만함, 없으면 정당(가상 데이터 생성 설계 §2.4). 이건 ⑤-2 임상 요건 점검과 같은 일이라 2단계 AI가 조정 건에도 돌아 제안한다. 최종은 늘 사람
- 재심 근거 조사 **에이전트**(문서 원안) — 판단은 규칙 + 2단계 요건 AI, 근거 찾기는 3단계 검색·차트 문장 고르기로 나눈다. 규칙 판단은 지표가 아니라 테스트
- 화면을 열 때마다 AI 호출(2단계 점검은 명령으로 미리 만들어 저장)

## 하면 실패인 것

- 상병 착오 건에 "재심 신청"·"보완 후 재청구"를 고를 수 있다(재청구 불가)
- 재심 신청 기한·남은 날 수가 `master.APPEAL_DAYS`와 다르게 계산된다
- AI 점검이 근거 없이 표시하거나, 표시한 근거 문장이 그 차트·기준 절에 실제로 없다
- 사유서에 인용도 추측 표시도 없는 문장이 "통과"로 보이거나, 검토 확인 없이 "제출 결정"을 누를 수 있다
- AI 점검이 "서술 있는 줄 전부" 기준선보다 나은지 보고하지 않는다
- backend가 `ground_truth/`·`generator/`·`evaluation/`을 import하거나, 정답(`truth_claim_errors`·`truth_claim_qa`)이 앱 쪽으로 새어 든다. 프롬프트·규칙을 test 분할로 고친다

## 정한 것

### 1. 1단계 — 화면과 규칙

**삭감 대응 탭 — 조정 목록**(와이어프레임 `R.claims`의 10칸이 잘 안 읽혀 5칸으로 줄이고, 상세는 행 아래로 펼침)
- 대상: 확정 월의 `adjusted`·`denied` 청구(장부 그대로) 중 **재심 신청 기한이 남은 건**(지금 데이터 633건 중 101건). 기한이 지난 건은 `기한 지남` 칩으로 따로 보고, 판단 버튼 없이 기록(사유·금액·이미 남긴 판단)만 보인다. 칩 건수·못 받은 금액 합계는 고른 칩 기준. 기본 탭은 삭감 대응(기한이 걸린 일)
- **목록 5칸**: `재심 신청 기한`(칸 안 `12/08 · 7일 남음`, 기한 = 통보일 + `APPEAL_DAYS`, `backend/claims.py` `SOON_DAYS`일 이내 위험·`WATCH_DAYS`일 이내 주의 꼬리표) · `환자 · 시술`(진료일·치아) · `못 받은 돈`(청구 − 지급, 전액 불능이면 "(전액)") · `왜 깎였나`(상세 사유 문구 — 코드가 아니라 사람 말) · `할 일`(판단 전에는 "판단 필요" 딱지와 규칙 추천 "추천: 보완 후 재청구"·"추천: 삭감 수용", 요건 사유는 1단계에서 "차트 확인 후 결정", 사람이 고르면 "재심 신청 · 데스크 11/09"처럼 확정 표시)
- 통보일·청구·지급 금액·사유 코드는 목록에서 빼고 펼친 곳으로
- 칩: 전체(기한 남음) · 상병 착오 · `신청 기한 SOON_DAYS일 이내`(상병 착오 제외) · 전액 불능 · 일부 조정 · `기한 지남`, 칩별 건수, 오른쪽에 못 받은 금액 합계
- 정렬: 재심 신청 기한 가까운 순(기본, 기한 지남 칩은 최근에 지난 순)과 못 받은 돈 큰 순 — 표 위에 지금 정렬
- 상병 착오(상세 사유 범주가 진단 — `master.ADJUST_REASONS`)는 기한 칸에 날짜와 `재청구 불가` 딱지(기한이 지났으면 `기한 지남` 딱지도)
- **펼친 내용 3칸**(직원이 묻는 순서): ① **왜 깎였나** — 사유·청구 → 지급·조정/불능·통보일·재심 신청 기한, 청구 기준 절 카드(§3) ② **어떻게 할까** — 제안과 이유 한 줄(요건 사유는 2단계부터 AI가 읽은 차트 근거 문장과 "근거 있음 → 재심 신청 / 없음 → 삭감 수용"), 판단 버튼 세 개 ③ **재심 사유서** — 사람이 "재심 신청"을 고른 건만(4단계)
- 상세 사유는 `adjust_note` 문구로 가린다(코드 'C' 등은 여러 사유가 공유 — ⑨ 설계에서 확인). 사유 → 범주·판단 규칙에 필요한 표는 생성기가 `ax_master_values`에 적재(§1 끝)

**판단 — 규칙 제안 + 사람 기록**
- 규칙 제안(가상 데이터 생성 설계 §2.4): `master.ADJUST_REASONS`의 `type`으로 — `diagnosis`(상병 착오) → 정당·재청구 불가, `external`(외부 이력) → 정당, `documentation`(내역설명·증빙·기재 누락) → 보완 후 재청구, `requirement` → **규칙으로 정하지 않음**("차트 확인 필요" — 2단계 AI가 제안). 사유 코드(C·B 등)는 사유끼리 겹치므로 `adjust_note` 문구로 가린다(실데이터 문구 11종이 master와 정확히 같음 — 확인함). 표는 `ax_master_values`에 문구 → `type`으로 적재
- 사람이 세 버튼 중 하나를 눌러 기록(누가 = 파트, 언제 = 실제 시계). 상병 착오는 "삭감 수용"만 누를 수 있다
- 추천·판단이 "보완 후 재청구"면 채울 항목(부위·산정 내역 / 내역설명·증빙) — 서류 사유 건은 그 아래 차트에서 옮겨 적을 문장(§3)
- 기록은 `ax_claim_judgments`(청구 id 단위, 다시 누르면 덮어씀)

**청구 전 점검 탭 — 상병 확인 경고**(와이어프레임 `preClaim`)
- 대상: 대기(`pending`) 청구 줄(지금 데이터 2026-11월분 218줄)
- 규칙: 시술 × 차트 상병(`emr_chart_notes.dx_code`)이 `master` 시술별 허용 상병 밖이면 경고. 지난 조정에서 같은 시술 × 상병 조합이 상병 착오로 깎였으면 "지난 조정에서 이 조합 n건, x원 못 받음"
- 칸: 진료일 · 환자(이름 → EMR) · 시술(치아) · 청구액 · 차트 상병 · 경고
- 탭 위 칩: `청구 전 n줄` · `상병 확인 경고(규칙) n` · `임상 요건·차트 기반 누락(AI)`(2단계 전에는 숨김 — 빈 자리를 두지 않는 오늘 화면 원칙과 같게). `서술 있는 줄`은 두지 않는다(§2 — 서술 구분은 정답 DB에만)

**오늘 화면 줄**(`backend/today.py` "사람이 볼 일", 0이면 숨김)
- `재심 신청 기한 임박 n건 → /claims?chip=soon`(30일 이내, 상병 착오 제외 — 칩과 같은 함수)
- `청구 전 상병 경고 n건 → /claims?tab=pre`

**생성기 적재**(④·⑨와 같은 방식, verify 먼저)
- `ax_master_values`에 이름 추가: 재심 기한 일수(`APPEAL_DAYS`), 시술별 허용 상병(`master.PROCEDURE_DIAGNOSES`), 상세 사유 문구 → `type`(`ADJUST_REASONS`), 상세 사유 → 청구 기준 절(`generator/doc_catalog.py` `CLAIM_HEADINGS` — 2단계 입력과 3단계 카드가 쓴다, 병원이 아는 기준 문서 목차라 정답 누출이 아님), 시술 → 요건 사유(`ADJUST_REASONS` 요건 유형의 시술을 뒤집음 — 2단계가 요건 점검 대상 시술을 거르는 데 씀). 이름은 [[치과 AX - 가상 데이터 생성 설계]] §3
- 데이터 상태 고정 — 기존 생성 테이블은 그대로. `make data`는 LLM 작업 0건인지 먼저 확인

### 2. 2단계 — ⑤-2 AI 점검

- **"서술 있는 줄"을 앱에서 가르지 않는다** — 서술/템플릿 구분은 정답 DB(`truth_chart_notes.kind`)에만 있고 본문 모양으로는 깔끔히 갈리지 않는다(길이·표현이 겹침). 생성기가 이 구분을 앱 표로 적재하는 것은 생성 메타 누출이라 하지 않는다
- **앱 대상**: 대기(`pending`) 줄 중 요건이 있는 시술 줄과 재심 신청 기한이 남은 요건 사유 조정·불능 건(`backend/claim_check.py` `targets` "app"). 입력 해시·프롬프트 버전·모델이 같고 통과한 줄은 다시 부르지 않는다(④ 준비표 꼴)
- **규칙으로 먼저 거름**: 임상 요건 점검은 요건이 있는 시술(`ax_master_values`의 시술 → 요건 사유)에만 묻는다. 차트 기반 누락은 요건 대상 여부와 무관하게 따로 묻는다(범위는 2b, 2a 답의 `omissions`는 화면·채점에 쓰지 않는다). 같은 부위 재시행처럼 앱이 해당 여부를 확정할 수 없는 요건(코스 정보는 정답 DB에만)은 후보 절을 모두 넣는다
- **입력**: 시술·치아·상병·나이·차트 서술 + 그 시술의 청구 기준 절. **청구 상태·조정 결과·사유는 넣지 않는다** — 확정 월 요건 오류는 전부 실제로 깎인 줄이라 상태를 보이면 차트를 안 읽고도 맞힌다. 생성 메타도 넣지 않는다(`emr_chart_notes` 허용 컬럼만)
- **출력**(④ 후검증 틀): 줄마다 `{임상 요건: 근거 있음 / 근거 없음(삭감 위험) / 판단 불가, 차트 기반 누락: [{처치, 근거 문장}], 근거: [{종류: 차트|기준, 인용}]}` — 인용은 그 차트·기준 절에 실제로 있어야 통과(③ 인용 확인·④ 후검증 재사용), 실패면 한 번 다시, 또 실패면 판단 없음. 차트 서술이 없는 줄은 부르지 않고 판단 불가로 저장
- **조정 건 판단(b)**: 요건 사유로 깎인 조정 건도 같은 판단(근거 있음 → 다툴 만함 제안, 없음 → 정당 제안). 앱은 기한이 남은 건만, 평가는 전부. 같은 줄을 한 번만 읽어 (a)·(b) 채점에 같이 쓴다
- **채점 범위(2a): 전 기간**(413줄 범위로 자르면 요건 오류 51건뿐이라 dev/test 각 25건 안팎으로 흔들린다)
  - 임상 요건형 오류 266건 전부(확정 월 215 · 제출 월 39 · 대기 12). 정밀도·재현율·근거 정확도를 **"서술 있는 줄 전부" 기준선**(정답 DB로 평가 쪽에서만 계산, 재현율 100%)과 나란히. **기간별로도 따로**(확정 월 / 제출·대기 월 — 확정 월 오류 비율은 평가용 비율이 아니라 심사 결과라 성격이 다르다)
  - 조정 건 판단(b): 요건 사유 조정 354건 — 정당 215 · 다툴 만함 139, "모두 정당"(약 61%)·"모두 다툴 만함" 기준선과 나란히
  - **추가 처치 누락**: 2b(아래)
  - 상병 착오(92)는 규칙 테스트
  - dev/test는 줄 단위 해시로 반반(다른 기능과 같은 방식), 프롬프트는 dev로만 고치고 test는 사람만(평가 설계 §2.7)
- **비용**: 프롬프트는 dev 고정 표본(`evaluation/claim_check.py` `dev_sample`)으로만 고치고 dev 전부는 버전을 정한 뒤 한 번. 실측은 [[치과 AX - AI 실험 기록]] §22
- **앱 화면**: 청구 전 점검 탭의 AI 칩에 판단·근거를 보이고, 조정 건 펼친 곳 ②에 요건 판단 제안과 근거 문장

### 2b. 2단계 나머지 — 추가 처치 누락

- **왜 따로**: 실데이터 추가 처치 누락 23건(제출 월 16 · 대기 7, `truth_claim_errors` kind `omitted_extra`)은 모양이 거의 하나다 — "스케일링 시행하고 이어서 12번 치아 아말감/GI 함께 진행함"(아말감/GI 21 · 실란트 2, `master.SAME_DAY_EXTRA`). 키워드로도 거의 잡히므로 AI가 키워드보다 나은지는 실데이터에 없는 모양의 합성 사례로 잰다
- **묻는 범위**: 제출·대기 줄 전부(2026-09 ~ 11, 678줄 — 요건 대상 여부와 무관). 실데이터 누락 23건이 모두 이 안이고, 확정 월에는 누락 정답이 없다(5b가 결과가 없는 달에만 심음). 앱 화면은 대기 줄만 보인다
- **질문**: 줄마다 짧게 — "차트에 그날 했다고 적혔는데 이 청구에 없는 급여 처치가 있나, 있으면 처치·치아·근거 문장". 입력은 청구된 시술·치아와 차트 서술(`emr_chart_notes` 허용 컬럼)만, 청구 상태·조정 결과는 넣지 않는다(§2와 같음). 2a와 별도 호출·별도 프롬프트(요건 점검 입력에는 청구 기준 절이 들어가 길고, 누락은 모든 줄에 묻는다). 인용 실재 후검증·한 번 더·해시 재사용은 2a와 같다
- **급여 판정은 코드**: AI는 그날 한 처치와 치아만 뽑고(급여 여부를 묻지 않음), 코드가 처치 이름을 `emr_procedures` 이름·별칭으로 시술 코드에 맞춘 뒤 비급여(`is_insured`)·치아 단위가 아닌 시술·그날 나이에 급여가 아닌 경우(실란트는 소아 — `age_group`)·청구된 시술·치아와 같은 것을 거른다. 맞출 수 없는 이름은 버린다. 합성 디코이에 성인 실란트·비급여 처치(레진)를 넣어 이 거름을 잰다
- **앱·평가 범위**(2a의 `scope`와 같은 꼴): 앱 명령·화면 버튼은 대기 줄만(버튼 건수·비용도 대기 줄), 제출 월은 평가 범위(`scope` "all")로 돌린다. 둘 다 `app.sqlite`의 같은 표(합성 사례만 `evaluation/`)
- **요건 대상 줄의 2a `omissions`**: 2a는 그대로 두고 화면·채점은 2b 답 하나만 쓴다(줄마다 기준이 둘이면 칩 건수가 어긋난다)
- **합성 사례**(코드가 정하고 LLM은 문장만): 평가 전용(`evaluation/claim_omission.py` `case_specs`). 원본 `emr_*`·`truth_*`는 그대로(데이터 고정)
  - 코드가 사례마다 정한다: 청구된 시술·치아·나이, 모양, 정답(누락 있음 → 처치·치아 / 없음)
  - 누락 있는 모양(실데이터에 없는 것): 시술 이름 대신 다른 표기("GI 충전"·"글라스아이오노머" — "때움"은 레진과 갈리지 않아 정답을 못 정함), 처치 문장이 본 시술 문장과 떨어짐, 치아 번호가 문장 앞, 실란트
  - 누락 없는 디코이: 계획만("다음 내원 때 아말감 예정"), 권했으나 거절·보류, 다른 병원에서 받은 처치, 청구된 시술 그 자체를 다시 적음, 지난 내원에 한 처치, 성인 실란트, 레진
  - LLM(과금, 이어 돎 — 캐시 파일은 `evaluation/` 아래)은 그 사실로 차트 서술 한 단락만 쓴다(실데이터 말투). 코드 검사(`check_note`)가 확인: 추가 처치 치아 번호·청구 시술 이름·모양 표지가 있다, 누락 있는 모양의 추가 처치 문장에는 그날 안 한 처치의 표지가 없다, 그날 하지 않은 디코이는 직접 부정 없이 맥락으로만, `master.CHART_FORBIDDEN_WORDS`가 없다. 통과 못 한 사례는 다시 쓴다
  - 합성 사례 dev/test는 모양마다 반반(`split_of`). 프롬프트는 합성 dev로만 고친다, 실데이터 23건은 test 전용(사람). 실데이터 정상 줄(누락 정답이 없는 줄)은 `claim_split`으로 나눠 dev 쪽 잘못 잡은 줄 수를 `make eval`에서 본다(실데이터 말투에서 생기는 오탐을 고칠 신호, 누락 줄 23건은 dev 집계에서 뺀다)
  - 합성 사례 실행 결과는 `app.sqlite`가 아니라 `evaluation/` 기록에(정답이 붙은 입력이라)
- **채점**(평가 설계 §5 ⑤-2): 실데이터 "23건 중 n건" + 그 범위 정상 줄에서 잘못 잡은 줄 수, 합성 정밀도·재현율 — 둘은 섞지 않고 따로. 기준선은 키워드 규칙(`evaluation/claim_omission.py` `keyword_items`)과 나란히. 맞음·잘못 잡음·놓침은 항목 단위(평가 설계 §5 ⑤-2)
- **앱 화면**: 청구 전 점검 탭 AI 칩 건수에 누락 줄을 더하고, 행에 딱지 `차트에 있는데 청구에 없음(AI)` + 처치·치아 + 근거 문장

### 3. 3단계 — ⑤-3 근거 찾기 (판단은 규칙, AI는 근거)

- **기준 조항 카드**: 조정 건을 펼친 곳 ① 왜 깎였나 칸에 그 사유의 청구 기준 절 본문을 그대로(사유 → 절 대응표 `adjust_note_headings`, 본문은 `ax_documents` claim_standard — 평가 설계 §5 "상세 사유 → 절은 테스트"). 모든 사유 유형, 접지 않고 펼치자마자 보인다. 카드 머리는 `문서 제목 › 절 제목`
- **차트에서 옮겨 적을 문장(AI)**: 서류 사유(`documentation`) 조정 건만 — 펼친 곳 ② 어떻게 할까 칸의 "채울 항목" 아래. 요건 사유 건은 2a 근거를 그대로 쓴다(새 호출 없음)
  - 입력: 그 진료의 시술·치아·차트 서술 + 그 사유의 기준 절 본문. 청구 금액·조정 결과·판단 기록은 넣지 않는다
  - 출력: 차트 인용 0~3개(그 절이 요구하는 내용에 해당하는 문장). 해당 문장이 없으면 빈 목록 — 화면은 "차트에 옮겨 적을 문장 없음"(방사선 증빙처럼 차트에 없는 자료). 인용은 차트에 실제로 있어야 통과(2a `found` 재사용), 실패면 한 번 다시, 또 실패면 결과 없음
  - 실행: 2a·2b처럼 명령으로 미리 만들어 저장(앱 범위 = 재심 신청 기한이 남은 서류 사유 건, 평가 범위 = 서류 사유 조정·불능 전부). 화면 "AI 점검 갱신하기" 버튼 하나가 2a·2b와 함께 돌린다(버튼 건수는 줄 합집합). 같은 입력은 다시 부르지 않는다(해시·버전·모델)
  - 채점: 인용 실재 후검증 통과율과 답 분포(인용 있음 / 없음). 정답이 없어 정확도는 재지 않는다
- **청구 기준 찾기**: 청구 점검 화면 맨 위, 두 탭이 함께 쓰는 검색칸. ③ 물어보기의 검색 엔진(`backend/rag_search.py` 하이브리드 + 리랭커)을 청구 기준 문서(`doc_type` claim_standard)의 절 청크로 좁혀(문서 머리 청크 — 제목·머리말만 — 는 뺀다) 절 5개를 원문 그대로 보인다 — AI가 답 문장을 쓰지 않는다. 검색했을 때만 "찾은 조항" 상자가 열리고 닫을 수 있다, 아래 탭·목록은 그대로. 색인(`make index`)이 없으면 검색했을 때 안내 한 줄
- **평가셋 `truth_claim_qa`**(AI 초안, 사람 검토): 상세 사유 11개마다 2문항(22), 코드·절 제목을 말하지 않는 직원 말투, 베끼기 검사(정답 절과 연속 4어절·정답 값 — 평가 설계 §3.1)를 통과한 초안만 검토에 올린다. 정답 절은 생성 규칙(상세 사유 → 절)에서. 초안은 `evaluation/`에서 게이트웨이로 직접 쓴다(생성기 단계를 더하지 않는다 — 데이터 고정). 검토는 `evaluation/` 안의 단독 로컬 페이지(작은 서버 + HTML 한 장, 앱과 따로 — 정답이 앱으로 새지 않게) — 문항마다 승인·수정(문장 고치기)·버림, 고친 문장은 베끼기 검사를 다시 돌려 경고를 보인다(경고는 막지 않고 사람이 정한다, 평가 설계 §3.1), 끝나면 정답 JSON(`ground_truth/`)으로 쓰고 `make data`가 `truth_claim_qa`에 적재한다(`ground_truth/schema.sql`에 새 표, 어려운 통화 정답 JSON과 같은 흐름). dev/test는 사유(절) 단위 반반(청구 기준 문서가 5개뿐이라 문서 단위로 나누면 test가 몇 문항뿐 — 같은 문서의 다른 절이 양쪽에 걸친다)
- **채점**: `truth_claim_qa`의 Hit@5·MRR — 맞음은 **절(청크) 단위**(③ 채점의 문서 단위로 세면 문서가 5개뿐이라 거의 저절로 맞는다, 정답 칸은 절 제목 `truth_claim_qa.answer_heading`). 검색 대상은 청구 기준 문서 절 11개뿐이라 리포트에 후보 수를 함께. 판단 3분류·사유 → 절은 규칙이라 테스트(헷갈리기 쉬운 '내역설명 누락' ↔ '상병 착오' 쌍 포함)

### 4. 4단계 — ⑤-4 재심 사유서 초안

- **대상**: 사람이 "재심 신청"(`contestable`)을 기록한 조정 건만(규칙·AI 추천이 아니라 사람 판단 기준). 펼친 곳 ③ 재심 사유서 칸에 [초안 쓰기]. 기한 지난 건은 판단을 못 남기니 초안도 없다. 판단을 다른 값으로 바꾸면 초안 칸을 숨기고 초안은 지우지 않는다(다시 "재심 신청"이면 보인다)
- **입력**: 조정 사유 문구, 시술·치아, 그 사유의 청구 기준 절(제목·본문 — §3 조항 카드와 같은 것), 그 진료의 차트 서술. 청구 금액·판단 기록은 넣지 않는다(사유서에 금액은 필요 없다)
- **출력**: 문장 목록 + 추측 목록(`assumptions[]`). 문장마다 근거 하나 — 조정 내역 인용 / 기준 절 인용 / 차트 인용(셋 다 인용 구절) / 추측(추측 목록 번호). 와이어프레임의 `조정 내역` 꼬리표처럼 조정 사유 문구도 인용 원문이다
- **후검증**: (1) 한 칸 = 한 문장 — 칸을 문장 나누기 규칙(아래)으로 나눠 둘 이상이면 실패 (2) 인용 구절은 그 원문(조정 사유 문구·기준 절 본문·차트 서술)에 실제로 있고(2a `found`) 그 문장 안에도 글자 그대로 있다 — 인용한 사실이 문장에 그대로 보이게 (3) 추측 번호는 목록에 있다. 하나라도 어기면 실패 — 한 번 다시, 또 실패면 "초안을 만들지 못했습니다"
- **화면**(와이어프레임 `appealDraft`): 초안 문장마다 꼬리표(`기준 절 인용`·`차트 인용`·`추측 ①`), 그 아래 "AI가 추측한 부분 — 여기만 확인하면 됩니다". "검토했고 정확함" 체크 뒤에만 [복사](사유서 본문을 클립보드에)와 [제출 결정](누가 = 파트·언제 기록만, AI는 제출하지 않는다)이 켜진다. 검토 확인도 서버에 저장한다(파트·시각 — 제출 결정은 서버가 검토 확인이 있을 때만 받는다). 화면에서 문장을 고치지 않는다 — 실제 제출은 심평원 포털·청구 프로그램에서 하고 고치기도 붙여 넣은 곳에서(앱에서 고치면 인용 꼬리표를 보장할 수 없다). [다시 쓰기]는 새 초안을 받고 검토 확인을 푼다. 제출 결정 뒤에는 다시 쓰기와 그 건의 판단 버튼을 잠근다(제출한 사유서와 판단이 어긋나지 않게)
- **실행**: 누를 때 일반 호출(사람이 기다림), 저장해 두고 다시 열면 그대로
- **채점**: 정답 기준 다툴 만함(요건 사유 조정 중 오류 없는 줄 — 가상 데이터 생성 설계 §2.4) 139건 중 dev 쪽(청구 id 해시, `evaluation/claim_check.py` `claim_split`)에 초안을 만든다. 평가 초안은 `app.sqlite`에 쓰지 않고 `evaluation/` 기록에만(앱 표에 두면 "초안이 있는 건 = 정답상 다툴 만함"이 앱에 남는다 — 2b 합성 사례와 같은 방식, 입력·요청·후검증 함수는 앱과 같은 것). 지표: 후검증 통과율(첫 답 · 다시 부른 뒤), **첫 답 원출력**에서 근거 없는 문장 비율(나눈 문장 중 인용이 그 문장에 없거나 원문에 없거나 추측 번호가 없는 것 — 최종 출력은 후검증을 통과해 0이라 첫 답으로 잰다). 문장은 마침표·물음표·느낌표 뒤 공백과 줄바꿈으로 나눈다(테스트로 고정)
