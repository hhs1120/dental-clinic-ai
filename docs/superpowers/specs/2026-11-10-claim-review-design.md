# ⑤ 청구 점검·삭감 대응 — 설계

원본 규칙은 [[치과 AX - 기능 정의]] §5 ⑤, [[치과 AX - 평가 설계]] §5 ⑤·§3.1, [[치과 AX - 가상 데이터 생성 설계]] §2.4·§4.2·§4.3, [[치과 AX - 앱 설계]](앱 테이블·화면), 와이어프레임 `docs/wireframe/index-v2.html`의 `R.claims`·`claimExpand`·`appealDraft`·`preClaim`. 이 문서는 그 위에서 정한 것을 적는다. 설계는 한 번에, 실행은 네 단계로 나눈다(사용자 결정) — 단계마다 브랜치 하나, 다음 단계 계획은 앞 단계를 머지한 뒤 쓴다.

## 왜

심평원 심사 결과는 청구 프로그램이 받아 장부에 반영돼 있다. 그 뒤에 남는 일 — 깎인 청구를 다툴지, 언제까지인지, 다음 청구에서 같은 실수를 막을지 — 은 사람이 청구 기준 문서와 차트를 뒤져 판단한다. 이 기능은 규칙으로 정확히 할 수 있는 것(기한·상병 조합·판단 제안)은 규칙으로, 서술을 읽어야만 보이는 것(차트의 임상 근거·청구에서 빠진 처치)과 근거 찾기·사유서는 AI로 돕는다. 청구 수정·재심 제출 결정은 사람만(기능 정의 §3 원칙 1).

## 목표 (단계별)

**1단계 — 코드(과금 없음)**
- 메뉴 "청구 점검"(`/claims`) 한 화면, 탭 `삭감 대응 | 청구 전 점검`
- 삭감 대응: 조정 목록 + 재심 기한 + 규칙 판단 제안 + 사람 판단 기록
- 청구 전 점검: 상병 확인 경고(규칙)
- 오늘 화면 "사람이 볼 일"에 줄 둘
- 생성기가 `ax_master_values`에 재심 기한·허용 상병 조합을 적재

**2단계 — ⑤-2 AI 점검**: 임상 요건·차트 기반 누락, 기준선 대비 채점

**3단계 — ⑤-3 근거 찾기**: 청구 기준 검색 + 그 진료의 차트 근거 문장, 청구 기준 질문 평가셋

**4단계 — ⑤-4 재심 사유서 초안**

## 하지 않는 것

- 장부와 심사 결과가 어긋나는 일(기능 정의 §5 ⑤ 전제)
- 청구 수정·재청구·재심 제출 자체(표시와 결정 기록만)
- **사유 코드만으로 정해지는 판단을 AI가 하기**(사용자 결정) — 상병 착오·외부 이력(정당), 서류 사유(보완 후 재청구)는 규칙이 제안한다. 다만 **요건 사유**는 코드로 정해지지 않는다 — 차트에 요건 근거가 있으면 다툴 만함, 없으면 정당(가상 데이터 생성 설계 §2.4). 이건 ⑤-2 임상 요건 점검과 같은 일이라 2단계 AI가 조정 건에도 돌아 제안한다(사용자 결정). 최종은 늘 사람
- 재심 근거 조사 **에이전트**(문서 원안) — 판단은 규칙 + 2단계 요건 AI, 근거 찾기는 3단계 검색·차트 문장 고르기로 나눈다. 규칙 판단은 지표가 아니라 테스트
- 화면을 열 때마다 AI 호출(2단계 점검은 명령으로 미리 만들어 저장)

## 하면 실패인 것

- 상병 착오 건에 "재심 신청"·"보완 후 재청구"를 고를 수 있다(재청구 불가)
- 재심 신청 기한·남은 날 수가 `master.APPEAL_DAYS`와 다르게 계산된다
- AI 점검이 근거 없이 표시하거나, 표시한 근거 문장이 그 차트·기준 절에 실제로 없다
- 사유서에 인용도 추측 표시도 없는 문장이 "통과"로 보이거나, 검토 확인 없이 "제출 결정"을 누를 수 있다
- AI 점검이 "서술 있는 줄 전부" 기준선보다 나은지 보고하지 않는다
- backend가 `ground_truth/`·`generator/`·`evaluation/`을 import하거나, 정답(`truth_claim_errors`·`truth_claim_qa`)이 앱 쪽으로 새어 든다. 프롬프트·규칙을 test 분할로 고친다

## 정한 것

### 1. 1단계 — 화면과 규칙

**삭감 대응 탭 — 조정 목록**(사용자 결정 — 와이어프레임 `R.claims`의 10칸이 잘 안 읽혀 5칸으로 줄이고, 상세는 행 아래로 펼침)
- 대상: 확정 월의 `adjusted`·`denied` 청구(장부 그대로) 중 **재심 신청 기한이 남은 건**(지금 데이터 633건 중 101건). 기한이 지난 건은 `기한 지남` 칩으로 따로 보고, 판단 버튼 없이 기록(사유·금액·이미 남긴 판단)만 보인다(사용자 결정). 칩 건수·못 받은 금액 합계는 고른 칩 기준. 기본 탭은 삭감 대응(**내 판단** — 기한이 걸린 일)
- **목록 5칸**: `재심 신청 기한`(칸 안 `12/08 · 7일 남음`, 기한 = 통보일 + `APPEAL_DAYS`, `backend/claims.py` `SOON_DAYS`일 이내 위험·`WATCH_DAYS`일 이내 주의 꼬리표) · `환자 · 시술`(진료일·치아) · `못 받은 돈`(청구 − 지급, 전액 불능이면 "(전액)") · `왜 깎였나`(상세 사유 문구 — 코드가 아니라 사람 말) · `할 일`(판단 전에는 "판단 필요" 딱지와 규칙 추천 "추천: 보완 후 재청구"·"추천: 삭감 수용", 요건 사유는 1단계에서 "차트 확인 후 결정", 사람이 고르면 "재심 신청 · 데스크 11/09"처럼 확정 표시)
- 통보일·청구·지급 금액·사유 코드는 목록에서 빼고 펼친 곳으로
- 칩: 전체(기한 남음) · 상병 착오 · `신청 기한 SOON_DAYS일 이내`(상병 착오 제외) · 전액 불능 · 일부 조정 · `기한 지남`, 칩별 건수, 오른쪽에 못 받은 금액 합계
- 정렬: 재심 신청 기한 가까운 순(기본, 기한 지남 칩은 최근에 지난 순)과 못 받은 돈 큰 순 — 표 위에 지금 정렬
- 상병 착오(상세 사유 범주가 진단 — `master.ADJUST_REASONS`)는 기한 칸에 날짜와 `재청구 불가` 딱지(기한이 지났으면 `기한 지남` 딱지도)
- **펼친 내용 3칸**(직원이 묻는 순서): ① **왜 깎였나** — 사유·청구 → 지급·조정/불능·통보일·재심 신청 기한(3단계부터 청구 기준 절 카드) ② **어떻게 할까** — 제안과 이유 한 줄(요건 사유는 2단계부터 AI가 읽은 차트 근거 문장과 "근거 있음 → 재심 신청 / 없음 → 삭감 수용"), 판단 버튼 세 개 ③ **재심 사유서** — 사람이 "재심 신청"을 고른 건만(4단계)
- 상세 사유는 `adjust_note` 문구로 가린다(코드 'C' 등은 여러 사유가 공유 — ⑨ 설계에서 확인). 사유 → 범주·판단 규칙에 필요한 표는 생성기가 `ax_master_values`에 적재(§1 끝)

**판단 — 규칙 제안 + 사람 기록**(사용자 결정)
- 규칙 제안(가상 데이터 생성 설계 §2.4): `master.ADJUST_REASONS`의 `type`으로 — `diagnosis`(상병 착오) → 정당·재청구 불가, `external`(외부 이력) → 정당, `documentation`(내역설명·증빙·기재 누락) → 보완 후 재청구, `requirement` → **규칙으로 정하지 않음**("차트 확인 필요" — 2단계 AI가 제안). 사유 코드(C·B 등)는 사유끼리 겹치므로 `adjust_note` 문구로 가린다(실데이터 문구 11종이 master와 정확히 같음 — 확인함). 표는 `ax_master_values`에 문구 → `type`으로 적재
- 사람이 세 버튼 중 하나를 눌러 기록(누가 = 파트, 언제 = 실제 시계). 상병 착오는 "삭감 수용"만 누를 수 있다
- "보완 후 재청구"를 고르면 채울 항목 자리(부위·산정 내역 / 내역설명·증빙) — 근거 차트 문장은 3단계에서 채운다
- 기록은 `ax_claim_judgments`(청구 id 단위, 다시 누르면 덮어씀)

**청구 전 점검 탭 — 상병 확인 경고**(와이어프레임 `preClaim`)
- 대상: 대기(`pending`) 청구 줄(지금 데이터 2026-11월분 218줄)
- 규칙: 시술 × 차트 상병(`emr_chart_notes.dx_code`)이 `master` 시술별 허용 상병 밖이면 경고. 지난 조정에서 같은 시술 × 상병 조합이 상병 착오로 깎였으면 "지난 조정에서 이 조합 n건, x원 못 받음"
- 칸: 진료일 · 환자(이름 → EMR) · 시술(치아) · 청구액 · 차트 상병 · 경고
- 탭 위 칩: `청구 전 n줄` · `상병 확인 경고(규칙) n` · `임상 요건·차트 기반 누락(AI)`(2단계 전에는 숨김, **내 판단** — 빈 자리를 두지 않는 오늘 화면 원칙과 같게). `서술 있는 줄`은 두지 않는다(§2 — 서술 구분은 정답 DB에만)

**오늘 화면 줄**(`backend/today.py` "사람이 볼 일", 0이면 숨김)
- `재심 신청 기한 임박 n건 → /claims?chip=soon`(30일 이내, 상병 착오 제외 — 칩과 같은 함수)
- `청구 전 상병 경고 n건 → /claims?tab=pre`

**생성기 적재**(④·⑨와 같은 방식, verify 먼저)
- `ax_master_values`에 이름 추가: 재심 기한 일수(`APPEAL_DAYS`), 시술별 허용 상병(`master.PROCEDURE_DIAGNOSES`), 상세 사유 문구 → `type`(`ADJUST_REASONS`), 상세 사유 → 청구 기준 절(`generator/doc_catalog.py` `CLAIM_HEADINGS` — 2단계 입력과 3단계 카드가 쓴다, **내 판단**: 병원이 아는 기준 문서 목차라 정답 누출이 아님), 시술 → 요건 사유(`ADJUST_REASONS` 요건 유형의 시술을 뒤집음 — 2단계가 요건 점검 대상 시술을 거르는 데 씀). 이름은 [[치과 AX - 가상 데이터 생성 설계]] §3
- 데이터 상태 고정 — 기존 생성 테이블은 그대로. `make data`는 LLM 작업 0건인지 먼저 확인

### 2. 2단계 — ⑤-2 AI 점검

- **"서술 있는 줄"을 앱에서 가르지 않는다**(사용자 결정) — 서술/템플릿 구분은 정답 DB(`truth_chart_notes.kind`)에만 있고 본문 모양으로는 깔끔히 갈리지 않는다(길이·표현이 겹침). 생성기가 이 구분을 앱 표로 적재하는 것은 생성 메타 누출이라 하지 않는다
- **앱 대상**: 대기(`pending`) 줄 중 요건이 있는 시술 줄과 재심 신청 기한이 남은 요건 사유 조정·불능 건(`backend/claim_check.py` `targets` "app"). 입력 해시·프롬프트 버전·모델이 같고 통과한 줄은 다시 부르지 않는다(④ 준비표 꼴)
- **규칙으로 먼저 거름**(사용자 결정): 임상 요건 점검은 요건이 있는 시술(`ax_master_values`의 시술 → 요건 사유)에만 묻는다. 차트 기반 누락은 모든 줄에 묻되 짧은 질문으로(모든 줄에서 나올 수 있어 거를 수 없다 — 2b, 2a는 요건 대상 줄의 답에서만 `omissions`를 받는다). 같은 부위 재시행처럼 앱이 해당 여부를 확정할 수 없는 요건(코스 정보는 정답 DB에만)은 후보 절을 모두 넣는다(**내 판단**)
- **입력**: 시술·치아·상병·나이·차트 서술 + 그 시술의 청구 기준 절. **청구 상태·조정 결과·사유는 넣지 않는다** — 확정 월 요건 오류는 전부 실제로 깎인 줄이라 상태를 보이면 차트를 안 읽고도 맞힌다. 생성 메타도 넣지 않는다(`emr_chart_notes` 허용 컬럼만)
- **출력**(④ 후검증 틀): 줄마다 `{임상 요건: 근거 있음 / 근거 없음(삭감 위험) / 판단 불가, 차트 기반 누락: [{처치, 근거 문장}], 근거: [{종류: 차트|기준, 인용}]}` — 인용은 그 차트·기준 절에 실제로 있어야 통과(③ 인용 확인·④ 후검증 재사용), 실패면 한 번 다시, 또 실패면 판단 없음. 차트 서술이 없는 줄은 부르지 않고 판단 불가로 저장
- **조정 건 판단(b)**: 요건 사유로 깎인 조정 건도 같은 판단(근거 있음 → 다툴 만함 제안, 없음 → 정당 제안). 앱은 기한이 남은 건만, 평가는 전부. 같은 줄을 한 번만 읽어 (a)·(b) 채점에 같이 쓴다
- **채점 범위: 전 기간 급여 청구 줄**(사용자 결정 — 413줄 범위로 자르면 요건 오류 51건뿐이라 dev/test 각 25건 안팎으로 흔들린다)
  - 임상 요건형 오류 266건 전부(확정 월 215 · 제출 월 39 · 대기 12). 정밀도·재현율·근거 정확도를 **"서술 있는 줄 전부" 기준선**(정답 DB로 평가 쪽에서만 계산, 재현율 100%)과 나란히. **기간별로도 따로**(확정 월 / 제출·대기 월 — 확정 월 오류 비율은 평가용 비율이 아니라 심사 결과라 성격이 다르다)
  - 조정 건 판단(b): 요건 사유 조정 354건 — 정당 215 · 다툴 만함 139, "모두 정당"(약 61%)·"모두 다툴 만함" 기준선과 나란히
  - **추가 처치 누락**(사용자 결정): 실데이터 11건은 dev/test로 나누지 않고 **test 전용**, 비율이 아니라 "11건 중 n건"으로 보고. 프롬프트는 요건 오류 dev로만 고친다. 여기에 **평가 전용 합성 사례 30~50건**(누락 있는 차트 + 청구, 누락 없는 비슷한 사례 섞음)을 `evaluation/` 아래에 따로 만들어 정밀도·재현율을 낸다 — 원본 `emr_*`은 그대로(데이터 고정), 운영 에이전트의 시나리오 정답과 같은 방식(생성 규칙·검사를 먼저). 실데이터 11건 성적과 합성 성적은 섞지 않고 따로 보고
  - 상병 착오(92)는 규칙 테스트
  - dev/test는 줄 단위 해시로 반반(다른 기능과 같은 방식), 프롬프트는 dev로만 고치고 test는 사람만(평가 설계 §2.7)
- **비용**: 프롬프트는 dev 고정 표본(`evaluation/claim_check.py` `dev_sample`)으로만 고치고 dev 전부는 버전을 정한 뒤 한 번. 실측은 [[치과 AX - AI 실험 기록]] §22
- **앱 화면**: 청구 전 점검 탭의 AI 칩에 판단·근거를 보이고, 조정 건 펼친 곳 ②에 요건 판단 제안과 근거 문장

### 3. 3단계 — ⑤-3 근거 찾기 (사용자 결정: 판단은 규칙, AI는 근거)

- 조정 건을 펼치면 제안 옆 **근거**: 그 사유의 청구 기준 절 카드(사유 → 절 대응표로 바로 — 평가 설계 §5 "상세 사유 → 절은 테스트") + 그 진료의 차트 문장 중 재심 근거가 되는 문장(LLM이 고르고 인용 실재 후검증)
- 코드 없이 묻기: "치석제거 다음 달로 넘어가면 왜 깎여?" 같은 질문으로 기준 절을 찾는다 — ③ 물어보기의 기록 검색과 같은 엔진, 청구 기준 문서로 좁힘(화면 위치는 빌더 판단 — 탭 안 검색칸이 자연스러움)
- **평가셋 `truth_claim_qa`**(사용자 결정 — AI 초안, 사람 검토): 상세 사유 11개마다 1~2문항, 코드를 말하지 않는 직원 말투, 베끼기 검사(정답 문단과 연속 4어절·정답 값 — 평가 설계 §3.1) 통과. 정답 절은 생성 규칙(상세 사유 → 절)에서. 초안을 사용자에게 보여 고치거나 승인받은 뒤 정답 저장소에 넣는다. dev/test는 **사유(절) 단위**로 나눈다(**내 판단** — 청구 기준 문서가 5개뿐이라 문서 단위로 나누면 test가 문서 2~3개·몇 문항뿐. 같은 문서의 다른 절이 양쪽에 걸칠 수 있음을 리포트에 적는다). `ground_truth/schema.sql`에 `truth_claim_qa`를 새로 만든다
- **채점**: 코드를 말하지 않는 질문(`truth_claim_qa`)의 Hit@5·MRR(③ 채점 재사용), 차트 근거 문장 인용 실재율. 판단 3분류는 규칙이라 테스트(헷갈리기 쉬운 '내역설명 누락' ↔ '상병 착오' 쌍 포함)

### 4. 4단계 — ⑤-4 재심 사유서 초안

- "재심 신청"(`contestable`)을 사람이 고른 건에만(규칙 제안이 아니라 사람 판단 기준)
- 입력: 조정 건 + 3단계 근거(기준 절·차트 문장). 출력: 문장 목록 — 모든 문장은 기준 절 인용 / 차트 문장 인용 / 추측 목록(`assumptions[]`) 중 하나에 묶인다. 둘 다 아닌 문장이 있으면 후검증 실패
- 화면(와이어프레임 `appealDraft`): 초안(문장마다 인용·추측 꼬리표) + "AI가 추측한 부분 — 여기만 확인하면 됩니다" + "검토했고 정확함" 체크 뒤에만 "제출 결정"(기록만, AI는 제출하지 않음)
- 채점: 정답 기준 다툴 만함 139건 중 dev 쪽으로(**내 판단**) 인용 실재 후검증 통과율 + 인용도 추측 표시도 없는 문장 비율(코드). 문장 나누는 규칙은 빌더 판단(마침표·줄바꿈 기준, 테스트로 고정)
- 실행: 누를 때 일반 호출(사람이 기다림), 저장해 두고 다시 열면 그대로
