# 자동 종결·처리 정답·후속 에이전트 설계

원본: `docs/치과 AX - 기능 정의.md` §4 ①(오늘 할 일·자동 종결·후속 에이전트·완료 기준)·§3 원칙 1(자동 처리)·§9 관련 줄, `docs/치과 AX - 앱 설계.md` §1(`ax_call_followups`)·§3b(`ax_auto_actions`·`apply_auto_action`·스케줄러)·§7.3(전환 뒤 상태), `docs/치과 AX - 평가 설계.md` §5(① 후속 처리·자동 종결 오류율)·§6(`truth_call_actions`), `docs/치과 AX - 가상 데이터 생성 설계.md` §5.1(평가 전용 단계). 이 문서는 그 규칙을 코드로 옮길 때 새로 정한 것만 적는다.

## 왜

통화를 분류하면 할 일 있는 통화는 "오늘 할 일"에 오르지만, 할 일 없는 통화는 처리됐다는 표시가 없고, 할 일 있는 통화는 직원이 환자 기록을 다시 찾아야 처리할 수 있다. 자동 종결은 확인할 것이 없는 통화를 근거와 함께 닫아 사람이 볼 양을 줄이고, 후속 에이전트는 할 일 있는 통화에 처리 종류와 조회한 사실을 미리 붙여 직원이 기록을 다시 찾지 않게 한다. 둘 다 정답으로 오류율·정확도를 잰다.

## 범위 — PR 둘

1. **PR ① 자동 종결**: 조건 함수, `apply_auto_action` 코드 경로, 되돌리기, "오늘 할 일"에서 빼기, `eval.py --section auto`(오류율)
2. **PR ② 처리 정답 + 후속 에이전트**: `truth_call_actions`(생성기 평가 전용 단계, verify 먼저), 후속 에이전트(하네스), `ax_call_followups`, 화면 A안, 규칙 기준선, `eval.py` 후속 처리 섹션

안 하는 것: 시나리오 DB·`truth_scenarios`(⑥·운영 에이전트 착수 때), 오늘 화면(`/today`, "AI가 한 일" 목록 — 오늘 화면 착수 때. 이번에는 통화 상세에서 되돌린다), `make nightly`(이번에는 명령을 따로 돌린다), 안내 문장 초안, 처리안 실행(전화·문자·예약).

실패로 볼 것: 응급·불만·급함·엇갈림·폴백이 있는 통화가 자동 종결되는 것, 판정 풀 통화가 자동 종결되는 것, `auto_policy`가 꺼져 있는데 종결되는 것, 처리안 근거에 도구 결과에 없는 사실(날짜·금액)이 들어가는 것, 정답 파생과 같은 규칙을 기준선이 쓰는 것(그러면 기준선이 만점).

## 사람이 정함

- **순서**: PR ① 자동 종결 → PR ② 처리 정답 + 후속 에이전트
- **처리안 모양**: 종류 1개 + 근거(조회한 사실). 안내 문장 초안은 쓰지 않는다
- **채점 모수**: 골드도 분류기(활성 분류)도 할 일 있음인 통화 — 처리안 자체만 잰다(기준선과 같은 모수). 골드는 할 일인데 분류기가 놓친 통화 수, 분류기만 할 일인 통화 수는 옆에 따로 적는다
- **평가 실행 범위·방식**: dev 판정 풀 + silver 검증 구간의 해당 통화(약 330, 두 수치를 따로 보고), **Batch API로**. 한 번 돌려 `evaluation/`에 쌓고 `eval.py`는 채점만(비용 0). 다시 도는 것은 에이전트 프롬프트·모델·도구가 바뀔 때, 바뀐 통화, test 1회(사람). 맛보기 단가 측정은 하지 않는다
- **처리안 종류 7가지**: 예약 잡기·변경 / 원장님 확인 후 회신 / 수납·미수 확인 / 서류 준비 / 보험·비용 안내 / 스케일링 시기 안내 / 기타(사람 판단)
- **화면 A안**: 오늘 할 일 카드에 처리안 한 줄(종류 딱지 + 요지), 통화 상세에 처리안 절(종류·근거 사실 목록·조회한 도구, "과정 보기"로 실행 단계)

## 내가 정함 (검토 바람)

### PR ① 자동 종결

- **조건 함수** `backend/autoclose.py` `autoclose_reason(cls, judge) -> str | None` — 넘으면 None이 아니라 종결 이유 문자열, 못 넘으면 None. 조건(기능 정의 §4 ① 완료 기준 그대로): 두 결과 모두 `ok`·폴백 아님, 두 모델 모두 `has_todo` 거짓, 응급·불만 거짓, 급함 urgent 아님(두 모델 모두), 엇갈림 없음(앱 엇갈림 규칙 그대로 — `differing_items` 빈 목록이고 분류기 할 일 목록이 비어 있음(`todo_mismatch` 아님)), 판정 풀 통화 아님. `eval.py`도 이 함수를 쓴다(평가 설계 §5)
- **실행**: `make autoclose` — 활성 분류 버전 × 활성 판정기 버전 결과가 모두 있는 통화에 조건을 계산해 `apply_auto_action(kind="call_autoclose", target=call_uid)`. 이미 종결됐거나 되돌린 통화는 건너뛴다(UNIQUE 키·되돌린 건 재종결 금지는 `auto.py`가 이미 함). 새로 추가한 통화는 분류·판정이 끝나는 같은 흐름에서 한 번 계산한다
- **스위치**: `auto_policy`의 `call_autoclose`(기본 끔). 켜고 끄는 명령 `make auto-policy KIND=call_autoclose ON=1|0`. 꺼져 있으면 아무것도 종결하지 않는다
- **오늘 할 일**: 종결된(되돌리지 않은) 통화는 오르지 않는다. 통화 기록 목록에는 "자동 종결" 딱지
- **되돌리기**: 통화 상세에 "자동 종결됨 · 이유 · 되돌리기" 줄. `POST /auto-actions/{id}/revert`(앱 설계 §3b 그대로) — 되돌리면 오늘 할 일로 돌아온다
- **사람 되돌림과 시스템 풀기를 구분한다**: 사람이 되돌린 통화(`revert_auto_action`, `reverted_at`)는 다시 종결하지 않는다(앱 설계 §3b — 되돌린 건이 다시 살아나지 않게). 조건이 바뀌어 시스템이 푸는 경우(분류·판정기 활성 버전이 바뀌어 조건을 못 넘음)는 그 종결 행을 지운다 — 다음에 조건을 다시 넘으면 다시 종결된다. `make autoclose`가 돌 때마다 활성 버전 쌍으로 다시 계산해 풀고 닫는다(버전 전환을 알릴 지점이 따로 없어서)
- **사람 판정이 종결을 푼다**: 운영 판정(`ax_judgments`)이 할 일·응급·불만·급함 중 하나를 켜면 그 통화의 종결을 되돌린다(되돌린 사람 = 판정자). 기능 정의 §4 ① 완료 기준
- **분류 버전 전환**: 앱 설계 §7.3 그대로 — 새 분류로 조건을 다시 계산해 못 넘는 통화만 종결을 푼다
- **오류율** `eval.py --section auto`(test 묶음, 키는 교차검증처럼 `분류 버전×판정기 버전` — 한 쌍) / dev 기본 포함(활성 쌍): 조건을 넘은 통화 중 골드가 할 일·응급·불만·급함(urgent)인 비율. dev는 silver 검증 구간(`silver_split`), test는 test 판정 풀. 분수와 95% 신뢰구간(Wilson). 자동 처리율(대상 중 종결 비율)도 함께. 판정 풀은 앱이 종결하지 않으므로 조건 함수를 직접 돌려 잰다
- **정확도 뷰**: 기능 정의 §9 "자동 종결 착수 시" 줄의 정확도 뷰 목록 정의는 이번 범위 — 앱 설계 §1에 이름·모수·컬럼을 적고 §4 ② 완료 기준의 뷰 개수·행 수를 맞춘다(구현은 이미 있는 `backend/metrics.py` 기준으로 문서만 맞추는 것이 목표)

### PR ② 처리 정답

- **위치**: 생성기 평가 전용 단계(`make scenarios` — 가상 데이터 생성 설계 §5.1). LLM 없이 `source.sqlite`·골드를 읽어 `truth_call_actions(call_uid, action, split)`를 쓴다. 기존 테이블은 바꾸지 않는다. verify 검사 먼저: 기존 테이블 해시 그대로, 골드 `has_todo`=1인 통화만 행이 있음, action이 7가지 중 하나
- **파생 규칙(초안 — 계획에서 표로 확정)**: 골드 `has_todo`=1인 통화만. 목적 기준 — `book`·`reschedule`·`confirm`·`cancel` → 예약 잡기·변경, `billing_q` → 수납·미수 확인, `document_req` → 서류 준비, `price_q`·`insurance_q` → 보험·비용 안내, `recall_q` → `used_fact.recent_visits`에 스케일링이 있으면 스케일링 시기 안내, 아니면 원장님 확인 후 회신, `treatment_q`·`emergency`·`complaint` → 원장님 확인 후 회신, `other`·`unknown` → 기타. 경계가 애매한 조합은 계획 단계에서 실제 통화 몇 건을 읽고 확정한다
- **이름**: 7가지 코드 값 `appointment`·`doctor_reply`·`billing`·`document`·`insurance_cost`·`scaling_timing`·`other`(우리말 이름은 화면용으로 `shared/`에)

### PR ② 후속 에이전트

- **대상**: 오늘 할 일에 오른 통화 중 활성 분류의 `has_todo`가 참인 통화(판정 풀 제외). 평가용은 위 "채점 모수"의 통화
- **입력**: 통화(방향·녹취록), 활성 분류 결과(9항목·요약·할 일), 환자 식별(차트 번호 — 있을 때). 차트 번호는 `ax_calls.patient_id`에서 — 통화 화면이 이미 이 값으로 환자를 잇고 있고(발신번호 매칭에 해당, 앱 설계 §1), 처음 연락한 사람은 비어 있다
- **도구**: 기존 `query_patient`·`query_schedule`(조회 전용) + 문서 검색(기존 `rag_search` 를 도구로 감싸 — 스케일링 급여 기준 같은 안내 문서) + `refuse`. 쓰기 도구 없음. 호출 상한은 `evaluation/metrics.py` `MAX_TOOL_CALLS`와 같은 6(앱 쪽 상수)
- **출력**(구조화): `{action: 7가지, summary: 한 줄 요지, facts: [근거 문장], used_tools: [...]}`. 후검증: `facts`·`summary`의 날짜·금액이 그 실행의 도구 결과나 녹취록에 있어야 한다(④ 후검증과 같은 방식) — 실패하면 한 번 다시, 또 실패하면 처리안 없이 실패로 남긴다
- **모델**: 게이트웨이 별칭 `followup` = `claude-sonnet-5-5`(앱 설계 §7 "그 밖의 에이전트")
- **기록**: `ax_call_followups(call_uid, classification_id, action, summary, facts, run_id, status, created_at)` — 분류 행 단위(분류 버전이 바뀌면 새 처리안). 실행 단계는 하네스의 `ax_agent_runs`·`ax_agent_steps`
- **실행**: `make followups` — 대상 중 그 분류 행의 처리안이 없는 통화만. 새로 추가한 통화는 분류 뒤 같은 흐름
- **할 일 체크와의 관계**: 처리안은 통화 단위 하나, 체크는 지금처럼 할 일 줄마다. 처리안이 체크를 대신하지 않는다. 분류 버전을 바꿀 때 체크를 이어 붙이지 않는다(앱 설계 §7.3 지금 규칙)
- **규칙 기준선**: 분류기 할 일 문장의 낱말 규칙(예: "예약·일정·시간" → 예약, "영수증·진단서·서류" → 서류, "금액·수납·미납" → 수납, "보험·실손·비용" → 보험·비용, "스케일링" → 스케일링 시기, 그 밖 "원장님" → 원장님 확인 후 회신, 나머지 기타). 정답 파생(골드 목적·사실)과 다른 입력·규칙이다
- **평가 실행 — 라운드 배치**: 에이전트는 도구 결과를 보고 다음 호출을 정하므로 한 번의 Batch로 끝나지 않는다. 라운드마다 아직 안 끝난 실행의 다음 턴을 모아 Batch로 제출 → 결과를 단계로 저장 → 도구를 로컬에서 실행 → 다음 라운드(최대 호출 상한 + 1 라운드). 하네스는 이미 저장된 단계로 대화를 다시 세워 이어 가므로(`backend/harness/loop.py` 재개) 이 구조를 쓴다. 남은 실행이 적어지면(기준 30건 이하 — 앱 상수) 그 라운드부터는 일반 호출로 끝낸다 — 양이 많은 앞 라운드는 반값, 몇 건 안 남은 꼬리에서 Batch 대기를 되풀이하지 않게(사람이 정함). 판정 풀 통화가 들어가므로 실행 기록은 앱 DB가 아니라 `evaluation/`의 별도 저장소(실행 단계 DB 사본 또는 jsonl)에 둔다. 앱의 `make followups`(오늘 할 일)는 일반 호출
- **채점**: `eval.py` 후속 처리 섹션 — 처리안 정확도(에이전트 vs 기준선, 7가지 일치, 종류별 k/n), 후검증 실패율, 실행 비용. dev는 매번, test는 묶음 1회(평가 설계 §1 원칙 2)
- **화면(A안)**: 카드 — 연락할 사람·할 일 칸의 그 통화 카드 아래에 처리안 한 줄(종류 딱지 + summary). 처리안이 없으면 줄 없음, 실패면 "처리안 실패" 흐린 글자. 상세 — 분류 위에 "처리안" 절(딱지·facts 목록·조회한 도구, "과정 보기"로 단계 펼침)

## 구현자에게

모듈·함수 나눔, 프롬프트 문장, 기준선 낱말 목록의 세부, 화면 문구·색(토큰 안에서), 신뢰구간 계산 세부, 후검증 정규식.
