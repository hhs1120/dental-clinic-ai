# 골드 점검 설계

원본: `docs/치과 AX - 평가 설계.md` §2.3 "골드 점검"(대상·중재·사람 표본·기록·쓰임·한계), §2.2(정확도 분리 보고), `docs/치과 AX - 기능 정의.md` §4 ② 완료 기준 "골드 점검(pytest)". 이 문서는 그 규칙을 코드로 옮길 때 새로 정한 것만 적는다.

## 왜

판정기(Solar)를 골드로 재고, 분류기(Haiku)도 골드로 잰다. 그런데 골드는 생성기가 붙인 "의도"라서 녹취록의 사실과 어긋날 수 있다. 판정기가 골드와 다르게 답한 통화를 제3의 모델이 가리고 사람이 표본으로 확인해, 골드가 얼마나 믿을 만한지(라벨 타당성)를 숫자로 낸다. 결과는 리포트·README의 한계 절에 쓰인다. 골드는 고치지 않는다(데이터 고정).

## 목표 / 안 하는 것

- 목표: 대상 선정 → 중재 판정(LLM) → 사람 표본 50통화(터미널) → `eval.py` 리포트에 일치율·골드 오류 추정 건수·오류 추정 건을 뺀 dev 수치
- 안 하는 것: 골드 수정, test 판정 풀 점검, 앱 화면(골드를 보므로 `evaluation/`만), 운영 판정(`ax_judgments`)과의 연결
- 실패로 볼 것: 중재·사람 입력에서 어느 쪽이 골드인지 드러나는 것, test 판정 풀 통화가 대상에 들어가는 것, 골드가 든 호출 기록·결과가 `data/`(app.sqlite)에 쓰이는 것

## 사람이 정함

- **대상의 급함 비교는 급함 여부만**: 판정기 라벨과 골드를 `shared/call_labels.py` `differing_items`(엇갈림 계산과 같은 규칙 — urgent냐 아니냐만)로 비교한다. 3값 비교는 대상 935통화 중 급함 814항목이 골드 추첨값(normal/low)이라 쓰지 않는다. 지금 데이터로 대상 **250통화·315항목**(test 판정 풀 제외, 판정기 v2)
- **중재 판정기 모델은 Opus, 추론 medium**(`claude-opus-5-5`, 프롬프트 머리말 `effort: medium`): 판정기(Solar)·생성기(Sonnet) 모두와 다른 모델. 게이트웨이 별칭 `gold_audit: [claude-opus-5-5]`, 서버 측 폴백 응답은 실패로 보고 다시 돈다(섞이면 중재가 바뀐다). low·medium 맞대 보기는 [[치과 AX - AI 실험 기록]] §13. 판정기 버전이 같으면 한 번만 드는 비용
- **사람 표본 50통화는 사용자가 직접**(평가 설계 §2.3 그대로). 값 `GOLD_AUDIT_SAMPLE = 50`은 `evaluation/metrics.py`

## 구현에서 정함

- **급함 항목은 두 값으로 보여 준다**: 대상이 urgent 여부로 정해졌으므로 중재·사람 화면에서 급함은 `급함 / 급하지 않음`으로 가린 두 라벨을 보인다(3값을 보이면 normal/low 차이를 고르게 된다)
- **"둘 다 아님"은 목적·상대에만**: 플래그 6개와 급함(두 값)은 골드와 판정기가 다르면 둘 중 하나가 반드시 맞으므로 `가 / 나`만 고른다(중재 스키마·사람 화면 모두). 애매함 선택지는 두지 않는다 — 애매함을 골드 오류로 세면 오류가 부풀고, 세지 않으면 쓸 데가 없다.
- **골드 오류 추정은 중재 결과로만 정한다**(평가 설계 §2.3 "쓰임" 그대로): 리포트의 오류 추정 건수와 dev에서 뺄 (통화, 항목)은 중재 선택만 쓴다. 사람 답은 dev 수치를 바꾸지 않는다 — 표본 50통화만 다른 기준으로 빠져 모수가 섞인다. 중재 기준 제외 수치는 참고이고 골드 오류 규모는 표본 안 사람 기준으로 말한다(평가 설계 §2.3 쓰임)
- **판정기 버전이 바뀌면**: 기록 키는 (`call_uid`, `judge_version`) — 한 줄 = 한 통화·한 판정기 버전. `gold-arbitrate`는 활성 판정기 버전의 대상 중 그 버전 줄이 없는 것만 호출하고, 표본은 버전마다 따로 뽑는다(옛 버전 사람 답은 다시 쓰지 않는다). 리포트는 활성 판정기 버전 줄만 읽는다. 판정기는 자동 개선 대상이 아니라(평가 설계 §2.7) 버전이 바뀌는 일은 드물다
- **중재 입력**: 방향·녹취록 + 다른 항목마다 `가`·`나` 두 값. 어느 쪽이 골드인지는 `call_uid`와 항목 이름의 해시로 정한다(통화 안에서도 항목마다 섞임). 항목 정의는 판정기 프롬프트(`prompts/judge/v2.md`)의 라벨 정의를 그대로 옮기고, 할 일은 "두 답 중 녹취록에 맞는 쪽(목적·상대는 둘 다 틀리면 둘 다 아님)". 프롬프트 파일 `prompts/gold_audit/v1.md`. 구조화 출력: 목적·상대는 `가 | 나 | 둘 다 아님`, 나머지는 `가 | 나`
- **호출 기록**: 중재 입력에 골드가 들어 있어 앱 DB(`ax_llm_calls`)에 쓰지 않고 `evaluation/gold_audit_llm.jsonl`(커밋, `shared/llm.py` `JsonlLog` — 맛보기 스크립트와 같은 방식)
- **기록 형식** `evaluation/gold_audit.jsonl`(커밋) — 한 줄 = 한 통화: `call_uid`, `transcript_sha`, `judge_version`, `items: {항목: {gold, judge, gold_side: 가|나, arbiter: gold|judge|neither, human: gold|judge|neither|null}}`, `arbiter_model`, `prompt_version`, `effort`. 판정자 선택은 가/나가 아니라 골드·판정기 쪽으로 풀어 저장한다. 재생성 뒤에는 `transcript_sha`로 다시 붙이고, 녹취록이 바뀐 통화는 리포트에서 빠진 수로 적는다
- **명령 둘**: `make gold-arbitrate [BATCH=1]`(중재가 없는 대상만 호출 — 과금, 실패·빠진 건만 다시. `BATCH=1`은 Batch API, 제출한 배치 id·기록 파일·대상 값은 `evaluation/gold_audit_batch.json`에 두어 끊겨도 다시 제출하지 않는다 — 커밋 안 함) / `make gold-audit`(사람 표본 터미널 화면). 모듈 `evaluation/gold_audit.py`
- **사람 화면**: 표준 입력만(새 의존성 없음). 한 통화씩 방향·녹취록(직원/환자 줄 구분) → 다른 항목마다 `가 / 나` 값을 보이고 `1 가 · 2 나`(목적·상대는 `3 둘 다 아님`도)을 입력(Enter). 통화의 항목을 다 고르면 저장하고 그때 중재 결과를 보여 준다. 매 통화 저장이라 중간에 끊어도 이어서 한다(`human`이 빈 표본 통화부터). 되돌리기는 없다(마지막 통화 다시 고르기만 — 구현자 판단으로 생략 가능)
- **표본 뽑기**: 통화를 중재 결과로 묶는다(판정기 쪽 항목이 하나라도 있으면 `judge`, 없고 둘 다 아님이 있으면 `neither`, 나머지 `gold`). 묶음마다 50/3을 `call_uid` 해시 순으로 뽑고, 모자란 묶음의 몫은 남은 묶음에 돌아가며 채운다. 사람 화면은 해시 순(묶음 순이면 중재 결과가 미리 샌다). 중재가 전부 끝난 뒤에만 뽑는다(결과가 바뀌면 표본이 바뀌므로)
- **리포트**: `eval.py`의 판정 섹션(`--section judge`와 dev 기본)에 붙인다
  - 중재 vs 사람 일치 `k/n`(분수) — 항목별·전체·중재 선택별
  - 골드 오류 추정 건수: 중재가 판정기 쪽을 고른 항목 수, 둘 다 아님 항목 수(따로, 항목별)
  - dev만: 모델 vs 골드·판정기 vs 골드를 오류 추정 (통화, 항목)을 모수에서 뺀 수치를 원래 수치 옆에. test에는 원래 골드 수치만
  - `gold_audit.jsonl`이 없으면 "골드 점검 전"이라고만 쓴다
- **pytest**(기능 정의 §4 ② 완료 기준): 대상에 test 판정 풀 통화가 없음, 중재 입력(메시지 전체 문자열)에 골드 쪽을 알 수 있는 표시가 없고 가/나 배치가 양쪽 다 나옴, 사람 화면 출력도 같음, 표본 뽑기가 묶음별로 고르고 결정적, 리포트의 오류 추정 제외가 dev에만. 가짜 게이트웨이로 돈다(과금 없음)

## 문서 변경

- 평가 설계 §2.3 골드 점검: 대상 비교가 급함 여부만이라는 것, 화면의 급함 두 값, 둘 다 아님은 목적·상대에만, 기록 키 (통화, 판정기 버전), 중재 모델은 `config/llm.yaml` `gold_audit`, 명령 `make gold-arbitrate`·`make gold-audit`, 호출 기록 위치. 평가 설계 §7 "골드 점검 결과는 `make gold-audit`가 생긴 뒤 붙인다" 줄 정리
- `CLAUDE.md` 명령에 두 명령 한 줄
- 기능 정의 §9: 착수 순서에서 골드 점검을 빼고, 남은 중재·사람 표본을 할 일 한 줄로
- 결과(일치율·오류 추정)는 실험 기록이 아니라 리포트에 나온다. 눈에 띄는 패턴(예: 특정 항목 골드 오류가 몰림)이 있으면 실험 기록에 한 절

## 구현자에게

모듈 안 함수 나눔, 프롬프트 문장, 화면 문구·색, 구조화 출력 스키마 세부, 리포트 표 모양.
