# ① 어려운 통화 평가셋 설계

기능 정의 §9 "① 어려운 통화 평가셋"을 구현한다. 근거 문제는 AI 실험 기록 §23이다. 지금 녹취는 프롬프트 예시 문구가 그대로 퍼져 있어서 글자 n-gram 기준선이 분류기와 거의 같은 점수를 낸다.

## 1. 목적

포트폴리오에서 정량으로 말할 수 있는 결과를 만든다. 목표 문장은 "예시 문구에 기대지 않는 어려운 통화에서는 분류기가 n-gram보다 확실히 앞선다"이다.

- **결과물:** `hard` 250건에서 규칙, 글자 n-gram, 분류기를 나란히 놓은 표다.
  - 항목은 §23 표와 같다: 목적, 상대, 급함, `wants_appt`, `appt_confirmed`, `has_todo`.
  - 줄은 전체 한 줄과 어려움 종류별 줄로 나눈다.
- **대비:** 기존 dev 표(§23)와 나란히 둔다. 쉬운 셋에서는 비슷하고 어려운 셋에서는 차이가 벌어지는 모습을 보이기 위해서다.

## 2. 하지 않을 것과 피할 것

- **기존 데이터는 바꾸지 않는다.**
  - 대상은 `c-` 통화, `emr_*`·`fin_*`의 모든 행, 기존 라벨과 분할, 기존 LLM 캐시다.
  - 이번 작업은 데이터 재설계가 아니라 단계 추가다.
- **n-gram은 다시 학습하지 않는다.** 지금처럼 silver 재료 구간으로만 학습한다(`evaluation/call_baselines.py`).
- **분류기 프롬프트와 라벨 정의는 이 셋 때문에 고치지 않는다.**
  - `hard`는 채점 전용이다.
  - 다음 어디에도 들어가지 않는다: 프롬프트 관문, 튜닝, 자동 개선, few-shot 예시, Qwen 학습 재료, silver 재료·검증, dev·test 판정 풀, 블라인드 풀, 골드 점검.
- **결과를 보고 셋을 다시 만들지 않는다(피할 것).**
  - 생성 프롬프트와 슬롯 규칙은 분류기·n-gram 결과를 보기 전에 고정한다.
  - 다시 생성하는 경우는 검증기 실패뿐이다.
  - 차이가 작게 나와도 그대로 보고한다. 이 셋은 "n-gram이 지도록 고른 셋"이라는 의심을 받으면 실패다.
- **정답이 애매한 통화는 만들지 않는다.** 라벨 정의 문장만 보고 판단할 수 있어야 한다. 경계 사례는 종류마다 규칙으로 막는다.

## 3. 생성

### 3.1 단계

- 생성기에 새 단계 `hard_calls`를 `build.STAGES` 맨 끝(`master_values` 뒤)에 더한다.
  - 자기 `stage_rng`를 쓴다.
  - 앞 단계의 결과와 캐시는 하나도 바뀌지 않는다.
- 같은 `ax_calls`에 `call_uid` `hc-0001`부터 더한다.
  - 기존 `c-` 번호는 통화 수에 걸린 순열이라 그 체계와 섞지 않는다.
  - `hc-` 행은 기존 행 뒤에 붙인다. 기존 행 id를 다시 매기지 않는다.
  - 시각순 행 검사(`check_call_row_order`)는 `c-`끼리만 본다(설계자 결정).

### 3.2 구성: 어려움 종류 5개 × 50건 = 250건

| `hard_type` | 무엇이 어려운가 |
|---|---|
| `indirect` | 플래그나 목적을 간접적으로만 드러낸다. 예: 예약하고 싶다는 뜻을 "그때 시간 되면…"으로만 말한다 |
| `reversal` | 통화 중 한 번 정한 것을 뒤집는다. 주 목적은 처음 꺼낸 용건 그대로이고(분류 정의 "처음 꺼낸 목적"), 표시 항목 하나가 뒤집혀 마지막 상태가 정답이다(사람 결정 A). 예약은 날짜를 정했다가 미룸(예약 확정 → 미확정), 그 밖(진료·보험·가격·수납·서류 문의)은 할 일 |
| `urgency_inverted` | 낱말과 급함이 거꾸로 간다. 25건 + 25건으로 나눈다(아래) |
| `misleading_noise` | 끊김이나 섞인 주제 때문에 첫 문장만 보면 다른 목적으로 읽힌다 |
| `outbound_real` | 병원이 거는 실제 발신 통화다 |

**`urgency_inverted` (사람 결정 A')**

| 절반 | 모습 | 정답 | 꼭 들어갈 말 |
|---|---|---|---|
| 25건 | 통증 낱말이 나오지만 지금은 급하지 않다. 예: 지난주에 아팠는데 지금은 괜찮음, 가끔 살짝 시림, 아이가 다쳤다 나음 | `normal`, `emergency` false | "지금은 괜찮다", "가볍다", "지난 일이다" 중 하나가 분명히 나온다 |
| 25건 | 통증 낱말 없이 담담하게 말하지만 정의상 오늘 봐야 하는 상태다. 예: 발치 뒤 피가 아직 조금씩 남, 볼 한쪽이 부음, 앞니가 깨졌는데 안 아픔 | `urgent`, `emergency` true | 정의 신호(붓기·출혈·파절·심한 통증, `prompts/classify/v2/labels.md` urgency 절) 중 하나가 지금 진행 중이라는 말 |

- **신호는 슬롯이 정한다.** 슬롯이 신호 하나를 골라 사실로 넘기고, 녹취는 그 신호를 담담한 말로만 쓴다.
- **경계 표현은 금지한다.** 검증기와 프롬프트 규칙으로 막는다. 예: "살짝 부은 것 같기도".
- **목적이 두 갈래로 읽히는 통화는 허용 목적에 둘 다 넣는다.** 예: "피가 나는데 원래 이런가요?"는 `accepted_purposes`에 `emergency`와 `treatment_q`가 모두 들어간다.

**`outbound_real`의 목적 (설계자 결정)**

라벨 정의상 발신 통화의 주 목적은 "병원이 건 이유"다.

- 리마인드 → `confirm`
- 리콜 안내 → `recall_q`
- 기존 발신 목적 → `billing_q`(미수 안내), `treatment_q`(경과 확인)
- 서류 준비 안내는 넣지 않는다. 정의상 `document_req`는 서류 **요청**이라 맞지 않는다.

**종류 안의 목적 할당**

- `CALL_PURPOSE_SHARE` 비율로 할당량을 정한다(최대 잔여 반올림). 종류와 말이 안 맞는 목적은 뺀다.
- 희귀 목적(`EVAL_RARE_PURPOSES`)은 말이 되는 종류에서만 종류별 최소 건수를 둔다. `outbound_real`에는 희귀 목적이 없다.
- 상수는 `generator/master.py`에 둔다. 예: `HARD_CALL_TYPES`, `HARD_CALLS_PER_TYPE = 50`, 종류별 허용 목적, 최소 건수.

이 셋은 일부러 고르게 나눈 셋이다. 현실 비율이 아니라는 점을 결과표에 적는다.

### 3.3 전자차트와 맞추기 (사람 결정)

전자차트(`emr_*`)는 한 줄도 바꾸지 않는다. 그래서 통화가 말하는 결과가 전자차트에 이미 있도록 슬롯이 고른다.

**통화 날짜 창**

- TODAY 전 **60일**이다. 변경·취소 기록이 30일로는 모자라서 넓혔다.
- 가중치는 `call_day_weight`와 같은 최근 가중이다.
- 영업시간 규칙은 기존과 같다.

**예약류 통화**

녹음이 없는 기존 예약 이벤트에 붙인다. 기존 `c-` 통화가 붙지 않은 이벤트를 말한다.

| 통화 | 붙이는 이벤트 | 통화 시각 |
|---|---|---|
| `book` | `booked_via='phone'`인 예약 | 예약의 `created_at` |
| `cancel` | 취소된 예약 | `cancelled_at` |
| `reschedule` | `rescheduled_from_id`가 있는 예약 | 새 예약의 `created_at` |
| `confirm` (리마인드 발신 포함) | 리마인드 문자를 받은 예약 | 기존 `check_booking_call_event` 규칙과 같다 |

- 이벤트 하나에는 통화를 최대 1건 붙인다. `c-`와 `hc-`를 합쳐서 센다.
- 변경·취소처럼 후보가 모자란 목적은 있는 만큼만 할당하고, 남는 몫은 다른 목적에 넘긴다.
- `reversal` 통화는 결과적으로 전자차트에 바뀌는 것이 없어 붙일 이벤트가 없다(예약은 미룸, 그 밖은 문의).

**응급 통화** (`emergency` 플래그가 켜진 환자 측 통화, `urgency_inverted` urgent 절반 포함)

- 통화일 당일 또는 다음 진료일에 이미 예약이 있던 환자만 고른다.
- 직원은 그 예약으로 내원을 안내한다. 예: "마침 오늘 오후 예약 있으시니 지금 바로 오세요".
- 새 응급 내원 예약은 만들지 않는다.
- **알려진 흠:** 그날 진료 기록에는 원래 시술만 적혀 있고, 통화에서 말한 증상은 없다. 이 흠은 받아들인다(생성 설계에 적는다).

**환자 제외**

다음 환자는 새 통화 대상에서 모두 뺀다.

- "통화 없음"을 전제로 만든 장면의 환자
  - ⑧ 정산 장부 실수 환자: `truth_ledger_errors`
  - 노쇼 → 취소 장면과 오늘 취소 장면 환자: `generator/cancels.py`
  - 그 밖에 생성 코드가 "그 뒤 통화 없음"으로 고른 환자. 계획 때 생성기의 `NOT EXISTS ... ax_calls`를 전수 조사한다.
- RAG 평가셋(`ground_truth/rag_qa.json`) 82문항의 정답이나 질문에 나오는 환자

**inbound 서류 요청**

- 기존 생성 규칙은 서류 요청 통화 뒤에 "서류 준비됨" 문자(`doc_ready`)를 보낸다. 새 통화에는 이 문자가 없다.
- 그래서 `hc-` 서류 요청 통화에서 직원은 "준비되면 문자 드릴게요"라고 약속하지 않는다. 대신 "방문하실 때 드릴게요"나 "다시 전화드릴게요"로 끝낸다.

**나머지 사실**

환자, 잔액, 리콜 같은 통화 시점 사실은 기존 6·7단계처럼 `emr_*`를 읽기만 해서 넘긴다.

### 3.4 라벨 (생성 라벨)

- 슬롯에서 먼저 정한다. 열은 `truth_call_labels`와 같고, `noise_type`과 `used_fact`도 기존 뜻을 그대로 쓴다.
- 생성기는 처음에 이 생성 라벨을 `truth_call_labels`에 `split='hard'`로 넣는다.

### 3.5 녹취

- **모델과 호출 방식**
  - 모델은 OpenAI `gpt-6.1-sol`이다(사람 결정).
  - 호출은 **Batch API**로 한다(사람 결정).
  - 단가는 2026-11-11 공식 가격표 기준이다. Batch는 입력 $1.00, 출력 $5.00/1M이고, 즉시 호출은 그 두 배다.
  - 녹취 생성, 분류, 라벨이 서로 다른 계열이 되게 하려는 선택이다. 녹취는 GPT, 분류는 Haiku, 라벨은 Opus다.
- **게이트웨이**
  - `config/llm.yaml`에 별칭(예: `gen_hard`)과 단가를 더한다. `provider: openai`다.
  - `shared/llm.py`에 OpenAI 채팅 갈래를 더한다. Upstage 갈래와 같은 openai SDK를 쓴다.
  - 배치 경로는 지금 Anthropic 전용이다("batch 미지원"). 여기에 OpenAI 배치 갈래를 더한다.
  - `make llm-fill-api`가 이 별칭을 배치로 채운다.
- **구조화 출력**
  - json_schema 지원은 착수 때 모델 문서에서 확인한다.
  - 지원하지 않으면 JSON 모드와 기존 검증기 재시도로 대신한다(설계자 결정).
- **프롬프트:** 새 파일 `prompts/gen_hard_transcript.md`를 둔다.
  - 입력 형식과 대화 규칙(화자 표시, 절대 날짜, 길이)은 기존 `gen_transcript.md`를 따른다.
  - **예시 문구는 넣지 않는다.** 어려움 종류마다 무엇을 어떻게 숨기거나 바꾸는지를 규칙으로만 쓴다.
- **검증기**
  - 형식, 화자, 길이, 금지 낱말은 7단계 검증기를 재사용한다.
  - 종류와 부딪히는 규칙은 종류별로 다시 정의한다. 기존 규칙은 c- 슬롯의 사실 형식에 맞춰져 있기 때문이다(`generator/transcripts.py` `checks`·`must_include`). 예:
    - reschedule에서 원래·새 날짜를 꼭 말하는 규칙도 같은 식으로 다룬다.
  - `urgency_inverted`의 "꼭 들어갈 말"과 경계 표현 금지는 검증기로 검사한다.
- **작업 흐름은 기존과 같다.** `make data`가 작업을 내보내고, 채우고, 들여온 뒤, `make data`를 다시 돈다.
- **전체 배치 전 샘플 확인 (사람 결정)**
  - 종류마다 4건(`urgency_inverted`는 절반마다 2건), 모두 20건을 GPT로 먼저 받는다(사람 결정). 즉시 호출이고, 비용은 50센트 안팎이다.
  - 사람이 읽고 확인한다. 블라인드 판독도 같이 한다: 정답을 가린 채 Opus 서브에이전트가 라벨 정의만 보고 라벨을 붙인다.
  - 확인할 것
    - 녹취가 생성 라벨대로 읽히는가
    - 종류별 어려움이 실제로 들어갔는가
    - 예시 문구 같은 반복 표현이 없는가
    - 경계 사례가 아닌가
  - 문제가 있으면 프롬프트와 검증기를 고치고 샘플을 다시 받는다.
  - 이 단계는 분류기·n-gram 결과를 보기 전이라 §2 "결과를 보고 고치지 않는다"와 부딪히지 않는다. 사람이 승인하면 프롬프트를 고정하고 전체 배치를 돈다.

## 4. 정답 라벨 (사람 결정 B)

1. **생성 라벨:** §3.4.
2. **Opus 독립 라벨**
   - 모델은 `claude-opus-5-5`, 새 별칭(예: `hard_label`), 폴백 없음, Batch다.
   - 녹취만 읽고 라벨을 붙인다. 생성 라벨, 시나리오, 어려움 종류는 보지 않는다.
   - 라벨 정의는 분류기 프롬프트 정의 문장(`prompts/classify/v2/labels.md`)을 그대로 쓴다.
   - 기록은 `evaluation/`에 둔다. 골드를 다루는 일이라 `app.sqlite`에 쓰지 않는다. 방식은 `gold_audit`와 같다.
3. **비교:** 항목마다 `shared.call_labels.same_value`로 본다. 급함은 urgent 여부만 비교한다.
   - 모든 항목이 같으면 확정이다.
   - 하나라도 다르면 사람 검토로 보낸다.
4. **사람 검토**
   - 대상은 엇갈린 통화 전부와, 일치해서 확정된 통화 중 고정 표본 30건이다(설계자 결정).
   - 방식은 골드 점검 사람 표본(`evaluation/gold_audit.py`)과 같다.
     - 두 라벨을 출처를 가린 채 보여 주고, 사람이 고른다.
     - 둘 다 틀렸을 때만 직접 입력한다(설계자 결정).
   - 표본에서 틀린 라벨이 나오면 결과에 적는다. 많으면 범위를 넓힐지 사람이 정한다.
5. **저장**
   - 최종 라벨과 어려움 종류, 라벨 출처(일치 / 사람)를 `ground_truth/`의 별도 JSON에 둔다(예: `hard_call_labels.json`).
   - 빌드 때 적재한다. 방식은 `rag_qa.json`과 같다(`generator/build.py`).
     - 생성 라벨 행을 최종 라벨로 덮어쓴다.
     - 새 표 `truth_hard_calls(call_uid, hard_type, label_source)`를 채운다.
   - 빌드는 truth.sqlite를 매번 새로 만들므로, 최종 라벨이 JSON에 있어야 살아남는다.
   - `ground_truth/schema.sql`의 `truth_call_labels.split` CHECK에 `hard`를 더한다.
6. **보고하는 숫자**
   - 생성 라벨과 Opus 라벨의 일치율(항목별, 종류별)
   - 사람이 고른 쪽의 분포
   - 표본 확인 결과

## 5. 분리 보장

- **분할이 섞이지 않게 한다.**
  - 평가 코드는 이미 `== 'silver'`나 명시 목록으로 거르므로 `hard`가 새지 않는다. 이것을 테스트로 고정한다.
  - 고칠 곳은 두 군데다.
    - verify `check_eval_pool`: 풀 밖 통화가 모두 silver라고 가정한다.
    - 생성기의 split 기록(`generator/calls.py`): `'silver'`가 박혀 있다.
- **verify 검사는 생성 코드보다 먼저 쓴다(TDD).**
  - 새 검사
    - 종류별 건수와 `urgency_inverted` 25/25
    - `hc-` 번호
    - 날짜 창
    - 발신 목적 매핑
    - 예약류 이벤트 붙이기(`c-`와 `hc-`를 합쳐 이벤트당 1건)
    - 응급 통화의 당일·다음 진료일 기존 예약
    - 제외 환자 없음
    - 판정 풀·블라인드 풀에 `hc-` 없음
  - 기존 검사(`check_booking_call_event`, `check_emergency_visits`, `check_call_row_order` 등)는 `hc-` 규칙에 맞게 나누거나 범위를 정한다.
- **앱:** `hc-` 통화를 평소처럼 분류·판정·검색한다. 시연용이다.
  - 앱은 `split`을 모른다.
  - 정답은 `data/`에 들어가지 않는다.

## 6. 채점

- `evaluation/eval.py`에 `hard` 묶음을 더한다.
- 같은 `hard` 통화에서 세 가지를 센다.
  - 학습 없는 규칙(`has_todo`)
  - 글자 n-gram(지금 모델 그대로)
  - 분류기 활성 버전(`make classify V=<활성>`이 `hc-`에 돈 결과)
- 결과는 전체 한 줄과 `hard_type`별 줄로 낸다. `urgency_inverted`는 절반별로도 낸다.
- **③ 검색**
  - `make index`를 다시 돈다. 추가분만 계산하고 비용은 1센트 미만이다.
  - 검색 평가(Hit@5 등)를 다시 잰다. 순위가 바뀌면 바뀐 대로 기록한다.
- **기록:** AI 실험 기록 새 절에 결과와 한계를 쓴다. 순서는 문제 → 원인 → 시도 → 결과 → 한계다.
  - 한계에 적을 것: 고르게 나눈 셋이라는 점, 라벨 쪽 Opus와 분류기 Haiku가 같은 계열이라는 점, 응급 통화와 그날 진료 기록이 어긋난다는 점.
