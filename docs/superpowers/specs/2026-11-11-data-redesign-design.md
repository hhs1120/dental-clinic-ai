# 데이터 재설계 — ⑧-1·⑧-2·⑤-2 차트 서술·③ 질문 보강 — 설계

원본 규칙은 [[치과 AX - 기능 정의]] §9 "데이터 재설계" 항목, [[치과 AX - AI 실험 기록]] §23(왜), [[치과 AX - 평가 설계]] §1 원칙 8·§3.1·§5, [[치과 AX - 가상 데이터 생성 설계]] §0(데이터 상태)·§2.4·§2.7·§4.2·§4.3·§5.1. ⑧ 쪽 앱·기준선은 `docs/superpowers/specs/2026-11-11-finance-recon-design.md`. 이 문서는 그 위에서 정한 것을 적는다. **사용자 결정**과 **내 판단**을 구분해 적는다.

## 왜

생성기가 라벨을 먼저 정하고 글·행이 그 라벨을 정해진 말·한 가지 모양으로 드러내, 단순 규칙이 AI와 같거나 낫다(AI 실험 기록 §23 — ⑧-1 규칙 34/36, ⑧-2 규칙 매칭 56~58/59·과목 57/59, ⑤-2 키워드 규칙 정밀도 138/140·재현율 138/138 vs AI v2 125/136·125/138). 이대로면 ⑧ 3·4단계와 ⑤-2는 "AI가 기준선보다 낫다"를 보일 자리가 없다. 데이터를 한 번 다시 만들어 **헷갈리지만 글을 읽으면 풀리는** 사례를 섞는다.

## 목표 (사용자 결정 — dev에서 재는 규칙 기준선의 목표 범위)

| 기능 | 지금 | 목표 |
|---|---|---|
| ⑧-1 원인 — 애매한 원인 묶음 | 25/27 | 55~65% (규칙으로 되는 원인 묶음은 지금처럼 100% 근처) |
| ⑧-2 매칭 | 56~58/59 | 75~85% |
| ⑧-2 계정 과목(거래처 기본값) | 57/59 | 80~85% |
| ⑤-2 요건 근거(키워드 규칙) 정밀도·재현율 | 약 99% | 둘 다 60~75% |

- **조건(사용자 결정)**: 헷갈리는 사례는 글·행을 읽으면 풀려야 한다 — 재생성 뒤 dev 헷갈리는 사례 20~30건을 상위 모델(Opus) 또는 사람이 읽고 거의 다 맞혀야 통과. 못 맞히면 난이도가 아니라 잡음
- **기준선을 데이터보다 먼저 고정**(내 판단 — 데이터와 규칙을 같이 맞추면 목표가 뜻을 잃는다). 이 브랜치 첫 커밋들로 `evaluation/`에 둔다
  - ⑤-2 키워드 규칙: 데이터 점검 때의 규칙 그대로 — 요건 사유별 근거 낱말(`chart.EVIDENCE_WORDS`) 포함 여부(부정 표현은 가리지 않음), R03은 치주낭 mm가 기준값 미만이면 근거 없음, 재시행(R01)·연결(R02)은 본문 "이력"·"N일 전" 문맥. ⑤ 2단계의 "서술 있는 줄 전부" 기준선 옆에 둔다
  - ⑧-2 규칙: 재무 대조 설계 §2의 매칭 규칙(금액·날짜 1:1, 월말 적요 거래처 1:N)과 거래처 기본 과목을 `evaluation/`에 먼저 두고 잰다(⑧ 2단계가 같은 규칙을 앱으로 옮긴다)
  - ⑧-1은 `backend/recon.py` `rule_cause`(고정됨)
- 헷갈리는 모양은 **그 기준선을 실제로 속이는지 단위 테스트로 확인한 것만** 쓴다(내 판단 — 리뷰에서 "정산 누락"은 규칙 10이, "이웃 날 같은 금액 날짜 밀림"은 규칙 6이 그대로 맞힌다는 지적)
- 비율은 생성기 상수로 정하고 재생성 뒤 dev에서 잰다. 범위를 벗어나면 비율만 고쳐 다시 만든다. test로 재지 않는다
- ⑤-2 차트 서술은 LLM(9b)이라 다시 채울 때마다 과금 — 표본 작업으로 비율·표현을 먼저 확인하고 전체를 채운다(내 판단)

## 하지 않는 것

- ⑨ 이탈 단서·노쇼 성향(예약·문자·통화 전부 재생성 — ⑨ 2단계 착수 때 결정), 기존 통화 녹취 다시 쓰기(① 어려운 통화 평가셋은 별도 항목)
- 규칙 기준선 코드 변경 — ⑧-1 `backend/recon.py` `rule_cause`는 1단계 머지 때 고정됐다. 데이터만 바꾼다
- ⑧-1 평가 달 밖으로 장부 실수 넓히기(사용자 결정 — 평가 달 그대로, 건수 늘리기)
- 앱 코드 기능 추가(⑧ 2·3·4단계는 각자 브랜치)

## 하면 실패인 것

- 기존 장부 실수 33건·청구 오류·청구 id가 이유 없이 바뀐다(새 실수는 새 이름의 난수로 — §5.1 단계별 독립 시드)
- 헷갈리는 사례가 글로 풀리지 않는다(Opus·사람 표본에서 거의 다 맞혀야)
- 규칙으로 되는 원인 묶음(분할결제·취소 후 재승인·수수료 차이·입금 지연) 규칙 정확도가 떨어진다
- 정답 누출 — 새 디코이·표현이 정답 칸·생성 메타를 앱 쪽 테이블에 남긴다
- verify가 새 모양을 검사하지 않거나, 검사보다 생성 코드를 먼저 쓴다(TDD 절대 규칙)
- ③ 새 문항이 dev/test 문서 격리를 깨거나(`check_qa_split_isolation`) 정답을 베낀다

## 정한 것

### 0. 진행 순서 (내 판단)

1. 가상 데이터 생성 설계 §0 데이터 상태를 "재설계"로
2. 부분마다 verify 검사 먼저 → 생성 코드 → `make data`(FAKE_LLM으로 코드 단계 먼저 확인) → dev 기준선 측정 → 비율 조정
3. ⑤-2: 9b 표본(요건 줄 일부) 채우기 → 키워드 규칙·Opus 표본 확인 → 전체 채우기(과금)
4. 실데이터 `make data` → `make verify` → 재생성 직후 확인(§6) → 색인 `make index`(바뀐 청크만, 과금) → ③ 평가셋 재확인·보강
5. 앱 재실행: ⑤-2 점검(바뀐 줄만 또는 전체 — §6), 판정기(Qwen, 바뀐 통화만), ⑧-1 dev 재채점
6. 데이터 상태를 다시 "고정"으로, 문서·실험 기록 숫자 갱신

### 1. ⑧-1 장부·재무 수입 (8b만 — 장부는 바꾸지 않음)

- 평가 달(`master.recon_months`)과 원인 enum 9개는 그대로(정답 스키마 `truth_recon_mismatches.cause` 유지)
- **건수**: 애매한 원인 위주로 늘려 dev·test 각 50건 안팎(내 판단 — 지금 36·29). 기존 `RECON_MISMATCH_COUNTS`는 그대로 두고 새 상수·새 자식 난수로 더한다(올리면 기존 건이 다시 뽑힌다 — 리뷰)
- **8b는 통째로 바뀌어도 된다**(내 판단): 8b는 주 난수를 수납 순서대로 써서 무엇을 더해도 발급사·승인번호·규칙 묶음 선택이 다시 뽑힌다. 8b 출력(`fin_*` 수입·`truth_recon_mismatches`)은 뒤 LLM 단계 입력이 아니라 번지지 않는다. ⑧-1 확정 기록은 재생성 때 버린다
- **5단계 장부(`emr_payments`)는 바꾸지 않는다**(사용자 결정): 미수 잔액이 바뀌면 통화 배정(`calls.py` 잔액 후보·수납 문의 `_ledger_debt_calls`)과 문자(`messages.stage`가 미수 행마다 난수 소비)가 넓게 바뀌어, 기존 통화 녹취 재생성과 test 판정 풀 통화 변경으로 번진다(리뷰). 자리 바뀜 오입력·0원 행이지만 진짜 미수처럼 장부를 바꿔야 하는 모양은 이번에 넣지 않고, 장부를 안 바꾼 결과가 목표(애매한 묶음 55~65%)에 못 미치면 다시 정한다
- **장부를 바꾸지 않는 모양(8b에서)**
  - **미수 정산 수납 누락**(`entry_missing`): 장부에 미수가 남은 환자가 실제로 일부·전부를 냈는데 장부에 안 적은 돈 — 금융에만 돈이 생긴다. 장부 행을 지우지 않으므로 수납 id·승인번호·잔액이 그대로다. 카드이고 금액이 구강용품 1~2개 합이면 규칙 9가 진료 외 매출로 틀린다(미수 잔액을 봐야 풀림)
  - 그 밖의 모양은 기존 정상 행 중에서 우연이 겹치게 고르는 선택으로(빌더 판단, 규칙을 속이는지 테스트)
- **정답 스키마**: 장부 행이 없는 누락은 `truth_ledger_errors.payment_id`를 비울 수 있게 하고 환자·실제 금액·일시·결제수단을 남긴다(내 판단). `payment_id`로 조인하는 곳(`calls.py`·`messages.py`의 장부 실수 미수, `finance._true_payments`, verify `check_ledger_errors`)이 이 행을 빠뜨리지 않게 같이 고친다
- 결제수단 오입력은 연동 실패일 카드·현금 입금 주당 1건이라 늘릴 여지가 작다 — 건수를 억지로 맞추지 않는다

### 2. ⑧-2 지출 (8c — LLM 비용 없음)

- **디코이 증빙**(어느 출금에도 안 붙음, 정답 밖): 같은 거래처 견적서·취소된 주문 메일, 지난달 명세서 재발송, 비슷한 금액의 다른 거래처 영수증
- **표기 변형**: 증빙 발행처(예: "(주)바른덴탈")·통장 적요(잘린 은행 표기)·카드 가맹점명(결제대행사 표기)을 거래처 이름과 다르게
- **새 짝 모양**: 증빙 하나로 출금 둘(부분 결제), 증빙 둘로 출금 하나(카드 사용에도)
- **과목**: 품목으로 정해지는 출금을 늘린다 — 쇼핑몰 비중·품목 혼합(한 주문에 두 과목이면 금액 큰 과목이 정답 — 내 판단), 기본값이 없거나 애매한 범용 가맹점(예: 오픈마켓)
- 재료상 명세서의 소모품 품목은 정답이 거래처 과목(재료비)인 규칙을 그대로 두고 가상 데이터 생성 설계 §2.7에 명시(내 판단 — 함정이 아니라 규칙)
- 정답 `truth_expense_matches` 모양은 그대로(증빙 id 집합·과목). 디코이는 정답에 들어가지 않는다
- ⑧-1 일계표의 출금 id가 바뀐다(⑧-1 확정 기록은 재생성 때 버림 — 앱 설계 §8)

### 3. ⑤-2 차트 서술 (5b 사실 + 9b LLM)

- **모든 요건 사유(R01~R06)의 근거 표현 다양화** — 근거 말은 LLM 자유 생성이 아니라 **코드의 표현 풀**에서 골라 서술에 넣게 하고(verify가 검사할 수 있게), 풀을 넓힌다(내 판단)
  - 근거 있는 줄: 지금 낱말(`chart.EVIDENCE_WORDS`) / 바꿔 말하기("충전물이 깨짐", "뼈를 일부 깎음") / 낱말 없이 상태만 서술
  - 근거 없는 줄: 근거 낱말의 부정·경과 관찰("파절 소견 없음", "재평가 예정") / 근거와 비슷하지만 기준에 못 미치는 소견
  - **라벨 규칙**(내 판단): 정답은 늘 기준 문서 문장으로 정해진다 — 기준을 다 채우면 근거 있음, 일부만 채우면(부분 소견) 근거 없음. 사유마다 기준 문장과 풀 문구를 짝지어 테스트한다
  - 요건 수치(R01 기간·R02 일수)는 지금처럼 서술에 넣는다(`narrative_must_include`). R03 치주낭 깊이만 일부 줄에서 "깊은 치주낭" 같은 말로 바꿔 쓸 수 있다(내 판단)
  - 근거 없는 줄 전용 C.C(`CC_NO_EVIDENCE`)는 없애고 C.C는 공통 풀에서
  - 지금 LLM 검증(`evidence_forbidden`·`check_chart_evidence_words`)은 근거 없는 줄에 근거 낱말을 금지해 부정 표현 풀과 충돌 — 검증을 "고른 풀 문구가 들어 있음 + 다른 사유의 근거 문구가 없음"으로 바꾼다
- **R03(사용자 결정 — 다양화와 한 묶음일 때만)**: 기준 문서 치주치료 산정 절에 복합 기준(치주낭 깊이 + 출혈·골소실 같은 염증 소견). 기준값은 `master` 상수 하나를 `generator/chart.py` 소견 생성과 `generator/doc_catalog.py` 기준 문장이 함께 읽는다. 차트는 부분만 맞는 사례(깊지만 염증 없음, 경계값, 여러 부위 중 하나만 깊음)를 근거 없음으로 섞는다
- **추가 처치 누락**: 기존 11건과 조건(결과가 없는 달만 — 생성 설계·`check_omitted_extra`)은 그대로 두고, 새 자식 난수로 결과 없는 달에 더한다. 표현을 풀에서, "같은 날 ○번 상담·예정" 디코이(내 판단 — 확정 월로 넓히지 않음)
- **verify 먼저**: `check_chart_evidence_words`·`check_chart_narrative_facts`·`check_omitted_extra`·`check_chart_decoy_ratio`를 표현 풀 기준으로 고치고, 키워드 규칙 정확도를 리포트(경고)로
- **9b 다시 채우기는 사실상 전체**(리뷰): 캐시 키에 금지어 목록·프롬프트 해시가 들어가고 특이 건 수가 바뀌면 디코이 할당·템플릿 줄이 다시 뽑힌다 — 약 $15. 표본 먼저(§0)
- ⑤-2 앱 점검 재실행도 사실상 전체(약 $4.3 — R03 기준 문장이 바뀌면 치주 문서를 LLM이 다시 쓰고 잇몸치료 줄 입력이 바뀜). `emr_claims`·청구 id·분할 해시는 그대로(청구 단계가 앞이고 난수 독립)

### 4. ③ 질문 보강 (재생성 뒤 평가셋 재확인과 함께)

- 새 문항(사용자 결정 목록): 여러 문서를 합쳐야 하는 질문, 외부 문서가 틀린 값을 주는 질문, 과거 값·시간 계산, 동명이인·같은 환자의 비슷한 통화 중 고르기(사례형)
- **배치(사용자 결정 — dev/test 방해 문서 문항 비율 맞추기)**: 기존 문항은 옮기지 않는다. 평가 설계 §3.1·`check_qa_type_counts`의 유형별 dev = test는 지키고, **방해 문서와 짝지은 새 문항은 test에, 짝 없는 새 문항은 dev에** 둬 방해 문서 문항 비율을 비슷하게 한다(내 판단 — 규칙을 바꾸지 않고 같은 효과). 방해 문서 문항 = 정답 문서에 비슷한 문서 짝(`doc_catalog` `similar`)이나 옛 공지가 있는 문항
- 여러 문서를 합치는 test 문항은 dev와 문서가 겹치기 쉬워 test 전용 새 문서가 필요할 수 있다(`check_qa_split_isolation`은 정답 출처만 본다)
- 필요하면 문서·공지 덧붙이기(`generator/documents.py` `APPENDED`, 문서당 약 $0.008)
- `verify.QA_TYPE_COUNTS`·`rag_qa.json`·문서 격리 검사를 함께. 정답 베끼기 검사 통과. 재생성으로 바뀐 차트형·잔액 질문의 정답도 다시 맞춘다

### 4b. 화면에서 보이게 배치 (사용자 결정 — 목적은 화면 시연)

- 헷갈리는 사례를 기준일 쪽으로 몰지 않는다 — ⑧은 달 단위 분할이라 몰면 test(마지막 `RECON_TEST_COUNT`달)로만 들어가 dev에서 목표를 잴 수 없다
- 대신 평가 달 안에 고르게 두고, **화면이 기본으로 여는 곳에도 비율만큼은 반드시** 들어가게 한다(verify 검사로)

  - ⑤-2: 청구 전 점검 대상(대기 청구 달)에 요건 사유별 헷갈리는 근거 표현(바꿔 말하기·부정·부분 소견)이 각각 들어가게. 요건 사유 조정 건은 확정 월에만 생기므로 그대로
