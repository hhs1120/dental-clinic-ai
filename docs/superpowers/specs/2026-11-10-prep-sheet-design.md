# ④ 진료 준비표 — 설계

원본 규칙은 [[치과 AX - 기능 정의]] §4 ④, [[치과 AX - 앱 설계]] §4·§9, [[치과 AX - 평가 설계]] §4. 이 문서는 그 위에서 이번 브랜치(`feat/prep`)가 만들 범위와 이번에 정한 것을 적는다.

## 왜

데스크·실장은 환자 한 명을 챙기려고 EMR의 데스크·전자차트·옆 패널을 옮겨 다닌다(전환 전 EMR 화면이 그 모습을 보인다). 준비표는 코드가 그날 예약 환자마다 흩어진 사실을 한 행으로 모으고, LLM은 그 사실을 그날 할 일 한두 줄로 묶기만 한다. 칩은 코드가 정확히 켜고, LLM이 쓴 문장은 코드가 사실과 대조해 거른다.

## 목표

- 그날 예약 환자마다 사실(`prep_facts`)·칩 7개·AI 제안(`{action, text, used_facts}`)·후검증 결과를 만들어 `ax_prep_sheets`에 저장한다
- 화면 두 개 — **준비표**(목록)와 **체어 보기** — 가 같은 행(`GET /prep?date=`)을 보인다
- 채점: 후검증 통과율·주의사항 반영률·과잉 언급률·과잉 제안률을 `eval.py`로 낸다(평가 설계 §4)
- 주의사항 → 관련 시술·행동 기준표를 앱이 읽을 수 있게 생성기가 `source.sqlite`에 적재한다

## 하지 않는 것

- **회의 보기**: 없앤다(사용자 결정). 시간 × 담당자 격자는 예약 화면(`/schedule`)이 이미 있고, 오늘 전체·할 일 환자는 준비표 목록과 같은 정보다. 회의 보기에만 있던 것 중 **신환 딱지·몰리는 시간대 막대·인쇄**는 준비표로 옮긴다. 체어 전체 격자는 버린다 — 필요해지면 예약 화면에 "체어별" 전환으로
- **야간 조사 에이전트**: 다음 브랜치로 미룬다(사용자 결정). 이번 브랜치 끝에 채점 결과(특히 주의 칩 행의 반영률·과잉 언급률)를 보고, 개선 여지가 있으면 다음 브랜치에서 도구·호출 상한·기준선("주의 환자면 최근 통화·차트 메모를 무조건 붙이는 코드")·조사 효과 짝 비교(평가 설계 §4)까지 만든다. 여지가 없으면 그 근거를 남기고 슬롯으로 넘어간다
- 칩 여러 개를 조합하는 필터, "다음 진료일", "다른 치과 추정"(기능 정의 §4 ④ 제외 목록)
- `make nightly`·운영 에이전트 연결

## 하면 실패인 것

- LLM이 사실에 없는 숫자나 사실에 없는 (키, 값)을 근거로 쓴 제안이 화면에 "통과"로 보인다(후검증은 평가 설계 §4대로 `used_facts` 일치 + 본문 숫자 — 본문의 이름을 따로 뽑아 대조하지는 않는다, **내 판단**)
- 모든 행에 제안을 강제해 근거 약한 제안을 지어낸다(`none` = "그대로 진행"을 허용한다)
- 칩을 LLM이 정한다(칩은 코드만)
- backend가 `generator/`를 import한다(절대 규칙)

## 정한 것

### 1. 기준표 적재 (사용자 결정: 생성기가 새 `ax_` 테이블로)

- `generator/master.py`의 값 중 앱이 읽어야 할 것을 생성기가 `source.sqlite`의 새 테이블에 적재한다. 병원 상수의 원본은 계속 `master.py` 하나다
- 이번에 적재할 것: 주의사항 종류별 관련 시술·행동 문구(`ALERT_TYPES`의 `procedures`·`action`), 보험 잔여 칩의 성인 나이 기준. 리콜 주기는 환자 칸 `emr_patients.recall_cycle_months`를 그대로 쓴다(기존 `backend/query_tools.py` `_family_recall`과 같은 기준)
- 테이블 모양(**내 판단**): 이름 → JSON 값 한 테이블 `ax_master_values(name TEXT PRIMARY KEY, value TEXT NOT NULL)`. ⑤·⑧이 같은 테이블에 이름만 더한다. 앱 설계 §8 미결 "backend가 master 값을 읽는 방법"을 이 방식으로 닫는다
- verify 검사를 생성 코드보다 먼저 쓴다(절대 규칙): 테이블 값 = `master` 값
- 데이터 상태는 고정 — 새 테이블 추가만이라 허용된다. 기존 테이블·LLM 입력은 바뀌지 않으므로 실데이터에 `make data`(과금 없음) → `make verify`. `app.sqlite`는 `make data`가 건드리지 않는다
- `backend/query_tools.py`에 박혀 있는 `SCALING` 같은 값은 이번에 옮기지 않는다(앱 설계 §8에 남김)

### 2. 사실 모으기 `prep_facts(conn, day, today)` (`backend/prep.py`)

- 그날 예약(취소 제외, 지난 날짜는 `completed`·`noshow` 포함 — 결과 칸) 한 건 = 한 행. 사실은 **그날 개원 전 기준**(그날 이전 수납·내원만). 주의사항은 평가 설계 §4대로 기록일 ≤ 그날 < 끝나는 날
- 지난 날짜의 치료계획 항목(**내 판단**): 지금 `status`를 쓰지 않고 그날 기준으로 다시 계산한다 — "끝남"은 그날 전에 `completed`된 연결 예약(`plan_item_id`), "대체됨"은 그날 전에 다른 계획으로 같은 치아(전체 구강 시술은 같은 시술)에 들어간 `completed` 진료(생성 규칙 `generator/records.py` — 대체는 그 진료 시각에 일어난다). 그날 내원에서 새로 만든 계획은 넣지 않는다(만든 날 < 그날)
- 지난 날짜의 가족 리콜·마지막 내원도 그날 전 내원만 센다(기존 `_family_recall`은 기준일 스냅샷이라 날짜 제한이 없다)
- 행 사실(키 이름은 **내 판단**, 첫 출력을 스냅샷으로 고정 — 평가 설계 §4 집계 회귀):
  - 예약: 시각·소요 시간·체어 번호(상담은 없음)·종류·예정 시술·담당자, 예약 확인 여부
  - 환자: 이름·차트 번호·나이·성별·신환 여부(첫 내원)
  - 마지막 내원일, 미수 잔액, 그날 보이는 주의사항(각각 그날 예정 시술과 관련 있는지와 행동 문구), 올해 스케일링 급여 미사용(성인만), 가족 리콜 지남(가족 구성원 이름·마지막 위생 내원), 남은 치료계획(열린 항목 중 그날 예정 시술이 아닌 것 — 시술·치아·예상 금액)
- 기존 `backend/emr.py` `patient_summary`의 쿼리와 같은 기준을 쓴다(같은 사실을 화면마다 다르게 세지 않게). 재사용할지 새로 쓸지는 빌더 판단
- 칩 7개는 사실에서 코드로 켠다: 예약(항상) · 보험 잔여 · 미수 잔액 · 가족 리콜 지남 · 주의(관련 있는 주의사항이 하나 이상) · 남은 치료계획 · 예약 미확인
- 칩은 아직 챙길 일이 남았을 때만 켠다(사용자 결정): **보험 잔여**는 그날 예정 시술이 스케일링이면 끈다. **가족 리콜 지남**은 그날 이후(그날 포함) 위생 예약이 이미 잡힌 가족을 뺀다. **남은 치료계획**은 그날 예정 시술을 뺀다(기능 정의 §4 ④)

### 3. 제안 (`prompts/prep/v1.md`, 게이트웨이 별칭은 `config/llm.yaml`의 ④ 제안 별칭 — 지금 `chat`)

- 입력: 행 사실에서 화면용 id와 **예약 미확인을 뺀 것**(제안 사실이 아니다 — 기능 정의 §4 ④)
- 출력 스키마 `{action: suggest|none, text, used_facts: [{key, value}]}`. `none`이면 `text`·`used_facts`는 비운다
- 후검증(`suggestion_valid`, 평가 설계 §4): `used_facts`의 모든 (key, value)가 입력 사실과 일치 and `text`의 숫자가 전부 `used_facts.value`에 속함(단위 정규화). **`none`은 `used_facts`가 비어 있으면 통과**(**내 판단** — 평가 설계 §4 "`none`의 후검증 처리"를 이렇게 닫는다. 주의 칩이 켜졌는데 `none`인 행은 반영률에서 걸린다)
- 실패하면 한 번 다시 부르고, 또 실패하면 `suggestion`을 null·`suggestion_valid` 0으로 저장(화면은 "제안 없음 — 후검증 실패")
- 다시 부르지 않는 조건(**내 판단**): `facts_hash`·프롬프트 버전·모델이 모두 같고 저장된 제안이 후검증을 통과했을 때. 후검증 실패(null) 행은 "다시 만들기"마다 다시 부른다. 행은 예약당 하나(UNIQUE 그대로) — 새 버전으로 만들면 덮어쓴다. v1 vs vN 비교가 필요해지면 그때 버전별 행을 둔다

### 4. 저장·실행

- `ax_prep_sheets`(앱 설계 §4 정의대로 `shared/app_schema.sql`에 추가) — 만든 시각·프롬프트 버전·모델도 남긴다
- 만들기: `make prep [DATE=]`(기본은 날짜 탭 범위 — 기준일 포함 최근 8일) 과금. `POST /jobs/prep-regenerate?date=`는 `ax_jobs`로 돌고 화면의 "다시 만들기"가 부른다
- `GET /prep?date=` — 그날 행 전부(체어 번호 포함). 행이 없으면 빈 목록과 "아직 만들지 않음"

### 5. 화면 (와이어프레임 `index-v2.html` 준비표·체어 보기 기준, 회의 보기 제외)

- `/prep` 한 화면에 보기 전환 **준비표 | 체어 보기**, 위에 날짜 탭(날짜마다 인원수)·기준 시각·"다시 만들기"
- **준비표**: 칩 필터(칩별 인원수), 종류 필터(전체·진료·위생·상담), "할 일 있는 환자만", 몰리는 시간대 막대(시작 시각 기준 예약 수), 인쇄(브라우저 인쇄 — 인쇄용 모양은 빌더 판단). 행: 시각·체어 / 환자(이름 옆 신환 딱지, 이름은 EMR 열기) / 예정 시술 / 칩 / 제안(없으면 "그대로 진행", 실패면 "제안 없음"), 지난 날짜는 결과 칸. 행을 펼치면 사실 목록 + 제안 + 근거(`used_facts`) + 후검증 결과
- **체어 보기**: 체어 고르기(체어별 인원수, 상담실 포함) → 왼쪽 그 체어의 순서("지금"·"다음" 표시), 오른쪽 한 장 — 주의사항을 가장 크게(행동 문구 함께), 예정 시술·마지막 내원·남은 계획·제안. "지금" = 기준일 + 실제 시계의 시:분, 시간이 되면 다음 환자로
- 색·부품은 `globals.css` 토큰과 `components/ui`만(CLAUDE.md)

### 6. 채점 (`eval.py`, 평가 설계 §4)

- 범위: 날짜 탭(기준일 포함 최근 8일)의 저장된 행
- 후검증 통과율, 주의사항 반영률(주의 칩 행 중 관련 주의사항 키가 `used_facts`에 모두 있는 비율), 과잉 언급률(관련 없는 주의사항이 `used_facts`에 있는 행 비율), 과잉 제안률(예약 칩 밖 칩이 모두 꺼진 행 중 `suggest` 비율). 분수 병기
- 관련 여부는 `master`를 직접 읽는다(`evaluation/`은 `generator/` import 허용) — 앱이 쓴 테이블과 같은 값인지는 verify가 보장
- 정답이 없는 코드 채점이라 dev/test 분할 없음(평가 설계 §4에 없는 분할을 새로 만들지 않는다)

### 7. 문서 반영

- 기능 정의 §4 ④: 화면에서 회의 보기를 빼고 준비표로 옮긴 것(신환·몰리는 시간대·인쇄), 야간 에이전트 착수 조건(§9로). §2 범위 표의 "회의 보기·체어 보기"
- 앱 설계 §4(`ax_prep_sheets` 칸), §8 미결 두 줄 닫기(`prep_facts` 키 목록, master 값 읽는 방법), §9 `/prep` 행
- 가상 데이터 생성 설계: 새 테이블과 verify 검사 목록
- 평가 설계 §4: `none` 후검증 처리
- §9: "표 보기 시간 구조" 항목 닫기(회의 보기를 없애고 시간 구조는 예약 화면이 맡음), "주의 칩 매핑" 관련 줄 정리, 야간 에이전트 판단 항목 추가
- 와이어프레임은 고치지 않는다(앱 설계 §9가 "와이어프레임과 그 예외"를 적는 곳 — 회의 보기 제외를 예외로 적는다)

## 테스트

- verify: `ax_master_values` = `master`(먼저)
- pytest: `prep_facts` 스냅샷 회귀, 칩별 켜짐·꺼짐(주의 관련/무관, 기간 있는 주의사항의 끝, 성인 기준, 그날 스케일링이면 보험 잔여 꺼짐, 위생 예약이 잡힌 가족은 리콜에서 빠짐, 그날 예정 시술은 남은 계획에서 제외, 지난 날짜의 끝남·대체됨 재계산, 미확인), 후검증(사실에 없는 값·숫자 거부, `none` 통과 조건), 실패 → 재시도 → null, `facts_hash` 같으면 호출 없음, 제안 입력에 예약 미확인 없음, API 모양, 채점 네 지표
- e2e: 날짜 탭 전환, 칩 필터, 행 펼침, 체어 보기 전환·환자 선택(실데이터 복사본, 기존 `make e2e` 방식)

## 빌더에게 남긴 것

- 사실 키 이름과 JSON 모양(스냅샷으로 고정되므로 처음에 정한 이름이 굳는다)
- 프롬프트 문구(예시 문장은 가상 데이터에서 그대로 옮기지 않는다)
- 인쇄 모양, 체어 보기의 자동 넘김 주기, 몰리는 시간대 막대의 시간 단위
- `make prep`의 병렬 수
