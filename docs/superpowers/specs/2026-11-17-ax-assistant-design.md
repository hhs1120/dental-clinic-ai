# AI 비서 설계 — 대화형 업무 에이전트와 앱 셸

근거: [[치과 AX - 기능 정의]] §4(앱 구성·③·오늘 화면)·§5 ⑨, [[치과 AX - 앱 설계]] §3·§3b·§7.3·§9, [[치과 AX - 평가 설계]] §3·§5, `CLAUDE.md` 절대 규칙(`emr_` 쓰기 금지·고정 데이터).

## 1. 왜, 무엇을 보여 주나

지금 앱은 기능마다 잘 만든 화면이 있지만, **화면을 넘나드는 일**(통화에서 예약 원한 환자를 찾아 → 빈 시간을 보고 → 예약을 잡기)은 사람이 화면을 옮겨 다니며 해야 하고, 예약 잡기는 아예 없다(EMR 몫). AI 비서는 기존 화면을 다시 그리지 않고 **그 사이의 일을 대화로 끝내는 층**이다.

- **주인공 장면**: "지난주에 전화로 예약 원했는데 안 잡힌 사람 있어?" → 환자 카드 → "김○○ 이번 주 금요일 오후로 잡아줘" → 빈 시간 안내 → 예약 초안 카드 → 사람이 **승인** → 예약표에 "AX가 넣은 예약", 미예약 목록에서 빠짐
- **보여 줄 것**: 여러 도구를 엮는 조회, 앞 대화를 기억하는 연속 대화, 쓰기는 초안까지·확정은 사람, 확정이 다른 화면에 반영됨, 평가된 ③ 검색 에이전트를 하위 에이전트로 씀
- **반-목표**: 기존 화면(오늘·준비표 등)의 내용을 챗 시작 화면에 다시 그리기, AI가 예약을 직접 확정, AI가 빈 시간을 지어내기, `emr_*`에 쓰기, 도구 결과에 없는 숫자·근거 밖 인용

## 2. 범위

- **넣는 것**
  - 앱 셸 교체: 위쪽 메뉴 → 왼쪽 **아이콘 줄 + 목록 칸**(§3.1), 떠 있는 물어보기 버튼·창 제거
  - AI 비서 화면(시작·대화·지난 대화), 대화 저장
  - AI 비서 에이전트(하네스) — 조회 도구, ③ 위임 도구, 예약 초안 도구
  - 예약 승인 API와 EMR 연동 함수(`ax_` 기록), 반영(§5.3)
  - 물어보기 → **자료실**(기록 검색·문서함, 질문하기 탭 제거)
  - 오늘 화면: "예약 원함, 미예약" 줄, 일부 줄의 "AI 비서로 처리" 버튼
  - 시나리오 평가셋(dev/test)과 채점
- **넣지 않는 것**: 예약 변경·취소(원본 예약을 화면에서 바꿔 보이게 하면 원본을 읽는 모든 곳이 합쳐 읽어야 한다 — 이번엔 새 예약만), 대화 관리(이름 바꾸기·삭제·검색·고정·공유), 문자 발송, 예약 외 쓰기 동작, 로그인
- **다음 묶음(따로 설계)**: 옛 종이 차트 OCR 이관(같은 EMR 연동 함수를 쓴다), 툴콜링 튜닝(Qwen SFT → GRPO, 무료 Colab T4·QLoRA, 단위는 "다음 도구 호출 한 번"). 이번 묶음은 그 재료가 남도록만 한다(§6 대화 저장, §7 정답 형식)

## 3. 화면

시안: 브레인스토밍 비주얼 컴패니언 `.superpowers/brainstorm/…/content/wireframe-v2.html`(저장소 밖, 흑백 클릭 와이어프레임 17화면). 색·모서리·글꼴은 `globals.css` 토큰, 부품은 `components/ui`(CLAUDE.md 규칙) — 시안의 흑백은 모양만이다.

### 3.1 앱 셸 (ChatGPT 데스크톱 앱 구조)

- **아이콘 줄**(맨 왼쪽, 아이콘 + 아래 작은 이름): AI 비서(`BotMessageSquare`) · 업무(`LayoutGrid`) · 자료실(`FolderSearch`) · AI 평가(`Scale`) · EMR(`Monitor`), 아래쪽에 테마(`Sun`)·파트 선택. 아이콘은 lucide-react
- **목록 칸**(아이콘 줄 옆): 고른 공간의 목록
  - AI 비서: "새 대화" + 최근 대화(최신순, 처음 N개 + 더보기)
  - 업무: 오늘 · 예약 · 준비표 · 통화 · 미예약 환자 · 청구 점검 · 재무 대조 · 경영 리포트 — 오른쪽에 건수(오늘 화면과 같은 함수 `backend/today.py`), 건수 없는 칸은 비움
  - 자료실: 기록 검색 · 문서함
  - AI 평가: 판정 · 블라인드 비교 · 정확도 표 · 자동 개선(지금 화면 탭이 목록 칸으로)
  - EMR: 목록 칸 없음 — 옛 프로그램 창 그대로
- 기준일은 목록 칸 아래. 위쪽 헤더 띠는 없다
- 시작 화면 `/` = AI 비서 새 대화. 지금 시작 화면(카드 4개)은 없어진다
- 좁은 화면: 아이콘 줄·목록 칸이 ☰ 서랍으로 접힌다
- AI 평가·EMR의 "별도 공간"(기능 정의 §4 앱 구성 — 메뉴 자리에 공간 이름과 돌아가기)은 아이콘 줄로 대신한다. 일상 업무와의 분리는 아이콘 줄의 칸이 다르다는 것으로 충분하다(Claude 판단)

### 3.2 AI 비서

- **시작**: 가운데 "무엇을 도와드릴까요?", 둥근 입력창, 예시 칩 5개, 아래 한 줄 "조회하고 예약 초안까지 — 확정은 사람이 합니다". 칩을 누르면 입력창에 채우고 바로 보낸다. 브리핑·바로 가기 칸은 두지 않는다(오늘 화면과 겹침)
- **예시 칩**(데모 데이터에서 실제로 답이 나오는 것으로 — §8): 📞 지난주 전화로 예약 원했는데 안 잡힌 사람 · 🩺 내일 환자 중 미수·주의사항 있는 사람 · 🧾 재심 낼 만한 삭감 건 · 💳 이번 주 카드 입금 안 맞는 날 · ☎️ (환자) 지난번에 전화로 뭐 물어봤지
- **대화**: 사용자 말은 오른쪽 말풍선, 답은 본문 글. 도구 호출은 "조회 n번 ›" 접힌 줄(누르면 단계마다 도구·조건·건수, 진행 중엔 SSE로 한 줄씩). 답 안의 카드 — 환자(→ 그 통화·EMR), 통화(→ 통화 화면), 청구·재무 건(→ 그 화면), 출처(③과 같은 출처 카드)
- **예약 초안 카드**(`AI` 배지): 날짜·시각–끝·담당·시술·환자·차트 번호, "겹침 없음 · 영업시간 안 · 근거 통화 …", 버튼 **승인 / 다른 시간 / 취소**. 승인 → `확정` 표시로 바뀌고 "AX가 넣은 예약 · 시각 파트 승인 · 일정에서 보기". 승인 때 검사에 걸리면 카드 아래 "승인하지 못했어요 — 이유" + 다시 만들기 제안. "다른 시간"은 입력창에 "다른 시간으로"를 채워 대화로 잇는다(Claude 판단). 취소는 초안을 `cancelled`로만 남긴다
- **문서 질문**: ③에 맡긴 답은 ③의 답·출처를 그대로, 거절이면 "문서함에 없음"
- **지난 대화**: 저장된 그대로 보인다(모델을 다시 부르지 않음). 이어서 물으면 같은 대화에 붙는다

### 3.3 기존 화면에 더하는 것

- **오늘 화면** "사람이 볼 일" — 통화에서 온 일에 **예약 원함** 줄 새로(활성 분류의 `wants_appt`가 참인 통화 중 통화 뒤 예약이 없는 환자, 기간·규칙은 §4.2 도구와 같은 함수). 이 줄과 재심 기한 임박·일계표 불일치 줄 끝에 "AI 비서로 처리" 버튼 — 누르면 AI 비서 새 대화를 정해진 질문으로 연다. 줄의 링크(→ 그 화면)는 그대로
- **예약표·EMR 예약 탭**: AX 예약을 원본과 함께 그리고 `AX` 꼬리표. 예약표 옆 패널 "어떻게 잡혔나"에 "AX가 넣은 예약 · 승인 시각·파트 · 근거 통화 → · 잡은 대화 보기 →"
- **준비표**: 당일(기준일) AX 예약도 행이 된다 — `prep_facts`가 원본 + AX 예약을 읽고, "다시 만들기"(`POST /jobs/prep-regenerate`)로 그 행이 생긴다. 평가 경로는 원본만 읽는다
- **미예약 환자**: 변경 없음 — 승인이 연락 기록을 남겨 기존 규칙으로 빠진다(§5.3)
- **자료실**: 지금 물어보기 화면의 기록 검색·문서함 탭 그대로. "이걸로 질문하기"는 "AI 비서에게 묻기"(AI 비서 새 대화에 질문을 채움), 오늘 화면 "근거 없는 질문" 줄도 AI 비서로 연다
- **질문하기 탭·떠 있는 창 제거**: ③ 에이전트(`backend/chat.py`)·`POST /chat`·평가·관문은 그대로 둔다 — 화면 입구만 AI 비서로 옮긴다. `/ask?tab=chat&log=` 같은 기존 링크는 자료실 또는 AI 비서로 돌린다

## 4. 에이전트

하네스(`backend/harness/`) 위 새 에이전트 `assistant`(파일 `backend/assistant.py` — 이름은 빌더 몫). 별칭은 `chat`(Sonnet 5.5, ③과 같은 모델 — Claude 판단: 새 별칭을 만들 이유가 아직 없다).

### 4.1 대화와 실행

- **대화 1턴 = 실행 1개**(`ax_agent_runs`, `agent='assistant'`, `target`=대화 id·턴 번호). 실행 입력 = 앞 턴들의 사용자 말·AI 비서 답(글)·카드가 가리킨 대상 id(환자·통화·예약 초안) + 이번 말. 앞 턴의 도구 결과 전체는 다시 넣지 않는다 — 필요하면 다시 조회한다(Claude 판단: 입력 크기와 낡은 결과를 피한다)
- "그 사람", "첫 번째", "김○○"가 앞 턴의 카드 대상으로 풀려야 한다 — 그래서 카드 대상 id를 입력에 넣는다
- 한 턴 = **도구 단계**(하네스 실행, 끝내는 도구 `done_tools` — 글로 끝나면 한 번 되돌림) → **답 단계**(도구 결과로 게이트웨이 1회, 구조화 출력 `{text, cards, cited_ids}`). 나누는 이유는 §7.1
- 상한: 턴당 도구 호출·비용 상한(③ 값 `CHAT_MAX_TOOL_CALLS`·`CHAT_MAX_USD`에서 시작, dev 실측으로 정함)
- 후검증(③ 재사용): 답 단계 글의 숫자는 이번 턴 도구 결과·입력에 있어야 하고(`backend/verify.py`), `cited_ids`는 이번 턴 검색·조회 결과 안이어야 한다. 첫 번째 어긋남은 이유를 붙여 답 단계를 한 번 다시 부르고, 두 번째는 고정 문구로 끝낸다(③과 같은 규칙). 카드는 이번 턴 도구 결과에 나온 대상 id만(코드가 카드 내용을 채운다)
- 입력 신뢰 경계: 통화 녹취·문자 등 도구 결과의 글은 데이터다(하네스 `TRUST_NOTICE`, [[치과 AX - 평가 설계]] §5 입력 신뢰 경계)

### 4.2 도구

조회는 전부 코드(SQL)이고 기존 함수를 재사용한다 — 새 함수는 그 화면이 쓰는 함수와 같은 것을 부른다(숫자가 화면과 어긋나지 않게).

| 도구 | 하는 일 | 재사용 |
|---|---|---|
| `query_patient` · `query_schedule` · `query_claims` · `query_charts` | ③ 그대로 | `backend/query_tools.py` |
| `find_calls(date_from, date_to, wants_appt?, purpose?, patient?)` | 활성 분류 기준 통화 목록(요약·목적·예약 원함·환자) | `backend/calls.py` |
| `unbooked_requests(date_from, date_to)` | 예약 원함 통화 중 통화 뒤 예약이 없는 환자 — 오늘 화면 새 줄과 같은 함수 | 새 함수(오늘 화면과 공유) |
| `free_slots(date, staff?, procedure)` | 그날 담당자별 빈 시간 — 영업시간·점심·휴진·시술 소요 시간·원본 + AX 예약 겹침을 코드로 | `backend/emr.py` `schedule_day`·`ax_master_values` |
| `prep_rows(date)` | 준비표 행(칩·주의) | `backend/prep.py` |
| `claim_items(kind)` | 재심 기한 임박·조정 목록·청구 전 경고 | `backend/claims.py` |
| `recon_days(month)` | 일계표 불일치 건 | `backend/recon.py` |
| `missed_patients(chip?)` | 미예약 환자 상위 | `backend/missed.py` |
| `ask_records(question)` | ③에 맡길 질문을 남긴다 — 도구 안에서 LLM을 부르지 않는 하네스 규칙 때문에, 도구 단계가 끝난 뒤 ③ `chat.chat`을 불러 그 답·출처·거절을 답 단계에 그대로 넘긴다 | `backend/chat.py` |
| `draft_appointment(patient_id, date, start, staff, procedure, source_call_uid?)` | **초안만** 만든다 — 같은 검사(§5.2)를 통과해야 초안이 생기고, 결과는 초안 id. 확정하지 않는다 | 새 |
| `done_tools()` | 도구 단계를 끝낸다(조회 끝) — 답은 답 단계가 쓴다 | — |

- 예약 시간은 `free_slots` 결과 안에서만 고른다 — `draft_appointment`가 겹침·영업시간을 다시 검사하므로 지어낸 시간은 초안이 되지 않는다
- 도구 설명은 짧게(다음 묶음 소형 모델 입력 길이)

## 5. 쓰기 — EMR 연동 함수

### 5.1 원칙

`emr_*`에는 쓰지 않는다(절대 규칙 — 재생성 때 사라지고, 고정 데이터 위 정답·verify·평가가 흔들린다). 승인 → **EMR 연동 함수 하나**(`backend/emr_bridge.py`, 예: `write_appointment`) → `ax_` 기록. 화면은 원본 + 기록을 합쳐 그린다. 실제 도입 때는 이 함수만 EMR 업체 API 호출로 바꾼다. 다음 묶음(차트 OCR 이관)도 같은 함수 모듈을 쓴다.

### 5.2 테이블(앱 DB, 이름은 빌더 몫)

- 예약 초안·확정 한 테이블(예: `ax_emr_writes` 또는 `ax_appointments`): 환자·날짜·시작·끝·담당·시술·근거 통화·대화 id·턴, 상태 `draft / approved / cancelled / rejected`(승인 검사 실패), 승인 파트·시각(실제 시계). 사람 데이터라 재생성 때 처리 규칙은 앱 설계 §7.3에 맞춘다
- 칸에 체어 번호·예약 종류(`treatment / hygiene / consult`)도 둔다 — 원본 예약과 같은 모양이라 예약표·준비표(`chair_no`·`type`을 읽음)가 그대로 그린다. 종류는 시술에서, 체어는 그 시각 빈 체어 중 코드가 고른다(Claude 판단)
- 승인 검사(코드, 초안 만들 때와 승인할 때 둘 다): **원본 예약이 지키는 운영 규칙 전부**([[치과 AX - 가상 데이터 생성 설계]] §1 (3)·(4), 값은 `generator/master.py`가 적재한 `ax_master_values`) — 영업시간·점심·휴진일(목·일), 기준일 이후(기준일은 개원 전 스냅샷이라 당일 영업시간 전체 허용), 시술 소요 시간, 시술에 맞는 담당 역할(스케일링은 위생사 등), 담당자 동시 건수(위생사 1, 원장 `DOCTOR_CONCURRENCY`), 체어 한 시각 1건(상담은 체어 없음), 같은 환자 같은 날 1건. 원본 + AX 예약을 합쳐 센다. 하나라도 걸리면 승인하지 않고 이유를 돌려준다. `free_slots`도 같은 검사로 빈 시간을 낸다(Claude 판단 — 원본 규칙으로 생길 수 없는 예약이 화면에 들어가지 않게)
- 승인은 사람만: `POST /assistant/drafts/{id}/approve`(파트) — 에이전트 도구에는 승인이 없다

### 5.3 반영 범위

| 곳 | 반영 |
|---|---|
| 예약표·EMR 예약 탭 | 원본 + AX 예약, `AX` 꼬리표 |
| ⑨ 미예약 환자 | 승인 때 `ax_missed_contacts`에 `booked`(채널 `call`, 승인 파트) — 기존 규칙으로 빠짐 |
| ④ 준비표 | 당일 AX 예약 행(§3.3), 평가 경로는 원본만 |
| 오늘 화면 숫자 | 당일 AX 예약을 오늘 예약·신환에 합침(예약표와 같은 함수) |
| 아침 브리핑 | 반영 안 함(그날 아침 기준) |
| 오늘 화면 "예약 원함" 줄·`unbooked_requests` | AX 예약도 "예약 있음"으로 친다 |
| AI 비서의 조회 도구(`query_schedule`·`query_patient` 포함) | 합쳐 읽는다 — 승인 직후 "금요일 일정 보여줘"에 방금 잡은 예약이 나와야 한다 |
| ③ 에이전트(`POST /chat`·`ask_records`)·③ 평가 | 원본만(평가 고정) |

원본 예약을 읽는 곳(`backend/emr.py`·`prep.py`·`missed.py`·`query_tools.py`·`recon_tools.py`·`report.py`) 중 위 표의 반영 곳만 합쳐 읽는다. 합쳐 읽는 쿼리는 한 곳(연동 모듈)에 두고, `query_tools`는 "AX 예약 합치기" 인자를 받아 AI 비서는 켜고 ③은 끈 채 쓴다(Claude 판단 — 도구를 두 벌 만들지 않는다). 평가 경로는 원본만 읽는다.

**예약 원함 미예약의 정의**(`unbooked_requests`·오늘 화면 줄·시나리오 정답이 같은 함수 — Claude 판단): 활성 분류에서 `wants_appt`가 참인 통화 중, 그 환자에게 통화 시각 뒤로 잡힌 살아 있는 예약(원본 `scheduled`·`completed` 또는 승인된 AX 예약)이 없는 것. 같은 환자는 최근 통화 하나로 묶는다. 오늘 화면 줄의 기간은 기준일 전 7일(통화일). 차트에 없는 문의(`patient_id` 없음)도 목록에 넣되 "차트 없음" 표시를 붙이고 초안은 만들지 않는다 — AI 비서는 "신환 등록은 EMR에서 먼저"라고 답한다(환자 등록은 범위 밖).

**재생성 때**(앱 설계 §7.3): 예약 기록·대화·메시지는 **버림**(⑨ 연락 기록과 같은 이유 — 환자·통화 id가 다른 실체를 가리킬 수 있다). 다음 묶음 재료가 실행 기록(§7.3 "다시 만듦")에 매이지 않게, 메시지 행에 그 턴의 도구 호출(이름·인자·결과 요약)을 같이 저장한다(§6).

## 6. 대화 저장

- 대화 테이블(예: `ax_assistant_conversations`: id·제목·파트·만든 시각) + 메시지 테이블(대화 id·순번·역할·글·카드 JSON·그 턴의 도구 호출 JSON·실행 id). 제목 = 첫 질문을 잘라 씀(LLM 없음)
- 모두가 같은 목록을 본다(로그인 없음). 관리 기능 없음 — 특히 삭제는 승인한 예약의 근거라 두지 않는다
- 다시 열기 = 저장된 메시지 그대로, 이어 쓰기 = 같은 대화에 새 턴(§4.1)
- 다음 묶음 재료: 메시지 + 실행 단계(`ax_agent_steps`)로 "대화 맥락 → 다음 도구 호출" 쌍을 뽑을 수 있어야 한다. 정답이 들어가지 않으므로 앱 DB에 둔다

## 7. 평가

- **시나리오 평가셋**: 시나리오 1개 = 사용자 턴 2~4개. 턴마다 정답 = 불러야 할 도구(순서 무관 집합)·핵심 인자(환자·날짜·담당·시술)·끝 상태(예약 초안의 환자·날짜·시각 범위, 또는 거절). dev 20~30 · test 20~30(사람만 test). 정답은 `ground_truth/`(JSON + 필요하면 `truth_` 테이블) — `data/`에 넣지 않는다
- 정답은 데이터에서 코드로 계산하고(예: 예약 원함 미예약 환자 목록, 그날 빈 시간), 질문 문장은 사람이 쓰거나 LLM이 쓰고 사람이 확인(빌더 몫). 유형: 예약 흐름 · 기능 조회(④⑤⑧⑨) · 문서 위임(③) · 거절(근거 없음·범위 밖 쓰기 요청 "예약 취소해줘") · 앞 턴 참조("그 사람")
- **지표**: 도구 선택(턴별 집합 일치), 인자 정확도, 과업 성공률(끝 상태 일치), **쓰기 안전 위반 0**(승인 없이 확정·검사 밖 시간 초안·범위 밖 쓰기), 턴당 비용·도구 호출 수
- 사용자 역할: 시나리오의 다음 사용자 말은 고정 대본(앞 답과 무관). 앞 답이 틀려 대본이 어색해지면 그 턴부터 실패로 센다(Claude 판단 — 가상 사용자 LLM을 두지 않는다)
- `make assistant-eval`(과금, 이어 돎, dev) / `python -m evaluation.assistant score --split test`(사람). 기준선: ③ 단일 턴 챗에 같은 첫 턴을 넣었을 때의 도구 선택(조회형 턴만) — 비교 보고, 관문 조건 아님
- `make gate`(코어) 조건에 넣지 않는다(Claude 판단 — 슬롯과 같은 위치)

### 7.1 다음 묶음(툴콜링 튜닝)과의 연결

**목표**: A(Sonnet이 도구 고르기와 답 쓰기를 모두) vs **C(도구 고르기는 강화학습한 로컬 Qwen, 답 쓰기 `reply`는 Sonnet)**를 같은 시나리오 평가셋에서 나란히 보이고, C가 A와 대등한 과업 성공·쓰기 안전 위반 0을 내면 AI 비서의 기본을 C로 넘긴다. 이번 묶음은 A로 만들고, 아래는 C로 넘어갈 때 고치지 않게 지켜 둘 것이다. 학습 방법·모델 크기·넘김 기준 값은 다음 설계에서 정한다.

- **두 단계로 나뉘는 실행**: 한 턴은 "도구 고르기 단계(도구 호출 반복) → 답 쓰기 단계(`reply`)"다. 도구 단계는 하네스 실행 하나(끝내는 도구 `done_tools` — 조회 끝), 답 단계는 그 실행의 도구 결과를 받아 게이트웨이를 한 번 부르는 구조화 출력(`{text, cards, cited_ids}`, LLM 호출 기록은 같은 실행에 `ref`로 묶음)이다. 두 단계의 모델 별칭을 따로 받는다(`TOOL_ALIAS`·`REPLY_ALIAS`, 지금은 둘 다 `chat`). C에서는 도구 단계 = 로컬 Qwen, 답 단계 = Sonnet. 하네스는 고치지 않는다(§4.1의 `reply` 끝내는 도구는 이 답 단계로 대신한다)
- **도구 단계 폴백**(C에서): 로컬 모델의 호출이 스키마에 안 맞거나 같은 호출을 반복하면 그 턴의 도구 단계를 Sonnet으로 넘기고 기록한다(폴백 비율도 비교 지표)
- **모델 자리**: 모델은 게이트웨이 별칭으로만 부른다. 튜닝한 Qwen은 판정기처럼 로컬 MLX 모델(`provider: mlx`)로 붙인다. 도구·후검증은 모델과 무관하게 그대로
- **비교 지표**: §7 지표 + 턴당 비용·응답 시간·폴백 비율, A·C(필요하면 B: Qwen이 전부)를 같은 dev·test 시나리오에서
- **도구 스키마 고정**: 도구 이름·인자는 버전으로 다룬다(바꾸면 학습 재료와 정답이 함께 낡는다). 설명은 짧게
- **학습과 평가 분리**: 시나리오 test는 학습 재료에 넣지 않는다(평가 설계 §2.7과 같은 원칙). 학습 재료는 dev 시나리오·앱 대화 기록(§6)·코드로 대량 생성한 시나리오, 정답은 같은 정의(§5.3·§7)를 코드로 계산
- **보상이 되는 채점**: §7의 도구 선택·인자 채점을 "다음 도구 호출 한 번" 단위로도 부를 수 있게 함수로 둔다 — 다음 묶음의 보상 함수가 그대로 가져다 쓴다
