# 작업 기록 — 설계 → 계획 → 구현 → 리뷰

기능마다 같은 순서로 일한 기록이다. 규칙의 원본은 `docs/치과 AX - *.md`이고, 이 폴더는 그 규칙을 정하고 구현한 과정이다. 결정 당시의 기록이라 지금 규칙과 다를 수 있다 — 다르면 원본 문서가 맞다.

## 일하는 순서

1. **설계**(`specs/날짜-주제-design.md`) — 무엇을 왜 만드는지, 목표·비목표, 사람이 정한 것. 대화로 요구를 좁힌 뒤 쓰고, 다른 에이전트가 "이것만 보고 만들 수 있나"를 먼저 읽어 빈 곳을 채운다
2. **계획**(`plans/날짜-주제.md`) — 설계를 작업 단위로 나눈 것. 작업마다 만들 파일·함수 시그니처·먼저 쓸 테스트·확인 명령
3. **구현** — 테스트를 먼저 쓰고 실패를 본 뒤 구현, 작업마다 커밋(`feat/<묶음>` 브랜치)
4. **리뷰** — 리뷰 에이전트(`.claude/agents/`)가 브랜치 전체를, 문서 점검 에이전트가 문서와 코드의 어긋남을 본다. 반영할지는 사람이 정하고, 고친 것은 다시 테스트로 확인
5. **PR** — CI(lint·test·프론트 빌드) 통과 뒤 머지

사람과 AI의 몫: 무엇을 만들지·범위·판단이 갈리는 결정은 사람이, 구현과 검사는 AI 코딩 에이전트가 맡았다. 일부 설계 문서는 **사용자 결정**과 **내 판단**(에이전트가 정한 것)을 나눠 적었다.

## 먼저 볼 예시

- **야간 실행 + ⑦ 아침 브리핑** — [설계](specs/2026-11-16-nightly-briefing-design.md) · [계획](plans/2026-11-16-nightly-briefing.md). 설계 대화에서 "운영 에이전트는 지금 데이터로는 의미가 약하다"고 판단해 코드 고정 순서로 줄인 과정, 리뷰 지적(색인 원자성·상한·잠금) 반영까지 한 묶음
- **⑧ 재무 대조** — [설계](specs/2026-11-11-finance-recon-design.md) · 계획 [1](plans/2026-11-11-finance-recon-1.md)·[2](plans/2026-11-12-finance-recon-2.md)·[3](plans/2026-11-12-finance-recon-3.md)·[4](plans/2026-11-12-finance-recon-4.md). 규칙 기준선부터 만들고 그 위에 조사 에이전트를 올린 단계별 진행

데이터를 다시 만든 경위(`specs/2026-11-11-data-redesign-design.md`·`specs/2026-11-11-hard-calls-design.md`)는 문서 맨 위 "지금 읽는 법"을 먼저 본다.
