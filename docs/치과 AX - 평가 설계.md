> **뭘 어떻게 측정하나.** `eval.py`와 사람 판정 절차가 읽는 문서. 데이터가 어떻게 만들어지는지는 [[치과 AX - 가상 데이터 생성 설계]], 기능별 완료 기준은 [[치과 AX - 기능 정의]].
> 정답 저장소(`ground_truth/truth.sqlite`)의 테이블 정의와 채우는 쪽은 **이 문서 §6에만** 있다.

## 0. 전체 흐름 (① 통화 분류)

지도 역할만 한다 — 규칙은 가리킨 절에 있다.

1. **생성**: 정답(라벨)을 먼저 뽑고 그에 맞춰 가짜 통화를 만든다. 골드는 `truth.sqlite`에만([[치과 AX - 가상 데이터 생성 설계]] §4.1, §1 원칙 1)
2. **나누기**: 전사(`config` `calls_with_transcript`) 중 판정 풀(`config` `eval_pool_size`)을 층화 추출해 dev·test 반반, 나머지는 비풀(§2.1)
3. **AI 풀이**: 모델이 분류([[치과 AX - 앱 설계]] §1)
4. **사람 판정**: 판정 풀을 사람이 판정. 골드가 있는데도 하는 이유 — 생성 라벨이 의도대로 나왔는지 확인(사람 vs 골드), 실제 병원 작업 흐름(정답지가 쌓이는 과정) 재현(§2.3)
5. **채점**: AI vs 골드 / AI vs 사람 / 사람 vs 골드(§2.2 정확도 셋 분리 보고)
6. **튜닝**: dev만 보며 반복, 개선 루프 1회([[치과 AX - 기능 정의]] §4 ②, 건별 덤프는 §7)
7. **최종 보고**: 조건별 test 1회 — v1·v2(경량)·v3-final(상위 모델) 각각(§1 원칙 2, [[치과 AX - 기능 정의]] §8)

## 1. 원칙

1. **정답은 앱 DB 밖**(`CLAUDE.md` 절대 규칙). 평가 스크립트만 `truth.sqlite`를 `ATTACH`해 조인
2. **튜닝 셋 ≠ 보고 셋.** 모든 평가셋은 dev/test로 나눔. 튜닝·`make gate`·CI는 `--split dev`만. **test는 데모 직전 1회**, `truth_eval_runs`에 이력 기록. 골드로 재는 지표(모델 vs 골드)도 같다 — dev는 test 판정 풀 통화를 뺀 전사(비풀 + dev 풀), test는 **test 판정 풀만**(역확률 가중). dev 골드는 희귀 카테고리가 test로 빠져 실제보다 적으므로 역확률 가중(§2.2)을 주 수치로, 비가중을 보조로 병기한다. 튜닝 중 본 통화가 보고 수치에 섞이지 않게
3. **절대값보다 조건 간 차이.** 합성 데이터라 절대 수치는 높게 나옴. README의 주 지표는 "리랭커 on/off", "프롬프트 v1→v2" 같은 차이
4. **분수 병기.** 모수가 작아(RAG dev 20·6·5·4문항, 분류 dev 판정 풀의 절반 — 카테고리별로는 몇 건) 1문항이 5~25%p를 움직임. 퍼센트만 쓰지 않음
5. **폴백 건 제외.** `ax_llm_calls.fallback_used`면 활성 모델 결과가 실제로는 폴백 모델 출력 → 블라인드·정확도 집계에서 제외
6. **재샘플링하지 않음.** 생성 분포의 치우침([[치과 AX - 가상 데이터 생성 설계]] §4.1)은 가중/단순 평균 병기로 드러냄
7. **EMR 지름길은 평가 입력에 넣지 않음.** 통화 뒤 EMR에 남는 결과가 라벨을 드러내는 경우가 있다 — 서류·기록 요청 통화 다음 진료일의 준비 완료 문자(`doc_ready`), 확정 예약 통화 시각에 생긴 예약. 분류는 `classify(transcript, direction)`만 받으므로 지표에는 영향이 없고, EMR을 조인하는 기능(④·요약)의 평가에서 이 연결을 정답 근거로 쓰지 않는다

## 2. 통화 분류 (①·②)

### 2.1 평가 풀

크기는 `config` `calls_with_transcript`·`eval_pool_size`·`blind_pool_size`. 아래 배분·분할은 전부 풀 크기에서 계산한다 — 고정 숫자를 두지 않는다.

- 전사 전체에 골드 라벨(`truth_call_labels`, 생성기 산출)
- **사람 판정 풀**: 생성기가 고정 시드로 층화 추출. 희귀 카테고리(불만·응급·모르겠음)는 각 카테고리 전사의 **60%를 뽑는다**(비례 배분보다 많이 뽑는 과표집. 전수를 뽑으면 비풀이 0건이라 60%에서 멈춤), 풀의 나머지는 남은 카테고리에 비례 배분. dev/test는 카테고리별 절반, 홀수 잔여는 카테고리를 돌며 dev/test에 번갈아 배정 → 합계 절반씩(풀이 홀수면 dev가 1건 더). 순번은 각 split 안에서 고정 셔플(층화 순서대로 두면 카테고리가 드러남)하고 **dev 전부 → test** 순으로 매긴다. 앱 DB에는 `in_eval_pool`·`eval_sort_order`만 — 카테고리 정보 없음. **카테고리별 최소**: 비례 배분이 split당 2건 미만인 카테고리는 split당 2건(dev 2·test 2)까지 올리고 그만큼 큰 카테고리에서 뺀다(풀이 작아 작은 카테고리가 dev 1건이 되는 것 방지). 리포트에 카테고리별 dev n 표시. 풀 150·현재 분포에서는 실제로 작은 카테고리 한두 개('기타' 등)에만 작동한다
- **블라인드 풀**: 판정 풀 안에서 고정 시드로 추출, `in_blind_pool` — 분류 배치 대상에 이미 포함
- 비풀 = `silver` (골드만 있음, 변화 병기용)

### 2.2 지표

| 지표 | 모수 | 정의 |
|---|---|---|
| 항목별 정확도 | 9항목 × 모델 × `prompt_version` | 라벨 일치 비율 + **n 표시** |
| 목적 Strict | 전체 | `purpose == primary_purpose` — **헤드라인** |
| 가중 / 단순 평균 | 전체 | 가중 = 현실 체감, 단순 = 카테고리 동등 |
| 판정 풀 정확도 | 풀 | **역확률 가중** w_c = N_c / n_c (층화 추출 보정). 가중 없이 전사 전체 골드와 비교하면 희귀 카테고리 비중 차이로 역전 |

**정확도 셋 분리 보고**
- 모델 vs 사람 (판정 풀) — 앱 화면의 "모델 일치율"은 이 중 **dev만** 집계(test 오염 방지). 붙여넣기 통화는 모수에서 제외
- 모델 vs 골드 (dev = 전사 − test 판정 풀, test = test 판정 풀만 — §1 원칙 2)
- **사람 vs 골드 (판정 풀)** — 라벨 타당성. 낮으면 생성 라벨이 '의도'일 뿐 사실이 아니라는 뜻

**버전 비교**: 두 버전 모두 `status='ok'`인 call_id **교집합**으로만, n 표시. 리포트는 버전마다 `model_actual`을 표기(`prompt_version` 정의는 [[치과 AX - 앱 설계]] §1).

### 2.3 사람 판정 절차

- 화면은 전사 기본 노출, 요약은 접힘
- 제시 순서 `eval_sort_order` 고정. dev 먼저, test는 `judge_upto`를 풀 크기로 올려 개방([[치과 AX - 앱 설계]] §6). 건너뛰기는 끝으로 복귀(영구 누락 없음)
- 판정 큐는 **분류가 `ok`인 건만**
- **플래그 판정 기준**(골드 생성 규칙과 같게): `appt_confirmed`는 이 통화에서 예약 날짜·시간이 새로 정해진 것만(확인 통화의 "그날 갈게요" 재확인은 아님). `wants_appt`는 예약 잡기가 함의하거나 다른 목적의 통화에서 새 예약을 원하는 것(변경 통화의 새 시간 요청은 변경 자체라 아님). `price_inquiry`는 앞으로 받을 진료의 비용을 묻는 것(보험 적용 여부만 묻는 것, 이미 낸 금액·수납 내역 확인은 아님 — 후자는 수납 문의 `billing_q`. 직원이 먼저 말한 금액도 아님). `has_todo`는 통화 뒤 직원이 할 일(회신·전달·서류 준비 등)이 남는 것
- **판정자 독립성 한계**: 판정자가 생성기를 만든 본인이라 라벨을 짐작할 수 있다. 사람 vs 골드는 생성 라벨 점검용으로 읽고, README에 이 한계를 적는다
- 데이터셋 재생성에도 판정 보존: `make export-human` / `import-human`(키는 [[치과 AX - 앱 설계]] §7)

### 2.4 블라인드 비교

- 두 `prompt_version` 요약을 버전 가리고 제시 — 기본은 같은 모델의 v1 vs v2(개선 루프의 요약 쪽 효과), 최종은 v2 vs v3-final(경량 → 상위 모델, 모델 교체 효과) → `left / right / tie / both_wrong`
- **문체 누출 방지**: 요약 프롬프트에서 출력 형식 고정(마크다운·글머리 금지, 명사형 종결 '~함/~음', 공백 포함 80~110자 단일 문단) + 코드 후처리로 줄바꿈·기호 정규화
- **좌우 배치** `hash(transcript, seed) % 2` — 새로고침·재생성에도 불변, 50:50
- 집계는 좌우 `(prompt_version, model_actual)` **쌍별**. 서로 다른 비교(v1 vs v2, v2 vs v3-final)의 투표가 섞이지 않음
- 리포트에 **위치 편향 지표**(left/right 선택 비율) 병기 — 50:50에서 벗어나면 문체 누출 의심
- 최종 비교(v2 vs v3-final)의 투표는 데모 고정 직전에 새로 받음
- **블라인드 큐**(원본은 여기): `in_blind_pool = 1`이고 `judge_status='done'`(판정 전에 요약을 보는 앵커링 방지)이며, `ax_settings.blind_versions`(비교할 두 버전)의 분류 ID 쌍에 대한 `ax_blind_votes`가 `NOT EXISTS`인 건

### 2.5 확장 — 모델 2개 교차검증 (나중)

[[치과 AX - 기능 정의]] §4 ① 확장을 붙였을 때만. 단위는 통화(9항목 중 하나라도 A ≠ B면 엇갈림), 폴백 건 제외, 골드·사람 판정 따로, 분수 병기.
- **일치 오류율**: 엇갈림이 없는데(A == B) 정답과 다른 비율 — 사람이 못 보는 오류의 규모
- **오류 포착률**: 모델이 틀린 통화 중 엇갈림이 붙은 비율. 같은 양 무작위 검토(= 엇갈림 비율)로 나눈 향상 배수가 1 근처면 모델 2개의 효용 없음

## 3. RAG 검색·챗 (③)

### 3.1 질문 70개

| 유형 | 수 | 예 | 정답 | 채점 |
|---|---|---|---|---|
| 매뉴얼형 | 18 | "노쇼 3회면 어떻게?", "실손 서류 발급 절차?" | 매뉴얼·FAQ 문단 | Hit@5, MRR |
| 공지형 | 10 | "스케일링 비용 언제 바뀌었어?", "추석 휴진?" | 최신 공지(옛 버전은 방해) | Hit@5 + **Top-1이 최신 버전** |
| 사례형 | 12 | "김○○ 지난번에 뭐 물어봤지?", "리마인드 문자 갔었나?" | 통화 전사·문자 스레드 | Hit@5 |
| 데이터형 | 12 | "내일 잔액 있는 환자 몇 명?", "오늘 취소 몇 건?" | `query_*` 도구 | 도구 선택 + `expected_args` + 숫자 일치 |
| 차트형 | 10 | "치석제거 뒤 치주치료로 이어진 환자는 간격·상병을 어떻게 적었지?" | 조건에 맞는 차트 기록 **여럿**(`answer_doc_ids`에 `chart:<treatment_id>` 전부 — `truth_chart_notes`·`emr_chart_notes`로 조건 SQL을 돌려 채움) | Hit@5(정답 중 하나), MRR |
| 거절형 | 8 | "원장님 자택 주소?", "○○ 직원 연봉?" (행정 비공개 6) + 생성 시 금지한 상식 2 | 없음 | 마지막 호출이 `refuse`인지 |

**작성 시점·방식** (문서·전사 생성 **후**)
- 매뉴얼·공지·사례형: 생성된 문서·전사를 보고 질문과 정답 청크를 지정. 질문 핵심 어휘가 정답 문단에 그대로 있으면 바꿔 씀(어휘 일치 비율 < 30%, verify 경고)
- 데이터형: 생성된 DB에서 **답이 2건 이상인 질문**을 고름. 선행 심기 안 함. "잔액 있는 환자"는 그 예약일 개원 전 잔액 > 0으로 센다(앱 설계 §3 `has_unpaid_balance`). 재생성 시 12문항 재확인(10분)
- 차트형: 환자 이름 없이 케이스 내용으로 묻는다(현장 인터뷰 — "이름을 몰라도 찾고 싶다"). 같은 템플릿 문장이 많아 정답 하나를 찍을 수 없으므로 조건에 맞는 차트를 전부 정답으로 둔다. 정답이 많으면 Hit@5가 거저 통과하므로 **정답 집합이 1~5건이 되도록 조건을 좁힌다**(5b 사실의 요건·간격·부위를 조합). 차트 하나는 한 split의 질문에만 정답으로 들어간다(dev/test 정답 집합이 겹치면 누출)
- 거절형 상식 2개: **`make data` 전**에 금지 토픽으로 지정(`forbidden_topics.json`) → 생성 지시 + 정규식 검사로 코퍼스에 없음을 보장(데이터에 자연스럽게 나오지 않는 주제로 고름)
- 복합 조건·시간 계산 질문 포함 ("10월 이후 바뀐 비용 중 환자 부담이 늘어난 건?")

청구 기준 문서([[치과 AX - 가상 데이터 생성 설계]] §4.2)는 말뭉치에 있지만 이 70개의 질문 대상은 아니다 — 청구 기준 질문은 슬롯 ⑤ 평가셋(§5)으로 따로. 다만 보험 안내와 내용이 겹치므로(예: 스케일링 연 1회 급여), 질문을 쓸 때 같은 답이 청구 기준 절에도 있으면 그 절을 `answer_doc_ids`에 함께 넣는다 — Hit@5·MRR·인용 정확도 모두 이 절의 청크를 정답으로 인정하고, 아래 dev/test 문서 단위 격리도 이 절에 적용한다.

**dev 35 / test 35**: 유형 비율 동일. **정답 문서 단위로 격리**(차트형은 차트 기록 단위) — 같은 공지·매뉴얼을 dev와 test가 공유하면 누출. 같은 사실을 담은 핵심 문서(공지와 FAQ·매뉴얼 — `truth_doc_meta.planted_facts`의 같은 묶음 키 `same`)는 함께 `answer_doc_ids`에 넣고 같은 split에 둔다. 최신성은 공지 대 그 옛 공지로만 판정한다. 공지형은 공지마다 옛 버전이 있어야 최신성 채점이 된다(옛 버전 구성은 가상 데이터 생성 설계 §4.2).

### 3.2 채점 규칙

- **`expected_tools[]`**: 순서 있는 목록. "그 환자 7월에 뭐가 삭감됐나?" = `[query_patient, query_claims]` 2단 호출이 정상 경로. **감점은 목록 밖 도구 호출만**(무차별 호출 방지)
- **`expected_args`**: 자유 텍스트 `query` 제외, **반환값에서 답을 못 얻는 키만 필수**, 부분집합 일치. 예: "오늘 취소 몇 건" → `query_schedule`은 `by_status`를 돌려주므로 `status` 필터는 필수 아님, 날짜 범위만 필수. 로그의 `args`는 Pydantic 정규화 후 기록(키 순서·타입 차이로 거짓 음성 방지)
- 숫자 일치: 정답 숫자가 답변 텍스트에 존재(단위 정규화 후)
- 거절 판정: **마지막 도구 호출이 `refuse`**면 통과(먼저 검색해 보고 거절하는 정상 경로 허용). 거절형이 아닌 질문에서 `refuse`를 부르면 그 문항 실패 — 과잉 거절은 다른 유형 정답률에 반영
- 도구 호출 상한 6회/질문 초과 = 실패
- 최신성: 최신 공지는 이전 값을 "기존 ○○"으로 함께 적는다(생성 설계 §4.2 `previous`). 옛 값이 답변에 나왔다는 것만으로 방해 문서 인용으로 보지 않고, 인용한 문서 id(옛 버전 문서인지)와 답으로 낸 값이 현재 값인지로 판단한다

### 3.3 지표

| 지표 | 모수 | 정의 |
|---|---|---|
| Hit@5 · MRR · Top-1 | 문서 검색형 **40**(매뉴얼 18 + 공지 10 + 사례 12; dev 20 / test 20) | 정답 청크 top-5 포함 / 순위 역수 / 1위 |
| 최신성 | 공지형 10 | Top-1이 최신 버전 (옛 버전이 top-5에 같이 있어도 됨) |
| 인용 정확도 | 문서 검색형 40 | 답변 `cited_ids`에 정답 문서(`answer_doc_ids`)의 청크가 하나 이상 **and** `cited_ids` ⊆ `retrieved_ids`(이번 질문의 검색 결과 합집합 — 검색 안 한 청크 인용은 실패). 공지형은 최신 버전 청크를 인용해야 통과(옛 버전을 같이 인용해도 됨). `refuse`·인용 없음은 실패. 로그만으로 계산(LLM 채점 없음), LLM 답변이 필요해 `--retrieval-only` 대상 아님 |
| 차트 Hit@5 · MRR | 차트형 **10**(dev 5 / test 5) — 문서 검색형 40과 따로 보고(정답 여럿 허용이라 채점이 다르고, `make gate` 기준 모수를 바꾸지 않으려고) | 정답 차트 중 하나라도 top-5 / 첫 정답 순위 역수 |
| 도구 선택 정확도 | 데이터형 12 | §3.2 규칙 통과 비율 |
| 환각 억제율 | 거절형 8 | 마지막 호출이 `refuse`인 비율 |

**`--retrieval-only`**: LLM 호출 없이 `retrieved_ids`만으로 Hit@5·MRR·Top-1·최신성 계산 — 리랭커 on/off, 하이브리드 vs 벡터만 비교는 전부 이 모드($0).

**조건 비교 표기**: 같은 문항에 두 조건을 적용한 paired 비교 → 분수(`14/20 → 17/20`) + 유의성 한 줄.
구제/손실 문항 목록과 원인(예: "옛 공지 배제는 리랭커가 구제")을 자동 출력 — **숫자보다 이 분석이 설득력의 본체.**

## 4. 준비표 (④)

- **집계**: ④ 착수 시 `prep_facts(date)` 첫 출력을 스냅샷으로 고정해 회귀 테스트
- **제안 후검증**(코드, 건별): `used_facts`의 모든 (key, value)가 입력 `facts`와 일치 **and** `text`에 등장하는 숫자가 전부 `used_facts.value`(단위 정규화 후)에 속함 → `suggestion_valid`. 실패율을 리포트에
- **주의사항 반영률**(코드, 건별): 주의 칩이 켜진 행(그날 예정 시술과 관련된 주의사항이 그날 보이는 행 — 기록일 ≤ 그날 < 끝나는 날) 중 `used_facts`에 그 주의사항 키가 모두 들어간 행의 비율. **과잉 언급률**: `used_facts`에 그날 시술과 관련 없는 주의사항이 들어간 행의 비율. 관련 여부는 `master` 주의사항 표(관련 시술)에서 바로 나온다
- **사람 채점**: 30행(환자 중복 없이) `유용 / 무난 / 틀림`. 대상은 준비표 범위(최근 7일 + 오늘)에서 칩(미수·보험 잔여·가족 리콜·주의 — 예약 칩은 모든 행에 켜져 제외)이 켜진 행 15 + 안 켜진 행 15를 고정 시드로 — 결과는 두 묶음 따로 보고. **보존하지 않는다**: 채점은 데이터 재생성·`export-human` 대상이 아니고, "다시 만들기"를 하면 그 표본 30행을 **전부 다시 채점**한다(틀린 행만 다시 만들고 나머지 채점을 남기면 집계가 좋게 치우침. 30행은 10~20분) — `ax_prep_sheets.human_rating`(`useful/ok/wrong`)·`rated_by`에 기록([[치과 AX - 앱 설계]] §4)

## 5. 심평원 청구 점검·삭감 대응 (슬롯 ⑤, 조건부)

단계는 [[치과 AX - 기능 정의]] §5 ⑤. 지표 세부 정의는 슬롯 착수 시.
- ⑤-1 대조: 레코드에 심은 불일치(결과 누락·장부에 없는 줄·대조 키 어긋남)의 대조 정확도(`truth_claims` 대비) + 재심 기한 테스트
- ⑤-4 사유서 초안: 인용(기준 절·차트 문장) 실재 후검증 통과율 + 사람 채점 표본(`유용 / 무난 / 틀림`, ④와 같은 척도). 표본 수는 슬롯 착수 시
- ⑤-2 점검: 정답은 5b가 심은 상병 착오·임상 요건형 오류(`truth_claim_errors`, 가상 데이터 생성 설계 §2.4). **"서술 있는 줄 전부" 기준선과 나란히**(가상 데이터 생성 설계 §4.3 디코이) AI(기준 문서·차트로 판단)의 정밀도·재현율과 근거 정확도(④처럼 입력 사실·기준 절과 대조해 후검증)를 보고한다. 나이·횟수 같은 급여 조건과 단순 누락·코드 착오는 규칙(SQL)이라 지표가 아니라 테스트. 상병 확인 경고는 규칙이라 지표가 아니라 테스트(허용 조합 밖 = 경고, 지난 상병 착오 조합이면 건수·금액 표시)
- ⑤-3: 상세 사유 → 절은 테스트. Hit@5·MRR은 `truth_claim_qa`(상세 사유마다 1~2문항, **코드를 말하지 않는 질문** — 예: "치석제거 다음 달로 넘어가면 왜 깎여?", 어휘 일치 방지 §3.1, 채점 §3.3, 정답 = 그 사유의 절). 판단 정확도 3분류(외부 이력 사유 = 정당) — 헷갈리기 쉬운 쌍인 '내역설명 누락(보완 후 재청구)'과 '상병 착오(정당)'는 따로도 보고(정답 = 가상 데이터 생성 설계 §2.4 — 상세 사유 유형과 오류 목록에서 파생돼 규칙으로도 풀리므로 ⑤-2와 같이 규칙 기준선과 나란히)

## 7. `eval.py`

```
eval.py --split dev|test [--retrieval-only] [--prompt-version v2] [--condition reranker=off]
  → reports/eval_<split>_<condition>_<ts>.md  (+ truth_eval_runs 1행)
```
- 분류: §2.2 표 + 3종 정확도 + 버전 비교(교집합) + 블라인드 쌍별 승률·위치 편향
- RAG: §3.3 표 + 조건 비교(지정 시) + 구제/손실 문항 덤프
- 준비표: 회귀 통과 여부 + `suggestion_valid` 비율 + 사람 채점 두 묶음(칩 켜진 / 안 켜진) 집계
- 평가 실행 시에만 게이트웨이 파일 캐시 `hash(model, prompt_version, messages, tools)` 활성 — 검색 파라미터만 바꾸는 실험에서 동일 컨텍스트 LLM 재과금 방지
- `is_eval=true`로 실사용 로그와 분리
- **건별 덤프는 `--split dev`에서만**: 개선 루프용 오류 목록(틀린 통화 id·전사)과 RAG 구제/손실 문항 덤프는 튜닝 범위에서만 출력한다. `--split test`는 집계만 내고 건별 목록을 내지 않는다(§1 원칙 2 — 튜닝 중 test 항목을 보지 않게)
- **few-shot 예시 제외**: 예시는 dev 판정에서만 고르고(개선 루프 — [[치과 AX - 기능 정의]] §4 ②), 프롬프트 파일 머리말의 예시 `call_uid`를 dev 집계에서 뺀다

`make gate`는 이 스크립트의 `--split dev` 출력을 읽음. 기준은 [[치과 AX - 기능 정의]] §6.
