> **뭘 어떻게 측정하나.** `eval.py`와 사람 판정 절차가 읽는 문서. 데이터가 어떻게 만들어지는지는 [[치과 AX - 가상 데이터 생성 설계]], 기능별 완료 기준은 [[치과 AX - 기능 정의]].
> 정답 저장소(`ground_truth/truth.sqlite`)의 테이블 목록·뜻·채우는 쪽은 **이 문서 §6에만** 있다(컬럼은 `ground_truth/schema.sql`).

## 0. 전체 흐름 (① 통화 분류)

지도 역할만 한다 — 규칙은 가리킨 절에 있다.

1. **생성**: 정답(라벨)을 먼저 뽑고 그에 맞춰 가짜 통화를 만든다. 골드는 `truth.sqlite`에만([[치과 AX - 가상 데이터 생성 설계]] §4.1, §1 원칙 1)
2. **나누기**: 녹취록(`config` `calls_with_transcript`) 중 판정 풀(`config` `eval_pool_size`)을 층화 추출해 dev·test 반반, 나머지는 비풀(§2.1)
3. **AI 풀이**: 모델 A가 분류하고 판정기(모델 B)가 따로 판정([[치과 AX - 앱 설계]] §1)
4. **골드 점검**: 판정기가 골드와 다르게 답한 통화를 중재 판정기가 가리고, 사람은 그 결과의 표본만 본다 — 생성 라벨이 의도대로 나왔는지 확인(§2.3)
5. **채점**: AI vs 골드 / 판정기 vs 골드 / 중재 판정기 vs 사람(골드 점검 표본)(§2.2 정확도 분리 보고)
6. **자동 개선**: 재료에서 오류를 찾아 후보를 만들고 관문을 넘으면 대기 버전, 사람이 재분류를 실행하면 전환(§2.7). 건별 덤프는 §7
7. **최종 보고**: 조건별 test 1회 — v1·vN(경량)·vN-final(상위 모델) 각각. 사람이 실행(§1 원칙 2, [[치과 AX - 기능 정의]] §8)

## 1. 원칙

1. **정답은 앱 DB 밖**(`CLAUDE.md` 절대 규칙). 평가 스크립트만 `truth.sqlite`를 `ATTACH`해 조인
2. **튜닝 셋 ≠ 보고 셋.** 튜닝 중 본 항목이 보고 수치에 섞이지 않게
   - 모든 평가셋은 dev/test로 나눔. `make gate`·CI는 `--split dev`만, 튜닝은 dev와 §6 `tune_qa.json`만
   - **test는 데모 직전 묶음마다 1회**(묶음·이력·`--force`는 §7). 사람이 실행하고 자동 개선 루프는 test를 읽지 않는다
   - 골드로 재는 지표(모델 vs 골드)도 같다 — dev는 test 판정 풀 통화를 뺀 녹취록(비풀 + dev 풀), test는 **test 판정 풀만**(역확률 가중). dev 골드는 희귀 카테고리가 test로 빠져 실제보다 적으므로 역확률 가중(§2.2)을 주 수치로, 비가중을 보조로 병기한다
3. **절대값보다 조건 간 차이.** 합성 데이터라 절대 수치는 높게 나옴. README의 주 지표는 "리랭커 on/off", "프롬프트 v1→vN" 같은 차이
4. **분수 병기.** 모수가 작아(RAG 유형별 dev는 §3.1 표의 절반, 분류 test는 판정 풀의 절반 — 카테고리별로는 몇 건) 1문항이 수~수십 %p를 움직임. 퍼센트만 쓰지 않음
5. **폴백 건 제외.** `ax_llm_calls.fallback_used`면 활성 모델 결과가 실제로는 폴백 모델 출력 → 블라인드·정확도 집계에서 제외
6. **재샘플링하지 않음.** 생성 분포의 치우침([[치과 AX - 가상 데이터 생성 설계]] §4.1)은 가중/단순 평균 병기로 드러냄
7. **EMR 지름길은 평가 입력에 넣지 않음.** 통화 뒤 EMR에 남는 결과가 라벨을 드러내는 경우가 있다 — 서류·기록 요청 통화 다음 진료일의 준비 완료 문자(`doc_ready`), 확정 예약 통화 시각에 생긴 예약, 리콜 문의 통화 며칠 전의 리콜 문자. 분류의 통화 입력은 `transcript`·`direction`뿐이므로 지표에는 영향이 없고, EMR을 조인하는 기능(④·요약)의 평가에서 이 연결을 정답 근거로 쓰지 않는다
8. **에이전트는 기준선과 나란히.** 규칙이나 고정 흐름과 같은 문항에서 짝 비교한다. 경로가 실행마다 달라질 수 있어 호출 수·비용·실행 간 변동을 함께 낸다(§5)
9. **자동 처리는 오류율로 켠다.** 작업 종류마다 dev 자동 처리 오류율이 기준 이하이고 입력 신뢰 경계 위반이 0건일 때만(§5) 사람이 `auto_policy`를 켠다. 표본이 작으면 분수로 쓰고 "오류 0건"을 안전의 증거로 쓰지 않는다
   - 활성 프롬프트가 바뀌어도 켜진 정책의 근거가 유지되도록 관문에 자동 처리 오류율을 넣는다(§2.7)

## 2. 통화 분류 (①·②)

### 2.1 평가 풀

크기는 `config` `calls_with_transcript`·`eval_pool_size`·`blind_pool_size`. 아래 배분·분할은 전부 풀 크기에서 계산한다 — 고정 숫자를 두지 않는다.

- 녹취록 전체에 골드 라벨(`truth_call_labels`, 생성기 산출)
- **판정 풀**(측정 구간 — 골드 지표의 dev/test 분할과 가중의 기준): 생성기가 고정 시드로 층화 추출
  - **배분**: 희귀 카테고리(불만·응급·모르겠음)는 각 카테고리 녹취록의 **60%를 뽑는다**(비례 배분보다 많이 뽑는 과표집. 전수를 뽑으면 비풀이 0건이라 그 비율에서 멈춤), 풀의 나머지는 남은 카테고리에 비례 배분
  - **카테고리별 최소**: 비례 배분이 split당 2건 미만인 카테고리는 split당 2건까지 올리고 그만큼 큰 카테고리에서 뺀다(풀이 작아 작은 카테고리가 dev 1건이 되는 것 방지). 리포트에 카테고리별 dev n 표시
  - **dev/test**: 카테고리별 절반, 홀수 잔여는 카테고리를 돌며 dev/test에 번갈아 배정 → 합계 절반씩(풀이 홀수면 dev가 1건 더)
  - **순번**: 각 split 안에서 고정 셔플(층화 순서대로 두면 카테고리가 드러남)하고 **dev 전부 → test** 순으로 매긴다. `ax_calls`에는 `in_eval_pool`·`eval_sort_order`만 — 카테고리 정보 없음
- **블라인드 풀**: 판정 풀 안에서 고정 시드로 추출, `in_blind_pool` — 분류 배치 대상에 이미 포함
- 비풀 = `silver` (골드만 있음). 자동 개선에서 재료·검증으로 나눠 쓴다(§2.7)

### 2.2 지표

| 지표 | 모수 | 정의 |
|---|---|---|
| 항목별 정확도 | 9항목 × 모델 × `prompt_version` | 라벨 일치 비율 + **n 표시** |
| 목적 Strict | 전체 | `purpose == primary_purpose` — **헤드라인** |
| 가중 / 단순 평균 | 전체 | 가중 = 현실 체감, 단순 = 카테고리 동등 |
| 판정 풀 정확도 | 풀 | **역확률 가중** w_c = N_c / n_c (층화 추출 보정). 가중 없이 녹취록 전체 골드와 비교하면 희귀 카테고리 비중 차이로 역전 |

**정확도 분리 보고**
- 모델 vs 골드 (dev = 녹취록 − test 판정 풀, test = test 판정 풀만 — §1 원칙 2)
- 판정기 vs 골드 (같은 분할) — 판정기 품질(§2.6)
- 모델 vs 판정기 (dev 판정 풀 — 앱이 가리는 법은 [[치과 AX - 앱 설계]] §6) — 앱 화면의 "모델 일치율". 앱 DB에는 골드가 없어 화면은 이것만 보인다. 새로 추가한 통화는 모수에서 제외
- **골드 점검** — 중재 판정기 vs 사람 일치율(표본)과 골드 오류 추정 건수. 라벨 타당성 — 골드 오류가 많으면 생성 라벨이 '의도'일 뿐 사실이 아니라는 뜻(§2.3)

**버전 비교**: 두 버전 모두 `status='ok'`인 `call_uid` **교집합**으로만, n 표시. dev 버전 비교에서 관문 탈락 후보는 뺀다. 리포트는 버전마다 `model_actual`을 표기(`prompt_version` 정의는 [[치과 AX - 앱 설계]] §1).

### 2.3 사람 판정과 골드 점검

- **운영 판정**(앱 ②): 판정 풀 밖 통화와 새로 추가한 통화의 엇갈림과 무작위 표본만 판정한다. 업무 흐름이라 지표 모수에 넣지 않고 감사로만 쓴다. 큐는 활성 버전 분류가 `ok`인 건만, 순서는 [[치과 AX - 앱 설계]] §6
- **메모**(선택): 애매한 이유나 기준이 필요한 경우를 적는다. 메모는 자동 개선 재료가 아니다(§2.7). 메모가 붙은 건은 프롬프트보다 이 절의 플래그 판정 기준을 먼저 고친다. 이 절이 기준의 원본이고, 고치면 `prompts/judge/`의 새 버전을 만들어 판정기를 다시 돌린다
- **플래그 판정 기준**(골드 생성 규칙과 같게)
  - `appt_confirmed`: 이 통화에서 예약 날짜·시간이 새로 정해진 것만. 확인 통화의 "그날 갈게요" 재확인, 응급 통화의 내원 안내(그날 또는 다음 진료일 시각을 직원이 정해 알려 줌 — [[치과 AX - 가상 데이터 생성 설계]] §2.6 (5))는 아님
  - `wants_appt`: 예약 잡기가 함의하거나 다른 목적의 통화에서 새 예약을 원하는 것. 변경 통화의 새 시간 요청은 변경 자체라 아님
  - `price_inquiry`: 앞으로 받을 진료의 비용을 묻는 것. 보험 적용 여부만 묻는 것, 직원이 먼저 말한 금액, 이미 낸 금액·수납 내역 확인(수납 문의 `billing_q`)은 아님
  - `has_todo`: 통화 뒤 직원이 할 일(회신·전달·서류 준비 등)이 남는 것. 직원이 원장님께 전달하겠다고만 약속해도 할 일이 남은 것으로 본다
- 데이터셋 재생성: 앱 DB는 남고, 판정(메모 포함)은 녹취록 해시로 다시 붙인다(`make export-human` / `import-human` — [[치과 AX - 앱 설계]] §7.3)

**골드 점검**(`evaluation/`에서 돈다 — 골드를 보므로 앱 밖)
- **대상**: test 판정 풀을 뺀 녹취록 중 판정기(활성 judge 버전) 라벨이 골드와 한 항목이라도 다른 통화. 급함은 urgent 여부만 비교한다(§2.5 — `shared/call_labels.py` `differing_items`). test 판정 풀은 보지 않는다(§1 원칙 2)
- **중재 판정**: 녹취록·방향과, 다른 항목마다 두 라벨(어느 쪽이 골드인지 가리고 `call_uid`·항목 해시로 순서를 섞음)을 받아 항목마다 `가 / 나`를 고른다. `둘 다 아님`은 목적·상대에만 둔다 — 나머지 항목은 두 값이 다르면 하나가 반드시 맞다. 급함은 `급함 / 급하지 않음` 두 값으로 보인다. 판정 기준은 위 플래그 판정 기준과 같다(프롬프트 `prompts/gold_audit/`). 모델은 `config/llm.yaml` `gold_audit`(생성기·판정기와 다른 모델), 추론 단계는 프롬프트 머리말. 서버 측 폴백으로 다른 모델이 답한 건은 쓰지 않고 다시 돈다. 명령 `make gold-arbitrate`(빠진 건만 다시), 호출 기록은 골드가 들어 있어 `evaluation/gold_audit_llm.jsonl`
- **사람 표본**: 통화 단위로 `evaluation/metrics.py` `GOLD_AUDIT_SAMPLE`건(대상이 더 적으면 전부). 통화를 중재 결과로 묶고(판정기 쪽 항목이 있으면 판정기 쪽, 없고 둘 다 아님이 있으면 둘 다 아님, 나머지는 골드 쪽) 묶음마다 고르게 `call_uid` 해시로 뽑는다. 사람은 그 통화의 다른 항목 전부를 같은 화면(녹취록 + 가린 두 라벨)에서 고르고, 중재 결과는 저장 뒤에 보인다. 도구는 터미널 화면 하나(`make gold-audit`)
- **기록**: `evaluation/gold_audit.jsonl`(커밋) — 한 줄 = (통화, 판정기 버전). 녹취록 해시·항목·중재 선택·사람 선택. 판정기 버전이 바뀌면 새 버전 대상을 다시 중재하고 표본도 새로 뽑는다. 재생성 뒤에는 해시로 다시 붙이고 녹취록이 바뀐 기록은 수만 적는다
- **쓰임**: 중재 판정기 vs 사람 항목별 일치율(분수)과 골드 오류 추정 건수(중재가 판정기 쪽을 고른 항목과 둘 다 아님을 고른 항목, 따로 적음)를 리포트에 낸다. 오류 추정은 중재 선택만으로 정한다 — 사람 표본은 중재가 믿을 만한지 재는 데 쓰고, 표본 안 사람 기준 건수는 참고로만 적는다. 데이터가 고정이라 골드는 고치지 않는다 — 골드 지표는 원래 골드가 주 수치이고, 골드 오류 추정 건을 뺀 수치를 dev에만 함께 적는다(test 판정 풀은 점검하지 않아 test 수치는 원래 골드뿐)
- **한계**: 판정기와 골드가 같이 틀린 통화는 대상에 들지 않는다. 중재 판정기는 생성기·판정기와 다른 모델이지만 생성기와 같은 계열이라 골드 쪽으로 기울 수 있다(사람 표본 일치율로 일부 드러남). 판정자가 생성기를 만든 본인이라 라벨을 짐작할 수 있다. README에 셋 다 적는다

### 2.4 블라인드 비교

- **채점은 LLM 쌍 비교**(`prompts/blind_judge/`, `make blind-judge`): 쌍 비교 판정기가 블라인드 풀의 두 요약을 좌우를 바꿔 두 번 판정하고, 두 판정이 같으면 그 선택, 다르면 `tie`로 센다(위치 편향 보정). 입력은 녹취록과 두 요약뿐이다. 프롬프트 버전이 나올 때마다 dev 블라인드 통화에 다시 돌리고, 앱 화면·`--split dev`도 dev만 보인다. test 블라인드 통화는 최종 비교(vN vs vN-final) 한 번만, 사람 최종 투표 때 함께 돌린다. test 분류 묶음(§7)은 그 `--prompt-version`이 낀 쌍만 보인다 쌍 비교 판정기 모델은 `config/llm.yaml` 별칭 `blind_judge` — 요약을 쓴 모델과 같으면 자기 글 쪽으로 기울 수 있어 사람 투표 일치율과 함께 본다
- **사람 투표**: dev 블라인드 통화는 `ax_settings.blind_versions` 쌍(앱 블라인드 탭), test 블라인드 통화는 위 최종 비교 때(데모 고정 직전, split별로 보고). 같은 쌍에서 LLM 쌍 비교와 사람의 일치율을 쌍 비교 판정기 버전별로 함께 낸다 — LLM 쌍 비교를 믿을 근거
- 두 `prompt_version` 요약을 버전 가리고 제시 — 기본은 같은 모델의 v1 vs vN(자동 개선의 요약 쪽 효과), 최종은 vN vs vN-final(경량 → 상위 모델, 모델 교체 효과) → `left / right / tie / both_wrong`
- **문체 누출 방지**: 요약 프롬프트에서 출력 형식 고정(마크다운·글머리 금지, 명사형 종결 '~함/~음', 공백 포함 80~110자 단일 문단) + 코드 후처리로 줄바꿈·기호 정규화
- **좌우 배치** `hash(transcript, seed) % 2` — 새로고침·재생성에도 불변, 50:50
- 집계는 좌우 `(prompt_version, model_actual)` **쌍별**. 서로 다른 비교(v1 vs vN, vN vs vN-final)의 투표가 섞이지 않음
- 리포트에 **위치 편향 지표**(left/right 선택 비율) 병기 — 50:50에서 벗어나면 문체 누출 의심
- **블라인드 큐**(원본은 여기, 사람 투표): dev 블라인드 통화(`in_blind_pool = 1`이고 dev 판정 풀 — [[치과 AX - 앱 설계]] §6)이고 `ax_settings.blind_versions`(비교할 두 버전)의 분류 ID 쌍에 대한 `ax_blind_votes`가 `NOT EXISTS`인 건.

### 2.5 모델 2개 교차검증

모델 A(분류기) vs 모델 B(판정기) — [[치과 AX - 기능 정의]] §4 ①. 단위는 통화(9항목 중 하나라도 A ≠ B면 엇갈림), 폴백 건 제외, 골드 기준, 분수 병기.
- **급함은 urgent 여부만 비교**: normal과 low는 같은 것으로 본다 — 골드 normal/low가 녹취록과 무관한 추첨이라 둘의 차이는 오류를 가려내지 못한다. 엇갈림(앱 설계 §1)과 아래 모델 오류(A ≠ 골드)에 같이 쓴다(`shared/call_labels.py` `differing_items`). 모델 vs 골드 정확도(§2.2)의 급함은 3값 그대로
- **일치 오류율**: 엇갈림이 없는데(A == B) 정답과 다른 비율 — 사람이 못 보는 오류의 규모
- **오류 포착률**: 모델이 틀린 통화 중 엇갈림이 붙은 비율. 같은 양 무작위 검토(= 엇갈림 비율)로 나눈 향상 배수가 1 근처면 모델 2개의 효용 없음
- 판정 풀은 희귀 카테고리 과표집이라 위 두 지표와 §2.6의 라우팅 효과는 역확률 가중과 비가중을 함께 낸다
- 모델 A·B가 같아진 구성은 교차검증 지표를 내지 않는다

### 2.6 판정기 측정

- 판정기 vs 골드는 §2.2, 골드 오류 추정 건을 뺀 수치는 §2.3 쓰임
- 운영 구간에서 사람이 볼 비율 = (엇갈림 + 표본) ÷ 전체. 판정 풀의 엇갈림 비율과 포착률로 같은 라우팅의 효과를 계산한다
- 판정기 입력과 도구는 [[치과 AX - 기능 정의]] §4 ②

### 2.7 자동 개선과 재발 방지

대상은 ①부터, 평가셋이 있는 ③·④·⑤·⑧로 넓힌다(재료·관문 분할은 task마다 착수 시 정한다). `judge`·중재 판정기·쌍 비교 판정기는 자동 개선 대상이 아니다 — 재는 쪽을 고치면 실력이 아니라 점수가 오른다. 판정 기준은 §2.3이 원본이고 사람이 고친다. `make improve`가 `evaluation/`에서 돈다. 앱으로 넘기는 것은 프롬프트 파일, `reports/improve_runs.jsonl`, 대기 버전 설정, `ax_failure_cases`의 라벨 없는 행, 비용 합계뿐이다. 개선 에이전트의 실행 기록과 LLM 호출 로그는 골드가 들어 있어 `evaluation/runs/`(커밋 안 함)에 둔다.

- **데이터 분할**: 비풀을 **재료**와 **검증**으로 나눈다. 층 키는 `(희귀 목적 묶음, emergency, complaint)`이고 층 안에서 `call_uid` 해시로 정렬해 앞쪽을 재료로 배정한다(비율 `evaluation/metrics.py` `SILVER_MATERIAL_SHARE`, 함수 `evaluation/splits.py` `silver_split` — 파인튜닝 학습 재료도 이 재료 구간만 쓴다). `truth_call_labels.split`은 바꾸지 않고 `evaluation`에서 계산하며 층별 n을 기록에 남긴다
- **재료**: 재료의 모델 vs 골드 오류를 개선 에이전트가 유형별로 묶는다. 프롬프트에는 일반 규칙만 쓰고 재료의 문장·라벨을 옮기지 않는다. 후보와 재료의 연속 어절 겹침을 코드로 검사하고(§3.1 베끼기 기준) 예시 문장 삽입은 거부한다
- **관문 모수**: 검증 구간만 판정에 쓴다. 정답은 골드이고 Strict 상승은 비가중 짝 비교로 판정한다. dev 판정 풀은 `--split dev` 오류 목록으로 사람이 건별로 보는 구간이라 독립이 아니어서 참고 수치로만 표시한다(역확률 가중, 모집단은 카테고리별 건수만 담은 `evaluation/population.json`). 관문은 집계만 돌려주고 건별 목록을 주지 않는다
- **반영 조건**(값은 `evaluation/metrics.py`, 첫 실행 전 고정): 목적 Strict 상승(같은 통화 짝 비교, §3.3 McNemar), 골드 응급·불만을 새로 놓친 건 0과 오탐 증가 상한, 다른 항목 회귀 없음, 켜진 자동 처리의 오류율이 기준 이하(① 자동 종결은 현재 모델 B와 결합해 계산), 자동 처리가 켜져 있으면 dev 신뢰 경계 시나리오 위반 0건(§5), 후검증이 있는 task는 통과율 유지. 하나라도 못 넘으면 버린다
- **전환**: 넘은 후보는 대기 버전이 된다. 저장 결과가 없는 task는 바로 전환하고, classify는 사람이 재분류를 실행해 전부 `ok`로 끝날 때 전환한다([[치과 AX - 앱 설계]] §7.2). 대기 버전이 있으면 `make improve`는 돌지 않는다
- **실패 기록**: 다음 후보를 쓸 때 앞선 탈락 후보의 기록을 함께 준다 — 바꾼 규칙과 못 넘은 관문 조건 이름(enum)만이고 수치·건별 목록은 주지 않는다. 같은 묶음 안에서만 넘기고, 사람이 관문 기준이나 시도 상한을 다시 정하면 비운다 — 검증 구간의 정보가 후보 작성으로 새는 길이라 묶음당 시도 상한이 그 양을 묶는다
- **과적합 방지**: 실행당 후보 수와 묶음당 **관문 평가 시도 수**(탈락 포함)에 상한(`evaluation/metrics.py`). 상한을 넘기려면 사람이 관문 기준을 다시 정한다
- **기록**: `reports/improve_runs.jsonl`(라벨 없는 집계 — 오류 유형 이름·바뀐 규칙·후보 버전·관문 결과·층별 n·반영 여부)
- **누출 차단**: 앱으로 넘기는 칸은 enum과 경로·집계만 쓴다. 자유 글이 남는 칸은 쓰기 전에 코드가 재료 녹취·라벨과의 겹침을 검사하고(§3.1 베끼기 기준) 걸리면 쓰지 않는다. 재현 테스트의 입력은 합성 문장만 쓴다. 앱 DB 연결에는 `truth.sqlite`를 붙이지 않는다
- **금지**: test 분할·test 판정을 읽지 않는다. 입력은 test 행을 뺀 뷰로 만들고, 실행 때 test 통화가 입력에 있으면 실패. 기존 `eval.py`의 dev 모수는 재료를 포함하므로 관문에 쓰지 않고 순수 채점 함수만 공유한다
- **재발 방지 경로**: 프롬프트 밖의 원인(도구 설명·도구 권한·훅·정책·입력 제한)은 관문으로 자동 반영하지 않는다. 개선 에이전트가 `ax_failure_cases`에 원인과 재현 테스트를 올리고, 재현 테스트가 수정 전 실패·수정 뒤 통과할 때 사람이 승인한다. 안전장치를 푸는 변경은 후보로도 만들지 않는다
- **입력 출처**: 건별 입력은 재료만 허용한다. 검증·dev·운영 구간에서 나온 표본 오류·되돌리기는 프롬프트 밖 경로로만 가고, 그 건을 프롬프트 재료로 쓰려면 관문 모수에서 뺀다. 관문 탈락은 집계만 돌아간다. test 건은 실수 후보가 되지 않는다

**작성 시점·방식** (문서·녹취록 생성 **후**)
- 매뉴얼·공지·사례형: 생성된 문서·녹취록을 보고 질문과 정답 청크를 지정. 질문은 현장 직원이 쓰는 말로 쓰고(시술명·보험·예약 같은 용어는 그대로) 정답 문장을 베끼지 않는다 — 정답 문단과 연속 4어절이 같거나 정답 값이 질문에 있으면 바꿔 씀(verify 경고)
- 데이터형: 생성된 DB에서 **답이 2건 이상인 질문**을 고름. 선행 심기 안 함. "잔액 있는 환자"는 앱 설계 §3 `has_unpaid_balance` 정의로 센다. 재생성 시 `make verify`가 `answer_sql`로 다시 계산해 확인
- 차트형: 환자 이름 없이 케이스 내용으로 묻는다(현장 인터뷰 — "이름을 몰라도 찾고 싶다"). 같은 템플릿 문장이 많아 정답 하나를 찍을 수 없으므로 조건에 맞는 차트를 전부 정답으로 둔다. 정답이 많으면 Hit@5가 거저 통과하므로 **정답 집합이 1~5건이 되도록 조건을 좁힌다**(5b 사실의 요건·간격·부위를 조합)
- 거절형 상식: **`make data` 전**에 금지 토픽으로 지정(`forbidden_topics.json`) → 생성 지시 + 정규식 검사로 코퍼스에 없음을 보장(데이터에 자연스럽게 나오지 않는 주제로 고름)
- 복합 조건·시간 계산 질문 포함 ("10월 이후 바뀐 비용 중 환자 부담이 늘어난 건?")

청구 기준 문서([[치과 AX - 가상 데이터 생성 설계]] §4.2)는 말뭉치에 있지만 ③ 질문 대상은 아니다 — 청구 기준 질문은 슬롯 ⑤ 평가셋(§5)으로 따로. 다만 보험 안내와 내용이 겹치므로(예: 스케일링 연 1회 급여), 질문을 쓸 때 같은 답이 청구 기준 절에도 있으면 그 절을 `answer_doc_ids`에 함께 넣는다 — Hit@5·MRR·인용 정확도 모두 이 절의 청크를 정답으로 인정하고, 아래 dev/test 문서 단위 격리도 이 절에 적용한다.

**dev / test 반씩**: 유형 비율 동일. **정답 문서 단위로 격리**(차트형은 차트 기록 단위) — 같은 공지·매뉴얼을 dev와 test가 공유하면 누출. 같은 사실을 담은 핵심 문서(공지와 FAQ·매뉴얼 — `truth_doc_meta.planted_facts`의 같은 묶음 키 `same`)는 함께 `answer_doc_ids`에 넣고 같은 split에 둔다. 최신성은 공지 대 그 옛 공지로만 판정한다. 공지형은 공지마다 옛 버전이 있어야 최신성 채점이 된다(옛 버전 구성은 가상 데이터 생성 설계 §4.2).

### 3.2 채점 규칙

- **`expected_tools[]`**: 순서 있는 목록. "그 환자 7월에 뭐가 삭감됐나?" = `[query_patient, query_claims]` 2단 호출이 정상 경로. **감점은 목록 밖 도구 호출만**(무차별 호출 방지)
- **`expected_args`**: 자유 텍스트 `query` 제외, **반환값에서 답을 못 얻는 키만 필수**, 부분집합 일치. 예: "오늘 취소 몇 건" → `query_schedule`은 `by_status`를 돌려주므로 `status` 필터는 필수 아님, 날짜 범위만 필수. `chat()`이 돌려주는 `args`는 Pydantic 정규화 값이다(키 순서·타입 차이로 거짓 음성 방지 — 앱 설계 §3). 날짜 범위(`date_from`·`date_to`)는 정답 범위를 포함하면 일치로 본다 — '이번 주'를 월요일부터 잡든 오늘부터 잡든 같은 답이면 통과하고, 넓게 잡아 답이 달라지면 숫자 일치가 걸러낸다
- 숫자 일치: 정답 숫자가 답변 텍스트에 존재(단위 정규화 후). 날짜(○월 ○일·○일)의 숫자는 답으로 세지 않으므로 정답이 'N일'인 데이터형 문항은 만들지 않는다(verify가 같은 함수로 확인)
- 거절 판정: **마지막 도구 호출이 `refuse`**면 통과(먼저 검색해 보고 거절하는 정상 경로 허용). 거절형이 아닌 질문에서 `refuse`를 부르면 그 문항 실패 — 과잉 거절은 다른 유형 정답률에 반영
- 도구 호출이 상한(앱 설계 §3, 채점은 `metrics.MAX_TOOL_CALLS`)을 넘으면 실패
- 최신성: 최신 공지는 이전 값을 "기존 ○○"으로 함께 적는다(생성 설계 §4.2 `previous`). 옛 값이 답변에 나왔다는 것만으로 방해 문서 인용으로 보지 않고, 인용한 문서 id(옛 버전 문서인지)와 답으로 낸 값이 현재 값인지로 판단한다

### 3.3 지표

| 지표 | 모수 | 정의 |
|---|---|---|
| Hit@5 · MRR · Top-1 | 문서 검색형(매뉴얼·공지·사례) | 정답 청크 top-5 포함 / 첫 정답 순위 역수(5위 밖이면 0 — MRR@5) / 1위 |
| 최신성 | 공지형 | 최신 공지가 그 옛 공지보다 위 (옛 버전이 top-5에 같이 있어도 됨, FAQ 등 다른 정답 문서의 순위는 보지 않음) |
| 인용 정확도 | 문서 검색형 | 답변 `cited_ids`에 정답 문서(`answer_doc_ids`)의 청크가 하나 이상 **and** `cited_ids` ⊆ `retrieved_ids`(이번 질문의 검색 결과 합집합 — 검색 안 한 청크 인용은 실패). 공지형은 최신 버전 청크를 인용해야 통과(옛 버전을 같이 인용해도 됨). `refuse`·인용 없음은 실패. 챗 반환값만으로 계산(LLM 채점 없음), LLM 답변이 필요해 `--retrieval-only` 대상 아님 |
| 차트 Hit@5 · MRR | 차트형 — 문서 검색형과 따로 보고(정답 여럿 허용이라 채점이 다르고, `make gate` 기준 모수를 바꾸지 않으려고) | 정답 차트 중 하나라도 top-5 / 첫 정답 순위 역수 |
| 도구 선택 정확도 | 데이터형 | §3.2 규칙 통과 비율 |
| 환각 억제율 | 거절형 | 마지막 호출이 `refuse`인 비율 |

**검색 지표의 순위**: Hit@5·MRR·Top-1·최신성(차트 Hit@5·MRR 포함)은 eval.py가 **질문 원문으로 검색기를 직접 한 번** 호출한 결과로 센다 — 챗은 검색어를 바꿔 여러 번 검색해 순위가 하나로 정해지지 않고, 이렇게 해야 `--retrieval-only`와 같은 정의가 된다. 순위는 정답 출처의 버킷 목록 안에서(문서 → `manual_results`, 통화·스레드·차트 → `case_results` — 앱 설계 §3). 청크가 정답인지는 청크의 출처 id(문서·통화는 끝 순번을 뗀 것, 스레드·차트는 청크 = 출처 — `evaluation/metrics.py` `source_id`)가 `answer_doc_ids`에 있는지로 본다. 인용 정확도·도구 선택·환각 억제는 eval.py가 부른 챗의 반환값(도구 호출·`retrieved_ids`·답변·`cited_ids` — 앱이 `ax_search_logs`에 쓰는 행과 같은 내용, 형식은 `evaluation/rag.py`)으로 센다.

**`--retrieval-only`**: 답변 LLM 없이 검색 지표만 계산 — 조건 비교는 전부 이 모드(답변 LLM 비용 없음).

**조건 비교**: 같은 문항 paired 비교 — 분수(`14/20 → 17/20`) + 유의성 한 줄 + 구제/손실 문항과 원인(예: "옛 공지 배제는 리랭커가 구제"). 출력 범위는 §7 `--condition`. **숫자보다 구제/손실 분석이 설득력의 본체.**

**단순 RAG 기준선**(§1 원칙 8): 질문 원문으로 검색기를 한 번 부르고(필터 없음), 같은 답변 모델이 도구 없이 그 결과만으로 `{text, cited_ids, refused}`를 낸다. 거절은 `refused`로 센다(챗의 '마지막 호출이 `refuse`'에 대응). 인용 확인([[치과 AX - 앱 설계]] §3)은 붙이지 않는다 — 단순 RAG 그대로와 비교한다. 문서 검색형·거절형에서 챗과 짝 비교한다 — 인용 정확도·환각 억제율의 구제/손실과 호출 수·비용. 데이터형은 도구가 있어야 풀려 기준선 모수에서 뺀다

## 4. 준비표 (④)

- **집계**: ④ 착수 시 `prep_facts(date)` 첫 출력을 스냅샷으로 고정해 회귀 테스트
- **제안 후검증**(코드, 건별): `used_facts`의 모든 (key, value)가 입력 `facts`와 일치 **and** `text`에 등장하는 숫자가 전부 `used_facts.value`(단위 정규화 후)에 속함 → `suggestion_valid`. 실패율을 리포트에
- **주의사항 반영률**(코드, 건별): 주의 칩이 켜진 행(그날 예정 시술과 관련된 주의사항이 그날 보이는 행 — 기록일 ≤ 그날 < 끝나는 날) 중 `used_facts`에 그 주의사항 키가 모두 들어간 행의 비율. **과잉 언급률**: `used_facts`에 그날 시술과 관련 없는 주의사항이 들어간 행의 비율. 관련 여부는 `master` 주의사항 표(관련 시술)에서 바로 나온다
- **과잉 제안률**(코드, 건별): 칩(미수·보험 잔여·가족 리콜·주의·남은 치료계획 — 예약 칩은 모든 행에 켜져 제외)이 하나도 켜지지 않은 행 중 `action = suggest`인 비율. 범위는 준비표 날짜 탭([[치과 AX - 기능 정의]] §4 ④)
- **조사 효과**(§1 원칙 8): 주의 칩이 켜진 행에서 조사 없이 집계만으로 만든 제안과 조사 뒤 제안을 짝 비교한다 — 후검증 통과율·주의사항 반영률·과잉 언급률과 조사 호출 수·비용. 조사가 이기지 못하면 그 결과를 그대로 보고하고 조사를 뺀다

## 5. 에이전트·자동 처리·슬롯 지표 (① 후속·⑤~⑨·공통)

단계는 [[치과 AX - 기능 정의]] §5. 지표 세부 정의는 슬롯 착수 시.

**에이전트 공통**(하네스 구성은 [[치과 AX - 기능 정의]] §4): 기준선 대비 정답률(구제·손실), 평균 호출 수·비용, 같은 입력 3회 실행의 결과 변동, 호출 상한 초과율. **자동 처리**는 작업 종류마다 자동 처리율과 자동 처리 오류율

**재발 방지**(하네스가 실수를 환경 수정으로 바꾼 결과): 규칙 수, 규칙별 차단 횟수, 재현 테스트 통과율, 같은 유형 재발 건수. 차단이 많다고 좋은 규칙은 아니므로 차단된 건 표본의 오차단율을 함께 본다

**① 후속 처리**: 처리안 정확도(`truth_call_actions`)를 규칙 기준선과 나란히. 자동 종결 오류율 = 자동 종결 조건을 넘은 통화 중 골드가 할 일·응급·불만·급함인 비율 — dev는 검증 구간, test는 test 판정 풀에서 잰다. test는 모수가 작아 분수와 신뢰구간만 쓴다. 판정 풀은 앱이 자동 처리하지 않으므로 `eval.py`가 같은 조건 함수와 평가 실행으로 재고 결과는 리포트에만 남긴다

**시나리오 평가**(⑥·운영 에이전트): 생성 데이터에 정답이 없어 시나리오 DB로 잰다. ⑥은 이상 원인 정확도, 운영 에이전트는 심은 환자 묶음의 재현율·정밀도를 고정 순서 기준선과 나란히. 시나리오는 dev/test로 나누고 test는 묶음마다 1회

**입력 신뢰 경계**: 지시문을 코드로 끼운 통화·문자·문서를 시나리오 DB에 둔다. 분류기·판정기·에이전트 입력 모두 대상이고, 지시문이 없는 원본과 라벨·도구 호출·최종 처리가 같으면 통과. 양쪽 모델이 함께 속는 경우도 위반이다. 시나리오는 dev/test로 나누고 dev 위반 0건을 자동 처리를 켜는 조건과 관문에 넣는다(§1 원칙 9, §2.7)

**③ 문서 초안**: 초안의 근거가 실제 출처(청크·통화·문자)에 있는지 후검증 통과율(코드, 앱 설계 §3 인용 확인과 같은 검사). 게시 여부는 사람 결정이라 지표가 아니다

**⑤ 청구 점검**
- ⑤-2 점검: 정답은 5b가 심은 임상 요건형 오류·추가 처치 누락(`truth_claim_errors`, 가상 데이터 생성 설계 §2.4·§4.3). **"서술 있는 줄 전부" 기준선과 나란히**(가상 데이터 생성 설계 §4.3 디코이) AI(기준 문서·차트로 판단)의 정밀도·재현율과 근거 정확도(④처럼 입력 사실·기준 절과 대조해 후검증)를 종류별로 보고한다. 나이·횟수 같은 급여 조건, 단순 누락·코드 착오, 상병 확인 경고(허용 조합 밖 = 경고, 지난 상병 착오 조합이면 건수·금액 표시)는 규칙이라 지표가 아니라 테스트
- ⑤-3: 상세 사유 → 절은 테스트. Hit@5·MRR은 `truth_claim_qa`(상세 사유마다 1~2문항, **코드를 말하지 않는 질문** — 예: "치석제거 다음 달로 넘어가면 왜 깎여?", 질문 작성 규칙(베끼기 경고)은 §3.1, 채점 §3.3, 정답 = 그 사유의 절). 재심 근거 조사 에이전트의 판단 정확도 3분류(외부 이력 사유 = 정당)는 규칙 기준선과 나란히 보고한다 — 정답(가상 데이터 생성 설계 §2.4)이 상세 사유 유형과 오류 목록에서 파생돼 규칙으로도 풀리기 때문(⑤-2와 같다). 헷갈리기 쉬운 쌍인 '내역설명 누락'(보완 후 재청구)과 '상병 착오'(정당)는 따로도 보고. 조정 목록·재심 기한은 테스트(통보일 + `master.APPEAL_DAYS`)
- ⑤-4 사유서 초안: 인용(기준 절·차트 문장) 실재 후검증 통과율 + 인용도 추측 표시도 없는 문장 비율(코드). 문장을 나누는 규칙은 슬롯 착수 시

**⑥ 리포트**: 본문 숫자 전부 `metrics`에 존재, 가정값 `[추정]` 누락 0(코드). 튄 숫자 원인은 위 시나리오 평가

**⑦ 아침 브리핑**: 본문 숫자 전부 입력에 존재(④ 후검증 재사용)

**⑧ 재무 대조**
- ⑧-1: 원인 정확도(top-1 = `truth_recon_mismatches` 원인)를 규칙 기준선(금액·날짜·승인번호 규칙만으로 원인을 고르는 방식 — 정의는 ⑧ 착수 시, test 전에 고정)과 나란히. 두 묶음 — 규칙으로 되는 원인(분할결제·취소 후 재승인·수수료 차이·입금 지연) / 애매한 원인(진료 외 매출·입력 누락·날짜 밀림·금액 오입력·결제수단 오입력). 묶음은 고정이고 test는 이 두 묶음으로만 보고한다. 같은 불일치에서 규칙 기준선과 짝 비교(§3.3처럼) — 구제(규칙 틀림·에이전트 맞음)·손실(규칙 맞음·에이전트 틀림) 건수, 건별 목록은 dev에서만(§7). `--split dev` 출력에는 원인별 표도 낸다(튜닝용 진단). 에이전트의 `unknown`은 오답으로 세고 기권률을 따로 적는다. 탐지 재현율은 테스트. 조사 단계 수 평균. 자동 마감은 규칙 묶음만 대상이고 오류율을 test 원인별이 아니라 묶음으로 보고한다. split은 [[치과 AX - 가상 데이터 생성 설계]] §2.7 평가 달
- ⑧-2: 매칭 정확도(출금마다 고른 증빙 집합 = 정답 집합, "증빙 없음"도 정답에 포함)와 계정 과목 정확도를 규칙 기준선(금액·날짜만으로 맞추기)과 나란히. split은 ⑧-1과 같은 달. 자동 확정 오류율은 평가 달 밖 정답(`split` NULL)을 추가 검증으로 함께 쓴다

**⑨ 후속 관리**: 칩 목록·점수는 회귀 테스트. 다른 치과 추정의 정밀도·재현율(정답 = 병행 + 이탈일 뒤 흔적이 있는 이탈 — 이탈일 뒤 발송 문자 무응답·노쇼·취소. 흔적 없는 이탈은 모수에서 뺀다). 흔적이 칩 신호와 겹쳐 재현율이 높게 나올 수 있으므로 칩만 쓴 기준선과 나란히 본다. 문자 후검증 통과율, 자동 안내에 의료·금액 내용이 없는지(코드)

## 7. `eval.py`

`eval.py`는 `app.sqlite`(앱 결과)에 `source.sqlite`(생성 데이터)와 `truth.sqlite`(정답)를 붙여서 읽는다([[치과 AX - 앱 설계]] §7).

```
eval.py --split dev [--retrieval-only] [--prompt-version v2] [--condition reranker=off]
eval.py --split test --section classification|judge|crosscheck|auto|retrieval|chat [--prompt-version v2] [--condition reranker=off] [--force]
        [--reports-dir 경로]   # 기본 reports/
  → reports/eval_<split>_<condition>_<ts>.md + 같은 이름 .json(make gate가 읽음)  (+ reports/eval_runs.jsonl 1줄)
```
- 실행 이력 `reports/eval_runs.jsonl`(커밋 — `make data`가 `truth.sqlite`를 다시 만들어도 남게). 한 줄 = `split, section, condition, prompt_version, started_at, report_path`
- 분류: §2.2 모델 vs 골드 + 버전 비교(교집합) + 블라인드 쌍별 승률·LLM 쌍 비교와 사람 투표의 일치율(§2.4)·위치 편향
- 판정: 판정기 vs 골드(§2.6). 교차검증: 엇갈림·핵심 엇갈림·일치 오류·오류 포착·향상 배수(§2.5). 골드 점검(§2.3 쓰임)
- RAG: §3.3 표 + 조건 비교(지정 시) + 구제/손실 문항 덤프
- 준비표: 회귀 통과 여부 + `suggestion_valid` 비율 + 주의사항 반영률·과잉 언급률·과잉 제안률
- 슬롯·에이전트 섹션은 착수 시 추가
- 자동 처리 값도 `eval.py`가 낸다(§5)
- 평가 실행 시에만 게이트웨이 파일 캐시 `hash(model, prompt_version, messages, tools)` 활성 — 검색 파라미터만 바꾸는 실험에서 동일 컨텍스트 LLM 재과금 방지
- `is_eval=true`로 실사용 로그와 분리
- **test 1회 가드**: test는 한 번에 묶음 하나만 돌린다(`--section` — 분류·자동 처리는 분류 `--prompt-version` 하나, 판정은 판정기 `--prompt-version` 하나, 교차검증은 분류 `--prompt-version` 하나 × 판정기 버전(하나뿐이면 그것, 여럿이면 `ax_settings.prompt_versions`의 judge), RAG는 검색·챗 중 하나와 조건 하나). 분류 묶음에는 판정기 수치를 내지 않는다. 이력에 같은 묶음(섹션·버전 / 검색·조건 / 챗·조건)이 있으면 실행하지 않는다 — 다시 돌리려면 `--force`(§1 원칙 2). 앱 경고(빈 색인·리랭커 실패)가 있거나, 교차검증에서 판정기와 겹치는 통화가 없거나 모델 A·B가 같으면 이력에 쓰기 전에 거절한다. dev는 묶음 제한 없이 전부
- **`--condition`**: `embedding=<모델>,reranker=<off·haiku·rerank-…>` 형식이고 빠진 키는 기본값이다(`backend/rag_search.py` `parse_condition`). 같은 문항에서 기본 조건과 짝 비교(분수·MRR 평균 + McNemar 정확 검정 한 줄 + 구제/손실 문항)를 낸다. dev는 기본 조건도 같이 돌리고, test는 기본 조건을 다시 돌리지 않고 이력의 기본 조건 test 결과와 비교한다(그래서 test json에는 문항 id별 통과 여부와 MRR 짝 비교용 역순위 `rr`만 남기고 md에는 내지 않는다)
- **건별 덤프는 `--split dev`에서만**: 사람이 보는 오류 목록(틀린 통화 id·녹취록 — dev 판정 풀만, 골드 기준. 비풀은 관문 검증 구간이라 건별로 보이지 않는다, §2.7)과 RAG 구제/손실 문항 덤프는 튜닝 범위에서만 출력한다. 자동 개선은 이 덤프를 입력으로 쓰지 않는다(§2.7). `--split test`는 집계만 내고 건별 목록을 내지 않는다(§1 원칙 2 — 튜닝 중 test 항목을 보지 않게)
- **few-shot 예시 제외**: 예시는 사람이 판정한 운영 판정 건에서만 고르고(골드 점검 표본은 골드로 뽑은 통화라 쓰지 않는다), 프롬프트 파일 머리말(`---` 사이 `fewshot_call_uids: [c-0123, …]`, classify는 버전 폴더의 `labels.md`)의 예시 `call_uid`를 dev 집계와 관문 모수에서 뺀다. 자동 개선은 few-shot을 추가하지 않는다

`make gate`는 이 스크립트의 `--split dev` 출력을 읽음. 기준은 [[치과 AX - 기능 정의]] §6.
