# 개발자 소개

> 팀원을 찾을 때 보여 주는 문서입니다. 무엇을 만드는지는 [[치과 AX - 프로젝트 소개]], 하루 흐름과 기능별 업무 전후는 [[치과 AX - 전환의 의미]] §2·§3에 있습니다. 여기는 **어떤 기술로, 기능마다 AI를 왜 그렇게 붙였고, 어떻게 일하고, 참여하면 무엇이 남는지**입니다.

## 1. 한 줄로

동네 치과의 진료 외 업무(전화·청구·마감·후속 연락)를 AI 에이전트로 옮기되, **에이전트의 결과를 숫자로 재고 코드와 관문으로 통제하는 것**을 중심에 둔 프로젝트입니다. "데모가 돌아간다"가 아니라 "v1 → vN으로 몇 % 나아졌고, 자동 처리를 왜 믿을 수 있는지"를 보여 주는 것이 목표입니다.

| 품질 | ruff(PEP 8) · pytest · GitHub Actions CI | 운영 중 |
| 배포·UI 테스트 | `docker compose` 로컬 배포 · Playwright | 앱 착수 뒤 |

선택 이유(왜 Chroma가 아니라 sqlite-vec인지, 왜 LiteLLM 없이 SDK 직접인지 등)는 [[치과 AX - 앱 설계]] §7에 근거와 함께 있습니다.

**아직 만들지 않은 데이터(추정)**

- **사람 판정**: 골드 점검 표본 `GOLD_AUDIT_SAMPLE`통화(판정기와 골드가 다른 항목만), 처리 정답 사람 표본 `ACTION_AUDIT_SAMPLE`통화, 최종 블라인드 비교 `blind_pool_size`통화 + 운영 구간의 엇갈림·표본
- **평가 전용 정답**: ⑥·운영 에이전트 시나리오(`truth_scenarios`). 기존 `emr_*`·`fin_*`는 바꾸지 않는다
- ⑦은 기존 EMR을 쿼리만 하므로 새 데이터가 없고, ⑧·⑨ 원본과 정답은 이미 생성돼 있다

## 4. 기능별 AI — 무엇을 맡기고, 왜 쓰고, 어떻게 믿나

이 프로젝트는 찾아볼 곳이 건마다 달라지는 일을 **에이전트에 맡기고**, 결과가 고정돼야 하는 계산은 코드에 남깁니다. 기능마다 네 가지를 정해 두었습니다.

- **AI가 하는 일**: 기능 안에서 AI가 맡는 좁은 구간
- **왜 AI인가**: 규칙(코드)으로 하면 무엇이 안 되는지
- **왜 이 방식인가**: 같은 AI라도 이 형태를 고른 이유
- **어떻게 믿나**: 결과를 숫자나 코드로 확인하는 방법. 이 칸이 없는 AI 기능은 만들지 않습니다

**이 문서의 두 용어** ([[치과 AX - 기능 정의]] §3에 기능별 구분표)
- **에이전트**: LLM이 도구를 쓰며 다음 단계를 스스로 정하는 시스템. 코드가 경로를 정하면 워크플로이고, 사람 확인이 있는지와는 별개다
- **하네스**: 모델이 아닌 코드·설정·실행 로직 전부. 모델이 일하도록 상태·도구 실행·피드백 루프·제약을 붙이고, 실수가 나면 같은 실수를 못 하게 환경을 고친다

### 바탕에 깔린 원칙 (모든 기능 공통, [[치과 AX - 기능 정의]] §3·[[치과 AX - 평가 설계]] §1)

| 원칙 | 왜 |
|---|---|
| 원본에 쓰는 건 사람, 자동 처리는 `ax_`까지 | 병원 기록은 틀리면 되돌리기 어렵고 책임이 따른다. LLM은 요청만 하고 코드가 정책으로 허용하며, 자동 처리는 이유와 되돌리기를 남긴다 |
| 숫자는 코드가 계산, AI는 해석만 | LLM은 숫자를 그럴듯하게 지어낸다. 매출·건수·잔액은 쿼리로 정확히 내고, AI 문장 속 숫자는 입력에 있는지 코드가 다시 확인(후검증)한다 |
| 분류·추출은 JSON 스키마 + 고정 enum | 자유 문장은 채점도 집계도 안 된다. 출력 칸과 선택지를 고정해야 정답과 기계적으로 비교하고, 화면·큐가 그 값으로 움직일 수 있다 |
| 스펙 → 평가셋 → 구현 | 평가셋 없이 프롬프트를 고치면 "좋아진 것 같다"만 남는다. 먼저 잴 방법을 만들고 고친다 |
| 조사는 에이전트, 고정 산출은 워크플로 | 경로가 달라지는 일만 LLM이 정한다. 모든 에이전트는 규칙이나 고정 흐름과 비교해 못 이기면 되돌린다 |
| 개선은 자동, 기준은 사람 | 자동 개선은 test를 볼 수 없고 미리 정한 관문을 넘어야 반영된다 |
| 실수는 환경을 고친다 | 프롬프트는 확률적으로만 막는다. 재현 테스트와 훅·정책으로 남기면 같은 실수를 구조로 막는다 |
| 튜닝 셋과 보고 셋 분리 | 튜닝하면서 본 문항으로 성적을 내면 과대평가된다. dev로 고치고 test는 마지막에 한 번만 |

### 가상 데이터 생성기 — 합성 데이터

- **AI가 하는 일**: 통화 녹취록, 매뉴얼·공지 문서, 진료 차트 서술을 사람이 쓴 것처럼 생성
- **왜 AI인가**: 실제 환자 정보는 쓸 수 없고, 템플릿 문장으로 찍어 내면 분류·검색이 너무 쉬워져 평가가 의미 없어진다. 말투·순서·군더더기가 자연스러운 글은 LLM만 만들 수 있다
- **왜 이 방식인가**: **정답을 먼저 정하고 글을 나중에 쓴다.** 코드가 "이 통화는 예약 변경 문의, 급함 아님, 할 일 있음"을 정하고, LLM은 그 라벨에 맞는 대화만 쓴다. 그래서 평가셋을 만들 수 있다. 다만 만든 사람이 정한 정답이라 실제보다 쉬울 수 있어서, 절대 점수가 아니라 조건 간 차이(v1 → vN, 리랭커 on/off)로 개선을 보이고, 정답지 자체는 다른 AI가 가린 결과를 사람이 표본으로 점검한다. 대량 생성은 Batch API로 비용을 줄이고, 결과는 캐시에 커밋해 같은 시드면 같은 데이터가 나온다
- **어떻게 믿나**: 생성된 글마다 반드시 들어갈 말·들어가면 안 될 말·길이를 검사하고, 실패하면 다시 생성한다. 전체 데이터는 `make verify`가 규칙 위반(예약과 문자 답장이 안 맞음, 정답 숫자를 채점기가 못 읽음 등)을 잡는다

### ① 통화 요약·분류 — 구조화 출력 + 후속 에이전트

- **현실과 다른 점**: 실제 병원에서는 교환기(PBX)가 대표번호로 오는 전화를 받아 녹음하고, 음성 인식(STT)이 통화 중에 말을 글로 옮긴다. 이 프로젝트는 교환기를 설치해 실제 전화를 받을 수 없으므로 그 구간을 건너뛰고, 통화 내용을 글로 옮긴 녹취록을 AI로 만들어 넣었다(위 생성기). 그래서 기능은 녹취록이 들어온 다음부터 만든다 — 화면에서 새로 추가한 녹취록도 같은 길로 처리한다. AI가 전화를 직접 받는 음성 응대는 범위 밖
- **AI가 하는 일**: 통화 녹취록을 읽고 요약, 할 일, 9개 항목 분류(목적·급함·응급 등)를 JSON으로 낸다. 그 뒤 후속 에이전트가 환자 기록을 조회해 처리안을 붙인다
- **왜 AI인가**: 환자는 "그 저번에 했던 거 있잖아요, 그거 날짜 좀…"처럼 말한다. 키워드 규칙으로는 목적을 못 잡고, 한 통화에 주제가 여럿 섞인다. 문맥을 읽어야 하는 일이다
- **왜 이 방식인가**
  - 출력을 스키마와 고정 enum으로 묶었다. 그래야 분류값으로 통화 화면 **"오늘 할 일"**(할 일을 병원 안에서 할 일과 연락할 사람으로 나눠 급한 순으로)이 자동으로 돌고, 정답과 항목별로 비교된다
  - 분류기의 통화 입력은 녹취록·방향(`classify(gw, transcript, direction, version)`의 `transcript`·`direction`) 두 개뿐이다. 환자 이름·번호·시각을 주면 모델이 EMR 기록에서 정답을 "커닝"할 수 있어서 함수 시그니처로 막았다. 실제 교환기가 넘겨주는 정보(녹음 → 녹취록, 수신/발신)와도 같다
  - 모델 2개로 교차검증한다. 자동 종결은 사람이 안 보는 오류를 만들기 때문에, 그 크기를 재는 교차검증이 필수다. 분류는 함수로 두고 에이전트는 분류 다음 단계부터 넣는다 — 분류에 도구를 주면 EMR에서 정답을 커닝할 수 있다
- **어떻게 믿나**: 정답(골드)으로 항목별 정확도를 재고, 자동 종결 오류율과 둘이 함께 틀린 비율을 낸다. 후속 처리안은 규칙 기준선과 비교한다

### ② 판정·자동 개선 + 블라인드 비교 — AI를 재고 고치는 루프

- **AI가 하는 일**: 판정기가 1차 판정을 하고, 개선 에이전트가 오류를 분석해 프롬프트 후보를 쓴다
- **왜 필요한가**: 분류 정확도를 모르면 프롬프트를 고쳐도 나아졌는지 알 수 없다. 요약처럼 정답이 하나가 아닌 글은 기계 채점이 안 된다
- **왜 이 방식인가**
  - **판정**: 사람은 엇갈림과 표본만 본다. 녹취록을 먼저 보여 주고 모델 라벨은 저장한 뒤에만 보인다 — 먼저 보이면 앵커링된다. 판정기는 골드로 재고, 골드는 판정기와 다른 건을 중재 판정기가 가린 뒤 사람이 표본으로 점검한다. 판정기는 녹취록과 방향만 받고 분류기 결과·EMR·도구는 받지 않는다. 판정 기준은 프롬프트에 들어 있다. 한 통화를 읽고 답하는 일이라 조사 경로가 필요 없고, 검색을 주면 정답 힌트가 샐 수 있어 일부러 에이전트로 만들지 않았다
  - **블라인드 비교**: 요약 두 개를 버전 이름을 가리고 LLM이 좌우를 바꿔 두 번 고른다. 사람도 일부 투표해(dev 블라인드 통화의 비교 쌍, 최종 비교) LLM 채점과 맞는지 본다. 좌우 배치를 섞어 위치 편향을 본다
  - **자동 개선**: 재료 구간의 오류를 묶어 후보를 만들고 → 검증 구간으로 관문을 재고 → 넘으면 대기 버전이 되고 → 사람이 재분류를 실행해 끝나면 전환한다. 응급·불만을 새로 놓치면 탈락한다. test는 루프 밖이고 사람이 1회만 돌린다
- **어떻게 믿나**: 비교는 같은 통화 묶음에서 조건 하나만 바꿔 한다(프롬프트 v1 → vN은 모델 고정, vN → 최종은 프롬프트 고정). 사람 표본은 AI끼리 함께 틀리는 오류를 잡는다. 합성 데이터라 절대 수치는 높게 나오므로 **조건 간 차이**를 주 지표로 쓰고, 모수가 작아 퍼센트와 함께 분수(14/20)를 적는다

### ③ 물어보기 — 하이브리드 RAG + 도구 호출 에이전트

- **AI가 하는 일**: 직원 질문을 받아 어떤 도구를 쓸지 고르고(문서 검색·환자·일정·청구·차트 조회·거절), 찾은 근거로 출처와 함께 답한다
- **왜 AI인가**: "치석제거 뒤 잇몸치료로 이어진 환자 차트 어떻게 적었지?"처럼 질문이 자연어이고, 답이 매뉴얼·공지·통화·문자·차트에 흩어져 있다. 차트 검색이 환자 이름으로만 돼서 이름을 모르면 못 찾는다는 현장 고충이 출발점이다
- **왜 이 방식인가**
  - **키워드(BM25) + 벡터 하이브리드**: 키워드는 "C-00795", 시술 코드 같은 정확한 말에 강하고, 벡터는 "잇몸이 붓는다 ↔ 치은 부종"처럼 뜻이 같은 말에 강하다. 둘 다 써야 둘 다 찾는다
  - **문서 버킷과 사례 버킷을 따로 검색**: 문서 청크는 통화·문자·차트 청크보다 훨씬 적어, 한 번에 찾으면 매뉴얼이 묻힌다. 따로 찾고 리랭커로 다시 줄 세운다
  - **청크마다 출처 머리말**(`[환자: … | 날짜 | 수신]`): 머리말 없이는 "그 환자 지난번 통화"를 찾을 수 없다. 차트는 이름 없이 차트 번호까지만 붙여 비식별을 지킨다
  - **숫자 질문은 검색이 아니라 도구로**: "내일 미수 환자 몇 명?"은 문서에 없다. `query_schedule`처럼 DB를 직접 세는 도구를 주고, 모델은 도구 선택과 인자만 정한다 — 숫자는 코드가 낸다
  - **거절도 도구**(`refuse`): 근거가 없으면 답을 지어내는 대신 거절을 "호출"하게 해서, 거절도 채점 가능한 행동으로 만들었다. 근거를 못 찾아 거절한 질문은 문서 초안 에이전트가 초안으로 만들어 오늘 화면에 올린다
  - **답변은 `{text, cited_ids}` 구조화 출력**: 모델이 근거 청크를 스스로 밝히게 해서 화면에 출처를 띄우고, 인용이 진짜인지 코드로 확인한다
  - **최신 공지 우선**: 바뀐 공지와 옛 공지를 혼동하는 게 실제 문제라, 최신 공지가 옛 공지보다 위에 오는지를 따로 잰다
- **어떻게 믿나**: 질문 유형별 평가셋(매뉴얼형·공지형·사례형·차트형·데이터형·거절형)으로 Hit@5·MRR(정답이 얼마나 위에 나오나), 최신성, 인용 정확도(인용한 청크가 정답 문서이고 실제로 검색한 것인지), 도구 선택·인자 정확도, 환각 억제율(답 없는 질문에 거절하는 비율)을 잰다. 검색 지표는 답변 LLM 없이 `--retrieval-only`로 돌려 리랭커 on/off를 답변 생성 비용 없이 비교한다. LLM에게 채점을 맡기지 않고 전부 코드로 채점한다

### ④ 진료 준비표 — 그라운딩 후검증 + 주의 환자 조사

- **AI가 하는 일**: 코드가 모은 환자 사실(예약·보험 잔여·미수·가족 리콜·주의사항·남은 치료계획)을 그날 할 일 한두 줄로 묶는다. 할 일이 없으면 "그대로 진행". 주의 칩이 켜진 환자는 야간에 에이전트가 지난 통화·차트를 더 조회한다
- **왜 AI인가**: 사실 하나하나는 코드가 정확히 띄운다(칩). 하지만 "항응고제 복용 + 오늘 발치 + 미수 있음 + 남편 리콜 지남"을 회의 전 30초에 읽을 문장으로 우선순위를 매겨 묶는 일은 조합이 너무 많아 규칙으로 쓸 수 없다
- **왜 이 방식인가**
  - 출력은 `{action, text, used_facts}`. 자유 문장에서 "어떤 사실을 썼는지"를 거꾸로 뽑아낼 수 없으니, 모델이 쓴 사실을 스스로 적게 했다
  - `none`("그대로 진행")을 허용했다. 매 행 제안을 강제하면 근거 약한 제안을 지어낸다
  - 주의사항 → 행동은 정해진 표라 칩은 코드가 띄우고, AI는 묶기만 한다
  - 조사는 야간에 돌리고 체어 보기는 저장된 결과만 읽는다. 진료 중에 호출을 기다리지 않게 하고, 도구 결과도 후검증의 입력 사실로 본다
- **어떻게 믿나**: 전부 코드 채점. `used_facts`가 실제 입력과 같은지, 문장 속 숫자가 전부 그 사실에 있는지(후검증 실패면 버리고 재시도), 관련 주의사항을 빠뜨리지 않았는지(반영률), 관련 없는 주의사항을 끌어오지 않았는지(과잉 언급률), 칩이 하나도 없는 환자에게 뭔가 권하지 않았는지(과잉 제안률)

### ⑤ 청구 점검·삭감 대응 — 규칙 + AI 역할 나누기, 도메인 RAG, 재심 근거 조사 에이전트

- **AI가 하는 일**: 차트 서술을 읽어야 보이는 청구 요건 확인, 차트에는 적혔는데 청구에서 빠진 처치 찾기, 깎인 건마다 에이전트가 청구 기준·차트·비슷한 지난 조정을 조사해 "정당 / 다툴 만함 / 보완 후 재청구" 판단, 재심 사유서 초안
- **왜 AI인가**: 나이·횟수 같은 조건은 규칙(SQL)으로 충분하고 실제로 규칙에 맡긴다. 그러나 "같은 부위를 다시 한 사유", "치주 상태 소견"은 차트의 자유 서술 속에 있어 글을 읽어야 한다. 이 경계가 과제의 핵심이다
- **왜 이 방식인가**: 조정 사유 검색은 ③ 검색 구조를 그대로 다시 쓴다. 사유서 초안은 모든 문장이 기준 절·차트 문장 인용이거나 "추측 목록"에 올라야 한다 — 둘 다 아닌 문장은 후검증 실패. 재심 근거는 건마다 찾아볼 곳이 달라 에이전트에 맡기고, 재심 여부와 제출은 사람이 검토 체크 뒤에만 한다
- **어떻게 믿나**: 가상 데이터에 일부러 심은 청구 오류를 얼마나 정확히, 빠짐없이 찾는지(정밀도·재현율)를 "서술 있는 줄 전부 표시" 같은 단순 기준선과 나란히 보여 준다. AI가 기준선보다 어디서 나은지가 결과다

### ⑥ 리포트 · ⑦ 아침 브리핑 — 숫자는 쿼리, 글은 LLM

- **AI가 하는 일**: 쿼리가 계산한 숫자(월간·주간·일간 매출·수금·노쇼·신환, 상병 착오, 오늘 예약·몰리는 시간대)를 읽기 쉬운 문장으로. 인건비 가정값이 들어간 손익은 `[추정]`으로 따로 표시. ⑥은 크게 움직인 숫자의 원인을 에이전트가 조사
- **왜 이 방식인가**: 리포트에서 숫자 하나가 틀리면 리포트 전체를 못 믿는다. 계산을 LLM에서 완전히 빼고 해석만 맡겼다
- **어떻게 믿나**: 본문 숫자가 전부 계산값에 있는지 코드로 확인(④ 후검증 재사용). 원인 조사는 이상을 심은 시나리오 DB로 잰다

### ⑧ 재무 대조 — 다단계 조사 에이전트

- **AI가 하는 일**: 장부와 카드·통장 숫자가 안 맞는 건마다 가설 → 조회(그날 내원·미수·다음 날 장부·구강용품 가격표·가족) → 비교를 반복해 원인(입력 누락·분할결제·수수료 차이 등)을 고르고, 조사 과정을 화면에 그대로 보인다. 지출은 출금과 증빙을 맞추고 계정 과목을 추천
- **왜 AI인가**: 안 맞는 걸 **찾는** 건 코드가 한다. 하지만 **왜** 안 맞는지는 여러 장부를 오가며 추리해야 하고, 경우마다 확인 순서가 다르다. ③ 챗이 짧은 도구 루프로 답만 낸다면, ⑧은 조사 과정 자체가 화면의 주인공이다
- **왜 이 방식인가**: 원인은 고정 enum이라 에이전트 출력·사람 확정·정답이 같은 값을 공유하고, 근거가 부족하면 `unknown`을 고르게 해 억지 추리를 막는다. 규칙으로 풀리고 장부 수정이 필요 없는 건만 자동 마감하고, 나머지는 사람이 확정한다. 장부 수정은 사람만 한다
- **어떻게 믿나**: 원인 정확도를 규칙 기준선과 나란히, "규칙으로 되는 원인 / 애매한 원인" 두 묶음으로 나눠 보여 준다. 에이전트가 쉬운 건만 맞히는지, 애매한 건에서 차이를 내는지가 드러난다

### ⑨ 후속 관리 — 순위는 코드, 조사는 에이전트

- **AI가 하는 일**: 상위 환자의 통화·문자·차트에서 이탈 근거를 찾고 연락 문자를 쓴다. 큰 치료계획은 "가장 급한 것 하나부터" 권하게 한다
- **왜 이 방식인가**: 누구에게 먼저 연락할지는 **설명할 수 있어야** 한다("순위는 어떻게 정해지나요?"). 그래서 순위는 코드 점수(마지막 방문·최근 연락·다른 치과 흔적)로 하고 AI에 맡기지 않았다. AI를 쓸 곳과 안 쓸 곳을 가르는 판단도 이 프로젝트가 보여 주려는 것이다
- **어떻게 믿나**: 다른 치과로 간 환자 추정의 정밀도·재현율, 문자 초안은 숫자 후검증

### 모든 기능을 받치는 것 — 하네스

- **에이전트 하네스**(`backend/harness/`): 모든 에이전트가 함께 쓴다
  - **상태**: 실행·단계 기록, 끊긴 실행 재개, 도구 결과 크기 제한, 운영 에이전트에는 요약만 전달
  - **도구 실행**: 도구 등록과 에이전트별 권한
  - **피드백 루프**: 공통 후검증, 판정·표본·관문, 재생 테스트
  - **제약**: 호출·비용 상한, 도구 전후 훅, 자동 처리 정책과 되돌리기, 중복 방지, 입력 신뢰 경계
  - **재발 방지**: 실수를 재현 테스트로 만들고 훅·정책·도구 설명·프롬프트 중 맞는 곳을 고친다. 프롬프트는 재료에서 나온 건만 관문을 넘겨 올리고, 그 밖은 사람이 승인한다
  - 밤에는 운영 에이전트가 우선순위를 정하고 기능 에이전트를 부른다
- **LLM 게이트웨이**(`shared/llm.py`): 모든 호출이 한 곳을 지나 모델 이름 대신 별칭으로 부르고, 장애 시 다음 모델로 폴백하고, 호출마다 토큰·비용·지연을 남기고, 하루 비용 상한을 건다. 폴백된 결과는 정확도 집계에서 뺀다(다른 모델 성적이 섞이지 않게). 실제 병원에 적용할 때 환자 정보가 밖으로 나가지 않게 로컬 모델로 바꿀 곳도 여기 한 군데다
- **평가 하네스**(`evaluation/`): 정답 DB는 앱 DB와 다른 파일이고 앱 코드는 정답 폴더를 import할 수 없다(테스트가 검사). 앱이 정답을 보고 맞히는 길을 구조로 막는다. 자동 개선도 여기서 돌고, 앱은 프롬프트 파일·라벨 없는 집계·실수 후보만 받는다
- **가짜 게이트웨이**: 같은 입력이면 같은 응답을 내는 가짜 LLM으로 테스트·CI가 키 없이, 과금 없이 돈다

## 5. 일하는 방식

- **설계 문서가 원본**: 규칙은 `docs/`, 값(숫자·enum·컬럼)은 코드·스키마·설정이 원본이고 문서는 이름으로 가리킵니다. 문서가 가리키는 코드 이름과 문서에 남긴 일부 값은 테스트(`tests/generator/test_doc_sync.py`)가 코드와 비교합니다.
- **테스트 우선**: 데이터 검사를 생성 코드보다, 테스트를 구현보다 먼저 씁니다. 같은 시드 → 같은 결과(단계별 독립 시드).
- **AI 코딩 에이전트와 협업**: Claude Code에 작업 규칙(`CLAUDE.md`)·리뷰 에이전트·막기 훅(`.claude/`)을 붙여 씁니다. 사람은 설계·결정·리뷰, 에이전트는 구현과 검사를 맡습니다.
- **깃**: 작업 묶음마다 `feat/<묶음>` 브랜치 → PR → CI(`make lint`·`make test`·프론트 빌드) 통과 후 머지.

## 6. 독립 과제 — 서로 기다리지 않고 따로 개발

기능들을 **서로 의존이 적은 독립 과제**로 나눠 두었습니다. 과제마다 읽는 원본 데이터, 채점에 쓰는 정답, 화면, 지표가 따로 있어서 한 사람이 한 과제를 맡아 다른 사람을 기다리지 않고 끝까지 만들 수 있습니다. 모두가 같이 쓰는 것은 공용 기반(가상 데이터·LLM 게이트웨이·평가 하네스·에이전트 하네스)입니다. 로직과 평가는 `source.sqlite`·`truth.sqlite`만으로 시작할 수 있고, 화면은 코어가 세우는 앱 틀(공통 레이아웃·오늘 화면)에 붙입니다.

**과제별 데이터와 연결 지점**

| 과제 | 읽는 원본 | 채점 정답 | 다른 과제와의 연결 |
|---|---|---|---|
| 코어 ①② 통화 분류·판정·자동 개선 | `ax_calls` | `truth_call_labels` + 처리 정답 라벨·골드 점검 표본 | 에이전트 하네스를 함께 씀 |
| 코어 ③ 물어보기 | `ax_documents`·`ax_calls`·`emr_messages`·`emr_chart_notes`, 조회 도구용 `emr_*` | `truth_rag_qa` | 검색 구조를 ⑤-3이 다시 씀 |
| 코어 ④ 준비표 (+⑦ 브리핑) | 환자·예약·수납·청구·주의사항 `emr_*` | 코드 채점(후검증) | 후검증 함수를 ⑤-4·⑥·⑦·⑨가 다시 씀. `make gate` 뒤 착수 |
| ⑤ 청구 점검·삭감 대응 | `emr_claims`·`emr_chart_notes`·청구 기준 문서 | `truth_claim_errors`·`truth_doc_meta`(기준 절)·`truth_claim_qa`(착수 때 작성) | ③ 검색 구조, ④ 후검증 |
| ⑥ 리포트 | `emr_treatments`·`emr_payments`·`emr_claims`·`emr_appointments`·`emr_staff`·`fin_*`, ⑧-2 확정 계정 | 코드 채점(본문 숫자 후검증), `truth_scenarios` | ④ 후검증 |
| ⑧ 재무 대조 | `fin_*`·`emr_payments` | `truth_recon_mismatches`·`truth_ledger_errors`·`truth_expense_matches` | 오늘 화면에 불일치 칸만 |
| ⑨ 후속 관리 | 예약·치료계획·문자 `emr_*` | `truth_patient_churn` | 문자 초안을 넣으면 ④ 후검증 |
| 운영 에이전트 | 기능 에이전트 결과 | `truth_scenarios` | 기능 에이전트를 모두 부름. 마지막에 착수 |

- **연결은 대부분 "가져다 쓰는 함수"입니다.** 예외는 운영 에이전트, 그 결과를 읽는 ⑦, ⑧-2 확정 계정을 읽는 ⑥(⑧ 전에는 거래처 표)뿐입니다. 하네스 코어와 ③ 검색은 이미 있습니다. ④ 후검증은 먼저 있으면 편하지만, 없으면 같은 인터페이스로 임시 구현을 두고 시작할 수 있습니다
- **같이 정해야 하는 것 하나**: 앱이 병원 상수(주의사항 → 관련 시술, 시술별 허용 상병, 재심 기한 등)를 읽는 방법은 ④·⑤·⑧이 함께 쓰므로 먼저 정합니다([[치과 AX - 앱 설계]] §8)
- ⑧은 다른 과제가 쓰지 않는 `fin_*` 테이블이 중심이라 가장 독립적입니다

**해 보는 것과 남는 것** — 범위와 완료 기준은 [[치과 AX - 기능 정의]] §5, 지표는 [[치과 AX - 평가 설계]] §5

| 과제 | 해 보는 것 | 포트폴리오에 남는 것 |
|---|---|---|
| ⑤ 청구 점검·삭감 대응 | 규칙 + AI 청구 전 점검, 조정 사유 검색, 재심 사유서 초안 | 규칙과 LLM의 역할 나누기, 도메인 RAG, 인용·추측을 후검증하는 생성 |
| ⑥ 리포트 | 숫자는 쿼리·글은 LLM(지난달 상병 착오 건수·못 받은 금액·많이 틀린 조합) | 숫자 환각을 코드로 막는 리포트 |
| ⑧ 재무 대조 | 원인 추적 에이전트를 처음부터, 증빙 매칭·계정 분류 | 에이전트 루프 설계, "규칙 기준선 대비 AI가 어디서 나은가"를 숫자로 |
| ⑨ 후속 관리 | 놓친 환자 목록·점수 순위·근거 찾기 에이전트 | 추천 순위 설계, 이탈 추정의 정밀도·재현율 |
| 운영 에이전트 | 조사 우선순위와 기능 에이전트 호출, 환자 단위 신호 묶기 | 멀티 에이전트 조율과 시나리오 기반 평가 |
| 코어 ①~④ | FastAPI 백엔드, Next.js 판정·검색·준비표 화면, 판정기·개선 에이전트 | 평가 하네스와 붙은 실서비스형 AI 앱, 관문을 통과해야 반영되는 자동 개선 |

## 7. 참여하면 남는 것

- **"AI를 써 봤다"가 아니라 "AI를 재고 고치게 했다"**: 프롬프트·모델·리랭커를 바꿀 때마다 같은 평가셋으로 전후 수치를 내고, 자동 개선을 관문으로 통제합니다. 면접에서 "정확도가 몇에서 몇으로, 왜"를 말할 수 있습니다.
- **실무형 구조**: 비용 기록과 상한, 모델 폴백, 결정적 테스트(가짜 게이트웨이), CI, 정답 격리 — 데모 코드가 아니라 운영을 고려한 코드입니다.
- **도메인 설계 경험**: 치과 EMR·건강보험 청구·일계표 같은 실제 업무 흐름을 테이블과 규칙으로 옮긴 설계 문서가 있어, 도메인을 코드로 옮기는 과정을 볼 수 있습니다.
- **AI 코딩 에이전트 실전 사용**: 규칙 문서·훅·리뷰 에이전트로 에이전트를 통제하며 개발하는 방식을 익힙니다.
- **결과물**: README 결과표의 한 줄(기능 × 비교 × 지표 — [[치과 AX - 기능 정의]] §8), 녹화 데모, 자기 과제의 설계·평가 문서.

## 8. 시작하려면

1. `uv sync` → `make test`(키 없이 돌아감) → `make data`(LLM 결과는 커밋된 캐시에서 읽어 과금 없음) → `make verify`
2. `make wireframe` 뒤 `docs/wireframe/`에서 `python -m http.server`로 화면 훑기
3. [[치과 AX - 기능 정의]]에서 맡을 과제의 절, `CLAUDE.md`의 절대 규칙 읽기
4. 진행 순서와 지금 할 일은 [[치과 AX - 기능 정의]] §9
